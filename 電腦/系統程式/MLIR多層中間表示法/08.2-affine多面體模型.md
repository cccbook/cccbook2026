# 8.2 affine 方言與多面體模型

[8.1](08.1-scf結構化控制流.md) 我們說明 `scf` 提供結構化控制流，但也留了一個缺口：`scf.for` 的下界與上界可以是任意 `index` 值，這對一般迴圈夠了，但對編譯器而言，**它無法知道迴圈的索引與某個多維陣列的哪個維度相關**。

若一個迴圈的索引與陣列維度之間的關係是「仿射的」，編譯器就能做很多事：判斷兩次存取是否可能指向同一個元素（陣列相依分析）、把多維索引空間重排成更 cache 友好的順序、辨識出可平鋪（tiling）的結構。

這就是 `affine` 方言與多面體模型（polyhedral model）存在的理由。

## 多面體模型的基本概念

多面體模型把程式表示為一組**多面體（polyhedra）**及其間的**關係（relations）**。核心物件有三個。

### 維度與迭代空間（iteration domain）

一個迴圈 nest 定義一個迭代空間。例如：

$$
D = \{ (i, j, k) \mid 0 \le i < M,\; 0 \le j < N,\; 0 \le k < K \}
$$

這是一個「盒子」（box），也就是三維直方體。若某些維度之間有相依（例如 $j < i$ ），則它變成一個一般多面體。

在多面體模型中，迭代空間被表示為**不等式的集合**：

$$
D = \{ z \mid A z \ge 0,\; z \in \mathbb{Z}^n \}
$$

### Access function（存取函數）

一個陣列存取被表示為「迭代空間的某個子集映射到陣列索引」。最簡單的例子是 $A[i][j]$ ：

$$
f_A : D \rightarrow \mathbb{Z}^2, \quad f_A(i,j,k) = (i, j)
$$

多面體模型中，access function 通常用 **access relation** 表達： $R_A \subseteq D \times D_A$ ，其中 $D_A$ 是陣列 $A$ 的索引空間。

這裡的關鍵是：**access function 是迭代空間到陣列索引的一個映射，其形式受限於「仿射」**。

### Schedule（排程）

Schedule 把迭代空間的維度重新映射到「時間維度」，決定執行的順序：

$$
\theta : D \rightarrow \mathbb{Z}^t, \quad \theta(i,j,k) = (j, i, k)
$$

$t$ 個維度中，前 $t-1$ 個是平行維度（可任意交換），最後一個是序列維度（決定了先後順序）。

多面體最佳化的本質就是：**改變 schedule 使得程式執行得更快**。

### 合法性（legality）：依賴關係

改變 schedule 不是自由的。必須滿足**依賴合法性**：若 $R_A$ 是從 $A$ 到 $B$ 的 flow dependence，也就是 $A$ 的值被 $B$ 使用，且執行序 $A \prec A'$ （同一個 $A$ 的兩次寫入），則必須有 $B \prec A'$ 。

形式化地，若 $\theta$ 與 $\theta'$ 是兩個 schedule， $\theta$ 對 $\theta'$ 合法，若：

$$
\theta' \text{ 保持 } \theta \text{ 的所有 flow dependences}
$$

更精確地說，dependence relation $R$ ，也就是 $R \subseteq D \times D$ ，必須被 $\theta$ 保持：對所有 $(x, y) \in R$ ，有 $\theta(x) \prec \theta(y)$ 。

多面體模型的核心貢獻，就是把「這個最佳化合法嗎」變成一個**多面體包含問題（polyhedral containment）**，而這個問題可以用 Presburger 算術判定。Polly 就是把這套理論實作成 C++ 編譯器框架的專案。

## MLIR affine 方言：刻意簡化的實作

MLIR 的 `affine` 方言**不是**完整的多面體模型。這是本節最重要的對比。

### MLIR affine 提供了什麼

`affine` 方言的核心操作：

| op | 用途 |
|---|---|
| `affine.for` | 帶仿射上下界的迴圈 |
| `affine.if` | 帶仿射條件的分支 |
| `affine.parallel` | 仿射的並行迴圈 |
| `affine.apply` | 計算仿射運算式的值 |
| `affine.load` | 仿射索引的讀取 |
| `affine.store` | 仿射索引的寫入 |
| `affine.dma_start` / `affine.dma` | DMA 傳輸描述 |
| `affine.min` / `affine.max` | 仿射運算式的 min/max |

### 刻意簡化在哪裡

MLIR affine 的「受限」表現在幾個地方：

**第一，索引必須是 restricted affine map。** `affine.load` 的索引不能是任意 affine map，而是 restricted affine map——每個結果維度是「dim 的常數倍 + 常數」，不能有 dim 之間的運算（例如 $d_0 + d_1$ 不行，但 $2 \cdot d_0 + 3$ 可以）。

這個限制的代價是表達力：**無法表達 $A[i+j]$ 這種索引**。但好處是：restricted affine map 保證了「在同一個迭代點上，所有運算的索引結構一致」，因而**依賴關係可以用簡單的方式分析**。

**第二，沒有完整的多面體最佳化。** Polly 會做完整的 dependence analysis、找到最佳 schedule、套用 Pluto 類的 transformation。MLIR affine **不做**這件事。MLIR affine 的定位是：**提供一個「循環 nest 的結構化表示」，讓一般目的的 pass（tiling、vectorization、parallelization）有東西可抓**，而不是取代 Polly。

**第三，沒有全域的 dependence relation 資料結構。** Polly 會建立一個完整的多面體 dependence graph。MLIR affine 沒有；它的 dependence 分析是**隱式**的，靠「對記憶體存取做一次掃描並比對索引」來完成，通常在 `affine` 相關的 pass 中以保守方式處理。

**第四，沒有 schedule 的獨立表示。** 在 MLIR 中，schedule 就是**迴圈 nest 的實際結構**——你透過重寫 `affine.for` 來改變 schedule。多面體模型裡 schedule 是一個獨立的、可做 schedule transformation 演算法的資料結構；MLIR 把這兩者綁在一起，這是工程上的簡化，也是 MLIR 風格的體現：**IR 的結構本身就是最佳化的表示**。

## AffineMap 的表示

`AffineMap` 是 affine 方言的基礎資料結構。讓我們把它拆開。

一個 `AffineMap` 有三部分：

1. **dim 的數量**（`numDims`）
2. **symbol 的數量**（`numSymbols`）
3. **結果運算式列表**（`results`），每個是 `AffineExpr`

語法形式：

```mlir
(d0, d1, ..., d_{n-1}, s0, s1, ..., s_{m-1}) -> (e0, e1, ..., e_{k-1})
```

其中前 $n$ 個輸入是**維度**（dimension），對應迭代空間的維度；後 $m$ 個是**符號**（symbol），對應尺寸參數。

### dim 與 symbol 的分工

這是 affine 語言最基礎也最重要的區分。

* **dim（維度）**：隨迭代變動的變數。例如迴圈索引 `i`、區塊參數。
* **symbol（符號）**：在整個迭代中固定的參數。例如矩陣尺寸 `M`、`N`。

在迴圈內部，symbol 的值是不變的；dim 的值隨迭代改變。這個區分讓「這個運算式是迴圈不變的」這件事在型別層面就是顯式的。

**symbol 代表什麼？** symbol 代表**尺寸參數（size parameter）**——陣列的長度、batch size、通道數這類在編譯期已知（或至少在該迴圈內恆定）的數值。

這個區分有實際的後果：`affine.load` 的索引中，symbol 出現是沒問題的，但若把一個 dim 當作 symbol 傳入，就會得到錯誤的答案——因為編譯器可能把它當作迴圈不變而做錯誤的優化。

在 C++ 中建立 affine map：

```cpp
MLIRContext *ctx = ...;
// (d0, d1) -> (d0 + 1, d1)
AffineExpr d0 = getAffineDimExpr(0, ctx);
AffineExpr d1 = getAffineDimExpr(1, ctx);
AffineExpr one = getAffineConstantExpr(1, ctx);
AffineMap m = AffineMap::get(2, 0, {d0 + one, d1}, ctx);

// (d0, d1)[s0] -> (d0 + s0, d1)
AffineExpr s0 = getAffineSymbolExpr(0, ctx);
AffineMap m2 = AffineMap::get(2, 1, {d0 + s0, d1}, ctx);
```

查詢 API：

```cpp
unsigned nDims = m.getNumDims();
unsigned nSyms = m.getNumSymbols();
unsigned nResults = m.getNumResults();
AffineExpr e = m.getResult(0);
```

`AffineMap` 的重要特性：**它是 context 內 uniqued 的**。`AffineMap::get` 對相同參數回傳同一個物件，所以比較地圖就是比較指標。

### restricted affine map 與 general affine map

MLIR 區分兩種 map：

**general affine map**：結果運算式可以包含 dim、symbol、常數，以及它們的仿射組合。運算式本身是 affine 的（不含乘法兩個變數）。

**restricted affine map**：額外要求每個結果運算式是「單一 dim 的常數倍 + 常數」，即：

$$
e_i = c_0 + c_1 \cdot d_{k_i}
$$

restricted map 的重要性在於它**保證了「維度身分」的對應關係**。在 restricted map 中，每個結果維度對應到恰好一個輸入 dim。這讓「把一個 map 投影到另一個 map」變成可能的操作。

MLIR 裡判定 restricted 的 API：

```cpp
bool isRestricted = m.isProjectedPermutation();
```

`isProjectedPermutation()` 是更強的條件（要求是 dim 的排列，不含常數偏移）。判定 restricted 的方法是 `m.getNumCols()` 加上對每個結果的檢查。

### affine.apply：把 map 變成運算

`affine.apply` 把一個 affine map 應用到具體的 dim/symbol 值上，產生一個 `index` 值：

```mlir
%v = affine.apply affine_map<(d0, d1) -> (d0 * 2 + d1)>(%i, %j)
```

它的用途是**計算索引**。例如在 memref 的 affine layout 中，給定一個邏輯索引 $(i,j)$ ，實際的記憶體位址需要經過 stride 計算：

$$
\text{offset} = i \cdot \text{stride}_0 + j \cdot \text{stride}_1 + \text{offset}_0
$$

這個計算就是一個 affine map，`affine.apply` 把它變成一條指令序列。

## affine.for：下界與上界的組合

`affine.for` 的上下界是**仿射運算式**，由兩類部分組成：

1. **map 部分（map operands）**：由 dim 與 symbol 組成的 affine map 的結果。
2. **operand 部分（bound operands）**：具體的值。

`affine.for` 的語法（以兩個 map operand + 多個 bound operand 為例）：

```mlir
affine.for %i = affine_map<(d0) -> (d0)>()[%n] to affine_map<(d0) -> (d0 + 4)>()[%n] {
  ...
}
```

更完整的語法形式是：

```mlir
affine.for %i = <lower bound> to <upper bound> step <step> {
  ...
}

lower bound := affine_map<...>(operands) | integer constant
upper bound := affine_map<...>(operands) | integer constant
```

上下界中出現的 dim 必須是**外層迴圈的歸納變數**（或 block argument）。這是 affine 迴圈 nest 的**結構性約束**：

> `affine.for` 的上下界只能依賴外層迴圈的索引。

這個約束稱為 **"single static assignment"-like 的 dependence**，它是 affine nest 保持「盒子形狀」的保證。

### 上下界的組合規則

`affine.for` 的實際上下界計算規則：

* 若上下界是**純常數**，則是靜態的。
* 若上下界是 **map + operands** 的形式，則 map 結果的每個元素分別加上一個 operand。若 operand 的數量少於 map 的結果數量，缺少的部分視為 0。

例如下面這個例子：

```mlir
affine.for %i = affine_map<(d0) -> (d0, 0)>(%n) to affine_map<(d0) -> (d0, 3)>(%n) {
```

map 的結果是兩個運算式，operand 只有一個 `%n`。依規則：

* 下界 = $(\%n + 0,\; 0 + 0) = (\%n,\; 0)$ ? 這裡的語意是「map 的第 $k$ 個結果 + 第 $k$ 個 operand（若無則 0）」。
* 上界 = $(\%n + 3,\; 0)$ 。

但對**單維**迴圈，map 的結果數量必須是 1。所以多結果 map 只在 `affine.apply` 這類 op 中有意義。

在實務中，最常見的形式是：

```mlir
// 下界 0，上界為變數 %n
affine.for %i = 0 to %n { ... }

// 下界為外層索引，上界為外層索引 + 長度
affine.for %j = %i to %i + %len { ... }

// 下界用 symbol 參數
affine.for %k = 0 to %K { ... }
```

### 一個完整的 affine nest

```mlir
func.func @conv1d(%A: memref<56x57xf32>, %B: memref<57xf32>, %C: memref<56xf32>) {
  affine.for %i = 0 to 56 {
    affine.for %j = 0 to 57 {
      %a = affine.load %A[%i, %j] : memref<56x57xf32>
      %b = affine.load %B[%j] : memref<57xf32>
      %s = arith.mulf %a, %b : f32
      %old = affine.load %C[%i] : memref<56xf32>
      %n = arith.addf %old, %s : f32
      affine.store %n, %C[%i] : memref<56xf32>
    }
  }
  return
}
```

這裡的 `%j` 是 reduction 維度。編譯器可以從中推導出：

* `$C[i]$` 被多次寫入，但索引不依賴 `$j$`，所以是 loop-invariant，相對於 `$j$` 迴圈是「不變」。
* `$A[i,j]$` 與 `$B[j]$` 對 `$j$` 的存取都是單一的、無相依的。
* 這個迴圈可以 fusion，也就是把 `$A` 與 `$B` 的載入合併；可以 tiling，也就是把 $i$ 與 $j$ 分塊；可以 interchange，也就是交換 $i$ 與 $j$ 以改善 cache。

這些推論之所以能做，正是因為索引是仿射的。

## 合法性分析：為什麼 affine 是安全的

讓我們把「合法性」講得更精確，這是 affine 方言存在的理論基礎。

**命題**：若一個迴圈 nest 中所有記憶體存取的索引都是 restricted affine map，且 nest 滿足 affine nest 的結構性約束，則**任意兩個 parallel 維度的交換都是合法的**。

**理由**：parallel 維度的交換不改變同一個迭代點內的執行順序，只是改變迭代點之間的順序。若兩個存取的索引只依賴不同的 dim（即它們是「正交的」），則交換不會改變任何相依。

反過來，reduction 維度的交換可能非法——例如若 nest 中有 `$C[i] += A[j] * B[j]$`，交換 $i$ 與 $j$ 會改變結果。

MLIR 的 affine 相關 pass 裡，這類分析由 `mlir::affine::` 命名空間下的函式完成，例如：

```cpp
// 檢查某個 operation 是否依賴某個迴圈變數
bool dependsOn(Operation *op, Value iv);

// 檢查兩個 operation 之間是否存在 dependence
LogicalResult checkMemrefAccessDependence(Operation *srcOp, Operation *dstOp,
                                           unsigned numCommonLoops,
                                           MemRefAccess dependence,
                                           const DenseSet<Operation *> &opsToIgnore,
                                           Value dstIndex, Value srcIndex,
                                           DependenceResult &result);
```

`DependenceResult` 的列舉值有 `NoDependence`、`HasDependence`、`Failure`，以及更精細的 `Independent`、`AffineForIndependence`、`CommonSurroundingLoop`、`SurroundingLoopCarried` 等分類。

在 C++ 中，一個 affine dependence 檢查的典型用法：

```cpp
mlir::affine::DependenceResult result;
mlir::affine::checkMemrefAccessDependence(
    loadOp, storeOp,
    /*numCommonLoops=*/2,
    mlir::affine::MemRefAccess::Read,
    /*opsToIgnore=*/{},
    /*dstIndex=*/storeOp->getOperand(1),
    /*srcIndex=*/loadOp->getOperand(1),
    result);
if (result == mlir::affine::DependenceResult::HasDependence) {
  // 不可交換
}
```

這段 API 的存在，就是多面體分析在 MLIR 中的落地方式。

## affine 到 scf 的降階

`affine` 方言**基本上可以直接降階到 `scf`**。原因是兩者的迴圈語意高度重疊：都是單一 entry、多個 exit、region 帶 terminator。

差異只在於上下界的表達：

```mlir
// affine.for %i = 0 to %n { ... }
// 降階為
scf.for %i = %c0 to %n step %c1 {
  ...
}
```

而 bound operands 的處理：

```mlir
// affine.for %i = affine_map<(d0) -> (d0 + 1)>(%n) to %m
// 降階為
%lb = arith.addi %n, %c1 : index
scf.for %i = %lb to %m step %c1 { ... }
```

`affine.apply` 降階成一串 `arith` 運算：

```mlir
// %v = affine.apply affine_map<(d0)[s0] -> (d0 * 4 + s0)>(%i, %s)
%t0 = arith.muli %i, %c4 : index
%v = arith.addi %t0, %s : index
```

`affine.load` / `affine.store` 降階成 `memref.load` / `memref.store`（索引先用 `affine.apply` 或直接用 dim expr 計算）。

### 降階的必要性

為什麼要降階，而不是讓 `affine` 直接產生 LLVM IR？

因為 **`affine` 是一個優化的中介層**。它存在的目的，是讓 `scf` 之上的最佳化 pass（tiling、vectorization、fusion）在**知道索引結構**的前提下工作。一旦最佳化完成，`affine` 的額外資訊就不再需要，`scf` 的簡單表示就夠了。

這是 MLIR 的漸進式降階哲學的典型體現：**每一層的價值在於它比下一層多知道的那些東西**。

### 一個重要的實務提醒

`affine` 方言的實際使用有爭議。MLIR 社群中曾有「是否應該保留 `affine` 方言」的討論（`affine` 上游被標記為可能逐步棄用，因為 `scf` + `memref` 的組合加上 `linalg` 已經能覆蓋大部分需求，而 `affine` 的 API 複雜度高）。

實務上的現狀是：`affine` 仍在上游，且在 `mlir/test` 中有大量測試；它對多面體風格的最佳化仍然是有價值的。但新設計的 pass 通常傾向於 `scf` + `linalg` 的組合。

## 與 Polly 的比較

| 面向 | Polly | MLIR affine |
|---|---|---|
| 目標 | 完整的多面體最佳化框架 | 提供結構化的索引資訊 |
| Dependence 分析 | 完整的多面體 dependence graph | 保守的、逐對檢查 |
| Schedule 表示 | 獨立的 schedule tree | 就是迴圈 nest 的結構 |
| Transformation | Pluto / ISL 演算法 | 無系統性 schedule transformation |
| 表達力 | general affine（維度間可加） | restricted affine |
| 整合性 | 獨立的編譯器框架 | MLIR 的一層，與其他方言共存 |
| 成熟度 | 已在 GCC 與 LLVM 上實測多年 | 較新，API 仍在演進 |

ISL（Integer Set Library）提供了 Presburger 算術的實作，是 Polly 的基礎。MLIR 的 affine **不依賴 ISL**——這是刻意的，因為引入 ISL 會帶來顯式的建置相依。

Polly 的做法是「把所有東西變成多面體」，MLIR affine 的做法是「保持 IR 結構，用簡單的區間/仿射分析足夠回答常見問題」。

## 一個完整的 MLIR affine 範例

```mlir
#map_in = affine_map<(d0, d1) -> (d0 + d1)>
#map_sym = affine_map<(d0, d1)[s0] -> (d0, s0)>

func.func @affine_example(%A: memref<?x?xf32>, %B: memref<?xf32>,
                          %M: index, %N: index) {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c2 = arith.constant 2 : index

  affine.for %i = 0 to %M {
    affine.for %j = 0 to %N {
      %off = affine.apply #map_sym(%i, %j)[%N]
      %v = affine.load %A[%off] : memref<?x?xf32>
      %b = affine.load %B[%j] : memref<?xf32>
      %s = arith.mulf %v, %b : f32
      affine.store %s, %A[%off] : memref<?x?xf32>
    }
  }
  return
}
```

這裡 `#map_sym` 是 `(d0, d1)[s0] -> (d0, s0)`：把迭代變數 `$i` 與符號 `$N` 組合成一個扁平的索引。注意 **symbol 是迴圈不變的**——`%N` 在整個 nest 中不變。

## 符號的語意細節

關於 symbol，有幾個實務上的重要規則：

* **symbol 的個數必須與 `affine.apply` 的 operands 中「被當作 symbol 的部分」一致。** `affine.apply` 的 operand 列表中，前 `numDims` 個對應 dim，後 `numSymbols` 個對應 symbol。
* **symbol 不一定是常數。** 它可以是執行期才知道的值（如 `%M`），重點是它在**該迭代空間內不變**。
* **在 `affine.for` 的上下界中，dim 只能是外層迴圈的索引。** 內層迴圈的索引不能在自身的上下界裡出現。
* **在 `affine.load` 的索引中，dim 可以是任何包含它的迴圈的索引**（包含當前迴圈）。

這些規則共同保證了「affine nest 是盒子形狀的」，讓 dependence 分析可以用區間算術保守地完成。

## 小結與延伸閱讀

* 多面體模型把程式表示為迭代空間（多面體）、access function 與 schedule；合法性由「保持 flow dependence」定義，本質上是 Presburger 算術的可判定問題。
* MLIR 的 `affine` 方言**刻意不是**完整的多面體模型：它只保證 restricted affine 的索引結構，dependence 分析保守，schedule 就是迴圈 nest 的實際結構，不做系統性的 schedule transformation。
* `AffineMap` 由 dim 數、symbol 數與結果運算式列表構成；dim 是隨迭代變動的變數，symbol 是迴圈不變的**尺寸參數**。restricted affine map 要求每個結果維度是「單一 dim 的常數倍 + 常數」。
* `affine.for` 的上下界可為常數或「affine map + operands」的組合，但 dim 只允許依賴外層迴圈索引，這保證了 nest 的盒子形狀。
* affine 相關 pass 靠 `mlir::affine::checkMemrefAccessDependence` 之類的 API 做 dependence 判斷，這是多面體分析在 MLIR 中的落地。
* `affine` 降到 `scf` 是直接的，因為 `affine` 的價值在於「比 `scf` 多知道的索引結構」，一旦最佳化完成即可捨棄。
* 與 Polly 相比，MLIR affine 放棄了完整的多面體最佳化與 ISL 相依，換取與 MLIR 生態的整合性與較低的複雜度。
