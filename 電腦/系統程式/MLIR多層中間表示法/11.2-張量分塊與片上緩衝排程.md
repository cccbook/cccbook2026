# 11.2 張量分塊（Tiling）與片上緩衝區排程

[11.1](11.1-脈動陣列與NPU的IR需求.md) 建立了硬體對 IR 的三項要求，其中「緩衝區容量必須是編�期常數」與「PE 數量必須是編�期常數」兩項，都必須靠**分塊（tiling）** 這個變換來落地。分塊不是一個可有可無的最佳化步驟：在 NPU 上，它是**決定程式能否執行**的前置條件。

本節要回答的問題是：

> 給定一個 NPU 的硬體參數（SRAM 容量、PE 陣列形狀、對齊要求），如何算出一組可行的 tile size？以及這個算出的結果，如何以可重現、可驗證的方式存在於 IR 中？

## tiling 的目標與本質

### 為什麼在 NPU 上 tiling 是必需的

在 GPU 上，tiling 主要的目的是**提升 cache 命中率**。GPU 有層層的 cache（[11.1](11.1-脈動陣列與NPU的IR需求.md) 提到 NPU 常常刻意移除 cache），所以 tiling 是「效能優化」。

在 NPU 上，情況不同。NPU 的片上 SRAM 是**唯一的**工作記憶體，容量以數 MB 計。一個典型的 transformer 前向傳播中，激活值的中間結果體積可以輕易超過數百 MB。因此：

> 在 NPU 上，如果沒有 tiling，程式在物理上無法執行——不是「跑得慢」，而是「跑不起來」。

這也解釋了為什麼 NPU 的編譯器往往**不支援動態形狀**（dynamic shape）：tile size 是編譯期常數，而 tile size 依賴形狀，形狀動態就意味著 buffer 大小動態，SRAM 排程就無解。11.2 最後一節會回到這個問題。

### tiling 在資料流機器上的意義

在傳統控制流機器上，tiling 的效果是「迴圈 nest 變小，所以可以放進 cache」。語意上完全等價，只是排程方式不同。

在資料流機器上，tiling 有本質不同的意義：**迴圈被靜態展開成一段磚序列**。

具體來說，一個 `scf.for` 迴圈在 NPU 上並不存在——硬體沒有迴圈計數器，也沒有分支。每一次迭代被「攤平」成一段靜態排程的資料流。那麼「迭代 $k$ 次」是怎麼表達的？

答案是：**迭代次數被靜態確定，然後展開成 $k$ 份硬體資源或 $k$ 段 pipeline stage**。

這帶來一個重要的可攤平性（flattenability）條件：

> 一個迴圈能夠在資料流機器上展開，前提是它的 trip count 在編譯期已知，或者它的 body 可以被映射成有限個資源的重複使用。

於是我們有了三種處理迭代空間的手段：

| 手段 | 語意 | NPU 上的代價 |
| --- | --- | --- |
| 靜態展開 | trip count 已知，複製硬體資源 | 硬體量爆炸（ $k$ 份 PE） |
| 循環不變的資源重用 | body 映射到固定的 PE 集合，靠 pipeline 餵資料 | 需要 II = 1 的排程能力 |
| 分塊 + pipeline | 切成固定的磚，磚之間 pipeline，磚內靜態 | **主流做法** |

第三種就是本節的主題。

## 容量估算：磚形狀與硬體參數的耦合

### 一個具體的估算模型

設 NPU 的硬體參數為：

* 片上 SRAM 容量 $S$ （bytes）
* PE 陣列形狀 $R \times C$ （例如 $128 \times 128$ ）
* 資料元素大小 $e$ （bytes，例如 f32 的 4 或 int8 的 1）

要做的是一個 $M \times K$ 與 $K \times N$ 的矩陣乘法，產生 $M \times N$ 結果。

**推論一：PE 陣列決定了 $M$ 與 $N$ 的 tile 上限。**

在脈動陣列中， $M$ 維對應沿列方向的 PE 數， $N$ 維對應沿行方向的 PE 數。若 PE 陣列是 $R \times C$ ，則：

$$
t_M \le R, \qquad t_N \le C
$$

通常取 $t_M = R$ , $t_N = C$ ，讓整個陣列都被用滿。若 $M < R$ ，則有 PE 閒置，這是「形狀不匹配」的效能損失。

**推論二： $K$ 維（歸約維度）與 SRAM 容量耦合。**

歸約維度 $K$ 是唯一會「吃掉」SRAM 容量的維度，因為歸約軸不能打斷（見 [11.1](11.1-脈動陣列與NPU的IR需求.md)），整條 $K$ 必須同時在 SRAM 中可容納。

需要的 buffer 有三個：

* $A$ 的 tile： $t_M \times t_K$ 個元素
* $B$ 的 tile： $t_K \times t_N$ 個元素
* $C$ 的 tile： $t_M \times t_N$ 個元素（若需要累加多次，可多份做 double buffering）

總需求：

$$
\text{bytes} = e \cdot (t_M t_K + t_K t_N + t_N t_M)
$$

**推論三：可行 $t_K$ 的上界。**

令 $t_M = R$ , $t_N = C$ ，代入得：

$$
\text{bytes} = e \cdot (R t_K + t_K C + R C) = e \cdot (R + C) t_K + e R C
$$

因此：

$$
t_K^{\max} = \left\lfloor \frac{S / e - R C}{R + C} \right\rfloor
$$

這就是**容量估算公式**。讓我們用一個具體的數字來算。

### 具體計算

假設：

* SRAM 容量 $S = 512\text{ KB} = 524288$ bytes
* PE 陣列 $R = 128$ , $C = 128$
* 元素大小 $e = 4$ （f32）

代入：

$$
t_K^{\max} = \left\lfloor \frac{524288 / 4 - 128 \cdot 128}{128 + 128} \right\rfloor = \left\lfloor \frac{131072 - 16384}{256} \right\rfloor = \left\lfloor \frac{114688}{256} \right\rfloor = \left\lfloor 448 \right\rfloor = 448
$$

也就是說，在不考慮 double buffering 與對齊的情況下，歸約維度可以一次處理 448 個元素。

**雙緩衝的修正。** 若使用 double buffering（同時載入下一塊），上面的 $A$ 、 $B$ buffer 都要兩份：

$$
\text{bytes} = e \cdot \big(2 R t_K + 2 t_K C + t_N t_M \big)
$$

此時：

$$
t_K^{\max} = \left\lfloor \frac{S/e - R C}{2(R + C)} \right\rfloor = \left\lfloor \frac{114688}{512} \right\rfloor = 224
$$

**對齊的修正。** 若 DMA 搬移需要對齊到 64 bytes（常見的 burst 邊界），則 tile 的位元組數必須是 64 的倍數。 $128 \times t_K \times 4 = 512 t_K$ bytes， $512$ 本身已是 64 的倍數，所以 $t_K$ 任意整數都滿足；但若 $t_M$ 是不規則值就要另外處理。

**實務上的取捨。** 通常不會用到 $t_K^{\max}$ ，因為：

1. 過大的 $t_K$ 會讓 pipeline 啟動延遲變長（第一塊要等最慢的 PE 填滿）。
2. 若 $K$ 不整除 $t_K$ ，尾磚會是部分填充的，浪費 PE。
3. 較小的 $t_K$ 提供更好的 SRAM 排程彈性（可以同時放更多不同 op 的 buffer）。

常見的策略是取 $t_K$ 為 $K$ 的因數，或取一個「典範值」（例如 64、128、256），由 autotuner 在候選集中挑選（見 [12.4](12.4-編譯器最佳化與自動化搜尋.md)）。

### 更完整的模型：三個層級的容量

上面的模型只考慮了單一 op 的 buffer。實務上，SRAM 是多個 buffer 共享的池子。完整的模型是：

$$
\sum_{i} \text{bytes}_i(t_1^{(i)}, t_2^{(i)}, \ldots) + \text{bytes}_{\text{double\_buf}} \le S
$$

這是一個**資源分配問題**，本質上是多維装箱（bin packing）。求解方法通常是貪婪式的「生命週期重疊分析」：先做程式的排程（哪些 op 在時間上交疊），再用 interval graph 的染色法分配 SRAM banks。

這也是為什麼 NPU 編譯器通常需要**兩階段**：先做一個「高階排程 pass」決定 op 的順序與 buffer 的生命週期，再做 tiling pass 決定形狀。或者反過來先做 tiling 再做排程。兩種順序都有實際系統採用，取決於是「形狀主導」還是「排程主導」的應用。

### 對齊與硬體 tile 大小不整除

另一個實務上很常遇到的問題：**PE 陣列的維度未必整除問題的形狀**。

若 $M = 200$ 而 PE 陣列列數是 128，則需要兩個 tile： $128 + 72$ 。第二個 tile 只有 72 列有效，等於 $72/128 \approx 56\%$ 的 PE 閒置。

處理方式有兩種：

* **允許部分 tile**（masking）：在 IR 中用 predicate 表達「這個 PE 不參與運算」，這要求硬體支援 per-lane masking。
* **padding**：把 tile 補到滿，硬體閒置但控制流簡單。

在 MLIR 中，masking 可以用 `linalg` 的 `linalg.generic` + `arith.select` 表達，或引入專門的 op；但**更實際的做法**是在高階就把 $M$ 對齊成 128 的倍數（在模型的輸入形狀層面處理），把硬體複雜度推給前端。

## loop tiling 在資料流機器上的落點

### 從 `linalg` op 到靜態磚序列

高階 IR 裡，一個矩陣乘法是一個 `linalg.matmul`。分塊之後（以 `transform` 方言或等價的 pass 為例），變成：

```mlir
%r = linalg.matmul ins(%a, %b : tensor<128x256xf32>, tensor<256x128xf32>)
              outs(%c : tensor<128x128xf32>) -> tensor<128x128xf32>
```

經過 tile 之後（概念上）：

```mlir
// 假設 K 被切成 128 x 2
%r = scf.for %k = %c0 to %c2 step %c128 iter_args(%acc = %c) -> tensor<128x128xf32> {
  %a_t = tensor.extract_slice %a[%k, 0] [128, 128] [1, 1] : tensor<128x256xf32> to tensor<128x128xf32>
  %b_t = tensor.extract_slice %b[%k, 0] [128, 128] [1, 1] : tensor<256x128xf32> to tensor<128x128xf32>
  %acc2 = linalg.matmul ins(%a_t, %b_t : tensor<128x128xf32>, tensor<128x128xf32>)
                   outs(%acc : tensor<128x128xf32>) -> tensor<128x128xf32>
  scf.yield %acc2 : tensor<128x128xf32>
}
```

注意 `%k` 這個迴圈。**在資料流機器上，這個 `scf.for` 不會以迴圈形式存在於硬體**。編譯器接下來要做的轉換是：把 trip count 為 2 的迴圈**完全展開**，然後把產生的兩次 matmul 排成 pipeline。

這就是「loop tiling 在資料流機器上的意義」：tiling 產生一個**有限的、靜態可數的迭代序列**，然後這個序列被「物化」（materialize）成硬體排程。

### 為什麼歸約迴圈特別難

上面的例子裡，`%k` 迴圈是**歸約迴圈**（reduction loop）。它的每一次迭代都依賴前一次的 accumulator。在 pipeline 排程中，這種依賴造成一個嚴格的問題：

> 若要在 II = 1 下排程（即每拍啟動一次新的 tile），accumulator 的更新就必須是「可重疊」的，也就是第 $i$ 次迭代的乘加必須在第 $i+1$ 次迭代開始前完成，或至少有獨立的 accumulator 空間。

解決的標準手段是**累加器複製（accumulator duplication / renaming）**：為 pipeline 的第 $k$ 個 stage 配置獨立的 accumulator bank，各 stage 之間用前進（forwarding）網路連接，形成脈動陣列的結構。這恰好就是 [11.1](11.1-脈動陣列與NPU的IR需求.md) 的脈動陣列！也就是說：

> 在 NPU 上，把歸約迴圈展開成 pipeline，其硬體結構自動就是一個脈動陣列。

這個觀察很重要，因為它意味著 tiling 的 $K$ 維 tile size，實際上決定了「要走多少拍才能算完一個 $M \times N$ 輸出磚」：

$$
\text{cycles\_per\_tile} \approx t_K + \text{fill\_drain}
$$

其中 fill/drain 是脈動陣列的啟動與排空開銷（對 $128 \times 128$ 陣列，通常是數十到數百拍）。這是 tiling 的一個非顯而易見的代價：**tile 太小，啟動開銷佔比就高**。

## double buffering 與 pipelining 的 IR 表達

### 概念模型

double buffering 的意思是：當硬體正在處理第 $i$ 塊的資料時，DMA 引擎同時在把第 $i+1$ 塊搬進 SRAM 的另一個 buffer。這需要：

* 兩份 buffer
* 一個「哪一份是當前 / 哪一份是下一份」的狀態
* 硬體在適當時機自發地切換

在 IR 中，這有兩種表達層次。

### 表達層次一：手動雙緩衝（明確、易驗證）

```mlir
%buf0 = mychip.sram.alloc() : !mychip.sram<65536>
%buf1 = mychip.sram.alloc() : !mychip.sram<65536>
// 啟動第 0 塊的搬移
mychip.dma.async.copy %buf0 <- %src[0] : !mychip.sram<65536> to memref<...>
// 啟動第 1 塊的搬移
mychip.dma.async.copy %buf1 <- %src[1] : !mychip.sram<65536> to memref<...>
// 等待第 0 塊
mychip.dma.async.wait %buf0
%t0 = mychip.compute %buf0, %w0
// 等待第 1 塊
mychip.dma.async.wait %buf1
%t1 = mychip.compute %buf1, %w1
```

這是**最接近硬體**、最容易推理的形式，也最容易正確實作。缺點是手寫冗長，而且 pass 需要小心地處理 buffer 的交替。

### 表達層次二：用 `async` 方言的 group

MLIR 上游的 `async` 方言提供 `async.execute` / `async.group` / `async.await`，把「非同步工作 + 群組 + 等待」標準化：

```mlir
%g = async.group {
  %t0 = async.execute { %c = async.copy %src0 to %buf0 : memref<...> to !mychip.sram<...> }
  %t1 = async.execute { %c = async.copy %src1 to %buf1 : memref<...> to !mychip.sram<...> }
  async.yield
}
async.await %g
```

`async.group` 的價值是**把「一組非同步操作」變成一個可以整體等待的句柄**。NPU 後端可以把一個 group 降階成一個 DMA descriptor 佇列，一次提交。

### 表達層次三：`transform` 方言的排程

最宣告式的是 `transform` 方言。MLIR 的 `transform` 方言把「排程」本身變成 IR：

```mlir
module attributes { transform.with_named_sequence } {
  transform.named_sequence @__transform_main(%arg0: !transform.any_op {transform.readonly}) {
    %0 = transform.structured.match ops{["linalg.matmul"]} in %arg0 : (!transform.any_op) -> !transform.any_op
    %1:2 = transform.structured.tile %0 sizes [128, 128, 128] : !transform.any_op
    %2 = transform.structured.tile %1 sizes [128, 128] : !transform.any_op
    %3 = transform.structured.vectorize %2 : !transform.any_op
    transform.yield
  }
}
```

這裡 `transform.structured.tile` 的 `sizes` 就是磚形狀。注意這個表示法的好處：**排程決策本身是可序列化、可搜尋、可 diff 的資料**。這是 [12.4](12.4-編譯器最佳化與自動化搜尋.md) 的基礎。

### `transform.structured.tile` 的細節

上游 `transform` 方言中，`transform.structured.tile` 的簽名大致是：

```
transform.structured.tile %target sizes [<int>, ...] 
    : !transform.any_op -> (!transform.any_op, !transform.any_op)
```

它回傳兩個結果：一個是「被切過之後的 op」（帶有 `linalg` 的 tile nest），另一個是「切塊之前的 handle」（有時用來做進一步的變換）。支援的參數包括 `sizes`（磚大小）、`static_sizes`（哪些維度是靜態的）等。

`transform` 方言有一個重要的設計選擇：它是**宣告式、資料驅動**的。轉換腳本是一段可以被人寫出、也可以被機器生成（由 autotuner 產生）的 IR。這與傳統的 C++ pass 最大的差別在於，傳統 pass 把控制流程寫在 C++ 裡，難以被外部程式生成。

## scratchpad memory space 在 MLIR 的落點

### memref 的 memory space 屬性

`memref` 型別可以帶一個 memory space 參數（見 [8.3](08.3-memref記憶體抽象.md)）：

```mlir
memref<128x128xf32, 3>
```

memory space 是一個整數（或某些方言定義的型別）。實務上有兩種常見做法：

* **約定整數**：像 SPIR-V 的 storage class 編號那樣，約定 0 = generic/flat、1 = shared、2 = global。
* **自訂型別**：定義 `Mychip_SRAMType`，帶著容量等資訊。

`memref` 的 memory space 屬性是最「輕量」的做法，優點是任何處理 `memref` 的既有 pass（bufferization、canonicalization）都自動支援。缺點是**能表達的資訊太少**：memory space 只是個整數，沒辦法說「這塊 buffer 屬於哪個 DMA channel」。

### 從 memory space 到可 DMA 的 buffer

對 NPU 而言，「這塊記憶體在 SRAM 上」還不夠——硬體的 DMA 引擎需要一個**描述符（descriptor）**，內容包含：

* 來源位址（在 DRAM 的位址空間）
* 目的位址（在 SRAM 的位址空間）
* 長度
* 位元組格式（8/16/32/64 bit）
* 通道與優先序

這些資訊不可能塞進一個整數 memory space。因此完整的設計需要一個**獨立的 buffer 描述機制**：

```mlir
// 宣告一個 SRAM buffer
%buf = mychip.sram.alloc() { size = 65536 : i64 } : !mychip.sram<65536>
// 綁定到 DMA channel 0
mychip.dma.bind %buf to channel 0
```

或者把 descriptor 做成一個**屬性陣列**：

```mlir
mychip.dma.submit channel 0 {
  descriptors = [
    { src = 0 : i64, dst = 0 : i64, len = 65536 : i64, stride = 0 : i64 },
    { src = 65536 : i64, dst = 65536 : i64, len = 65536 : i64, stride = 0 : i64 }
  ]
}
```

### 一個更完整的方案：用 `builtin.unrealized_conversion_cast` 之外的橋接

實務上常見的橋接方式是定義一個 **`#mychip.sram<...>` 的型別別名**，並用一條專門的轉換把 `memref<..., 3>` 轉成 `!mychip.sram<...>`：

```mlir
// 高階：一般的 memref
%m = memref.alloc() : memref<128x128xf32, 3>
// 轉換之後
%s = mychip.to_sram %m : memref<128x128xf32, 3> to !mychip.sram<65536>
```

`mychip.to_sram` 這個 op 的語意是「**取得這塊 SRAM 區域的硬體句柄**」，它的存在讓後端可以把它變成 descriptor。

不過這裡有一個更乾淨的選擇，值得推薦：**讓 `memref` 的 memory space 直接攜帶容量資訊**。做法是定義一個 memory space 的型別別名：

```tablegen
def Mychip_SRAMMemorySpace : MemorySpaceAttr<"SRAM", "sram"> {
  let parameters = (ins "int64_t":$capacityBytes);
  let assemblyFormat = "`<` $capacityBytes `>`";
}
```

於是型別變成 `memref<128x128xf32, #mychip.sram<65536>>`。這樣：

* memory space 攜帶容量 → 排程 pass 可以直接檢查「這塊 buffer 會不會超出」。
* 不需要額外的 `to_sram` op。
* 缺點是自訂 memory space 需要對應的 dialect 支援，某些通用 pass（尤其 bufferization 的部分路徑）需要擴充才能正確處理。

兩種方案的取捨，取決於團隊願意花多少力氣讓通用 pass 理解自訂 memory space。

## 動態形狀的挑戰

### 問題

動態形狀（dynamic shape）在 NPU 上是個真正的難題，不只是「少最佳化一些」而已。

如果 $M$ 是動態的：

1. **buffer 大小不確定** → SRAM 排程無法在編譯期決定要分配多少、是否能放得下。
2. **tile size 不確定** → 尾磚形狀不確定，PE 使用率與 latency 都無法預估。
3. **迴圈 trip count 不確定** → 無法靜態展開成磚序列（本節「loop tiling 在資料流機器上的落點」的可攤平性條件被破壞）。

### 應對策略

| 策略 | 做法 | 代價 |
| --- | --- | --- |
| **完全靜態化** | 前端把形狀推成常數；模型固定 batch size | 失去動態 batch 的彈性 |
| **一組靜態特化** | 對常見 shape 組合做特化，runtime 選擇 | 編譯時間與程式碼空間爆炸 |
| **保守上界** | 對動態維度取最大可能值，buffer 按上界分配 | 浪費 SRAM，PE 使用率低 |
| **硬體支援動態** | 硬體有 descriptor 與 mask 機制可處理變長 tile | 需要特殊硬體，通用 NPU 罕見 |

TPU v1 的做法是「保守上界 + 硬體 padding」：編譯器以靜態 shape 編譯，執行時若 shape 不符則拒絕（fall back 到 CPU）。TPU v2 之後與其他 NPU 逐漸支援有限的動態維度，主要是 batch 維度與序列長度維度（可用 bucketing 處理）。

### 在 IR 中標記靜態化需求

MLIR 裡可以透過 `tensor` 的靜態維度直接表達，也可以在方言層定義「必須靜態」的約束。以 ODS 為例：

```tablegen
def Mychip_Op : Mychip_Op<"..."> {
  let arguments = (ins Mychip_StaticTensor:$input);
}
```

其中 `Mychip_StaticTensor` 是一個 type constraint，要求所有維度都是靜態的。這樣 verifier 會在編譯期就擋下不合法的輸入，而不是留到最後的 codegen 才發現。

另一種做法是在 **pass pipeline 開頭就做 shape 推導**（使用 `tensor.dim` 的 fold、`scf` 的推導 pass），把能推導的維度全部推成常數，剩下的動態維度再依上面表格的策略處理。

## 一個完整的容量計算與 IR 範例

把以上串起來。我們要為一個具體的 NPU 產生對應的 IR。

**硬體參數：**
* SRAM $= 512$ KB，PE 陣列 $= 128 \times 128$ ，資料型別 f32
* 問題： $M = 256$ , $K = 512$ , $N = 128$ 的 matmul

**計算：**

由 $t_M = R = 128$ , $t_N = C = 128$ ， $t_K$ 由容量公式決定。雙緩衝下：

$$
t_K^{\max} = \left\lfloor \frac{524288/4 - 16384}{512} \right\rfloor = 224
$$

$K = 512$ 不能整除 224，所以往下一格找能整除 $K$ 的最大值： $512$ 的因數有 1, 2, 4, 8, 16, 32, 64, 128, 256, 512。在 $\le 224$ 的範圍內最大的因數是 **128**。所以取 $t_K = 128$ ， $K$ 被切成 4 塊。

**驗證容量：**

$$
\text{bytes} = 4 \cdot (2 \cdot 128 \cdot 128 + 2 \cdot 128 \cdot 128 + 128 \cdot 128) = 4 \cdot (32768 + 32768 + 16384) = 4 \cdot 81920 = 327680 \le 524288
$$

有餘量（因為 $t_K = 128$ 小於上界 224），可以把剩餘的 SRAM 留給其他 op 的 buffer，或把 double buffering 擴充成 triple buffering。

**對應的 IR：**

```mlir
// 高階
%r = linalg.matmul ins(%a, %b : tensor<256x512xf32>, tensor<512x128xf32>)
              outs(%c : tensor<256x128xf32>) -> tensor<256x128xf32>
```

```mlir
// 分塊後（scf.for 的 K 維）
%r = scf.for %k = %c0 to %c4 step %c1 iter_args(%acc = %c) -> tensor<256x128xf32> {
  %a_t = tensor.extract_slice %a[%k, 0] [128, 128] [2, 4] : tensor<256x512xf32> to tensor<128x128xf32>
  %b_t = tensor.extract_slice %b[%k, 0] [128, 128] [4, 1] : tensor<512x128xf32> to tensor<128x128xf32>
  %acc2 = linalg.matmul ins(%a_t, %b_t : tensor<128x128xf32>, tensor<128x128xf32>)
                   outs(%acc : tensor<256x128xf32>) -> tensor<256x128xf32>
  scf.yield %acc2 : tensor<256x128xf32>
}
```

注意 `extract_slice` 的 stride `[2, 4]` 與 `[4, 1]`： $M = 256 = 2 \times 128$ ， $K = 512 = 4 \times 128$ ，所以 $A$ 的 tile 在 $M$ 方向的 stride 是 2（在原張量中每隔 128 行取一個 tile 的起點），在 $K$ 方向是 4。

**再降到硬體層（概念示範）：**

```mlir
%acc = mychip.pe.mma %a_tile_sram, %b_tile_sram
    { rows = 128 : i64, cols = 128 : i64, k_depth = 128 : i64 }
    : tensor<128x128xf32> -> tensor<128x128xf32>
```

`k_depth = 128` 就是 $t_K$ ，被記錄下來，硬體後端據此生成 PE 陣列的深度配置與 accumulator 的生命週期。

## 排程與分塊的耦合：把問題拆成兩層

前面提過「高階排程 + 低階 tiling」與反過來兩種順序。讓我們把這個選擇講清楚，因為它影響 pass 管線的架構。

**方案一：先排程後分塊（scheduling-first）**

1. 在 `linalg` / `tosa` 層做 fusion，把可以融合的 op 合併成大的 op。
2. 做**生命週期分析**：為每個中間 buffer 估計其生命週期區間（哪些 op 的執行期間它是 live 的）。
3. 用 SRAM 容量做約束，求出每個 op 的 tile size。
4. 分塊。

這個方案適合「**形狀多樣、op 種類雜**」的模型（例如 transformer）。它的難點是生命週期分析需要排程資訊。

**方案二：先分塊後排程（tiling-first）**

1. 先用固定或啟發式的 tile size 分塊。
2. 之後用一個排程 pass 決定 buffer 的分配與生命週期重疊。
3. 若發現 SRAM 不足，回頭縮小 tile size。

這個方案適合「**op 數量少、形狀規律**」的模型。它的優點是實作簡單、容易預測；缺點是可能陷入 trial-and-error。

實務上越來越多的系統採**方案一的變體**：先用一組啟發式參數產生初步分塊，再用排程器反饋調整，即 12.4 探討的 autotuning。

## 驗證：怎麼確認分塊結果是對的

分塊是個容易出錯的變換（index arithmetic、邊界、padding）。MLIR 提供了幾層防線：

* **Verifier**：確保 `extract_slice` 的 offset + size <= shape。
* **Shape 推導**：`scf.for` 的 `iter_args` 型別必須前後一致。
* **等價性檢查**：用 `mlir-opt` 的 canonicalization 加上隨機測試比對結果。
* **邊界案例測試**：形狀不整除 tile size 時的尾磚。

特別值得強調的是**尾磚**。 $M = 256$ , $t_M = 128$ 剛好整除，但 $M = 200$ 時就會產生一個只有 72 行的尾磚。這個尾磚的 `extract_slice` 必須被 clamp，否則會讀到越界資料。在 MLIR 中，clamp 通常由 `tensor.extract_slice` 的邊界處理或 `linalg` 的 tiling pass 自動完成，但**自訂 pass 必須自己處理**。這是自訂 tiling pass 最常見的 bug 來源。

## 小結與延伸閱讀

* 在 NPU 上，tiling 不是效能優化而是**可行性前提**：SRAM 容量決定了程式能否執行。
* 核心容量公式為 $t_K^{\max} = \left\lfloor \frac{S/e - RC}{m(R + C)} \right\rfloor$ ，其中 $m$ 是 double buffering 的份數；實務上還需考慮對齊與 $K$ 的整除性。
* 在資料流機器上，tiling 的本質是**把迴圈靜態展開成磚序列**；歸約迴圈的展開會自然形成脈動陣列結構。
* 磚形狀與 SRAM 排程是耦合的，實務上採用「兩階段」：先融合與生命週期分析求 tile size，或先分塊再由排程器反饋修正。
* `transform` 方言把排程變成可序列化、可被搜尋器生成的 IR（`transform.structured.tile`），是 autotuning 的基礎設施。
