# 1.3 Region 的兩種語意：SSACFG 與 Graph Region

在 [1.2](01.2-Block與BlockArgument.md) 我們描述了 block 與 block argument 的機制，也提到「region 的語意決定了 block 是否需要 terminator」。這一節要正式面對這個問題：MLIR 的 `Region` 並非只有一種讀法，它有兩種**根本不同的控制流語意**，而方言設計者必須在每一個 region 上明確宣告自己屬於哪一種。

這個二分法不是 MLIR 發明者的偏好，而是從既有的編譯器實務中提煉出來的：機器學習編譯器裡大量出現的資料流圖式運算，本質上就沒有控制流。

## Region 是 Operation 內嵌的 IR 容器

先回到定義。`mlir::Region` 是一個**operation 內部的 IR 容器**，它持有一到多個 `Block`，每個 block 持有操作。

```cpp
class Region {
  BlockListType &getBlocks();
  Block *empty() const;
  Block &front();
  Block &back();
};
```

`Region` 的幾個關鍵屬性：

* `RegionKind`：`SSACFG` 或 `Graph`。
* `IsolationKind`：`IsolationKind::None`、`IsolationKind::IsolatedFromAbove`、`IsolationKind::IsolatedFromAboveIncludingVars`。
* `RegionArgumentList`：region 的入口參數（在 graph region 中也可用）。
* `numArguments`：region 參數的數量。

Region 參數與 Block Argument 是不同的東西，這一點很容易混淆：

| | Block Argument | Region Argument |
|---|---|---|
| 宣告位置 | block 的開頭 | region 的開頭 |
| 數量 | 每個 block 各自有 | 每個 region 一組 |
| 典型用途 | 傳遞前驅的值 | 區域入口的隱式參數 |
| 對應概念 | LLVM `phi` 的替代品 | 隱式函式參數 |

在 SSACFG region 中，region argument 通常被 entry block 的 block argument 綁定；在 graph region 中，region argument 被所有 block 共用，作為 region 範圍內的「全域常數／參數」。

## 兩種語意的差異

### SSACFG Region

SSACFG（Single-Static-Assignment with Control Flow Graph）region 的規則：

1. 可以有零個、一個或多個 block。
2. 每個 block 的最後一個 op 必須是 **terminator**。
3. block 之間的控制流由 terminator 表達。
4. entry block（`region.front()`）是區域的入口。
5. 存在支配關係（dominance）概念。

概念上，一個 SSACFG region 的抽象語意是：

$$
\mathcal{R} : \text{Args} \rightarrow \text{Outputs} \times \text{Control}
$$

其中 control flow 是一個有向圖，圖上的節點是 block，邊是 terminator 的分支目標。

### Graph Region

Graph region 的規則：

1. **沒有隱含的控制流**：block 之間沒有「執行順序」的預設假設。
2. **不需要 terminator**：block 的最後一個 op 不必是 terminator。
3. 沒有 dominance 關係，也沒有「支配者」的定義。
4. 值的使用只受**資料依賴**約束：使用某個值必須在資料流上支配它，但在 graph region 中「支配」的意義被弱化為「依賴順序」。
5. block 之間的關係透過 operand 隱含表達，而非透過顯式的分支。

概念上，一個 graph region 的抽象語意是：

$$
\mathcal{R} : \text{Args} \rightarrow \text{Outputs}
$$

是一個**無副作用順序約束的資料流圖**，或更精確地說，是一個偏序（partial order）上的資料流。

在實務上，graph region 中的操作被視為「只要其 operand 就緒就可以求值」，這正是 SIMD 化、向量化、以及資料流排程所需要的語意。

### 對照表

| 面向 | SSACFG region | Graph region |
|---|---|---|
| Terminator | 必須 | 不需要 |
| Entry block | 有意義（區域入口） | 區分不明顯 |
| 執行順序 | 由 CFG 決定 | 由資料依賴決定（偏序） |
| Dominance | 有嚴格定義 | 不適用 |
| `RegionKind` | `RegionKind::SSACFG` | `RegionKind::Graph` |
| SSA 支配規則 | 完整適用 | 弱化為依賴規則 |
| 常見用例 | `func.func`、`scf.if`、`cf` 區域 | `linalg` op 的 region、`sparse_tensor`、`tosa`、變換 dialect |
| 融合分析 | 需要 | 天然支援 |

## 為什麼需要 graph region

這個問題值得深入。假設我們只有 SSACFG 一種語意，要表達一個 matrix multiply 該怎麼辦？

最直接的想法是用 `scf.for` 巢狀迴圈：

```mlir
scf.for %i = %c0 to %M step %c1 {
  scf.for %j = %c0 to %N step %c1 {
    scf.for %k = %c0 to %K step %c1 {
      // C[i, j] += A[i, k] * B[k, j]
    }
  }
}
```

這個寫法有兩個問題：

1. **它是過度具體的。** 這個迴圈 nest 綁定了具體的維度與迭代順序。當我們想把它變成一個通用的 matrix multiply 運算（能夠再往下轉成 `linalg.matmul` 或直接呼叫 BLAS）時，必須先把它「反向推回」一個抽象的 op 描述。這就是 linalg 方言試圖解決的問題。

2. **它硬編碼了資料依賴以外的控制流資訊。** 巢狀迴圈的合法性來自 SSA 支配規則與迭代變數的歸納變數語意，而不是來自資料本身。

Graph region 提供了另一條路：把「運算」本身當作一個有結構的資料流圖描述。

```mlir
"linalg.matmul" ins(%A, %B : tensor<128x256xf32>, tensor<256x64xf32>)
                  outs(%C : tensor<128x64xf32>) {
^bb0(%a: f32, %b: f32, %c: f32):
  %prod = arith.mulf %a, %b : f32
  %sum = arith.addf %c, %prod : f32
  linalg.yield %sum : f32
}
```

這裡的 region 是 graph 語意：沒有 terminator（`linalg.yield` 是「把結果交給呼叫者」的機制，但不是控制流 terminator），`^bb0` 的參數對應 reduction 維度的切片值。

### Dataflow 的需求

Graph region 特別適合表達**資料流**計算：編譯器可以在 region 內重新排程、重複、融合操作，只要保持 operand 的資料依賴順序。

對比之下，SSACFG region 的操作若要重排，必須保證不違反 terminator 定義的執行順序，且要重新維護 block argument 的一致性，代價高得多。

### Sparse 的需求

`sparse_tensor` 方言需要表達稀疏儲存的複合結構：dense 與 sparse 區域的交織、壓縮參數的產生過程、以及組合索引的計算。這些過程本質上是資料流，而非控制流。

用 SSACFG 表達會得到一堆沒有分支的 `cf` 區域——那只是把 graph region 用更彆扭的方式寫出來，還要付上 terminator 的成本。

### Symbolic 的需求

「符號化」操作（例如把某個計算表達成帶有符號常數的形式、或產生形狀推導）本質上是一組符號代數運算，這些運算彼此獨立，順序無關，正是 graph region 的模型。

### MLIR 的 Transform Dialect 與此的關係

`transform` 方言本身就是 graph region 的重度使用者。它用 graph region 表達「轉換計畫」，節點間的依賴透過 operand 表達：

```mlir
transform.sequence {
^bb0(%arg0: !transform.any_op):
  transform.structured.match ops{["linalg.matmul"]} in %arg0 : (!transform.any_op) -> !transform.any_op
  transform.structured.generate_placeholder_op ...
  transform.yield
}
```

這裡沒有控制流，每個節點的合法性由 operand 隱含的資料依賴保證。

## SSACFG region 的 SSA 支配規則與 region isolation

### 支配規則

在 SSACFG region 中，SSA 的核心規則是：

> 一個值只能被「支配它」的 op 使用。

支配（dominance）的定義：block $B$ 支配 block $D$ ，若且僅若從 region 的 entry 到 $D$ 的**每一條**路徑都經過 $B$ 。

用這個定義，LLVM 的 SSA 有效性就變成一個局部可檢查的條件。MLIR 把它實作在 `mlir::DominanceInfo`：

```cpp
mlir::DominanceInfo domInfo(region.getParentOp());
// 判斷某個 op 是否支配另一個 op
bool dominates = domInfo.dominates(defOp, useOp);
```

在 MLIR 中，支配關係是**跨 operation 層級**定義的：這是 MLIR 相較 LLVM 的一個重要擴充。LLVM 的 `DominatorTree` 只在函式內的 block 之間運作；MLIR 的 `DominanceInfo` 處理的是 operation 樹，因此「一個 op 是否支配另一個 op」可以跨 region 層級判定。

一個 op $A$ 支配 op $B$ 的條件（簡化版）：

1. $A$ 與 $B$ 在同一個 block 內，且 $A$ 在 $B$ 之前；或
2. $A$ 定義了 $B$ 使用的值；或
3. $A$ 所在的 block 支配 $B$ 所在的 block。

第 3 條在 SSACFG 中成立，在 graph region 中則被弱化——graph region 中「block 之間無順序」使得 block 級的支配退化為「同一 block 內或依賴鏈上」。

### Region Isolation

Region isolation 決定 region 能否引用外部的值。`Region::getIsolationKind()`：

| 隔離層級 | 語意 |
|---|---|
| `None` | region 可以引用外部定義的值 |
| `IsolatedFromAbove` | region **不能**引用 region 外部定義的值（但可以使用全域變數） |
| `IsolatedFromAboveIncludingVars` | region 不能引用外部的值，也不能存取全域變數 |

`IsolatedFromAbove` 的驗證規則很簡單：region 中任何 op 的 operand，若其定義 op 不在此 region 內，就會報錯。

```mlir
// 錯誤範例：region isolated from above，但引用了外部的 %x
"test.isolated"() ({
  %0 = arith.addi %x, %x : i32   // %x 定義在外部
}) : () -> ()
```

### isolated-from-above 的代價

隔離帶來強大的能力，代價則是實質的：

1. **無法直接引用外部值**。任何外部值都必須透過 region argument 傳入。這增加了參數傳遞的樣板程式碼。
2. **無法引用全域變數**（在 `IsolatedFromAboveIncludingVars` 之下）。symbol reference 在這個模式下也被禁止。
3. **對重寫與轉換框架的影響**。轉換 pattern 常常需要讀取 region 外部的上下文（例如目標 op 的屬性、來源位置），這些資訊必須透過 region argument 或 attribute 顯式帶進來。

為什麼隔離值得？因為它讓 region 成為**可獨立分析、可獨立重用、可獨立最佳化**的單位。特別是：

* **可重用性**：`linalg` op 的 region 是通用的 payload，可以被複製到不同形狀的 tensor 上。
* **可分析性**：整體分析不必跨越 region 邊界，因此 region 可以作為快取鍵。
* **安全性**：驗證器能保證 region 的行為只由其參數決定，這是許多轉換的正確性前提。

## 混合語意的常見手法

實務上，graph 語意的「無控制流」太嚴格——很多運算確實需要分支（例如 `linalg.generic` 的某些形式、或稀疏儲存的不同路徑）。MLIR 提供了幾種混合手法。

### 手法一：在 graph region 內嵌入 SSACFG region

`linalg.generic` 的 region 本身是 graph 語意，但可以在其中使用 `scf.if`：

```mlir
linalg.generic {
  indexing_maps = [#map, #map],
  iterator_types = ["parallel", "parallel"]
} ins(%A : tensor<128x128xf32>) outs(%B : tensor<128x128xf32>) {
^bb0(%in: f32, %out: f32):
  %cond = arith.cmpf ogt, %in, %zero : f32
  %selected = scf.if %cond -> (f32) {
    %scaled = arith.mulf %in, %two : f32
    scf.yield %scaled : f32
  } else {
    scf.yield %in : f32
  }
  linalg.yield %selected : f32
}
```

這裡 `scf.if` 是一個 **SSACFG region**（嵌在 graph region 裡），而外層 `linalg.generic` 的 region 保持 graph 語意。MLIR 允許 region 語意巢狀。

### 手法二：用 op 的屬性表達分支預測

在不需要真正分支的場合，把「分支」降級為**選擇**：

```mlir
// 用 select 取代分支
%r = arith.select %cond, %a, %b : i32
```

這把控制流轉換成資料流，是 graph region 能夠工作的關鍵技巧之一。轉換框架中有專門的 pass 負責把 SSACFG 區域中的分支「拉平」（region simplification / control flow to dataflow）。

### 手法三：Graph region + 外部 CFG

`scf.execute_region` 把一個 region 當作可呼叫的單位，其內部可以是 SSACFG：

```mlir
scf.execute_region -> (i32) {
^bb0(%arg0: i32):
  cf.cond_br %cond, ^a, ^b
^a:
  scf.yield %x : i32
^b:
  scf.yield %y : i32
}
```

### 手法四：用 SuccessorOperands 讓 graph op 參與 CFG 分析

某些 op 雖然 region 是 graph 語意，但它本身是一個 terminator 或具有分支語意（例如 `scf.condition`）。`SuccessorOperands` 介面讓它們依然能被 CFG 演算法處理。

## 兩段 MLIR 程式碼對照

讓我們直接對照同一個計算（向量加法後取最大值）在兩種語意下的寫法。

### SSACFG 版本

```mlir
func.func @ssacfg_max(%a: memref<128xf32>, %b: memref<128xf32>,
                      %out: memref<128xf32>) {
  %c0 = arith.constant 0 : index
  %c128 = arith.constant 128 : index
  %c1 = arith.constant 1 : index
  scf.for %i = %c0 to %c128 step %c1 {
    %va = memref.load %a[%i] : memref<128xf32>
    %vb = memref.load %b[%i] : memref<128xf32>
    %sum = arith.addf %va, %vb : f32
    %old = memref.load %out[%i] : memref<128xf32>
    %max = arith.maximumf %sum, %old : f32
    memref.store %max, %out[%i] : memref<128xf32>
  }
  func.return
}
```

這裡 `scf.for` 的 region 是 SSACFG：它有 entry block（隱含）、有 `scf.yield` 作為 terminator、有迭代參數 `%i` 與累積參數。

### Graph 版本

```mlir
linalg.generic {
  indexing_maps = [affine_map<(d0) -> (d0)>, affine_map<(d0) -> (d0)>,
                   affine_map<(d0) -> (d0)>],
  iterator_types = ["parallel"]
} ins(%a, %b : memref<128xf32>, memref<128xf32>)
   outs(%out : memref<128xf32>) {
^bb0(%va: f32, %vb: f32, %out_val: f32):
  %sum = arith.addf %va, %vb : f32
  %max = arith.maximumf %sum, %out_val : f32
  linalg.yield %max : f32
}
```

差異清單：

| | SSACFG | Graph |
|---|---|---|
| 迭代 | `scf.for` 顯式表達 | 由 `linalg` 的 indexing map 隱含 |
| 存取記憶體 | `memref.load` / `memref.store` 顯式 | 由 `ins` / `outs` 隱含 |
| Block 參數 | 迭代變數 + 累積參數 | 只有 iteration-space 的切片值 |
| Terminator | `scf.yield` | `linalg.yield`（非 terminator） |
| 可否重新排程 | 受 terminator 約束 | 可依資料依賴自由排程 |

**關鍵觀察**：graph 版本攜帶的**額外控制資訊更少**，但隱含的結構資訊（迭代空間、索引對映）反而更豐富。這正是 graph region 的價值——它把「怎麼迭代」從控制流提升為宣告式的屬性（`indexing_maps`、`iterator_types`），讓最佳化變成在宣告式描述上的運算。

## 在 C++ 中宣告與操作 Region

```cpp
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinTypes.h"

// 查詢 region 語意
Region &region = op->getRegion(0);
if (region.getKind() == RegionKind::Graph) {
  // graph 語意：無需 terminator
}

// 在一個 op 的 region 中建立 entry block
OpBuilder builder(ctx);
builder.createBlock(&region, {}, TypeRange{builder.getF32Type()});
```

區域的語意在建構時由持有它的操作決定；`Region::getKind()` 之後可用於查詢。

在 TableGen 中，region 的語意通常由操作定義宣告：

```tablegen
def MyOp : MyDialect_Op<"myop", [Pure]> {
  let regions = (region AnyRegion:$body);
  let builders = [
    OpBuilder<(ins), [{
      $_state.addRegion();
      Region &bodyRegion = $_state.regions[0];
      bodyRegion.push_back(new Block());
    }])>
  ];
}
```

而 dialect 層級可以強制所有 region 都是 graph 語意：

```tablegen
def MyGraphDialect : Dialect {
  let name = "my_graph";
  let useDefaultTypeConverterParser = 1;
  let useDefaultAttributePrinterParser = 1;
  let extraClassDeclaration = [{
    // 讓此 dialect 的所有 region 都是 graph 語意
  }];
}
```

實務上，MLIR 也提供 `RegionKind` 檢查工具：

```cpp
// 檢查 region 是否為 SSACFG
bool isSSACFG(Region &region) {
  return region.getKind() == RegionKind::SSACFG;
}

// 檢查 operation 的所有 region 是否都沒有 terminator
bool hasNoTerminator(Operation *op) {
  for (Region &region : op->getRegions()) {
    for (Block &block : region) {
      if (block.mightHaveTerminator())
        return false;
    }
  }
  return true;
}
```

`Block::mightHaveTerminator()` 檢查的是最後一個 op 是否帶有 `OpTrait::IsTerminator`，這正是 `NoTerminator` trait 的實作基礎。

## 小結與延伸閱讀

* `Region` 是 operation 內嵌的 IR 容器，具有兩種控制流語意：`RegionKind::SSACFG`（有 entry block 與 terminator，適用支配規則）與 `RegionKind::Graph`（無隱含控制流、無 terminator、順序由資料依賴決定）。
* Graph region 的必要性來自真實需求：資料流運算（`linalg`）、稀疏儲存（`sparse_tensor`）、符號運算與轉換計畫（`transform`）本質上沒有控制流，用 SSACFG 硬寫只會付出 terminator 成本而得不到好處。
* `Region::getIsolationKind()` 決定 region 能否引用外部值；`IsolatedFromAbove` 換來可獨立分析與重用的能力，代價是必須透過 region argument 傳遞所有外部依賴。
* 兩種語意可以巢狀混用：graph region 內可放 `scf.if` 等 SSACFG region，實務上也常把分支降級為 `arith.select` 以維持 graph 語意。
