# 10.2 撰寫 TableGen 規格與 C++ 實作

[10.1](10.1-自訂方言的抽象層級設計.md) 決定了 `npu` 方言的抽象層級、op 集合與 operand/屬性歸屬。本節把那些決策**翻譯成程式碼**。

這是一節「照著做就能跑」的操作指南。目標是完成：

* 一個 `NPUDialect` 的 C++ 類別。
* 一個帶量化參數的 `npu.tensor` 型別。
* `npu.matmul`、`npu.quantize`、`npu.tile` 三個 op。
* 一個自訂的 assembly format 與它的 parse/print。
* 完整的 CMakeLists。

## 分工邊界：ODS 與手寫 C++

先講清楚這個分工，因為它是初學者最常搞混的地方。

| 產物 | 產生方式 | 包含 |
| --- | --- | --- |
| `NPUOps.h.inc` | `mlir-tblgen -gen-op-decls` | op 的 C++ 類別宣告、accessor、`getOperationName()`、trait 的宣告 |
| `NPUOps.cpp.inc` | `mlir-tblgen -gen-op-defs` | op 的 `build` 方法、operand/result 型別檢查（若宣告了 `hasCanonicalizer` 等則含 dispatch 點） |
| `NPUOpsDialect.h.inc` | `mlir-tblgen -gen-dialect-decls` | dialect 類別宣告 |
| `NPUOpsDialect.cpp.inc` | `mlir-tblgen -gen-dialect-defs` | dialect 的 `initialize()`、型別/屬性的 parser printer |
| `NPUTypes.h.inc` | `mlir-tblgen -gen-typedef-decls` | 型別類別宣告 |
| `NPUTypes.cpp.inc` | `mlir-tblgen -gen-typedef-defs` | 型別類別定義、storage 類別 |

ODS **不**產生的是：

* `verify()` 的主體（除非用 declarative ODS 的 `hasVerifier`，但那需要 `AllTypesMatch` 之類的宣告式約束，且功能有限）
* `fold` 的實作（`hasFolder` 只產生 dispatch 點）
* `canonicalize` pattern
* 自訂的 `parse` / `print`
* `build` 的自訂 overload（ODS 產生的 `build` 是固定簽章的）
* 任何需要「操作語意」而非「操作形狀」的邏輯

一句話總結：**ODS 描述形狀，TableGen 無法描述語意；語意必須手寫。**

## Type 定義：`NPUTypes.td`

我們需要一個帶量化參數的張量型別。MLIR 的 `TensorType` 已經有 encoding（`tensor<128x256xf16, #npu.q<...>>` 中的 encoding 位置），但我們的量化參數需要是**自訂 encoding**。有兩種做法：

**做法 A：用 `tensor` 的 encoding（`AnyEncoding`）**，然後在 `npu` 方言中註冊 encoding 的 parser/printer。

**做法 B：定義自己的 `npu.tensor` 型別**，裡面包一個 `TensorType`。

做法 B 更簡單也更常見（很多加速器方言都這麼做），但會失去 `tensor` 方言的既有工具（例如 `tensor.extract_slice` 的 pattern 對 `npu.tensor` 不適用）。

我們採**做法 A 的變體**：定義一個**量化參數的 attribute**，把它當作 `tensor` 的 encoding 使用。這樣 `npu.matmul` 的 operand 型別仍是 `TensorType`，相容性最好。

先定義量化屬性。因為 `AttrDef` 需要引用 dialect 定義，dialect 必須放在**獨立的檔案**裡（否則 `NPUTypes.td` 與 `NPUOps.td` 會互相 include，形成循環）。

## Dialect 定義：`NPUDialect.td`

```tablegen
// NPUDialect.td
#ifndef MLIR_NPU_DIALECT_TD
#define MLIR_NPU_DIALECT_TD

include "mlir/IR/OpBase.td"

def NPU_Dialect : Dialect {
  let name = "npu";
  let summary = "張量加速器（NPU）方言";
  let description = [{
    `npu` 方言描述一款可程式化張量加速器。它站在圖層（類似 `linalg`），
    但攜帶 NPU 專有的量化與片上 SRAM 資源語意。
  }];
  let cppNamespace = "::mlir::npu";
  let useDefaultTypePrinterParser = 1;
  let useDefaultAttributePrinterParser = 1;
  let hasOperationAttrVerify = 1;
}

#endif // MLIR_NPU_DIALECT_TD
```

接著是量化屬性：

```tablegen
// NPUTypes.td
#ifndef MLIR_NPU_TYPES_TD
#define MLIR_NPU_TYPES_TD

include "mlir/IR/AttrTypeBase.td"
include "mlir/IR/OpBase.td"
include "MLIR/NPU/NPUDialect.td"

def NPU_QuantParamsAttr : AttrDef<NPU_Dialect, "QuantParams"> {
  let summary = "NPU 量化參數，綁定在張量型別的 encoding 上";
  let mnemonic = "q";
  let parameters = (ins
    "::mlir::FloatAttr":$scale,
    "::mlir::IntegerAttr":$zeroPoint
  );
  let assemblyFormat = "`<` $scale `,` $zeroPoint `>`";
  let genVerifyDecl = 1;
}

#endif // MLIR_NPU_TYPES_TD
```

`AttrDef` 會產生 `QuantParamsAttr` 類別，以及 `getScale()` / `getZeroPoint()` 兩個 accessor（回傳 `FloatAttr` 與 `IntegerAttr`）。`mnemonic = "q"` 讓它印出成 `#npu.q<0.5, 0>`。

`genVerifyDecl = 1` 會要求我們在 C++ 中實作 `LogicalResult QuantParamsAttr::verify(...)`；若不想實作，可以拿掉這一行，改用 ODS 的 `let builders = [...]` 自行檢查。

## `npu.matmul` 的 ODS 定義

```tablegen
def NPU_MatMulOp : NPU_Op<"matmul", [Pure]> {
  let summary = "帶量化語意的矩陣乘法";
  let description = [{
    計算 `C = requant(A_quantized * B_quantized)`。

    累加以 int32 進行，最後依結果型別上的量化參數 requantize 回元素型別。
    這個 op 是純函數，沒有副作用。

    ```mlir
    %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16, #npu.q<0.5, 0>>
    ```
  }];

  let arguments = (ins
    TensorOf<[F16, BF16, F32]>:$lhs,
    TensorOf<[F16, BF16, F32]>:$rhs,
    TensorOf<[F16, BF16, F32]>:$out
  );
  let results = (outs TensorOf<[F16, BF16, F32]>:$result);

  let assemblyFormat = [{
    `ins` `(` $lhs `,` $rhs `)` `outs` `(` $out `)` attr-dict `:` type($lhs) `,` type($rhs) `,` type($out)
  }];

  let extraClassDeclaration = [{
    /// 取得左operand 的第 0 維長度（M）。
    int64_t getM() { return ::llvm::cast<::mlir::RankedTensorType>(getLhs().getType()).getDimSize(0); }
    /// 取得縮減維度長度（K）。
    int64_t getK() { return ::llvm::cast<::mlir::RankedTensorType>(getLhs().getType()).getDimSize(1); }
    /// 取得右operand 的第 1 維長度（N）。
    int64_t getN() { return ::llvm::cast<::mlir::RankedTensorType>(getRhs().getType()).getDimSize(1); }
  }];

  let hasVerifier = 1;
  let hasFolder = 1;
}

def NPU_QuantizeOp : NPU_Op<"quantize", [Pure]> {
  let summary = "把浮點張量量化為整數張量";
  let arguments = (ins TensorOf<[F32, F16]>:$input);
  let results = (outs TensorOf<[I8, I16]>:$result);
  let assemblyFormat = "$input attr-dict `:` type($input) `->` type($result)";
  let hasFolder = 1;
}

def NPU_TileOp : NPU_Op<"tile"> {
  let summary = "把張量切成 NPU 片上 SRAM tile";
  let arguments = (ins TensorOf<[F16, BF16, F32]>:$input);
  let results = (outs TensorOf<[F16, BF16, F32]>:$result);
  let assemblyFormat = "$input attr-dict `:` type($input) `->` type($result)";
  let hasVerifier = 1;
}
```

### 一個重要的取捨：`outs` operand

`npu.matmul` 有**三個 operand**（`lhs`、`rhs`、`out`）與**一個 result**。這看起來彆扭——為什麼不只要兩個 operand，然後產生一個 result？

理由是 **destination-passing style（DPS）**。NPU 的運算核心是「把結果寫進某個具體的 buffer」，這是硬體的本質。若只用兩個 operand 加一個 result，後端就得自己配置輸出 buffer，而硬體並不支援「配置 + 計算」的組合。

MLIR 的 `linalg` 也有同樣的設計（`linalg.matmul` 有 `ins` 與 `outs`）。這是**硬體驅動的 IR 設計**的典型例子。

ODS 對此有個便利：`AttrSizedOperandSegments` trait。當一個 op 有**可變數量**的 operand（這裡是 2 或 3 個 `ins`，加上固定 1 個 `outs`），需要：

```tablegen
def NPU_MatMulOp : NPU_Op<"matmul", [Pure, AttrSizedOperandSegments]> {
  let arguments = (ins Variadic<TensorOf<[F16, BF16, F32]>>:$ins,
                       Optional<TensorOf<[F16, BF16, F32]>>:$out);
  let results = (outs TensorOf<[F16, BF16, F32]>:$result);
  let builders = [
    OpBuilder<(ins "::mlir::Value":$lhs, "::mlir::Value":$rhs,
                   "::mlir::Value":$out)>,
  ];
}
```

`AttrSizedOperandSegments` 會讓 op 帶一個 `operandSegmentSizes` 屬性，記錄每一段的 operand 數量，使得「可變 operand 組」能被正確解析。

### 另一個便利：`SameOperandsAndResultType`

若要求三個 tensor 的元素型別與形狀有特定關係，可以用 ODS 的組合 trait：

```tablegen
def NPU_MatMulOp : NPU_Op<"matmul", [Pure, AllTypesMatch<["lhs", "rhs", "out", "result"]>]> {
```

但 `matmul` 的三個 tensor 形狀**不**相同（ $M \times K$ 、 $K \times N$ 、 $M \times N$ ），所以不能用 `AllTypesMatch`。這類「形狀之間的關係」無法用 ODS 宣告式表達，必須靠 verifier（[10.3](10.3-Verifier與自訂Pass.md)）。

**這是 ODS 的一個重要邊界**：ODS 能表達「型別相同」這類**同一性**約束，但不能表達「 $K$ 維相等」這類**跨位置**約束。

## `build` 方法

ODS 會為每個 op 產生若干 `build` overload：

```cpp
// 自動產生：給定 operand 值，result 型別由推導規則決定
static void build(OpBuilder &odsBuilder, OperationState &odsState,
                  Value lhs, Value rhs, Value out);
static void build(OpBuilder &odsBuilder, OperationState &odsState,
                  Type resultType, Value lhs, Value rhs, Value out);
```

但**自動推導 result 型別**在 `matmul` 這種情況下做不到，因為結果形狀是 $M \times N$ ，需要從兩個 operand 的形狀推導出來。所以我們手寫一個 overload。

在 ODS 中宣告：

```tablegen
  let builders = [
    OpBuilder<(ins "::mlir::Value":$lhs, "::mlir::Value":$rhs,
                   "::mlir::Value":$out)>,
  ];
```

然後在 C++ 中實作：

```cpp
// NPUOps.cpp
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/Dialect/Arith/IR/Arith.h"
#include "mlir/IR/OpImplementation.h"

#include "mlir/Dialect/NPU/NPUOps.h"
#include "mlir/Dialect/NPU/NPUDialect.h"

using namespace mlir;
using namespace mlir::npu;

void MatMulOp::build(OpBuilder &builder, OperationState &state,
                     Value lhs, Value rhs, Value out) {
  auto lhsType = cast<RankedTensorType>(lhs.getType());
  auto rhsType = cast<RankedTensorType>(rhs.getType());
  auto outType = cast<RankedTensorType>(out.getType());

  // 結果形狀是 M x N
  auto resultType = RankedTensorType::get({lhsType.getDimSize(0), rhsType.getDimSize(1)},
                                          lhsType.getElementType(),
                                          outType.getEncoding());
  build(builder, state, resultType, lhs, rhs, out);
}
```

注意最後一行呼叫的是 **ODS 產生的那個 `build`**（`Type resultType, Value lhs, ...`）。這個「手寫 build 呼叫自動 build」的技巧，是 MLIR 裡擴充 builder 的標準手法。

## Assembly Format

### 宣告式 assemblyFormat

ODS 的 `assemblyFormat` 讓我們用一小段類似模板的語法描述組裝與解析：

```tablegen
let assemblyFormat = [{
  `ins` `(` $lhs `,` $rhs `)` `outs` `(` $out `)` attr-dict `:` type($lhs) `,` type($rhs) `,` type($out)
}];
```

這會產生對應的 `parse` 與 `print` 方法，語法為：

```mlir
%npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
```

`attr-dict` 會把未在 format 中出現的屬性印出來。

### 宣告式 format 的限制與 escape hatch

宣告式 format 的限制是：**它無法描述任何需要「根據 operand 值決定結構」的語法**。例如：

* 一個屬性的數量可變的 op。
* 需要根據型別決定用哪個分隔符。
* 需要「選擇性出現」的區段。

這時要改用**自訂 format**：在 ODS 中宣告 `let hasCustomAssemblyFormat = 1;`，然後手寫 `parse` 與 `print`。

我們為 `npu.tile` 示範自訂 format，因為它需要一個「可選的 tile 形狀列表」：

```tablegen
def NPU_TileOp : NPU_Op<"tile"> {
  let summary = "把張量切成 NPU 片上 SRAM tile";
  let arguments = (ins TensorOf<[F16, BF16, F32]>:$input);
  let results = (outs TensorOf<[F16, BF16, F32]>:$result);
  let hasCustomAssemblyFormat = 1;
  let hasVerifier = 1;
}
```

C++ 實作：

```cpp
// NPUOps.cpp

ParseResult TileOp::parse(OpAsmParser &parser, OperationState &result) {
  OpAsmParser::UnresolvedOperand inputOperands;
  Type inputType;
  SmallVector<int64_t> tileSizes;

  if (parser.parseOperand(inputOperands) ||
      parser.parseOptionalAttrDict(result.attributes))
    return failure();

  // 解析選擇性的 `[` tile 大小 `]`
  if (succeeded(parser.parseOptionalLBrace())) {
    if (parser.parseCommaSeparatedList(AsmParser::Delimiter::Square, [&]() {
          int64_t v;
          if (parser.parseInteger(v))
            return failure();
          tileSizes.push_back(v);
          return success();
        }))
      return failure();
    if (parser.parseRBrace())
      return failure();
  }

  if (parser.parseColonType(inputType))
    return failure();

  // 結果型別由 verifier 依 tile 大小推導；在 parse 階段先放一個空的
  result.addTypes(inputType);
  result.addAttribute("tile_sizes",
                       parser.getBuilder().getI32ArrayAttr(tileSizes));
  result.addOperands(inputOperands);
  return success();
}

void TileOp::print(OpAsmPrinter &printer) {
  printer << " ";
  printer.printOperand(getInput());
  printer.printOptionalAttrDict((*this)->getAttrs(),
                                /*elidedAttrs=*/{"tile_sizes"});
  if (!getTileSizes().empty()) {
    printer << " [";
    llvm::interleaveComma(getTileSizes(), printer,
                          [&](int64_t v) { printer << v; });
    printer << "]";
  }
  printer << " : " << getInput().getType();
}
```

### 關於 `printOptionalAttrDict` 的 elidedAttrs

一定要把自訂印出的屬性從 `attr-dict` 中排除，否則會重複印出。`printOptionalAttrDict` 的第二個參數就是 elided 列表。

### `getTileSizes` 這個 accessor 從哪來

ODS 會為**宣告在 `let arguments` 之外的 `let attributes`** 產生 accessor。我們在 ODS 中加上：

```tablegen
  let attributes = (ins DenseI64ArrayAttr:$tile_sizes);
```

但 `DenseI64ArrayAttr` 在 attribute 定義中叫 `DenseI64ArrayAttr`（`I64ArrayAttr`），而且 ODS 產生的 accessor 回傳 `::mlir::DenseI64ArrayAttr`，不是 `SmallVector<int64_t>`。上面程式碼中的 `getTileSizes().empty()` 與 `llvm::interleaveComma(getTileSizes(), ...)` 因此需要調整。

正確版本：

```tablegen
  let attributes = (ins DenseI64ArrayAttr:$tile_sizes);
```

```cpp
void TileOp::print(OpAsmPrinter &printer) {
  printer << " ";
  printer.printOperand(getInput());
  printer.printOptionalAttrDict((*this)->getAttrs(),
                                /*elidedAttrs=*/{"tile_sizes"});
  DenseI64ArrayAttr sizes = getTileSizes();
  if (sizes && sizes.size() > 0) {
    printer << " [";
    llvm::interleaveComma(sizes.asArrayRef(), printer,
                          [&](int64_t v) { printer << v; });
    printer << "]";
  }
  printer << " : " << getInput().getType();
}
```

注意 ODS 產生的 accessor 命名規則：屬性 `tile_sizes` 對應 `getTileSizes()`（snake_case 轉 camelCase）。

## `NPUOps.cpp` 骨架

```cpp
// lib/Dialect/NPU/NPUOps.cpp
#include "mlir/Dialect/NPU/NPUOps.h"
#include "mlir/Dialect/NPU/NPUDialect.h"

#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/IR/OpImplementation.h"
#include "llvm/ADT/TypeSwitch.h"

using namespace mlir;
using namespace mlir::npu;

//===----------------------------------------------------------------------===//
// MatMulOp build
//===----------------------------------------------------------------------===//

void MatMulOp::build(OpBuilder &builder, OperationState &state,
                     Value lhs, Value rhs, Value out) {
  auto lhsType = cast<RankedTensorType>(lhs.getType());
  auto rhsType = cast<RankedTensorType>(rhs.getType());
  auto outType = cast<RankedTensorType>(out.getType());
  auto resultType = RankedTensorType::get(
      {lhsType.getDimSize(0), rhsType.getDimSize(1)},
      lhsType.getElementType(), outType.getEncoding());
  build(builder, state, resultType, lhs, rhs, out);
}

//===----------------------------------------------------------------------===//
// MatMulOp fold
//===----------------------------------------------------------------------===//

OpFoldResult MatMulOp::fold(FoldAdaptor adaptor) {
  // 任一 operand 是常數 0 時，整個 matmul 為 0 —— 這是硬體的實際行為
  // （int32 累加器從 0 開始），但我們不在此做，因為量化語意下
  // 「0 的量化值」不一定是整數 0。留給 [10.3] 的 canonicalizer。
  (void)adaptor;
  return {};
}

### `fold` 的簽章

ODS 的 `hasFolder = 1` 會產生：

```cpp
OpFoldResult fold(FoldAdaptor adaptor);
```

`FoldAdaptor` 是一個 struct，把 operand 換成 `Attribute`（若該 operand 是常數）或 `Value`（否則）。可以用 `adaptor.getLhs()` 取得。

### `canonicalize` pattern

`canonicalize` pattern 不是 op 的方法，而是獨立的 `RewritePattern` 類別。ODS 的 `hasCanonicalizer = 1` 只會產生一個 dispatch 點：

```tablegen
def NPU_QuantizeOp : NPU_Op<"quantize", [Pure]> {
  let hasCanonicalizer = 1;
  let hasFolder = 1;
}
```

```cpp
void QuantizeOp::getCanonicalizationPatterns(RewritePatternSet &results,
                                             MLIRContext *context) {
  results.insert<QuantizeConstantPattern>(context);
}
```

```cpp
namespace {
/// `npu.quantize` 作用於常數時，直接折疊成量化後的常數。
struct QuantizeConstantPattern : OpRewritePattern<QuantizeOp> {
  using OpRewritePattern<QuantizeOp>::OpRewritePattern;

  LogicalResult matchAndRewrite(QuantizeOp op, PatternRewriter &rewriter) const override {
    auto input = op.getInput();
    auto inputAttr = input.getDefiningOp<arith::ConstantOp>();
    if (!inputAttr)
      return failure();

    auto dense = dyn_cast<DenseFPElementsAttr>(inputAttr.getValue());
    if (!dense)
      return failure();

    auto resultType = cast<ShapedType>(op.getResult().getType());
    auto quantAttr = getQuantParams(op.getResult().getType());
    if (!quantAttr)
      return failure();

    SmallVector<int8_t, 8> values;
    values.reserve(dense.size());
    for (APFloat v : dense.getValues<APFloat>()) {
      float scaled = v.convertToFloat() / quantAttr.getScale().convertToFloat();
      int64_t q = std::llround(scaled) + quantAttr.getZeroPoint().getInt();
      q = std::max<int64_t>(std::min<int64_t>(q, 127), -128);
      values.push_back(static_cast<int8_t>(q));
    }
    auto quantAttrValue = DenseIntElementsAttr::get(resultType, values);
    rewriter.replaceOpWithNewOp<arith::ConstantOp>(op, quantAttrValue);
    return success();
  }
};
} // namespace
```

這個 pattern 展示了 canonicalization 的核心價值：**把高階 op 折疊成常數**，讓後續的 dead code elimination 能移除它。

#include "mlir/IR/BuiltinTypes.h"

using namespace mlir;
using namespace mlir::npu;

std::optional<QuantParamsAttr> npu::getQuantParams(Type type) {
  auto shaped = dyn_cast<ShapedType>(type);
  if (!shaped)
    return std::nullopt;
  auto encoding = shaped.getEncoding();
  if (!encoding)
    return std::nullopt;
  return dyn_cast<QuantParamsAttr>(encoding);

## 一個完整的方言使用範例

```mlir
module {
  func.func @quantized_matmul(%a: tensor<128x256xf16, #npu.q<0.5, 0>>,
                              %b: tensor<256x64xf16, #npu.q<0.25, 0>>,
                              %c: tensor<128x64xf16, #npu.q<0.125, 0>>) {
    %r = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16, #npu.q<0.5, 0>>,
                                       tensor<256x64xf16, #npu.q<0.25, 0>>,
                                       tensor<128x64xf16, #npu.q<0.125, 0>>
    return
  }
}
```

注意 `#npu.q<0.5, 0>` 這個 encoding 的語法：`QuantParamsAttr` 的 `assemblyFormat` 是 `` `<` $scale `,` $zeroPoint `>` ``，所以印出成 `#npu.q<0.5, 0>`。

## 常見錯誤與排查

| 症狀 | 原因 | 解法 |
| --- | --- | --- |
| `use of undefined identifier 'NPU_Dialect'` | `NPUOps.td` 未被 include 到 op 的 .td | 在 op 的 .td 加上 `include "MLIR/NPU/NPUOps.td"` |
| op 無法被解析 | `initialize()` 沒呼叫 `addOperations` | 檢查 `NPUDialect.cpp` |
| 存取器不存在 | 屬性沒在 `let attributes` 宣告 | 加上宣告並重新產生 |
| `hasCustomAssemblyFormat` 但沒實作 `parse`/`print` | 只宣告了 trait | 兩者都要寫 |
| 生成的 `build` 與手寫的衝突 | `let builders` 宣告錯 | 確認宣告的簽章與實作一致 |
| dialect 找不到 | 沒註冊進 `DialectRegistry` | 在工具的初始化裡 `registry.insert<npu::NPUDialect>()` |

## 小結與延伸閱讀

* ODS 負責**形狀**（類別宣告、accessor、build overload、`getOperationName()`、dialect 註冊），**語意**（verifier、fold、canonicalize、custom parse/print）必須手寫；兩者的接縫是 ODS 產生的 dispatch 點（`hasVerifier`、`hasFolder`、`hasCanonicalizer`、`hasCustomAssemblyFormat`）。
* `AttrSizedOperandSegments` 是處理「可變數量 operand」的必要 trait；`AllTypesMatch` 只能表達同一性約束，形狀之間的關係（如矩陣乘法的 $K$ 維相等）必須靠 verifier。
* 手寫 `build` 的標準技巧是「推導 result 型別後呼叫 ODS 產生的 `build`」，避免重複實作型別檢查。
* 宣告式 `assemblyFormat` 覆蓋大多數需求，但需要「依值決定結構」時要改用 `hasCustomAssemblyFormat`，並注意 `printOptionalAttrDict` 的 elided 列表避免重複印出。
* CMake 側的最小組合是 `mlir_tablegen`（六個檔案）+ `add_mlir_dialect_library` + `add_mlir_doc`，再把 dialect 加進 `DialectRegistry` 讓 `mlir-opt` 認識它。
