# 10.4 單元測試與 mlir-opt 整合測試流程

[10.3](10.3-Verifier與自訂Pass.md) 完成了 `npu` 方言的 verifier 與兩個 pass。但「寫完」不等於「對了」——方言的正確性體現在**它對非法輸入的反應**與**它對合法輸入的轉換結果**上。

本節說明 MLIR 的測試基礎設施：`lit` + `FileCheck` 的整合測試，以及 gtest 的 C++ 單元測試。目標是建立一套能**自動驗證方言正確性**的流程。

## 測試的兩個層次

MLIR 的測試分成兩層，各有各的用途：

| 層次 | 工具 | 測什麼 | 位置 |
| --- | --- | --- | --- |
| 整合測試 | `lit` + `FileCheck` | 工具的**行為**：給定輸入，輸出是否正確 | `test/Dialect/NPU/` |
| 單元測試 | gtest | 類別的**行為**：給定 C++ 物件，操作是否正確 | `unittests/Dialect/NPU/` |

兩者不可互相取代：

* 整合測試**無法**覆蓋「這個 op 的 build 方法是否正確產生預期的 result 型別」這種細節，因為那需要直接檢查 IR 結構。
* 單元測試**難以**覆蓋「從命令列輸入一段 MLIR 文字，經過 parse 與 pass 後是否得到預期輸出」，因為這需要完整的工具環境。

MLIR 的實務上是**兩者都寫**：整合測試確保每個 dialect op 至少有一個往返測試，單元測試確保複雜的轉換邏輯正確。

## `lit` 與 FileCheck

### `lit` 是什麼

`lit` 是 LLVM 專案使用的測試驅動器（LLVM Integrated Tester）。它的工作很簡單：

1. 找到所有符合副檔名規則的測試檔（`.mlir`、`.cpp` 等）。
2. 讀取每個檔案開頭的 `// RUN:` 行。
3. 執行那些命令。
4. 比對輸出與期望值。
5. 收集失敗報告。

`lit` 的設定檔是 `test/lit.cfg.py`（或 `.cfg`），它定義了「哪些副檔名算測試」、「有哪些工具可用」、「測試的執行順序」。

MLIR 的 `test/lit.cfg.py` 大致是這樣的：

```python
import os
import re
import shutil
import sys

import lit.formats
import lit.llvm

import lit.llvm.initialize

# 設定測試格式：副檔名到 lit.TestFormat 的對應
config.name = 'MLIR'
config.test_format = lit.formats.ShTest(not llvm_config.use_lit_shell)
config.suffixes = ['.mlir', '.py']
config.excludes = ['CMakeLists.txt', 'lit.local.cfg', 'Inputs']

# 把 MLIR 的 build 目錄加入 PATH，讓 lit 可以找到 mlir-opt 等工具
llvm_config.with_environment('PATH', [
    os.path.join(config.mlir_tools_dir, 'bin'),
    os.path.join(config.llvm_tools_dir, 'bin'),
    os.environ['PATH'],
], append_path=True)

# 設定 FileCheck 的路徑
config.environment['FILECHECK_OPTS'] = ...
```

### `// RUN:` 行

每個測試檔的第一行（或前幾行）必須有 `// RUN:`，說明這個測試要怎麼跑。

```mlir
// RUN: mlir-opt %s --npu-expand-matmul | FileCheck %s
```

`%s` 會被替換成測試檔本身的路徑。

多個命令用 `\`，並且可以用 `&&` 或 `|` 串接：

```mlir
// RUN: mlir-opt %s --split-input-file --npu-expand-matmul | FileCheck %s
```

`|` 表示把左邊的 stdout 接到右邊的 stdin。`2>&1` 把 stderr 也導出來（診斷訊息在 stderr）。

### 副檔名與位置

MLIR 慣例是：

| 路徑 | 內容 |
| --- | --- |
| `test/Dialect/NPU/` | `npu` 方言的整合測試 |
| `test/Dialect/NPU/Inputs/` | 測試用的輸入檔（不被當成獨立測試） |
| `test/lib/Dialect/NPU/` | 需要 C++ 工具的整合測試 |
| `unittests/Dialect/NPU/` | gtest 單元測試 |

`Inputs/` 目錄的排除在 `lit.cfg.py` 的 `config.excludes` 中。

## FileCheck 指令

FileCheck 是一個「依序比對文字」的工具。它讀取 stdin，把 `CHECK:` 指令視為「期望在輸出中出現的樣式」。

### 基本指令

| 指令 | 語意 |
| --- | --- |
| `CHECK:` | 必須在輸出中出現（相對於前一個 CHECK 之後的位置） |
| `CHECK-NEXT:` | 必須是輸出的**下一行** |
| `CHECK-SAME:` | 必須與上一個 CHECK 在**同一行** |
| `CHECK-NOT:` | 在下一個 CHECK 之前**不得**出現 |
| `CHECK-DAG:` | 與其他 `CHECK-DAG` 順序無關 |
| `CHECK-LABEL:` | 定義一個「區塊起點」，把輸出切成多段分別比對 |
| `CHECK-COUNT-<N>:` | 必須出現恰好 $N$ 次 |
| `CHECK-EMPTY:` | 必須是空行 |

### 樣式語法

FileCheck 的樣式語法（pattern）分三部分：

1. **固定字串**：直接比對。
2. **`{{...}}`**：正則表達式。
3. **`[[...]]`**：變數定義或引用。

```mlir
// CHECK: npu.matmul
// CHECK-SAME: %[[VAL:.*]] = npu.matmul
// CHECK: linalg.matmul
// CHECK-NOT: npu.
// CHECK-DAG: %[[A:.*]] = tensor.extract
// CHECK-DAG: %[[B:.*]] = tensor.extract
```

**變數**是 FileCheck 的核心機制。`[[NAME:regex]]` **定義**變數（把匹配到的文字記下來），`[[NAME]]` **引用**變數（比對文字是否相同）。

這讓測試可以檢查「資料流關係」而不只是「文字存在」：

```mlir
// CHECK: %[[RES:.*]] = npu.matmul ins(%[[LHS:.*]], %[[RHS:.*]])
// CHECK: linalg.matmul ins(%[[LHS]], %[[RHS]])
```

這個測試同時檢查了三件事：`npu.matmul` 存在、它的兩個 operand 是 `%LHS` 與 `%RHS`、以及降階後的 `linalg.matmul` 用了**同樣的**兩個 operand。

### `CHECK-LABEL` 的重要性

若一個測試檔有多個獨立的函式或區塊，應該用 `CHECK-LABEL` 切分：

```mlir
// CHECK-LABEL: func.func @matmul
// CHECK: npu.matmul
// CHECK-LABEL: func.func @conv
// CHECK: npu.quantize
```

`CHECK-LABEL` 的行為是：**輸出被分成以各個 CHECK-LABEL 為界的段落，每段獨立地做 CHECK 比對**。這防止了「第一個函式的內容被拿去滿足第二個函式的 CHECK」這種常見的測試弱化。

**規則：每個測試檔的第一個 CHECK 應該是 `CHECK-LABEL`。**

### `CHECK-DAG` 與非確定性

`CHECK-DAG` 用於「順序不確定」的輸出，例如 `linalg` 的 fusion 結果中多個 op 的相對順序可能取決於實作細節。

```mlir
// CHECK-DAG: %[[A:.*]] = arith.constant
// CHECK-DAG: %[[B:.*]] = arith.constant
```

`CHECK-DAG` 之間**可以**有 `CHECK-NOT`，但 `CHECK-DAG` 區塊之後必須有一個順序的 `CHECK` 來錨定。

## `--split-input-file` 與 `// -----`

一個 `RUN:` 行只能有一份輸入。但很多時候我們想在一個檔案裡測多個**獨立的**案例。

`--split-input-file` 讓 `mlir-opt` 把輸入檔按 `// -----` 分隔符切成多塊，**逐塊獨立處理並把輸出串接**。

```mlir
// RUN: mlir-opt %s --split-input-file --npu-expand-matmul | FileCheck %s

// -----

func.func @case1(%a: tensor<128x256xf16>) {
  %0 = npu.quantize %a : tensor<128x256xf16> -> tensor<128x256xi8>
  return
}

// -----

func.func @case2(%a: tensor<128x256xf16>) {
  %0 = npu.quantize %a : tensor<128x256xf16> -> tensor<128x256xi8>
  return
}
```

**關鍵性質**：若某一塊的 verifier 報錯，`mlir-opt` 只會讓**那一塊**失敗，其它塊仍然處理。因此一個檔案裡可以放多個案例，每個案例的失敗是獨立的。

但要注意：**`FileCheck` 看到的是所有塊的串接輸出**，所以不同塊的 `CHECK:` 必須互不干擾。用 `CHECK-LABEL` 切分即可。

### 另一種做法：`// -----` 配合 `-split-input-file`

在 `RUN:` 行裡也可以寫 `--split-input-file`。

## `--verify-diagnostics` 與 `expected-error`

這是測試 verifier 的**標準機制**。

`--verify-diagnostics` 讓 `mlir-opt` 把診斷訊息當成**期望的輸出**來檢查，而不是錯誤。

```mlir
// RUN: mlir-opt %s --verify-diagnostics

func.func @bad_k(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>) {
  // expected-error @+1 {{expects the K dimension of lhs and rhs to match, but got 256 and 128}}
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}
```

### 語法

* `expected-error` — 期望一則 error 診斷。
* `expected-warning` — 期望一則 warning。
* `expected-note` — 期望一則 note（通常是「see also」）。
* `@+1` — 期望診斷出現在**下一行**。
* `@+2` — 下一行的下一行。
* `@above` — 上一行。
* `{{...}}` — 診斷訊息必須匹配的樣式（正則表達式）。
* 若省略 `{{...}}`，則只檢查診斷的**位置**。

### 位置的重要性

`expected-error` 預設檢查位置。若診斷被掛在某個 op 上（而不是某一行），位置檢查會失敗。這時可以用：

```mlir
// expected-error@above {{message}}
```

或者對 op 級的診斷，用 `{{.*}}` 放寬。

### 多行診斷

診斷訊息若跨行，可以只匹配第一行，或使用正則表達式的特殊語法。實務上建議保持診斷訊息單行。

### 完整的 verifier 測試檔

```mlir
// RUN: mlir-opt %s --verify-diagnostics --split-input-file

// -----

func.func @ok(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>,
              %c: tensor<128x64xf16>) {
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}

// -----

func.func @k_mismatch(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>) {
  // expected-error @+1 {{expects the K dimension of lhs and rhs to match, but got 256 and 128}}
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}

// -----

func.func @bad_rank(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>) {
  // expected-error @+1 {{expects rank-2 tensors}}
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}

// -----

func.func @no_quant(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>) {
  // expected-error @+1 {{expects all operands to carry quantization parameters}}
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}

// -----

func.func @bad_tile(%a: tensor<128x250xf16>) {
  // expected-error @+1 {{expects the dimension 1 (250) to be a multiple of the tile size 16}}
  %0 = npu.tile %a [16, 16] : tensor<128x250xf16> -> tensor<16x16xf16>
  return
}
```

**注意 `--split-input-file` 與 `--verify-diagnostics` 的組合**：`--verify-diagnostics` 會讓「預期有錯誤的塊」成功（因為錯誤被驗證為預期），但「預期沒錯誤的塊」若真的報錯，仍然是失敗。

### 診斷訊息的穩定性

`--verify-diagnostics` 測試把診斷訊息的**文字**也釘住了。這是雙刃劍：

* **好處**：訊息品質是 API 的一部分，改動時會被 CI 抓到。
* **壞處**：措辭微調就會破壞所有下游的測試。

實務上的折衷：**只匹配關鍵片語**（如 `{{expects the K dimension of lhs and rhs to match}}`），不要匹配整句。

## `-not` 前綴工具

有時我們要確認某個東西**不存在**。MLIR 提供 `not` 工具：

```mlir
// RUN: not mlir-opt %s --npu-expand-matmul 2>&1 | FileCheck %s
```

`not` 的語意是：**期望被包裝的命令失敗**（exit code 非 0）。若命令成功，`not` 會報錯。

這是最常用來測試 verifier 的方式（不需要 `--verify-diagnostics`）：

```mlir
// RUN: not mlir-opt %s 2>&1 | FileCheck %s
// CHECK: 'npu.matmul' op expects the K dimension of lhs and rhs to match
```

`2>&1` 是必要的：診斷在 stderr。

### `not` 與 `--verify-diagnostics` 的比較

| 方式 | 優點 | 缺點 |
| --- | --- | --- |
| `not mlir-opt ...` | 簡單，直接檢查錯誤訊息 | 不能在同一檔案裡混合「合法」與「非法」案例 |
| `--verify-diagnostics` | 位置精確、可混合案例 | 訊息文字被釘住 |

實務上：**測試 verifier 用 `--verify-diagnostics`，測試工具的失敗行為用 `not`。**

## `-verify-each`

`--verify-each`（預設開啟）讓 `mlir-opt` 在**每個 pass 之後**都驗證 IR。這能抓到「pass 產生非法 IR」的 bug。

```mlir
// RUN: mlir-opt %s --npu-expand-matmul -verify-each
```

`--verify-each=false` 關閉它。關閉後，非法 IR 會被保留到後面，最後在 `mlir-translate` 或 LLVM 後端才爆炸，診斷訊息會非常難懂。

**永遠不要在正式 pipeline 中關閉 `-verify-each`**，除非你明確知道在做什麼（例如做 massive 的實驗）。

## 一個完整的整合測試檔

把上面所有元素組合：

```mlir
// RUN: mlir-opt %s --split-input-file --npu-expand-matmul | FileCheck %s
// RUN: mlir-opt %s --split-input-file --npu-expand-matmul --verify-diagnostics -verify-each > /dev/null

// CHECK-LABEL: func.func @simple_matmul
// CHECK: %[[RES:.*]] = linalg.matmul ins(%[[A:.*]], %[[B:.*]]) outs(%{{.*}}) : tensor<128x64xf16>
// CHECK-NOT: npu.

// -----

func.func @simple_matmul(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>,
                          %c: tensor<128x64xf16>) {
  %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}

// -----

func.func @quantized(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>,
                      %c: tensor<128x64xf16>) {
  // CHECK-LABEL: func.func @quantized
  // CHECK: %[[Q:.*]] = npu.quantize %{{.*}} : tensor<128x256xf16> -> tensor<128x256xi8>
  // CHECK: linalg.matmul
  %q = npu.quantize %a : tensor<128x256xf16> -> tensor<128x256xi8>
  %0 = npu.matmul ins(%q, %b) outs(%c) : tensor<128x256xi8>, tensor<256x64xf16>, tensor<128x64xf16>
  return
}
```

第二個 `RUN:` 行是「健全性檢查」：跑一遍並確認沒有診斷輸出（`> /dev/null` 丟掉 stdout，若有診斷則 exit code 非 0，lit 會視為失敗）。

## C++ 單元測試

### 測試 fixture

MLIR 的單元測試用 gtest，並提供一個 `MLIRContext` fixture：

```cpp
// unittests/Dialect/NPU/NPUOpsTest.cpp
#include "mlir/Dialect/NPU/NPUOps.h"
#include "mlir/Dialect/NPU/NPUDialect.h"
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinOps.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/IR/MLIRContext.h"
#include "mlir/IR/Verifier.h"
#include "mlir/Parser/Parser.h"
#include "mlir/Support/LogicalResult.h"
#include "gtest/gtest.h"

using namespace mlir;
using namespace mlir::npu;

namespace {

/// 提供一個帶有 npu 方言的 MLIRContext。
class NPUTest : public ::testing::Test {
protected:
  void SetUp() override {
    context.getOrLoadDialect<NPUDialect>();
    context.allowUnregisteredDialects();
  }

  MLIRContext context;
};

} // namespace
```

### 測試 verifier

驗證 verifier 的方式是：**構造一個非法的 op，確認 `verify()` 回傳失敗**。

```cpp
TEST_F(NPUTest, MatMulRejectsKMismatch) {
  OpBuilder builder(&context);
  Location loc = builder.getUnknownLoc();

  auto f32Type = builder.getF32Type();
  auto lhsType = RankedTensorType::get({128, 256}, f32Type);
  auto rhsType = RankedTensorType::get({128, 64}, f32Type);
  auto outType = RankedTensorType::get({128, 64}, f32Type);

  auto lhs = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(lhsType, 0.0f));
  auto rhs = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(rhsType, 0.0f));
  auto out = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(outType, 0.0f));

  auto matmul = builder.create<MatMulOp>(loc, lhsType, lhs, rhs, out);
  (void)matmul;

  EXPECT_TRUE(verify(*context.getOperation()));
}
```

注意：DSL 裡 `builder.create<MatMulOp>(loc, lhsType, lhs, rhs, out)` 會用到 ODS 產生的 `build(OpBuilder&, OperationState&, Type, Value, Value, Value)` overload。

但上面這個測試有個問題：`MatMulOp::verify()` 會因為缺少量化 encoding 而先失敗（我們的 verifier 第 5 步先檢查量化），所以錯誤訊息不是 K mismatch。**測試要檢查的是「特定的錯誤」**。

更好的做法是直接呼叫 op 的 `verify()`，並檢查診斷訊息：

```cpp
TEST_F(NPUTest, MatMulVerifiesShapes) {
  OpBuilder builder(&context);
  Location loc = builder.getUnknownLoc();

  auto f16Type = builder.getF16Type();
  auto lhsType = RankedTensorType::get({128, 256}, f16Type);
  auto rhsType = RankedTensorType::get({128, 64}, f16Type);
  auto outType = RankedTensorType::get({128, 64}, f16Type);

  Value lhs = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(lhsType, 0.0f));
  Value rhs = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(rhsType, 0.0f));
  Value out = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(outType, 0.0f));

  MatMulOp matmul = builder.create<MatMulOp>(loc, lhsType, lhs, rhs, out);

  // 直接呼叫 verifier
  LogicalResult result = matmul.verify();
  EXPECT_TRUE(failed(result));
}
```

更精確的做法是**捕捉診斷訊息**並斷言其內容：

```cpp
TEST_F(NPUTest, MatMulRejectsKMismatchWithMessage) {
  OpBuilder builder(&context);
  Location loc = builder.getUnknownLoc();
  auto f16Type = builder.getF16Type();
  auto lhsType = RankedTensorType::get({128, 256}, f16Type);
  auto rhsType = RankedTensorType::get({128, 64}, f16Type);
  auto outType = RankedTensorType::get({128, 64}, f16Type);

  Value lhs = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(lhsType, 0.0f));
  Value rhs = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(rhsType, 0.0f));
  Value out = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(outType, 0.0f));

  MatMulOp matmul = builder.create<MatMulOp>(loc, lhsType, lhs, rhs, out);

  std::string message;
  {
    // 接管診斷輸出
    raw_string_ostream os(message);
    ScopedDiagnosticHandler handler(context, [&](Diagnostic &diag) {
      os << diag.str();
      return success();
    });
    EXPECT_TRUE(failed(matmul.verify()));
  }
  EXPECT_TRUE(message.find("K dimension") != std::string::npos);
}
```

`ScopedDiagnosticHandler` 是捕獲診斷的標準工具。

### 測試 pass 的轉換結果

單元測試也能測 pass。要測 `npu-expand-matmul`，需要：

1. 建一個 module（放一個 `func.func` 與 `npu.matmul`）。
2. 執行 pass。
3. 檢查結果。

```cpp
TEST_F(NPUTest, ExpandMatMulProducesLinalg) {
  OpBuilder builder(&context);
  Location loc = builder.getUnknownLoc();

  auto f16Type = builder.getF16Type();
  auto lhsType = RankedTensorType::get({128, 256}, f16Type);
  auto rhsType = RankedTensorType::get({256, 64}, f16Type);
  auto outType = RankedTensorType::get({128, 64}, f16Type);

  Value lhs = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(lhsType, 0.0f));
  Value rhs = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(rhsType, 0.0f));
  Value out = builder.create<arith::ConstantOp>(loc, DenseElementsAttr::get(outType, 0.0f));

  auto funcType = builder.getFunctionType({lhsType, rhsType, outType}, {outType});
  auto func = builder.create<func::FuncOp>(loc, "simple", funcType);
  Block *body = func.addEntryBlock();
  builder.setInsertionPointToStart(body);

  builder.create<MatMulOp>(loc, outType, lhs, rhs, out);
  builder.create<func::ReturnOp>(loc, outType, out);

  // 執行 pass
  PassManager pm(&context);
  pm.addNestedPass<func::FuncOp>(createNPUExpandMatMulPass());
  EXPECT_TRUE(succeeded(pm.run(*context.getOperation())));

  // 檢查結果
  bool foundLinalg = false;
  func.walk([&](linalg::MatmulOp op) { foundLinalg = true; });
  EXPECT_TRUE(foundLinalg);
}
```

**關鍵技巧**：`func.walk([&](SomeOp op) { ... })` 是最方便的「IR 中是否有某種 op」的檢查方式。

### 從字串解析的輔助函式

有時單元測試從 MLIR 文字開始更方便：

```cpp
/// 解析一段 MLIR 文字並交給 pass。
static std::unique_ptr<ModuleOp> parseAndRun(
    MLIRContext &context, StringRef input, 
    std::function<void(PassManager &)> setupPasses) {
  auto module = parseSourceString<ModuleOp>(input, &context);
  EXPECT_TRUE(module != nullptr);
  if (!module)
    return nullptr;

  PassManager pm(&context);
  setupPasses(pm);
  EXPECT_TRUE(succeeded(pm.run(*module)));
  return module;
}
```

用法：

```cpp
TEST_F(NPUTest, ExpandMatMulFromText) {
  auto module = parseAndRun(context, R"(
    func.func @f(%a: tensor<128x256xf16>, %b: tensor<256x64xf16>,
                 %c: tensor<128x64xf16>) {
      %0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>,
                                                tensor<256x64xf16>,
                                                tensor<128x64xf16>
      return
    }
  )", [](PassManager &pm) {
    pm.addNestedPass<func::FuncOp>(createNPUExpandMatMulPass());
  });

  ASSERT_TRUE(module != nullptr);
  bool found = false;
  module->walk([&](linalg::MatmulOp) { found = true; });
  EXPECT_TRUE(found);
}
```

### 測試 `applyPatternsAndFoldGreedily`

[5.1](05.1-GreedyPatternRewriteDriver.md) 提到的 greedy driver 本身也可以測：

```cpp
TEST_F(NPUTest, GreedyFoldQuantizeConstant) {
  OpBuilder builder(&context);
  Location loc = builder.getUnknownLoc();

  auto f32Type = builder.getF32Type();
  auto inType = RankedTensorType::get({4}, f32Type);
  auto outType = RankedTensorType::get({4}, builder.getI8Type());

  Value input = builder.create<arith::ConstantOp>(
      loc, DenseElementsAttr::get(inType, {1.0f, 2.0f, 3.0f, 4.0f}));

  RewritePatternSet patterns(&context);
  QuantizeOp::getCanonicalizationPatterns(patterns, &context);

  auto func = builder.create<func::FuncOp>(loc, "f",
      builder.getFunctionType({inType}, {outType}));
  Block *body = func.addEntryBlock();
  builder.setInsertionPointToStart(body);
  builder.create<QuantizeOp>(loc, outType, input);
  builder.create<func::ReturnOp>(loc);

  EXPECT_TRUE(succeeded(applyPatternsAndFoldGreedily(func.getOperation(),
                                                     std::move(patterns))));

  // 折疊後應該只剩下一個 arith.constant
  unsigned constantCount = 0;
  func.walk([&](arith::ConstantOp) { ++constantCount; });
  EXPECT_EQ(constantCount, 1u);
}
```

## 測試矩陣：該測什麼

一個方言的測試應該覆蓋以下維度：

| 維度 | 測試內容 | 工具 |
| --- | --- | --- |
| **解析/印出往返** | 每個 op 都能 parse 回等價的 IR | 整合測試 + `--mlir-print-op-generic` |
| **verifier** | 每個不變式都有一個非法案例 | `--verify-diagnostics` |
| **build 方法** | 產生的 result 型別正確 | gtest |
| **fold** | 常數輸入被折疊 | gtest + 整合測試 |
| **canonicalization** | pattern 生效且結果正確 | gtest |
| **pass** | 轉換後的 IR 符合預期 | 整合測試（FileCheck） |
| **互動** | 與其他方言一起用不衝突 | 整合測試 |

### 往返測試

一個非常划算的測試是「parse → print → parse」：

```mlir
// RUN: mlir-opt %s | mlir-opt | FileCheck %s
```

這測的是「印出的語法能被重新解析」——這是方言最容易出錯的地方（尤其是自訂 format 與可選屬性）。

更強的版本：

```mlir
// RUN: mlir-opt %s | mlir-opt | mlir-opt | FileCheck %s
```

連續三次，確保輸出是**不動點**（idempotent）。

### 通用形式測試

```mlir
// RUN: mlir-opt %s --mlir-print-op-generic | FileCheck %s --check-prefix=GENERIC
// RUN: mlir-opt %s | FileCheck %s

// GENERIC: "npu.matmul"(%arg0, %arg1, %arg2) : (tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>) -> tensor<128x64xf16>
```

`--mlir-print-op-generic` 印出的是**通用格式**（op 名稱 + operand/result 型別 + 屬性字典），完全繞過自訂 printer。這是檢查「自訂 format 與通用 format 是否一致」的最佳工具。

## CI 整合

### 標準的 CI 檢查

LLVM 專案的 CI 通常執行：

```bash
ninja check-mlir          # 所有 MLIR 測試
ninja check-mlir-headers  # 標頭檔獨立性檢查
```

`check-mlir-headers` 很重要：它驗證每個標頭檔可以**單獨被包含**。若你的 `NPUOps.h` 意外依賴了某個沒有 include 的標頭檔，只有這個檢查會抓到。

### 自訂 CI 步驟

若方言有自己的 lint 規則，可以加一個獨立的 target：

```cmake
add_custom_target(check-npu
  COMMAND ${LLVM_TOOLS_BINARY_DIR}/llvm-lit -v ${CMAKE_CURRENT_SOURCE_DIR}/../test/Dialect/NPU
  DEPENDS MLIRNPUOps
  USES_TERMINAL
)
```

### 在 Pull Request 中檢查變更

CI 通常會用 `git diff` 找出新增的測試檔，優先執行它們（加速回饋迴圈）。這是 lit 的 `--filter` 或自訂腳本可以做的事。

### 覆蓋率

若要追蹤方言的覆蓋率，LLVM 提供 `llvm-cov`：

```bash
ninja check-mlir
llvm-cov report ./bin/llvm-lit -instr-profile=default.profdata
```

對方言而言，覆蓋率的重點不是「每個 op 都被執行」，而是「**每個 verifier 分支都被觸發**」。可以透過刻意構造的非法案例達成。

## 檢查清單

在把一個方言貢獻回上游（或在專案中使用）之前，可以用這張清單自查：

- [ ] 每個 op 至少有一個整合測試，覆蓋 parse → print 往返。
- [ ] 每個 verifier 檢查至少有一個 `expected-error` 案例。
- [ ] 每個 `build` overload 都有對應的 gtest。
- [ ] 每個 fold / canonicalization pattern 都有測試（包含「不該觸發」的反例）。
- [ ] 每個 pass 都有 FileCheck 測試，且用 `CHECK-LABEL` 切分。
- [ ] 有 `--mlir-print-op-generic` 的對照測試。
- [ ] 有 `--verify-each` 的健全性檢查（確保 pass 不產生非法 IR）。
- [ ] 連續三次 `mlir-opt` 的輸出是不動點。
- [ ] `check-mlir-headers` 通過。

## 小結與延伸閱讀

* MLIR 的測試分兩層：`lit` + `FileCheck` 的整合測試驗證「工具行為」，gtest 驗證「類別行為」；兩者互補，方言的常態是兩者都寫。
* FileCheck 的核心是變數：`[[NAME:regex]]` 定義、`[[NAME]]` 引用，讓測試能檢查資料流關係而非只是文字存在；`CHECK-LABEL` 是切分區塊、防止測試弱化的關鍵。
* 驗證 verifier 的兩種方式：`--verify-diagnostics` + `expected-error`（位置精確、可混合案例，但會釘住訊息文字）與 `not mlir-opt ...`（簡單，適合檢查失敗行為）。
* 單元測試的關鍵技巧是 `ScopedDiagnosticHandler` 捕獲診斷、`func.walk` 檢查 IR 結構、以及從 MLIR 文字解析的輔助函式。
* 覆蓋率的真正目標不是「每個 op 都被執行」，而是「每個 verifier 分支與每個 pattern 的正反案例都被觸發」。
