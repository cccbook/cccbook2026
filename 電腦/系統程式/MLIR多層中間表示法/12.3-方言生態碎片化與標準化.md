# 12.3 方言生態的碎片化與標準化

[12.1](12.1-MLIR在HLS與HDL降階的角色.md) 展示了硬體領域如何長出一整套方言（`firrtl`、`sv`、`comb`、`seq`、`hw`、`llhd`），[12.2](12.2-管線化與資料流排程的IR表達.md) 則在方言內部討論了排程的表達。這兩節合起來給出一個印象：只要需要新的抽象，就該開一個新方言。

但現實並不如此簡單。當你把視角拉遠到整個生態，會看到另一個問題：

> 不同的專案各自創造了相似的方言，彼此無法互通。MLIR 該如何在「鼓勵多元」與「避免碎片化」之間取得平衡？

本節要處理的是 MLIR 社群治理層面的問題：方言的准入標準、命名規範、版本相容性，以及一份「何時貢獻上游、何時留在自家」的決策準則。

## 方言治理：upstream 的准入標準

上游 LLVM 專案對新方言的態度是明確的：**不是所有方言都該進入上游**。上游採納一個方言，等於承諾長期的維護成本、相容性承諾與文件責任。

### 典型的准入條件

綜合 LLVM 專案的實務（可參考 `mlir/docs/Dialects.md` 與相關的設計文件），一個方言要進入上游，通常需要滿足以下條件：

**條件一：通用性。** 這個方言要解決的問題不能是某一個專案的特例。判斷標準通常是：至少有多個獨立的專案需要它，或者它是某個廣為人知的硬體或框架標準。

**條件二：完整的實作。** 僅有一份 ODS 宣告是不夠的。方言需要能夠被載入、能夠被驗證、能夠被列印往返（round-trip），並且需要一個能證明它可用的端到端轉換路徑。

**條件三：維護者承諾。** 上游方言需要至少一位持續維護者，且必須在 LLVM 的 mailing list 上活躍。

**條件四：文件。** 方言需要一份說明其語意、型別系統、與其他方言的關係的文件。

**條件五：與既有方言的邊界清晰。** 新的方言不能與既有方言的職責重疊。若有重疊，需要說明為何不能擴充既有的方言。

**條件六：位元組碼相容性考量。** 若方言要進入 bytecode serialization，需要保證序列化格式的穩定性，這提高了後續變更的成本。

### 語法名稱空間的保留

LLVM 專案維護一份「保留的方言前綴」清單，避免不同專案在同一個名稱空間下互相衝突。社群方言（例如 `stablehlo`、`iree`）通常把自己的名稱空間放在主線之外，這樣即使同名也不會與上游衝突，但也意味著它們**不是上游方言**，它們的 API 沒有上游的穩定性承諾。

## 社群方言的現狀

MLIR 之外存在著一個龐大的方言生態。讓我們盤點主要的幾個，以及它們各自的存在理由。

| 方言或專案 | 領域 | 定位 | 為何不在上游 |
| --- | --- | --- | --- |
| `stablehlo` | 高階張量運算 | 跨框架的中介表示 | 來自 TensorFlow 的 MHLO 血統，介面仍在演進 |
| IREE | 端到端編譯與執行 | 從模型到裝置的完整流水線 | 是產品而非單一 IR，需要自己的執行時與 ABI |
| CIRCT | 硬體 | 硬體描述與 HLS 基礎設施 | 2021 年起在 LLVM 內發展，屬於特殊狀況 |
| Torch-MLIR | 框架前端 | PyTorch 到 MLIR | 前端耦合較深，介面隨 PyTorch 演進 |

| `tosa` | 張量運算子集 | 硬體友善的運算子子集 | 已在上游，但歷史上曾與 TFLite 專案有重疊 |

### 為什麼社群方言會存在

**原因一：上游的准入成本高於自建的收益。** 如果一個方言只服務單一專案，申請上游要花的時間（RFC、審查、文件、持續回應 review）可能超過收益。

**原因二：演進速度。** 專案需要快速試探新的抽象；上游的審查流程會拖慢這個過程，雖然這種緩衝在長期看是有益的。

**原因三：生態綁定。** 一個方言往往與它的執行時、ABI、編譯選項深度綁定，把它變成上游方言意味著要處理這些綁定的通用化問題。

### StableHLO 的角色

`stablehlo` 值得單獨說明，因為它是「可攜高階 IR」這個概念的具體化身。它的目標是：**提供一個穩定的、跨框架的、硬體無關的高階張量運算介面**。

當一個模型從 PyTorch 匯出時，可以先轉成 StableHLO，然後由任何支援 StableHLO 的編譯器（IREE、XLA、某些硬體廠商的工具鏈）消費。這個設計解決的是一個真實的痛點：**模型框架的碎片化**。每個框架都有自己的圖 IR（TorchScript、TF GraphDef、ONNX、JAX 等），轉換時總是有資訊損失。StableHLO 的角色是「所有轉換的匯合點」。

值得強調的是它命名裡的 "Stable" 與 "HLO"（High Level Operation）：它刻意選擇了一個**保守的運算子集合**，只包含那些幾乎所有後端都能高效實作的運算，而不是追求完整表達能力。這個取捨是刻意的：中介表示的價值在於它的**交集性質**，不在於它的表達能力。

## 重複方言的問題

### 一個真實的案例：bufferization 的分裂

歷史上，MLIR 的 bufferization 走過一段荊棘路：早期有「bufferization」方言與 one-shot bufferize 的新路徑並存，前者是較舊的方案（以 `bufferization.to_memref` 與 `to_tensor` 為核心），後者是新的分析式方法。兩者在很長一段時間裡共存，導致使用者困惑：該用哪一個？

這個教訓是：**當同一個問題有兩套機制時，即使其中一套更好，遷移成本也會很高**。因為使用者已經建立的工作流、pass 管線、測試都依賴舊的那一套。

### `tosa` 的歷史重疊

另一個案例是 `tosa`（Tensor Operator Set Architecture）。TOSA 原本是 Arm 主導、放在獨立的 TFLite 儲存庫中的規範，同時 MLIR 上游也存在一個 `tosa` 方言。兩者在初期有重疊，後來透過上游的 `tosa` 方言吸收 TFLite 版本而收斂。

### 教訓

* **教訓一：重複的代價不是重複本身，而是遷移成本。** 兩套機制並存期間，所有使用者都要做選擇，所有文件都要解釋兩者差異。
* **教訓二：領域方言的邊界必須清楚。** 「描述運算子集合」與「描述完整資料流圖」是兩件事，混在一起就會重疊。
* **教訓三：拆分與合併都要有遷移路徑。** 引入新機制時，舊機制要標記為 deprecated，提供轉換路徑，並在文件裡明確說明時程。

## 命名與命名空間的規範

### 前綴約定

實務上的慣例是：**自訂方言使用一個組織或專案專屬的前綴**。

```mlir
// 良好範例：前綴清楚表明來源
mycompiler.nn.conv2d
mycompiler.pe.mma
mycompiler.dma.copy
```

```mlir
// 不良範例：佔用通用名稱，容易與上游或其他專案衝突
conv2d
mma
dma
```

理由很直接：MLIR 的 op 名稱在全域範圍內唯一（前綴是方言名的一部分）。若一個方言用了 `conv2d` 而沒有前綴，另一個專案也想用同樣的名字，就產生了不可解決的衝突。

### 命名空間的層次劃分

除了前綴，命名空間的**內部結構**也應該反映抽象層次。回到 [11.1](11.1-脈動陣列與NPU的IR需求.md) 的建議：一個方言內部用子命名空間劃分領域層與硬體層。

```mlir
mycompiler.nn.*    // 領域層: 硬體無關的演算法操作
mycompiler.pe.*    // 硬體層: 綁定到特定硬體
mycompiler.dma.*   // 硬體層: 資料搬移
```

這樣的劃分讓「跨硬體重用的部分」可以被辨認出來，也讓「需要換硬體就換的部分」有明確界線。

### 命名風格的細則

其他值得遵循的慣例：

* op 名稱用小寫加底線（snake_case），例如 `mycompiler.pe.mma`。
* op 名稱反映「做了什麼」而非「是什麼資料」，例如 `mycompiler.dma.copy` 而非 `mycompiler.dma.tensor`。
* 型別名稱反映「值的種類」，例如 `!mycompiler.sram<65536>`。
* 避免用硬體行話，除非該行話是跨廠商通用的（例如 `mma` 在多家加速器中通用）。

## 版本相容性

### 為什麼版本重要

方言會演進。演進的方式包括：新增 op、新增屬性、改變既有 op 的語意、改變型別的參數布局。每一種變化都可能破壞下游工具鏈。

MLIR 對此的機制是 `dialect.version` 屬性。方言可以宣告自己的版本，序列化系統會把它記錄下來，使得舊的 bytecode 在新的編譯器上載入時能被辨識為不相容，而不是產生難以除錯的錯誤。

### 版本策略的實務

一個可操作的版本策略：

| 變化類型 | 版本影響 | 遷移方式 |
| --- | --- | --- |
| 新增 op | 需 bump 版本 | 下游需支援新 op |
| 新增可選屬性 | 通常不 bump | 提供預設語意 |
| 改變既有 op 語意 | 必須 bump | 需要明確的遷移 pass |
| 移除 op | 必須 bump | 保留 deprecated 版本數期 |
| 改變型別參數 | 必須 bump | 需要轉換 pass |

實務上的建議是：**對 op 集合的變動使用 major 版本，對純擴充使用 minor 版本**，並在方言文件中記錄變更歷史。

### 與上游方言的相容性

上游方言（如 `linalg`、`scf`）有版本相容性的承諾：上游不會在同一個 major 版本內移除 op 或改變語意。這是採用上游方言的主要好處之一——**你不需要維護自己的相容性承諾**。

對照之下，社群方言的相容性由社群自己決定：IREE 與 StableHLO 都提供版本化的承諾，但它們不是 LLVM 專案的承諾。

## API 穩定性與 deprecated 機制

### MLIR 的 API 演進

MLIR 的 C++ API 也會演進。LLVM 專案對 C++ API 的承諾弱於對 MLIR 語意的承諾：

* **方言與 op 的語意**：相對穩定，變動會經過 deprecation 週期。
* **C++ API**：變動更自由，但仍在實務上遵循 deprecation 週期（例如 `mlir::OpBuilder` 的部分方法、operation 取用位置的介面等）。

常見的 deprecation 機制是：舊的 API 標記為 `[[deprecated]]`，保留一個版本的過渡期，並在遷移指南中說明替代方案。

### 在方言層的應用

方言作者應該在自己的方言中實踐同樣的紀律：

```cpp
// 舊的 op 保留，但標記 deprecated
def Mychip_OldMMAOp : Mychip_PE_Op<"mma_old", [Deprecated]> {
  let summary = "已棄用的 MMA 操作，請改用 mychip.pe.mma";
  let deprecationMessage = "請改用 mychip.pe.mma，其屬性介面更精確";
}
```

ODS 的 `Deprecated` trait 會讓工具鏈在使用該 op 時發出警告。

### 一個務實的相容性策略

對於自訂方言，一個實用的做法是：

1. **方言層面提供轉換 pass**，把舊形式轉成新形式（例如 `mycompiler-legacy-to-modern`）。
2. **在 pass 管線開頭自動執行**遷移，讓使用者不需要手動處理。
3. **在版本說明中明確列出遷移路徑**。

這正是 MLIR 在方言合併歷史上的做法，值得直接借用。

## 平衡：靈活性與整合成本

### 碎片化的成本模型

可以用一個簡單的模型來評估「自己造一個方言」的總成本：

$$
C_{total} = C_{design} + C_{impl} + C_{docs} + C_{migrate} + C_{interop}
$$

* $C_{design}$ ：設計語意與 ODS 宣告。
* $C_{impl}$ ：verifier、builder、轉換 pattern 的實作。
* $C_{docs}$ ：文件與範例。
* $C_{migrate}$ ：**與其他專案的方言對接**（最容易被低估的一項）。
* $C_{interop}$ ：長期的維護與相容性承諾。

如果一個方言最終要與其他專案的方言互操作， $C_{migrate}$ 會急遽上升。這正是「重複方言」問題的經濟學解釋。

### 判斷準則

一個較為可靠的判斷準則是「**這個抽象是否描述了演算法本身**」：

* 若抽象描述的是**領域演算法**（例如張量運算、迴圈 nest、記憶體存取），它很可能有跨專案的需求，適合上游或至少需要社群共用的中介表示。
* 若抽象描述的是**特定硬體的機制**（例如某個加速器的 DMA 描述符格式、某個 ASIC 的陣列配置），它很可能是自家專屬的，上游並不合適。

StableHLO 屬於前者，`mycompiler.pe.mma` 屬於後者。

### 一個務實的架構建議

很多專案會採用「**兩層方言**」策略來同時獲得兩者好處：

1. **可攜層**：用上游方言（`linalg`、`tosa`、`scf`）或社群中介表示（`stablehlo`）描述演算法。
2. **專屬層**：用自家方言描述硬體機制，並提供從可攜層到專屬層的轉換。

好處是：可攜層的部分可以在專案之間共享，甚至貢獻回上游；專屬層則保留了針對硬體最佳化的自由度。這正是 [11.1](11.1-脈動陣列與NPU的IR需求.md) 建議的領域層與硬體層分離。

## 實務建議：何時貢獻上游，何時留在自家

讓我們把上面的討論整理成一張決策表。

| 情境 | 建議 | 理由 |
| --- | --- | --- |
| 抽象描述通用演算法，且已有兩個以上獨立使用者 | 申請上游 | 通用性條件成立，共享成本低於重複成本 |
| 抽象描述特定硬體機制 | 留在自家 | 上游的通用性條件不成立 |
| 只是想避免重複既有上游方言 | 先擴充既有方言 | 優先重用既有抽象 |
| 需要快速實驗新抽象 | 留在自家，但設計成可遷移 | 保留未來上游的可能 |
| 已經是社群共用的中介表示 | 維護社群版本，提供雙向轉換 | 避免重複造輪子 |
| 需要長期穩定承諾但無社群支持 | 留在自家並自訂版本策略 | 上游的承諾你承擔不起 |

### 提交上游前的檢查清單

* [ ] 這個抽象描述的是演算法還是硬體？若是硬體，是否真的沒有更一般的抽象？
* [ ] 是否已搜尋過上游與主要社群方言，確認沒有等價物？
* [ ] 是否有端到端的轉換路徑，能證明方言的實用性？
* [ ] 是否有維護者承諾，以及至少一位 reviewer 願意長期參與？
* [ ] 是否有方言文件，說明語意與邊界？
* [ ] op 集合是否已足夠穩定，未來一年不需要大改？
* [ ] 命名是否使用了專屬前綴，且不會與保留前綴衝突？

### 對本書讀者的具體建議

如果你正在設計一個自訂方言，建議的順序是：

1. **先確定它在整體架構中的位置**：它是可攜層還是硬體層？這與 [10.1](10.1-自訂方言的抽象層級設計.md) 的抽象層級設計直接相關。
2. **先在專案內用「假想的上游方言」形式把它寫出來**（用 ODS、寫 verifier、寫轉換），這一步能暴露很多設計問題。
3. **在寫完轉換 pass 之後，再評估是否申請上游**。此時你有了可展示的證據，也更清楚它的邊界。
4. **若決定留在自家，把「相容性承諾」寫進文件**。使用者需要知道哪些東西會變、變的時程是什麼。

## 上游方言一覽

把 MLIR 上游的主要方言依領域整理，可以看出「什麼樣的抽象被社群認為值得共享」。

| 領域 | 上游方言 | 說明 |
| --- | --- | --- |
| 核心控制流 | `func`、`cf`、`scf`、`affine` | 函式、分支、結構化迴圈、多面體模型 |
| 算術 | `arith`、`math`、`complex` | 整數與浮點運算、數學函式 |
| 記憶體 | `memref`、`bufferization` | 緩衝區視圖與 bufferization 介面 |
| 張量 | `tensor`、`linalg`、`sparse_tensor` | 值語意張量、結構化運算、稀疏 |
| 硬體加速 | `gpu`、`rocdl`、`xegpu`、`nvvm`、`amd_gpu`、`arm_neon`、`arm_sve` | 各家加速器 |
| 跨平台 | `spirv`、`llvm`、`tosa` | SPIR-V、LLVM 橋接、硬體友善運算子集 |
| 分散式 | `mlprogram` | 分散式訓練的程式抽象 |
| 工具鏈 | `transform`、`pdl`、`ub` | 排程語言、可程式化 dialect 定義、無法消除的 UB |

這張表也說明了另一件事：**上游方言的數量是有節制的**。MLIR 沒有為每一種加速器、每一種框架、每一種演算法風格都建立上游方言。這不是保守，而是因為每一個上游方言都是一份長期的維護與相容性承諾，而方言之間的組合爆炸會讓承諾難以維持。

因此，當你在設計一個新的自訂方言時，值得先問的問題不是「我怎麼把它寫得更好」，而是「**它有沒有可能成為上游方言**」。這個問題的答案，會影響你從一開始的抽象粒度選擇：能成為上游的抽象，必須是別人也用得上的。

從這張表可以歸納出一條線索：**上游方言的共同點是「抽象的是演算法或硬體架構的通則」，而不是某個產品的細節**。`tosa` 之所以在上游，是因為它的運算子集合是多家硬體都能實作的交集；`gpu` 之所以在上游，是因為 GPU 程式模型是業界共通的。

## 一份方言文件的建議模板

方言文件是「抽象被共享」的前提。一份實用的方言文件應該包含以下幾節：

1. **動機與範圍**：這個方言解決什麼問題，**明確不解決**什麼問題。第二點往往更重要，因為它劃定了與其他方言的邊界。
2. **與既有方言的關係**：哪些既有方言可以轉換到本方言，反向又是什麼情況。
3. **型別系統**：型別的定義，以及型別之間的轉換規則。
4. **op 語意**：每個 op 的語意、副作用、驗證規則。
5. **轉換路徑**：本方言如何被降到通用方言，以及從哪裡降級進來。
6. **版本與相容性承諾**：哪些保證穩定、哪些可能變動。
7. **範例**：從輸入到輸出的完整轉換範例。

第 1 節的「不解決什麼」是最容易被省略、也最值得寫的部分。少了它，使用者會把方言當成萬用抽象來用，然後在某個轉換點發現它表達不了自己的需求。

## 常見的失敗模式

在實務中，方言生態的問題通常以以下幾種形式出現。認出它們是防止踩坑的第一步。

**失敗模式一：過度抽象的方言。** 把硬體細節全部藏起來，結果沒有任何硬體能高效實作它。症狀是轉換到硬體層時需要大量「反抽象」的展開工作。

**失敗模式二：過度具體的方言。** 把某個產品的配置寫進 op 的屬性，導致方言無法被重複使用。症狀是每接一個新產品就要複製一份方言。

**失敗模式三：缺少轉換路徑的方言。** 方言本身設計得不錯，但沒有提供從通用方言轉入的轉換，因此永遠沒有人用。症狀是方言文件很完整，但沒有任何 pipeline 引用它。

**失敗模式四：重複的轉換路徑。** 兩個專案各自實作從 `linalg` 到自家方言的轉換，兩者行為不一致。症狀是使用者要在兩條路徑間來回比對。

**失敗模式五：缺少維護者。** 方言進入上游後無人維護，最後淪為「文件存在但不能用」的狀態。症狀是 issue 累積無人回應。

這五種失敗模式裡，前兩種是設計問題，第三、四種是生態問題，第五種是組織問題。設計問題可以在第一時間避免；生態問題需要社群協作；組織問題則是上游准入機制存在的根本理由。

## 與其他專案協作的三種模式

當你的方言需要與別人的方言互動時，有三種可行的模式：

**模式一：直接對接。** 你的方言提供從對方方言到你的方言的轉換，或反向。優點是路徑最短，缺點是產生了方言之間的耦合。

**模式二：透過中介表示。** 雙方都與一個共同的中介表示（例如 `stablehlo` 或 `linalg`）互動，彼此不直接依賴。這是長期最穩健的模式，代價是多一次轉換。

**模式三：共用可攜層，專屬層各自為政。** 雙方共享高階的演算法描述，但各自的硬體層互不認識，轉換發生在可攜層。這正是 [11.1](11.1-脈動陣列與NPU的IR需求.md) 建議的領域層與硬體層分離在生態層面的延伸。

選擇模式二的判斷依據是：**雙方是否會長期共存**。若是，共用中介表示的初期成本會在後續攤平；若是短期專案，直接對接更快。

## 方言成熟度檢查表

把本節的內容收斂成一張可以逐項檢查的清單，適用於評估「這個方言是否已經可以交付給別人使用」。

| 面向 | 檢查項目 | 達標的表現 |
| --- | --- | --- |
| 定位 | 文件明確說明解決什麼與不解決什麼 | 使用者不會誤用它 |
| 命名 | 使用專屬前綴，內部以子命名空間反映抽象層次 | 不與其他專案衝突 |
| 型別 | 型別有 verifier，參數布局有文件 | 錯誤在早期被擋下 |
| op | 每個 op 有語意說明、副作用宣告與驗證規則 | 可安全地做分析與重寫 |
| 轉換 | 有從通用方言轉入的路徑，且有端到端範例 | 有人真的用得起來 |
| 降階 | 有降到通用方言的路徑 | 可被其他後端消費 |
| 版本 | 有版本策略與變更紀錄 | 下游知道什麼會變 |
| 相容性 | 舊形式有 deprecated 週期與轉換 pass | 演進不破壞既有使用者 |
| 文件 | 有方言文件與範例 | 讓新貢獻者能起步 |
| 組織 | 有維護者與回應流程 | 不會變成無人維護的孤兒 |

最後值得提醒的是：方言治理的目的不是限制創新，而是**把創新的成本外部化給真正需要共用的人**。一個只有你需要的抽象，留在你自己的倉庫裡，成本最低；一個很多人需要的抽象，把它标准化，成本則由整個社群分攤。判斷自己屬於哪一邊，是本節最核心的技能。

把標準化想成一個**分攤成本的選擇**，而不是一道風格審查。

## 小結與延伸閱讀

* MLIR 的「方言自治」帶來快速成長，也帶來碎片化；上游以通用性、完整性、維護者承諾、文件與邊界清晰作為准入條件。
* 社群方言（`stablehlo`、IREE、Torch-MLIR、CIRCT）存在的三個結構性原因：上游准入成本高、演進速度需求、以及與執行時的生態綁定。
* `stablehlo` 展示了可攜中介表示的價值：它靠的是**保守的運算子交集**而不是表達能力，因為中介表示的價值在於交集。
* 重複方言的真正成本在遷移；教訓是新舊機制並存期間要提供明確的轉換路徑與 deprecation 週期。
* 命名規範（前綴加上子命名空間反映抽象層次）與版本策略（`dialect.version`、major 與 minor 區分）是方言成熟度的指標。
* 判斷「自己造方言」的準則：描述**演算法**的抽象傾向共享，描述**硬體機制**的抽象適合留在自家；「可攜層加專屬層」的兩層架構是務實的折衷。
* 協作模式有直接對接、透過中介表示、共用可攜層三種；長期共存的專案應選中介表示，因為初期成本會在後續攤平。
* 常見的失敗模式有五種：過度抽象、過度具體、缺少轉換路徑、重複的轉換路徑、缺少維護者；前兩者是設計問題，可在一開始避免。
* 方言成熟度可用一張檢查表逐項確認：定位、命名、型別、op、轉換、降階、版本、相容性、文件、組織。
* 延伸閱讀：MLIR 上游文件 `mlir/docs/Dialects.md`（方言設計與准入原則）與 `mlir/docs/GettingStarted.md`；LLVM 專案 `docs/` 中的方言 RFC 與設計文件；StableHLO 專案的文件（其儲存庫中的 `docs/` 目錄）；IREE 專案的設計文件；CIRCT 文件 `circt/docs/WhyCIRCT.md`。
