# 10.3 自訂 Verifier 與 Pass 的實作

[10.2](10.2-TableGen規格與C++實作.md) 把 `npu` 方言的形狀刻到了程式碼裡，但形狀不等於語意。本節補上兩塊：**verifier**（保證 IR 合法）與 **pass**（讓 IR 變得更好）。

這兩件事是方言的「行為主體」，也是一個方言能否被 ecosystem 接受的關鍵。理由很簡單：一個會產生非法 IR、或者沒有任何 pass 的方言，等於只是把錯誤推給使用者。

## 為什麼需要 Verifier

### IR 的不變式在哪裡保證

MLIR 的 IR 合法性与否，是在**每次 operation 被建立或被修改之後**檢查的。這個檢查由 `Operation::verify()` 觸發，而它會依序呼叫：

1. **Operation 的結構性驗證**：由 `mlir::OpState::verifyInvariants` 系列完成，包含 ODS 宣告的型別約束（`AnyTypeOf`、`SameOperandsAndResultType` 等）。
2. **Dialect 的 `verifyOperationAttribute`**（若宣告 `hasOperationAttrVerify`）。
3. **Op 自己的 `verify()`**（若宣告 `hasVerifier`）。

第 1 層是**宣告式**的，由 ODS 自動生成；第 3 層是**程序式**的，要我們手寫。ODS 無法表達的約束（形狀之間的關係、數值範圍、硬體限制）都在第 3 層。

### 什麼樣的約束該放進 verifier

判準是：

> **這個約束是「型別系統表達不了的必要條件」，還是「實務上的建議」？**

* **必要條件** → 放進 verifier。例如矩陣乘法的 $K$ 維必須相等。若不相等，程式碼在硬體上**沒有任何意義**。
* **建議** → 不要放進 verifier，而用 canonicalization 修正，或用診斷警告。例如 tile 大小建議是 16 的倍數，但執行期 fallback 到較慢路徑也許還能工作。

這個區分很重要：**verifier 太嚴格會擋掉合法程式，太鬆則會讓錯誤在後端才爆炸**（那時的錯誤訊息會非常難懂）。

### 診斷訊息的品質

一個好的 verifier 診斷要回答三個問題：

1. **哪裡錯了？**（哪個 op、哪個 operand）
2. **為什麼錯？**（期望什麼、實際什麼）
3. **怎麼修？**（可行的方向）

MLIR 的 `emitOpError` 會自動加上 op 的位置與「op 名稱」前綴：

```cpp
return emitOpError("expected K dimension to match, but got ")
       << lhsK << " vs " << rhsK;
```

產生類似：

```text
error: 'npu.matmul' op expected K dimension to match, but got 256 vs 128
```

## 完整的 `MatMulOp::verify()`

我們的 `npu.matmul` 需要檢查四類東西：

```cpp
// lib/Dialect/NPU/NPUOps.cpp

LogicalResult MatMulOp::verify() {
  //===--------------------------------------------------------------------===//
  // 1. 型別檢查：operand 與 result 必須都是 ranked tensor
  //===--------------------------------------------------------------------===//
  auto lhsType = dyn_cast<RankedTensorType>(getLhs().getType());
  auto rhsType = dyn_cast<RankedTensorType>(getRhs().getType());
  auto outType = dyn_cast<RankedTensorType>(getOut().getType());
  auto resultType = dyn_cast<RankedTensorType>(getResult().getType());

  if (!lhsType || !rhsType || !outType || !resultType)
    return emitOpError("expects all operands and result to be ranked tensors");

  //===--------------------------------------------------------------------===//
  // 2. Rank 檢查：矩陣乘法要求 rank == 2
  //===--------------------------------------------------------------------===//
  if (lhsType.getRank() != 2 || rhsType.getRank() != 2 ||
      outType.getRank() != 2 || resultType.getRank() != 2)
    return emitOpError("expects rank-2 tensors, but got ")
           << lhsType.getRank() << ", " << rhsType.getRank() << ", "
           << outType.getRank() << " and " << resultType.getRank();

  //===--------------------------------------------------------------------===//
  // 3. 形狀檢查：M x K * K x N -> M x N
  //===--------------------------------------------------------------------===//
  int64_t m = lhsType.getDimSize(0);
  int64_t k = lhsType.getDimSize(1);
  int64_t rhsK = rhsType.getDimSize(0);
  int64_t n = rhsType.getDimSize(1);

  if (k != rhsK)
    return emitOpError("expects the K dimension of lhs and rhs to match, but got ")
           << k << " and " << rhsK;

  if (outType.getDimSize(0) != m || outType.getDimSize(1) != n)
    return emitOpError("expects the out tensor to have shape ")
           << m << "x" << n << ", but got "
           << outType.getDimSize(0) << "x" << outType.getDimSize(1);

  if (resultType.getDimSize(0) != m || resultType.getDimSize(1) != n)
    return emitOpError("expects the result to have shape ")
           << m << "x" << n << ", but got "
           << resultType.getDimSize(0) << "x" << resultType.getDimSize(1);

  //===--------------------------------------------------------------------===//
  // 4. 元素型別檢查：三個 operand 的元素型別必須一致
  //===--------------------------------------------------------------------===//
  if (lhsType.getElementType() != rhsType.getElementType() ||
      lhsType.getElementType() != outType.getElementType() ||
      lhsType.getElementType() != resultType.getElementType())
    return emitOpError("expects all operands and the result to have the same "
                       "element type");

  //===--------------------------------------------------------------------===//
  // 5. 屬性必須性檢查：量化參數存在且合法
  //===--------------------------------------------------------------------===//
  auto lhsQuant = getQuantParams(getLhs().getType());
  auto rhsQuant = getQuantParams(getRhs().getType());
  auto outQuant = getQuantParams(getOut().getType());

  if (!lhsQuant || !rhsQuant || !outQuant)
    return emitOpError("expects all operands to carry quantization parameters "
                       "in their encoding");

  // zero-point 必須落在元素型別的表示範圍內
  auto elemType = lhsType.getElementType();
  unsigned bitWidth = 0;
  if (auto intType = dyn_cast<IntegerType>(elemType))
    bitWidth = intType.getWidth();
  else if (elemType.isF16() || elemType.isBF16())
    bitWidth = 16;

  if (bitWidth > 0) {
    int64_t zp = lhsQuant->getZeroPoint().getInt();
    int64_t lower = -(int64_t(1) << (bitWidth - 1));
    int64_t upper = (int64_t(1) << (bitWidth - 1)) - 1;
    if (zp < lower || zp > upper)
      return emitOpError("expects zero-point of the lhs encoding to be within [")
             << lower << ", " << upper << "], but got " << zp;
  }

  //===--------------------------------------------------------------------===//
  // 6. 硬體限制：K 必須是累加器 tile 大小（16）的倍數
  //===--------------------------------------------------------------------===//
  constexpr int64_t kAccumulatorTile = 16;
  if (k % kAccumulatorTile != 0)
    return emitOpError("expects the K dimension to be a multiple of ")
           << kAccumulatorTile << ", but got " << k;

  return success();
}
```

### 關於檢查順序

**順序有意義**。若先檢查 K 倍數再檢查 K 相等，使用者會先看到一個「K 不是 16 的倍數」的訊息，而真正的原因是兩個 operand 的 K 根本不同。

原則是：**先檢查「語意上必要」的約束，再檢查「硬體策略」的約束**。

### `emitOpError` 的串流

`emitOpError` 回傳一個 `InFlightDiagnostic`，可以 `<<` 串接內容：

```cpp
return emitOpError("expects shape ") << m << "x" << n;
```

注意它**回傳的是 diagnostic 物件**，不是 `LogicalResult`。在 `LogicalResult` 的函式裡直接 `return` 是可行的，因為 `InFlightDiagnostic` 有轉換為 `LogicalResult` 的 operator（`operator LogicalResult()`），它會在物件析構時發出診斷。

## `TileOp::verify()`

第二個 verifier，展示「動態維度」與「硬體資源限制」的檢查：

```cpp
LogicalResult TileOp::verify() {
  auto inputType = dyn_cast<RankedTensorType>(getInput().getType());
  auto resultType = dyn_cast<RankedTensorType>(getResult().getType());
  if (!inputType || !resultType)
    return emitOpError("expects ranked tensors");

  if (inputType.getElementType() != resultType.getElementType())
    return emitOpError("expects the result to have the same element type as "
                       "the input");

  DenseI64ArrayAttr sizes = getTileSizes();
  if (!sizes || sizes.size() == 0)
    return emitOpError("expects at least one tile size");

  if (sizes.size() != static_cast<int64_t>(inputType.getRank()))
    return emitOpError("expects the number of tile sizes (")
           << sizes.size() << ") to match the rank of the input ("
           << inputType.getRank() << ")";

  for (int64_t i = 0, e = sizes.size(); i < e; ++i) {
    int64_t tile = sizes[i];
    if (tile <= 0)
      return emitOpError("expects tile sizes to be positive, but got ")
             << tile << " at dimension " << i;

    int64_t dim = inputType.getDimSize(i);
    if (!inputType.isDynamicDim(i) && dim % tile != 0)
      return emitOpError("expects the dimension ")
             << i << " (" << dim
             << ") to be a multiple of the tile size " << tile;
  }

  return success();
}
```

注意 `isDynamicDim(i)` 的檢查：動態維度無法靜態驗證倍數關係，必須放行。

## 把 verifier 接進 ODS

```tablegen
def NPU_MatMulOp : NPU_Op<"matmul", [Pure]> {
  // ...
  let hasVerifier = 1;
}

def NPU_TileOp : NPU_Op<"tile"> {
  // ...
  let hasVerifier = 1;
}
```

`let hasVerifier = 1;` 會讓 ODS 產生 dispatch：

```cpp
LogicalResult MatMulOp::verify();  // 宣告（在 .h.inc）
// 定義（在 .cpp.inc）：
LogicalResult MatMulOp::verify() { return ::mlir::success(); }
```

ODS 產生的版本是 stub，我們在 `NPUOps.cpp` 裡**另外定義** `MatMulOp::verify()` 就會造成重複定義！

正確的做法是：ODS 的 stub 是 `static` 或由 `hasVerifier` 註解掉。實際上，MLIR 的行為是：

* `let hasVerifier = 1;` → ODS **不**產生 `verify()` 的定義，只產生一個宣告（`LogicalResult verify();`）在 op 類別中，並在 `Op::verifyInvariants` 中呼叫它。
* 具體地說，ODS 產生的 `.cpp.inc` 會包含：

```cpp
LogicalResult MatMulOp::verify();
```

這是**宣告**（重複宣告是合法的），而真正的定義由我們提供。

實務上，正確的寫法是：`hasVerifier = 1` 只產生宣告，我們在 `NPUOps.cpp` 提供定義。這是 MLIR 的標準模式，不會衝突。

### 驗證器的執行時機

```mlir
%0 = npu.matmul ins(%a, %b) outs(%c) : tensor<128x256xf16>, tensor<256x64xf16>, tensor<128x64xf16>
```

若 $K$ 不匹配（256 vs 128），`mlir-opt` 會在解析後立即報錯：

```text
error: 'npu.matmul' op expects the K dimension of lhs and rhs to match, but got 256 and 128
```

若關閉驗證（`--verify-each=false`），錯誤會被延後，導致後續 pass 看到非法 IR 而產生不可預期的行為。

### 一個完整的 Pass：`npu-expand-matmul`

這個 pass 把 `npu.matmul`（原子形式）展開成一個 `linalg.matmul` 加上量化處理，讓通用的 `linalg` 最佳化（fusion、tiling）能作用在它上面。

```cpp
namespace {

/// 把 `npu.matmul` 展開成 `linalg.matmul`（量化參數被剝離，
/// 因為 linalg 不理解量化）。
struct ExpandMatMulPattern : OpRewritePattern<npu::MatMulOp> {
  using OpRewritePattern<npu::MatMulOp>::OpRewritePattern;

  LogicalResult matchAndRewrite(npu::MatMulOp op,
                                PatternRewriter &rewriter) const override {
    Location loc = op.getLoc();
    Value lhs = op.getLhs();
    Value rhs = op.getRhs();
    Value out = op.getOut();

    //===--------------------------------------------------------------------===//
    // 1. 剝離量化 encoding，換成純整數語意的 linalg.matmul
    //===--------------------------------------------------------------------===//
    auto lhsType = cast<RankedTensorType>(lhs.getType());
    auto rhsType = cast<RankedTensorType>(rhs.getType());
    auto outType = cast<RankedTensorType>(out.getType());

    auto plainLhs = RankedTensorType::get(lhsType.getShape(),
                                          lhsType.getElementType());
    auto plainRhs = RankedTensorType::get(rhsType.getShape(),
                                          rhsType.getElementType());
    auto plainOut = RankedTensorType::get(outType.getShape(),
                                          outType.getElementType());

    Value plainLhsVal = createTypeCast(rewriter, loc, lhs, plainLhs);
    Value plainRhsVal = createTypeCast(rewriter, loc, rhs, plainRhs);
    Value plainOutVal = createTypeCast(rewriter, loc, out, plainOut);

    //===--------------------------------------------------------------------===//
    // 2. 產生 linalg.matmul
    //===--------------------------------------------------------------------===//
    auto matmul = rewriter.create<linalg::MatmulOp>(
        loc, TypeRange{plainOutType}, ValueRange{plainLhsVal, plainRhsVal},
        ValueRange{plainOutVal});
    rewriter.replaceOp(op, matmul.getResults());
    return success();
  }

private:
  /// 用 `builtin.unrealized_conversion_cast` 改變型別。
  /// 這是跨方言轉換時改變 tensor encoding 的標準手段。
  Value createTypeCast(PatternRewriter &rewriter, Location loc, Value value,
                       Type newType) {
    return rewriter.create<UnrealizedConversionCastOp>(
        loc, newType, value);
  }
};

} // namespace
```

`UnrealizedConversionCastOp` 是 `builtin` 方言提供的轉換 op，專門用來「改變型別但不改變值」。它是**暫時的**，在 pipeline 末端必須由 `reconcile-unrealized-casts` pass 消除。這是 MLIR 中「型別轉換」的标准手段。

### Pass 本體

```cpp
namespace {

struct NPUExpandMatMulPass
    : public impl::NPUExpandMatMulBase<NPUExpandMatMulPass> {
  using impl::NPUExpandMatMulBase<NPUExpandMatMulPass>::NPUExpandMatMulBase;

  void runOnOperation() override {
    RewritePatternSet patterns(&getContext());
    patterns.add<ExpandMatMulPattern>(&getContext());

    // Greedy 驅動：反覆套用 pattern 直到收斂
    if (failed(applyPatternsAndFoldGreedily(getOperation(),
                                            std::move(patterns))))
      signalPassFailure();
  }
};

} // namespace
```

### `OperationPass<func::FuncOp>` 與 `OperationPass<>`

`runOnOperation()` 中的 `getOperation()` 的型別取決於 pass 的型別參數：

| Pass 型別 | `getOperation()` 回傳 | 適用 |
| --- | --- | --- |
| `OperationPass<>` | `Operation *` | 整個 module |
| `OperationPass<ModuleOp>` | `ModuleOp` | module 層級的轉換 |
| `OperationPass<func::FuncOp>` | `func::FuncOp` | 函式內部的轉換 |
| `OperationPass<func::FuncOp>` + `getOperation().getBody()` | region | 逐函式處理 |

**為什麼選 `func::FuncOp`？**

因為 `npu.matmul` 通常出現在函式內部。用 `OperationPass<func::FuncOp>` 讓 pass 由 pass manager **自動地對每個函式執行一次**，而且可以加上 `OpPassManager` 的平行機制（[4.2](04.2-多執行緒平行化.md)）。

但要注意：**若 `npu.matmul` 出現在 module 層級**（例如在 `gpu.module` 裡的 kernel），`OperationPass<func::FuncOp>` **不會**作用到它。這是一個常見的 bug 來源。解法是寫兩個 pass，或改用 `OperationPass<>` 再手動遍歷。

### `applyPatternsAndFoldGreedily` 的行為

這個函式（[5.1](05.1-GreedyPatternRewriteDriver.md)）的行為：

1. 反覆遍歷 IR，套用 `RewritePatternSet` 中的 pattern。
2. 同時套用 op 的 `fold()` 方法。
3. 直到沒有變化，或達到 `maxIterations`（預設 10）。

```cpp
LogicalResult applyPatternsAndFoldGreedily(Operation *op,
                                            const RewritePatternSet &patterns,
                                            GreedyRewriteConfig config = {});
```

`GreedyRewriteConfig` 可控制：

```cpp
GreedyRewriteConfig config;
config.maxIterations = 20;
config.enableRegionSimplification = GreedySimplifyRegionLevel::Disabled;
config.strictness = GreedyRewriteStrictness::ExistingOps;
if (failed(applyPatternsAndFoldGreedily(getOperation(), patterns, config)))
  signalPassFailure();
```

`strictness = ExistingOps` 表示**不新建原本不存在的 op**（只允許在既有 op 上做 in-place 修改）。這對 dialect conversion 很有用。

### `signalPassFailure()`

`signalPassFailure()` 標記 pass 失敗，pass manager 會中止 pipeline（或依 `--allow-unregistered-dialect` 等選項繼續）。**每個可能失敗的 pass 都必須呼叫它**，否則失敗會被吞掉，產生錯誤的輸出。

### 另一個完整 Pass：`npu-lower-to-linalg`

這個 pass 把 `npu.tile` 降成 `tensor.extract_slice` 的序列：

```cpp
namespace {

/// `npu.tile` 降成 `tensor.extract_slice` + `tensor.insert_slice`。
struct LowerTilePattern : OpRewritePattern<npu::TileOp> {
  using OpRewritePattern<npu::TileOp>::OpRewritePattern;

  LogicalResult matchAndRewrite(npu::TileOp op,
                                PatternRewriter &rewriter) const override {
    Location loc = op.getLoc();
    auto inputType = cast<RankedTensorType>(op.getInput().getType());
    DenseI64ArrayAttr sizesAttr = op.getTileSizes();
    SmallVector<int64_t> tileSizes(sizesAttr.asArrayRef());

    Value input = op.getInput();
    Value result = op.getResult();

    // 建立 offsets 與 sizes
    SmallVector<Value> offsets;
    SmallVector<int64_t> shape;
    for (int64_t i = 0, e = tileSizes.size(); i < e; ++i) {
      auto zero = rewriter.create<arith::ConstantIndexOp>(loc, 0);
      offsets.push_back(zero);
      shape.push_back(tileSizes[i]);
    }

    auto sliceType = RankedTensorType::get(shape, inputType.getElementType(),
                                            inputType.getEncoding());
    auto slice = rewriter.create<tensor::ExtractSliceOp>(
        loc, sliceType, input, offsets, offsets, shape, shape);
    rewriter.replaceOp(op, slice.getResult());
    return success();
  }
};

struct NPULowerToLinalgPass
    : public impl::NPULowerToLinalgBase<NPULowerToLinalgPass> {
  using impl::NPULowerToLinalgBase<NPULowerToLinalgPass>::NPULowerToLinalgBase;

  void runOnOperation() override {
    RewritePatternSet patterns(&getContext());
    patterns.add<LowerTilePattern>(&getContext());
    if (failed(applyPatternsAndFoldGreedily(getOperation(),
                                            std::move(patterns))))
      signalPassFailure();
  }
};

} // namespace
```

## Pass 的註冊

### 在 `mlir-opt` 中註冊

Pass 要能被 `mlir-opt --npu-expand-matmul` 這樣的命令列選項呼叫，需要三件事：

**1. Pass 的 TableGen 定義（可選，但推薦）**

```tablegen
// include/MLIR/NPU/Transforms/Passes.td
#ifndef MLIR_NPU_TRANSFORMS_PASSES_TD
#define MLIR_NPU_TRANSFORMS_PASSES_TD

include "mlir/Pass/PassBase.td"

def NPUExpandMatMul : Pass<"npu-expand-matmul", "::mlir::func::FuncOp"> {
  let summary = "把 npu.matmul 展開成 linalg.matmul";
  let description = [{
    展開 `npu.matmul` 為 `linalg.matmul`，讓通用的 linalg 最佳化可以作用於它。
  }];
  let dependentDialects = ["linalg::LinalgDialect", "arith::ArithDialect",
                           "tensor::TensorDialect"];
}

def NPULowerToLinalg : Pass<"npu-lower-to-linalg", "::mlir::func::FuncOp"> {
  let summary = "把 npu 方言的 op 降成通用方言";
  let dependentDialects = ["tensor::TensorDialect", "arith::ArithDialect"];
}

#endif // MLIR_NPU_TRANSFORMS_PASSES_TD
```

`dependentDialects` 是**必需的**：它讓 pass manager 在需要時先載入這些方言。少了它，若 IR 中出現 `linalg` op 而方言未註冊，會得到「unregistered dialect」錯誤。

**2. 產生 `Passes.h.inc` 與 `Passes.cpp.inc`**

mlir_tablegen(NPUTransformsPasses.cpp.inc -gen-pass-defs -name NPUTransforms)

```

**3. 註冊函式**

}
```

`PassRegistration<T>` 是一個 static 物件，其存在本身就是註冊。**注意：它必須被實際呼叫到**，否則 linker 可能把整個物件移除（static initialization order 問題）。

`registerNPUPasses()` 必須被明確呼叫。通常的做法是在 dialect 的 `initialize()` 裡呼叫，或在工具的 `main()` 裡。

```cpp
// lib/Dialect/NPU/NPUDialect.cpp
void NPUDialect::initialize() {
  addOperations<
#define GET_OP_LIST
#include "mlir/Dialect/NPU/NPUOps.cpp.inc"
      >();
  registerNPUPasses();
}
```

這是最省事的做法：只要 dialect 被載入，pass 就自動註冊。

### DialectRegistry 與 `registerAllDialects`

`mlir-opt` 的 `main()` 大致是：

```cpp
int main(int argc, char **argv) {
  mlir::registerAllPasses();
  mlir::registerAllDialects(registry);
  mlir::registerAllExtensions(registry);

  return asMainReturnCode(mlir::MlirOptMain(argc, argv, "MLIR optimizer driver\n", registry));
}
```

`registerAllDialects(DialectRegistry &registry)` 註冊所有上游方言。我們的自訂方言要加進去，有兩個選擇：

**選擇 A：修改上游的 `InitAllDialects.h`（不推薦）**

**選擇 B：建立自己的工具**

```cpp
// tools/npu-opt/npu-opt.cpp
#include "mlir/InitAllDialects.h"
#include "mlir/InitAllPasses.h"
#include "mlir/Tools/mlir-opt/MlirOptMain.h"
#include "mlir/Dialect/NPU/NPUDialect.h"
#include "mlir/Dialect/NPU/Transforms/Passes.h"

int main(int argc, char **argv) {
  mlir::DialectRegistry registry;
  mlir::registerAllDialects(registry);
  registry.insert<mlir::npu::NPUDialect>();
  mlir::registerAllPasses();
  mlir::npu::registerNPUPasses();

  return mlir::asMainReturnCode(
      mlir::MlirOptMain(argc, argv, "npu-opt: NPU 專用 MLIR 優化工具\n", registry));
}
```

`MlirOptMain` 提供了 `--help`、`--split-input-file`、`--verify-diagnostics` 等所有標準選項。

**選擇 C（最簡潔）：用 dialect 的 `getCanonicalizationPatterns` 註冊 pass**

有些方言把「轉換類」的行為直接放在 canonicalization 裡，這樣不需要獨立的 pass 註冊。

## 用 `mlir-opt` 驗證自己的方言

### 基本檢查

```bash
mlir-opt test.mlir --npu-expand-matmul
```

若 verifier 有問題，會立刻報錯：

```text
error: 'npu.matmul' op expects the K dimension of lhs and rhs to match, but got 256 and 128
```

### 檢查 pass 的前後

```bash
mlir-opt test.mlir --npu-expand-matmul -o out.mlir
```

### 檢查 pass 是否真的被註冊

```bash
mlir-opt --help | grep npu
```

若沒有列出 `--npu-expand-matmul`，說明註冊沒生效。

### 常見錯誤與原因

| 症狀 | 原因 |
| --- | --- |
| `unregistered dialect 'npu'` | dialect 沒 `registry.insert` |
| pass 在 `--help` 中不存在 | `registerNPUPasses()` 沒被呼叫，或被 linker 移除 |
| `expected X dialect to be registered` | 忘了宣告 `dependentDialects` |
| pattern 沒有生效 | pattern 的 root op 沒被匹配到；檢查 `matchAndRewrite` 的前置條件 |
| 結果不正確 | `fold` 或 pattern 的語意寫錯 |
| 轉換後出現 `unrealized_conversion_cast` | 忘記跑 `reconcile-unrealized-casts` |

## 小結與延伸閱讀

* Verifier 的兩層分工：ODS 的宣告式約束處理「型別同一性」，手寫 `verify()` 處理「跨位置關係」（矩陣乘法的 $K$ 維相等）與「硬體限制」；判準是「這個約束是必要條件還是建議」。
* 診斷訊息要回答「哪裡錯、為什麼錯、怎麼修」；`emitOpError` 提供了 op 位置與名稱的前綴，串流 `<<` 讓細節易讀。檢查順序要先「語意必要」後「硬體策略」，否則使用者會看到次要的錯誤。
* Pass 的結構是 `OperationPass<T>` + `runOnOperation()` + `RewritePatternSet` + `applyPatternsAndFoldGreedily`，失敗必須 `signalPassFailure()`；`dependentDialects` 不可省。
* 註冊鏈是三段：`Passes.td` 宣告（`-gen-pass-decls` / `-gen-pass-defs`）→ `PassRegistration<T>()` → 確保 `registerNPUPasses()` 被呼叫（最好在 dialect 的 `initialize()` 裡）。
* `mlir-opt` 驗證方言的三個動作：跑一次看 verifier 診斷、跑 pass 看前後差異、`--help` 看選項是否註冊。
