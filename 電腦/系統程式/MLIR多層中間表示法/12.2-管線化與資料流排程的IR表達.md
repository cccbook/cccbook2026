# 12.2 管線化、資料流排程與硬體資源映射的 IR 表達

[12.1](12.1-MLIR在HLS與HDL降階的角色.md) 說明了 HLS 流程中「迴圈到硬體控制結構」這一步是 HLS 特有的一步。這一步的核心動作是 **pipelining（管線化）**：把一段組合邏輯沿著時間切成若干段，每段之間用暫存器隔開，使得每次時脈邊界可以啟動一個新的運算。

本節要把這件事講透，因為它是 HLS 與 NPU 排程的共同核心：

> 如何把「一段迴圈」變成「一條管線」？II（initiation interval）如何決定？有限的硬體資源（乘法器、DSP、BRAM）如何在多個管線之間分配？這些決策在 IR 裡長什麼樣？

## 管線化的語意

### 定義

給定一段組合邏輯 $F$ ，把它切成 $k$ 段，從 $F_1$ 到 $F_k$ ，並在 $F_i$ 與 $F_{i+1}$ 之間插入暫存器 $R_i$ 。管線化後的功能等價於依序套用 $F_1$ 、 $F_2$ 直到 $F_k$ ，中間以暫存器隔開。

這個分解必須**保持語意等價**：管線化的結果與原組合邏輯的結果相同，只是延遲變了。

管線化帶來三個性質：

1. **延遲變成 $k$ 拍**：輸入進來後，要經過 $k$ 拍才得到結果。
2. **吞吐量變成每拍一個**：只要管線填滿，每個時脈邊界都能接受一組新資料。
3. **時序變好**：每段邏輯的組合延遲變短，因此可以用更高的時脈頻率。

第三點是 HLS 的主要動機：現代製程下，單一組合路徑的延遲往往超過時序需求，必須切段。

### 一個具體例子

考慮 $F(x) = (x + 1) * 2 + 3$ 。切成兩段：

* $F_1(x) = x + 1$
* $F_2(y) = y * 2 + 3$

管線化後的時間展開：

```
第 0 拍: 輸入 x0 -> F1 -> R1
第 1 拍: 輸入 x1 -> F1 -> R1；R1(x0) -> F2 -> 輸出
第 2 拍: 輸入 x2 -> F1 -> R1；R1(x1) -> F2 -> 輸出
```

結果序列比原本延遲 1 拍，但每拍都有一個結果。

### 為什麼這需要編譯器的支援

關鍵在於「切哪裡」不是唯一問題，**真正難的是決定 $k$ 與 II**，而這取決於：

* 每段邏輯的**組合延遲**（取決於運算子種類與目標製程）。
* **資源限制**：如果整個設計只有 2 個乘法器，而 $F$ 需要 4 個乘法器，那麼切段並不能解決問題，必須先做資源共享。
* **迴圈的相依性**：迴圈內部的資料相依（例如累加）會限制 II。

這些都是編譯器（排程器）的工作，而不是硬體設計者的工作。這正是 HLS 的價值所在。

## II 與 throughput 的取捨

### 定義

**II（initiation interval）** 定義為：相鄰兩次啟動（launch）之間的時脈週期數。

* II = 1：每拍啟動一次，吞吐量最大。
* II = 2：每兩拍啟動一次。
* II = $n$ ：退化成完全沒有管線化，等同於把整個迴圈序列執行。

一個 $k$ 段的管線，若 II = 1，其總延遲是 $k$ 拍，吞吐量是每拍一個運算。若 II = 2，則每兩拍啟動一次。

### II 的下界

管線化的 II 不能任意小，它受到三個因素限制。

**約束一：資源限制。** 若迴圈每次迭代需要 $m$ 個乘法器，而硬體只有 $p$ 個，則 II 的下界是 $m$ 除以 $p$ 向上取整：

$$
II \ge \left\lceil \frac{m}{p} \right\rceil
$$

這個式子是資源共享（resource sharing）的數學表達：當運算量超過硬體供應時，必須拉長啟動間隔來分攤。

**約束二：相依性限制（recurrence constraint）。** 迴圈內若存在迴圈攜帶相依（loop-carried dependence），例如累加：

$$
a_i = a_{i-1} + b_i
$$

若 $a$ 的更新需要 $L$ 拍才能完成（ $L$ 是迴圈體的關鍵路徑延遲），且沒有其他手段打散這個相依，則 II 至少為 $L$ 。

**打散相依的標準手段是「前瞻（look-ahead）」或「延遲更新」。** 把累加器更新延後 $d$ 拍：

$$
a_i = a_{i-d} + b_i
$$

這需要額外的暫存器來保存 $d$ 份 accumulator 的不同副本。這個技術在硬體編譯裡叫 accumulator renaming 或 look-ahead pipelining。

**約束三：記憶體埠限制。** 若迴圈每次迭代需要從同一個 BRAM 讀取 2 個字，而 BRAM 是單埠的，則 II 至少為 2。解決方式是 array partitioning（把 BRAM 切成多份），這是 [11.2](11.2-張量分塊與片上緩衝排程.md) 與 [12.1](12.1-MLIR在HLS與HDL降階的角色.md) 提到的 array partition 最佳化。

### II 的理論下界

把上述三個約束合起來，II 的下界是三者的最大值：資源下界、迴圈攜帶相依的關鍵路徑延遲 $L_{rec}$ （在打散相依之後）、以及記憶體埠約束。

**關於 $k$ （管線段數）與 II 的關係**：段數越多，每段延遲越短，時序越好，但需要的暫存器越多。段數 $k$ 的選擇在原則上是自由的（切得更細只是多花暫存器），而 II 是由約束決定的。但兩者之間有耦合：管線的「填充與排空」（fill/drain）開銷大約是 $(k-1) \times II$ 拍，若 $k$ 遠大於 loop trip count，開銷就佔滿了。

### 一個數值例子

考慮一個簡單的 FIR 濾波器迴圈：

```
sum = 0
for i in 0..N:
  sum += a[i] * b[i]
```

* 資源：設計中有 $p = 4$ 個乘法器， $m = 1$ 個（每次迭代一個乘法），資源約束為 II 至少 1。
* 相依性：累加需要 1 拍（乘法已 pipelined），加法 1 拍，關鍵路徑 $L = 2$ 。若採用 1 拍前瞻打散， $L_{rec} = 1$ 。
* 記憶體：`a` 與 `b` 各讀 1 個，雙埠 BRAM 可同時讀，無額外約束。

結果：II = 1，管線段數 $k = 2$ 或 $3$ （取決於目標時序）。

若設計中只有 1 個乘法器：資源約束仍為 1，但關鍵路徑不變。若迴圈裡有 2 個串聯乘法且沒有 pipelined 乘法器：資源約束為 2， $L_{rec} = 2$ ，因此 II = 2，吞吐量減半。

## 資源共享與資源綁定

### 資源共享（resource sharing）

**資源共享**是指：當硬體上的運算器數量有限時，把多個使用點映射到同一組實體運算器上，並用多路選擇器（mux）在時間上區分。

形式化：設計中有 $p$ 個乘法器，程式中有 $n$ 個乘法運算點，映射 $f$ 把它們分配到 $p$ 個實體。若 $f$ 不是單射，則需要 mux。

資源共享的代價是 mux 的延遲與面積，以及 II 的增長。收益是**面積**。這是一個典型的時間與空間取捨。

### 資源綁定（binding）

**資源綁定**是指：把某個特定型別的運算（通常是乘法累加）綁定到特定種類的硬體資源上，例如 FPGA 上的 DSP block。

在 IR 中，綁定的結果通常表現為：

* 一個帶有「資源類型」屬性的 op，例如 `myhw.mul` 而非通用的 `arith.mulf`。
* 一個資源清單（inventory），說明有多少個 DSP 可用。
* 一份綁定結果的報告或註解。

### 硬體資源的建模方式

在 MLIR 與 CIRCT 的脈絡裡，硬體資源的建模有三種深度。

**深度一：不建模，靠約定。** 資源綁定 pass 直接產生特定 op，資源數量寫在 pass 的配置裡。簡單，但無法做全域最佳化。

**深度二：用 instance 表示。** CIRCT 的 `hw.instance` 語意上就是「實例化一個模組」，這正是硬體資源實例的自然表達：

```mlir
hw.module @MulPipeline(in %clk: !seq.clock, in %a: i32, in %b: i32, out %p: i32) {
  %prod = comb.mul %a, %b : i32
  %r = seq.compreg %clk, %prod : i32
  hw.output %r : i32
}

hw.module @Top(in %clk: !seq.clock, in %a: i32, in %b: i32, out %p: i32) {
  %m = hw.instance "mul0" @MulPipeline(in %clk, %a, %b) -> (p: i32)
  hw.output %m : i32
}
```

這裡 `@MulPipeline` 就是一個「乘法器資源」的實例。若設計中有多個乘法器，就有多個 instance，綁定 pass 負責把 `comb.mul` 分配到這些 instance。

**深度三：用專屬的資源方言。** 定義一個 `myhw` 方言，包含資源宣告 op：

```mlir
myhw.resource @dsp_mul { count = 4 : i64, latency = 3 : i64, throughput = 1 : i64 }
myhw.resource @bram { count = 2 : i64, ports = 2 : i64 }
```

然後在 op 上標記需求：

```mlir
%r = myhw.mul %a, %b { bound = "dsp_mul" } : i32
```

這種方式最靈活，但需要自訂的資源分配演算法。

### 資源多個體與 sharing 屬性

一個實用的折衷，是不引入完整的資源方言，而是用**屬性**在既有的 op 上表達資源需求：

```mlir
%r = arith.mulf %a, %b : i32 { myhw.resource = "dsp_mul", myhw.instance_count = 1 }
```

`instance_count = 1` 表示這個運算需要一個實體；若多個運算被分到同一實體，則需要在它們之間插 mux，並在 IR 中記錄：

```mlir
%r = myhw.shared_mul %a, %b { slot = 0 : i64, total_slots = 4 : i64 } : i32
```

`slot` 指出它被分到第幾號實體。這個資訊對後端非常有用，它直接告訴 Verilog 生成器「這四個乘法的 `p` 埠要接到同一個模組的輸入」。

## 資料流排程：software pipelining 與 modulo scheduling

### 兩種不同的「排程」

在 HLS 與 NPU 的語境裡，「排程」其實指兩件不同的事，容易混淆。

**宏觀排程（macro scheduling）**：決定整個程式的 op 順序、哪些 op 可以重疊執行、資源如何分配給不同 op。在 NPU 上，這是 [11.3](11.3-DMA搬移生成.md) 的 DMA 排程；在 HLS 上，這是 op 間的排程。

**微觀排程（micro scheduling）**：在單一迴圈內部，決定每次迭代的運算如何在時間上攤開。這就是 software pipelining。

### Software pipelining

**Software pipelining（軟體管線化）** 是在**沒有硬體管線**的機器上，用軟體的方式模擬管線：在迴圈的不同迭代中，把不同的階段交錯執行。

原始迴圈：

```
for i in 0..N:
  A[i] = f(B[i]) + g(C[i])
```

軟體管線化之後（prologue / kernel / epilogue 三段式）：

```
prologue:  A[0] = f(B[0]) 部分完成
kernel:    同時做 f(B[i+1]) 與 g(C[i]) 的剩餘部分
epilogue:  收尾
```

在**指令層級**的排程看，典型的一個 kernel 迭代會被交錯成：

```
iter i:   f(B[i])  | g(C[i])  | store A[i]
iter i+1:           f(B[i+1])| g(C[i+1])| store A[i+1]
```

其中 `f` 是多週期的（需要多條指令），`g` 是單週期的。

**Modulo scheduling** 是 software pipelining 的更一般形式，來自模排程理論：它把迴圈的迭代映射到有限的資源上，用「模」的方式週期性地重複使用資源，並且能處理迴圈攜帶相依（透過相依向量與 distance 來描述）。

Modulo scheduling 的核心概念是 **dependence distance**：迭代 $i$ 與迭代 $i + d$ 之間的相依距離 $d$ 。多維迴圈時則是 **dependence distance vector**。排程的約束是：若迭代 $i$ 與迭代 $i + d$ 之間有相依，則排程後的執行順序必須保持，也就是說被相依限制的操作之間的時間差不能為負。

### 從迴圈結構推導 pipeline stage 的演算法

這是本節最實用的部分。讓我們給出一個可實作的演算法。

**輸入**：一個 `scf.for` 迴圈，其 body 是一串 op；每個 op 有已知的延遲 $l_i$ （乘法的延遲通常取目標 DSP 的 pipeline latency，例如 3 拍）與資源需求。

**輸出**：把 body 重新組織成 $k$ 個 stage，並插入暫存器。

**演算法（Greedy Stage Partitioning）**：

```
輸入: op 序列 O = [o_1, o_2, ..., o_n]，每個 o_i 有延遲 l_i
      目標時序週期 T
      資源上限 R（每種資源的數量）

1. 建立依賴圖 G：頂點是 op，邊是資料相依
2. 對 G 做 ASAP 排程（as-soon-as-possible）：
   start(o_1) = 0
   start(o_j) = 對已排程前驅 p 取 max(start(p) + l_p)
   資源衝突處理：若某時間步的資源使用超過 R，將該 op 延後到資源有空
   finish(o) = start(o) + l_o
3. 決定管線段數 k：k = ceil( (max finish - min start) / T )
   若 T 給定（時序需求），k 由 T 決定；否則 k 取最小可行值
4. 切割：把時間軸切成 k 個長度為 T 的區間，落在區間 j 的 op 屬於 stage j
5. 插入暫存器：對每個跨越區間邊界的資料相依邊，插入一個暫存器
6. 剝離 prologue 與 epilogue
```

第 5 步是最需要注意的：暫存器的**數量**等於跨越邊界的相依邊數，而且這些暫存器的寬度等於被相依值的寬度。在實務中，這些暫存器通常被聚合成一個「stage register bundle」，以方便實作為 BRAM 或 register array。

第 6 步的剝離（peeling）也很關鍵：管線化後的迴圈不再是單純的 `scf.for`，而是「先跑一段 prologue（只有前幾個迭代的部分階段），再跑 kernel（每拍一個完整迭代），最後跑 epilogue」。這個形狀用 `scf.for` 加上 `scf.if` 表達會很彆扭，因此實務上通常引入一個專門的 op 來表達。

### 在 MLIR 中怎麼表達管線化

有幾種可能的表示法。

**做法一：用 `scf.for` 加手動的 stage 迴圈。**

```mlir
// 概念示範：把 body 切成兩段
scf.for %i = %c0 to %cN step %c1 {
  %s0 = stage.compute %i : index
  %s1 = stage.compute %s0 : index
}
```

這個做法太簡化，沒有表達出暫存器與剝離。

**做法二：引入專屬的 pipeline op。**

```mlir
scf.pipeline %i = %c0 to %cN step %c1 {
  %a = stage0 %x[%i] : f32
  %b = stage1 %a : f32
  scf.pipeline.yield %b : f32
}
```

這個 op 的語意是：body 被視為一個 pipeline stage，內部的 stage 邊界由屬性或子 op 指定。

**做法三：在 CIRCT 的脈絡裡，用 `seq.firreg`（暫存器）與 `seq` 的結構表達。**

```mlir
hw.module @Pipelined(in %clk: !seq.clock, in %a: i32, out %p: i32) {
  %v = comb.mul %a, %a : i32
  %r = seq.firreg %clk {name = "stage"} : i32
  seq.assign %r, %v : i32
  hw.output %r : i32
}
```

`seq.firreg` 表達「這是一個由時鐘觸發的暫存器」，正是管線的 stage 邊界。

**做法四：用屬性記錄 stage 資訊，讓 Verilog 生成器處理剝離。**

```mlir
scf.for %i = %c0 to %cN step %c1 { ... }
    { pipeline.stages = 3 : i64, pipeline.ii = 1 : i64 }
```

這種做法最簡單，但把複雜度推給後端。

### 一個完整的前後對照

我們來看一個具體的例子：一個乘累加迴圈。

**管線化前：**

```mlir
func.func @dot(%a: memref<1024xf32>, %b: memref<1024xf32>) -> f32 {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c1024 = arith.constant 1024 : index
  %f0 = arith.constant 0.0 : f32
  %sum = scf.for %i = %c0 to %c1024 step %c1 iter_args(%s = %f0) -> f32 {
    %av = memref.load %a[%i] : memref<1024xf32>
    %bv = memref.load %b[%i] : memref<1024xf32>
    %m = arith.mulf %av, %bv : f32
    %s2 = arith.addf %s, %m : f32
    scf.yield %s2 : f32
  }
  return %sum : f32
}
```

**管線化後（結構性表示，k = 3, II = 1）：**

```mlir
func.func @dot(%a: memref<1024xf32>, %b: memref<1024xf32>) -> f32 {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c1024 = arith.constant 1024 : index
  %f0 = arith.constant 0.0 : f32

  %pipe = scf.for %i = %c0 to %c1024 step %c1
      iter_args(%av0 = %f0, %m0 = %f0, %s0 = %f0) -> (f32, f32, f32) {
    // stage 0：載入
    %av = memref.load %a[%i] : memref<1024xf32>
    %bv = memref.load %b[%i] : memref<1024xf32>
    // stage 1：乘，使用上一拍載入的值
    %m_cur = arith.mulf %av0, %bv : f32
    // stage 2：累加，使用上一拍的乘積
    %s_cur = arith.addf %s0, %m0 : f32
    scf.yield %av, %m_cur, %s_cur : (f32, f32, f32)
  }
  %result = arith.addf %s0, %m0 : f32
  return %result : f32
}
```

（上面刻意保留了結構的笨拙：真正可用的表示需要處理 `iter_args` 的初值與剝離，這正是下一節要討論的問題。）

**關鍵洞察**：MLIR 的 `scf.for` 的 `iter_args` 機制**天然就是前進（forwarding）暫存器的表達**。`iter_args` 的值在迭代之間傳遞，正好對應硬體的 stage register。差別只在於：MLIR 的 `iter_args` 是「值」，硬體的暫存器是「暫存器陣列」，而後者需要在剝離時產生 $k$ 份副本。

### 剝離（peeling）的表達

管線化後的迴圈有三段：

```
prologue (k-1 次迭代的部分執行)
kernel    (n-k+1 次完整迭代)
epilogue  (k-1 次迭代的收尾)
```

在 IR 中表達 prologue 與 epilogue 的方式：

**方式一：巢狀 `scf.for` 與 `scf.if`。**

```mlir
// prologue：迭代 0 到 k-2
scf.for %p = %c0 to %cK step %c1 {
  scf.if %inRange {
    // 只執行 stage 0 與 stage 1
  }
}
// kernel
scf.for %i = %cK to %cN step %c1 {
  // 完整的三個 stage
}
// epilogue
scf.for %e = %cN to %cNPlusK step %c1 {
  scf.if %inRange {
    // 只執行 stage 2
  }
}
```

**方式二：引入專門的 pipeline op**，把三段封裝在一個 op 內，由後端展開。

實務上方式二更常見，因為方式一會讓 IR 膨脹且難以最佳化。而且方式一有個隱蔽問題：`scf.if` 會破壞「每個迭代都產生同樣形狀的資料」這個假設，讓後續的剝離與資源分析變複雜。

### 重定時與 II 的關聯

**重定時（retiming）** 是在電路圖上移動暫存器的操作，把暫存器從一個輸入路徑移到另一個，改變各節點的到達時間但不改變整體功能。重定時是管線化的基礎技術，它讓排程器可以把暫存器「推」到迴圈邊界，讓 II 下降。

在 MLIR 中，重定時並沒有直接的支援。它的功能部分被 `iter_args` 的表達能力取代，因為 `iter_args` 本質上就是把值跨越迭代邊界傳遞。

重定時與 II 的關聯可以用一個簡單的模型說明。對一個有迴圈攜帶相依距離 $d$ 的迴圈，若可以攤平成 $c$ 份相依副本，則 II 的下界是 $d$ 除以 $c$ 向上取整，與資源約束取最大值：

$$
II \ge \max\left(\left\lceil \frac{d}{c} \right\rceil,\; \text{資源約束}\right)
$$

其中 $c$ 是可以攤平的相依副本數，由前瞻深度決定。前瞻深度 $c$ 越大， $d/c$ 越小，但需要的硬體暫存器越多。

因此：**降低 II 的有效途徑是增加前瞻深度或增加資源**。這是一個清楚的資源與吞吐量的取捨，也是硬體設計中最核心的取捨之一。

## 從迴圈結構推導 stage 的完整偽碼

把上面的演算法寫成可實作的偽碼：

```text
function pipelineLoop(loop, targetPeriod T, resourceLimits R):
    body = loop.body
    ops = topologicalOrder(body)

    # 步驟 1: 建立依賴圖
    G = DependencyGraph(ops)
    for op in ops:
        for use in op.operands:
            if use.definedOutsideLoop(use):
                G.addEdge(use, op)

    # 步驟 2: 資源感知的 ASAP 排程
    schedule = {}
    resourceUse = {}
    for op in ops:
        est = 0
        for pred in G.predecessors(op):
            est = max(est, schedule[pred].finish)
        while true:
            conflict = false
            for r in op.requiredResources:
                used = countAt(resourceUse, r, est, op.latency)
                if used >= R[r]:
                    est = est + 1
                    conflict = true
            if not conflict:
                break
        schedule[op] = Interval(start=est, finish=est + op.latency)
        for r in op.requiredResources:
            resourceUse.add(r, est, op.latency)

    # 步驟 3: 決定段數
    totalSpan = max(schedule[o].finish for o in ops) - min(schedule[o].start for o in ops)
    k = ceil(totalSpan / T)

    # 步驟 4: 依時間區間切割
    stages = [[] for _ in range(k)]
    for op in ops:
        idx = floor(schedule[op].start / T)
        stages[idx].append(op)

    # 步驟 5: 插入 stage registers
    for edge in G.edges:
        if stageOf(edge.src) != stageOf(edge.dst):
            insertRegister(edge, width = edge.valueType.width)

    # 步驟 6: 剝離
    result = peel(loop, k, stages)
    return result
```

這個演算法的複雜度是 $O(|ops| + |edges|)$ （忽略資源衝突迴圈），相當高效。

### 演算法的侷限

必須誠實地指出這個演算法忽略了什麼：

* **相依向量**：它只處理單維迴圈。多維迴圈需要 dependence distance vector 與 modulo 的擴充。
* **前瞻的自動推導**：上面的演算法不會自動產生 accumulator renaming，前瞻深度 $c$ 通常需要另外的 pass 或人工設定。
* **迴圈間的相依**：跨迴圈的相依（不在同一個 `scf.for` 內）不在處理範圍。
* **時序的實際模型**：延遲 $l_i$ 是簡化模型，真實的 FPGA 時序分析是靜態時序分析（STA）的問題。

## 硬體資源映射的討論

### 資源映射的決策層次

把「資源」這件事分成三個決策層次，有助於理解複雜度從哪裡來：

**第一層：型別映射（operation mapping）。** 決定「`arith.mulf` 變成什麼」。選項：映射到 DSP、映射到 LUT、映射到帶特定點陣格式的運算器。這個決策通常在工具配置階段就固定。

**第二層：實例分配（instance binding）。** 決定「第 $i$ 個乘法運算用第幾號實體」。這是一個指派問題，通常用貪婪或以資源為約束的著色演算法。

**第三層：排程（scheduling）。** 決定「什麼時候執行」。這是 II 與吞吐量之間的取捨。

### 著色演算法的視角

第二層可以看成一個圖著色問題：建一張圖，頂點是運算點，邊連接「被分配到同一實體」的兩個運算點（因為它們需要時間上互斥），然後用 $p$ 種顏色著色。

更精確地，資源共享決策需要同時考慮**面積**與**時間**：

* 若兩個運算點可以合併（共享實體），面積減少，但 II 可能增長。
* 這是一個 bi-criteria 最佳化問題，沒有簡單的多項式解。

實務上通常用啟發式：先假設不共享，按 II 約束排程；若資源超標，則貪婪地合併最不需要同時執行的運算對。

### 一個具體的資源報告

一個實用的工具是「資源報告」，它在 HLS 中扮演類似 [12.1](12.1-MLIR在HLS與HDL降階的角色.md) 提到的「最佳化報告」角色，但因為是在 MLIR 框架裡做的，可以在最佳化過程中持續更新：

| 資源 | 總數 | 已使用 | 剩餘 |
| --- | --- | --- | --- |
| DSP48E2 | 8 | 4 | 4 |
| BRAM36 | 4 | 2 | 2 |
| FF 暫存器 | 1200 | 340 | 860 |
| LUT | 8000 | 2100 | 5900 |

這份報告可以在 pass 管線中的多個點產生，讓使用者即時看到資源壓力。這個做法把「報告型優化」變成「過程型優化」，是 CIRCT 帶來 HLS 領域的一個實質改進。

## 與 NPU 排程的對照

值得把本章的內容與第四部對照，因為兩者共享底層思想：

| 面向 | HLS | NPU |
| --- | --- | --- |
| 排程對象 | 硬體操作與暫存器 | DMA 搬移與 PE 運算 |
| 平行度來源 | 管線段之間的時序重疊 | 資料流圖的天然平行 |
| 關鍵資源 | DSP、BRAM、FF | PE 陣列、SRAM、DMA 通道 |
| II 的對應物 | initiation interval | 每拍可接受的 tile 數 |
| 前瞻的對應物 | accumulator renaming | 脈動陣列的 skewing |
| 剝離 | prologue 與 epilogue 剝離 | pipeline 的 fill 與 drain 開銷 |

最有趣的是「前瞻」與「skewing」的對應。HLS 中為了打斷累加相依而做的 accumulator renaming，在 NPU 上就是脈動陣列把資料「歪斜」（skew）地送入 PE 陣列，也就是**同一個想法的兩種硬體實現**。這也說明為什麼 [11.1](11.1-脈動陣列與NPU的IR需求.md) 說脈動陣列是「歸約迴圈展開成 pipeline 的自然結果」。

## 小結與延伸閱讀

* 管線化把組合邏輯切成 $k$ 段並插入暫存器，換取更高時序頻率與每拍一個的吞吐量；代價是延遲增加 $k$ 拍與暫存器面積。
* II 的下界是三個約束的最大值：資源上限、迴圈攜帶相依的關鍵路徑、記憶體埠數。前瞻（accumulator renaming）是打破相依約束的主要手段。
* 資源共享在時間上互斥多個運算點以節省面積，代價是 mux 延遲與可能的 II 增長；資源綁定則把特定運算映射到 DSP 等專用硬體。
* 從迴圈推導 stage 的演算法是「ASAP 排程 + 資源感知 + 時間軸切割 + 插入 stage register + 剝離」，其中 `iter_args` 天然就是前進暫存器的 IR 表達。
* HLS 的前瞻與 NPU 脈動陣列的 skewing 是同一個想法的兩種硬體實現：迴圈攜帶相依的打散方式決定了硬體結構。
