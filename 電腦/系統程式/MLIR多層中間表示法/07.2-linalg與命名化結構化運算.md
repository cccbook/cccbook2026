# 7.2 linalg 方言：具名的結構化運算與 Structured Ops

[7.1](07.1-tensor與結構化運算.md) 我們建立了 `tensor` 這個「不可變數學值」的抽象層，指出它能延後記憶體佈局決策。但 `tensor` 方言本身只提供元素級的存取與生成，缺乏**更高階的運算結構**：我們能表達「逐元素相加」，卻無法直接表達「矩陣乘法」這個帶有複雜索引結構的運算。若只用 `tensor.generate` 硬寫矩陣乘法，得到的會是一個巨大的 region，後續的 tiling、fusion、向量化成為難事。

本節要引入的 `linalg` 方言，回答的是：**如何用一個既能被人讀懂、又能被機器結構化最佳化的形式，表達「結構化的多維運算」？**

## 為什麼需要 Structured Op

先看一個問題的兩種表達方式。第二種是「通用 elementwise + broadcast」表示法：

```mlir
#map = affine_map<(d0, d1) -> (d0, d1)>
#map_b = affine_map<(d0, d1) -> (d1)>
%0 = tensor.empty() : tensor<4x8xf32>
%1 = linalg.generic {
  indexing_maps = [#map, #map_b, #map],
  iterator_types = ["parallel", "parallel"]
} ins(%A : tensor<4x8xf32>) ins(%B : tensor<8xf32>) outs(%0 : tensor<4x8xf32>) {
^bb0(%a: f32, %b: f32, %c: f32):
  %s = arith.addf %a, %b : f32
  linalg.yield %s : f32
} -> tensor<4x8xf32>
```

這種表示法有一個明顯的優點：**統一**。任何運算都能用 `linalg.generic` 表達，不需要新增方言操作。編譯器只需實作一套最佳化邏輯（tiling、fusion、vectorization）就能處理所有運算。

但它也有對應的明顯代價：

1. **資訊在 generic 形式中已被「扁平化」**。當看到 `linalg.generic` 的 affine map 時，編譯器知道的是「迭代空間是 $4 \times 8$ 」與「B 被廣播」，但**不知道這是一個矩陣乘法**。因此，許多與語意相關的最佳化機會就消失了。
2. **最佳化難以泛化**。像「把 batch 維放到最外層」這類以語意為名的最佳化，在 generic 形式下無法表達。
3. **來源資訊遺失**。編譯器無法根據語意選擇專用 lowering（例如矩陣乘法在 GPU 上可用 MMA 指令、在 CPU 上可用 blocked tiling）。

`linalg` 方言的解法是**兩者都要**：提供 named form（`linalg.matmul`）以保留語意，同時提供 generic form（`linalg.generic`）作為可退化到的通用形式與自訂運算的表達方式。

這正是 Linalg 專案最初的設計 rationale。它的核心洞察是：**運算的「迭代空間結構」與「元素語意」是可以分離描述的**，而這個分離描述（affine map + iterator type）就是編譯器最佳化所需的全部資訊。

## 三大特性：元素語意、索引映射、多重輸入輸出

一個 Structured Op 的定義由三部分組成。

### 特性一：元素語意（element semantics）

每個 op 內含一個 **payload region**，描述「對單一元素做什麼」。region 的 block argument 對應每個輸入與輸出的**單一元素**，region 最後以 `linalg.yield` 結束。

以 `linalg.matmul` 為例，其 payload region 的語意是：

```mlir
給定 C[i,j] 的累加值 c，以及 A[i,k]、B[k,j]，
yield (c + A[i,k] * B[k,j])
```

注意這裡的「索引 $k$ 」不屬於 payload region 的 block argument——它是 reduction 維度。reduction 維度的索引變數是隱含的，region 只針對「最終座標 $(i,j)$ 」的元素語意。

這個區分非常重要：payload region 描述的是**逐元素的計算**，而迭代空間與索引映射由外部的 metadata 描述。

### 特性二：索引映射（indexing maps）

每個輸入與輸出都有一個 **indexing map**，把 op 的迭代空間維度映射到該 operand 的索引空間。indexing map 是一個 `AffineMap`。

以 `linalg.matmul` 為例：

```mlir
ins:  A : (M, K)   map = (d0, d1, d2) -> (d0, d2)
ins:  B : (K, N)   map = (d0, d1, d2) -> (d2, d1)
outs: C : (M, N)   map = (d0, d1, d2) -> (d0, d1)
```

迭代空間有三個維度 $(d_0, d_1, d_2) = (i, j, k)$ ，其中 `d_0` 對應 $M$ ，`d_1` 對應 $N$ ，`d_2` 對應 $K$ 。最後一個維度 `d_2` 是 reduction 維度。

這個 mapping 就是「matmul 之所以是 matmul」的結構性描述。編譯器可以從中推導出：

* **迴圈 nest 的順序**：三個迭代維度依序是 `i`、`j` 與 `k`，其中 `i` 與 `j` 是 parallel，而 `k` 是 reduction。
* **哪些維度可以互換**（parallel 之間可以自由交換順序）。
* **哪些維度可以融合**（同一個 parallel 維度在多個 operand 中出現，代表可以一起迭代）。
* **矩陣乘法的形狀相容性**。 $K_A = K_B$ 這個約束，可以從以下事實推導出來： $A$ 的最後一維與 $B$ 的第一維都被 reduction 維 `d_2` 索引，且兩者共用同一個迭代變數。

換言之，**索引映射把語意資訊重新變成可最佳化的結構資訊**。

### 特性三：多重輸入與輸出

一個 Structured Op 可以有多個輸入與多個輸出，且輸入輸出可以形狀不同、可以廣播。

例如一個「加權殘差連接」：

```mlir
%r = linalg.generic {
  indexing_maps = [
    affine_map<(d0, d1) -> (d0, d1)>,
    affine_map<(d0, d1) -> (d0, d1)>,
    affine_map<(d0, d1) -> (d0, d1)>,
    affine_map<(d0, d1) -> (d0, d1)>
  ],
  iterator_types = ["parallel", "parallel"]
} ins(%x : tensor<8xf32>) ins(%w : tensor<8xf32>) ins(%bias : tensor<8xf32>) outs(%init : tensor<8xf32>) {
^bb0(%x_e: f32, %w_e: f32, %b_e: f32, %acc: f32):
  %m = arith.mulf %x_e, %w_e : f32
  %s = arith.addf %m, %b_e : f32
  %r = arith.addf %s, %acc : f32
  linalg.yield %r : f32
} -> tensor<8xf32>
```

這個 op 有 3 個輸入、1 個輸出，形狀相同但語意完全不同。若用 elementwise 表示法，這也只是「四個輸入的 elementwise」，沒有任何「殘差」語意。

多輸出的例子是像「最大值與總和同時計算」這種 op：兩個輸出共用同一個迭代空間，但各自的 payload 計算不同。

## named form 與 generic form

### named form

`linalg.matmul` 的 named form 是：

```mlir
%c = linalg.matmul ins(%a : tensor<64x32xf32>) ins(%b : tensor<32x128xf32>) outs(%c_init : tensor<64x128xf32>) -> tensor<64x128xf32>
```

named form 有幾個好處：

1. **閱讀性**：一眼看出是矩陣乘法。
2. **專用 lowering**：`linalg.matmul` 可以被 lowering 成使用 `vector.contract`、GPU MMA 指令、或直接呼叫 BLAS 的形式；`linalg.generic` 則只能用通用路徑。
3. **語意感知最佳化**：可以根據「這是 matmul」套用特定的最佳化，例如在 GPU 上把 $M$ 維當作 batch 並合併。

`linalg.matmul` 有多個變體：`linalg.matmul`, `linalg.batch_matmul`, `linalg.matmul_ins_vec`, `linalg.matmul_transpose_a/b`。命名遵循 `[batch_]op[_modifier]` 的慣例。

### generic form

`linalg.generic` 是通用形式，上述已示範。它的語法元素有四項：

| 元素 | 意義 |
|---|---|
| `indexing_maps` | 每個 operand（inputs + outputs）一個 affine map |
| `iterator_types` | 每個迭代維度的類型 |
| `ins(...)` / `outs(...)` | operand 分組 |
| payload region | 元素語意 |

`iterator_types` 的三種值：

* `parallel`：維度之間互相獨立，可任意重排。
* `reduction`：維度被累加，必須被累加到初始值中。
* `window`：用於卷積類運算，代表維度同時扮演輸入與輸出的角色。

`operand segment sizes` 是一個 attribute，用來記錄 operands 中前幾個是 inputs、其餘是 outputs：

```mlir
%r = "linalg.generic" {
  indexing_maps = [...],
  iterator_types = ["parallel", "parallel"],
  operandSegmentSizes = array<i32: 2, 1>
} ins(%a : tensor<4x8xf32>) ins(%b : tensor<8xf32>) outs(%o : tensor<4x8xf32>) {
^bb0(...):
  ...
} -> tensor<4x8xf32>
```

這是 MLIR 的 variadic operands 分組慣例（`AttrSizedOperandSegments`）。在 C++ 中，可以透過 `getInputs()` / `getOutputs()` 這類 accessor 直接取用。

## affine map 作為索引映射語言

索引映射語言是 `linalg` 的核心發明。讓我們仔細看它的形式。

一個 `AffineMap` 由「輸入維度數」（dim）、「輸入符號數」（sym）與「結果運算式列表」組成：

```mlir
AffineMap ::= (dim0, dim1, ..., dim_{n-1}, sym0, ..., sym_{m-1}) -> (expr0, expr1, ...)
```

在 `linalg` 的 indexing map 中，輸入維度就是迭代空間的維度，符號則通常不用（`linalg` 中 indexing map 限定為只使用 dims 的 restricted affine map）。

上面 `linalg.matmul` 的三個 map：

```mlir
(d0, d1, d2) -> (d0, d2)     # A 的索引
(d0, d1, d2) -> (d2, d1)     # B 的索引
(d0, d1, d2) -> (d0, d1)     # C 的索引
```

這裡所有的運算式都是 dim 或 dim 的常數倍，沒有一般 affine 運算式（如 `d0 + d1` 或 `d0 * 2`）。這是刻意的限制：**restricted affine map**。

為什麼要限制？因為 restricted affine map 保證了：

1. **索引空間是「笛卡兒積的子集 + 仿射變換」**，而不是任意的非線性映射。
2. 每個輸出維度都是**輸入維度的仿射函數**，因此迭代空間的 shape 可以從 operand shape 推導。
3. **合法性（legalization）變成可解的問題**：給定一個目標 tiled loop nest（其實是一個 affine map），要判斷一個原生的 map 是否能被「projeced」成目標的 map，是多面體投影問題；若 map 是 restricted 的，這類問題有高效解法。

在 C++ 中建立這些 map：

```cpp
MLIRContext *ctx = ...;
AffineMap aMap = AffineMap::get(3, 0,
                                {getAffineDimExpr(0, ctx), getAffineDimExpr(2, ctx)},
                                ctx);
AffineMap bMap = AffineMap::get(3, 0,
                                {getAffineDimExpr(2, ctx), getAffineDimExpr(1, ctx)},
                                ctx);
AffineMap cMap = AffineMap::get(3, 0,
                                {getAffineDimExpr(0, ctx), getAffineDimExpr(1, ctx)},
                                ctx);
```

`AffineMap::get(numDims, numSymbols, ArrayRef<AffineExpr> results, context)` 是主要的建構入口。結果運算式數量即為 map 的 rank。

## broadcasting 與 shape 推導

有了 indexing map，shape 推導就變成了一個明確的計算。

**規則**：對每個 operand，其 shape 由它的 indexing map 的**結果維度**決定。每個結果維度 $r$ 的長度，是所有映射到它的迭代維度的長度，**取其中最大的**（廣播規則），但必須符合**廣播相容性**：若兩個維度都被映射到同一個結果維度，其長度必須相等，或其中一個是 1。

讓我們用 `linalg.generic` 的例子具體算：

```mlir
map_A = (d0, d1) -> (d0, d1)
map_B = (d0, d1) -> (d1)
map_C = (d0, d1) -> (d0, d1)
```

迭代空間由什麼決定？在 `linalg` 中，迭代空間的形狀是**由 outputs 與 inputs 共同推導**的：對每個 operand 的每個結果維度 $r$ ，取所有把迭代維度映射到 $r$ 的 operand 中，該 operand 對應維度的最大長度。

具體而言：

* 對 output $C$ ， $C$ 的 shape 是 $[4, 8]$ ， $C$ 的 map 用了 $d_0, d_1$ ，因此 $d_0 = 4$ 、 $d_1 = 8$ 。
* 對 input $A$ ， $A$ 的 shape $[4, 8]$ ，其 map 用了 $d_0, d_1$ ，一致。
* 對 input $B$ ， $B$ 的 shape $[8]$ ，其 map 只用了 $d_1$ ，因此 $B$ 的維度對應 $d_1 = 8$ ，一致。

若把 $B$ 改成 shape $[1]$ ，那麼 $d_1$ 就有兩個來源： $C$ 給 8、 $B$ 給 1。廣播規則取 8，並且 $B$ 在 $d_1$ 上是「size 1 可廣播到 8」。這正是 NumPy 的廣播語意。

在 MLIR 裡，這個檢查由 `linalg` 的 verifier 與 `mlir::linalg::verify` 家族完成；更具體的 shape 推導可透過 `mlir::linalg::inferContiguousShape` 或各個 named op 的 `inferReturnTypes` 取得。

## linalg.yield 的作用

`linalg.yield` 是 payload region 的 terminator。它的規則很簡單但語意關鍵：

* 每個 payload region **有且只有一個** `linalg.yield`（區塊結尾）。
* `linalg.yield` 恰好 yield **一個**值。
* 該值的型別必須與 op 的**輸出元素型別**相容。

`linalg.yield` 存在的原因是 payload region 的 block argument 數量等於「輸入加輸出的總數量」，而**輸出值**並不是 block argument——block arguments 給的是「累加前的元素值」（reduction 情況下）。`linalg.yield` 給出的是「累加後的元素值」。

在 reduction op 中，這個區別是本質的：

```mlir
%r = linalg.generic {
  indexing_maps = [affine_map<(d0, d1) -> (d0, d1)>],
  iterator_types = ["parallel", "reduction"]
} ins(%a : tensor<8xf32>) outs(%init : tensor<f32>) {
^bb0(%in: f32, %acc: f32):
  %s = arith.addf %in, %acc : f32
  linalg.yield %s : f32
} -> tensor<f32>
```

這裡的 block argument `%acc` 是「累加器目前累積到的值」（在區域外被視為 $0$ ），`%in` 是「當前被歸約的元素」。`linalg.yield %s` 給出「新的累加值」。

這種「迭代空間 + 映射 + 累加器初值」的組合，使得 **reduction 可以完全用第一類的 parallel loop 表達**——這正是 `linalg` 能被 tiling、vectorize 的原因。向量化一個 reduction 的做法是：把 reduction 維切成若干段，每段做一個「水平」的向量加法，最後再做一次水平歸約。

## DestinationStyleOpInterface

`linalg` 的一個關鍵設計是 `DestinationStyleOpInterface`。

「destination style」指的是 `linalg` op 的 operand 佈局：operands 被分成 **inputs** 與 **outputs**，其中 outputs 扮演「目的緩衝區」的角色——payload region 的 block argument 包含 output operand 的當前元素，op 的結果則是更新後的 output。

這個介面提供了統一的方法：

| 方法 | 意義 |
|---|---|
| `getIndexingMapsArray()` | 取得所有 operand 的 indexing map |
| `getIteratorTypesArray()` | 取得迭代維度類型 |
| `getNumLoops()` | 迭代空間維度數 |
| `getNumParallelLoops()` | parallel 維度數 |
| `getNumReductionLoops()` | reduction 維度數 |
| `getSlices()` | 取得每個 operand 對應的 `OpFoldResult` slice |
| `getStaticLoopRanges()` | 靜態迭代範圍 |
| `hasBufferSemantics()` | 是否為 buffer 語意 |
| `hasPureBufferSemantics()` | 純 buffer 語意（無 tensor/其他） |
| `hasPureTensorSemantics()` | 純 tensor 語意 |

這個介面讓**方言無關的最佳化 pass** 可以作用在 `linalg` op 上，而不必知道具體是哪個 named op。它也讓 `linalg` op 能與 `mlir::linalg::LinalgOp` 介面配合：`LinalgOp` 提供了 `getMatchingIndexingMap`、`getBlock` 等進階查詢。

一個實用的 C++ 片段：

```cpp
struct CountParallelLoops : public OpRewritePattern<linalg::GenericOp> {
  using OpRewritePattern::OpRewritePattern;
  LogicalResult matchAndRewrite(linalg::GenericOp op,
                                PatternRewriter &rewriter) const override {
    unsigned numParallel = 0;
    for (linalg::IteratorType it : op.getIteratorTypesArray()) {
      if (it == linalg::IteratorType::parallel)
        ++numParallel;
    }
    if (numParallel == 0)
      return rewriter.notifyMatchFailure(op, "no parallel loops");
    return failure();
  }
};
```

## 為什麼 linalg 是「編譯器友善」的

把前面幾點綜合，我們可以回答「為什麼不用 elementwise + broadcast 的通用表示」。

| 設計面向 | 通用 elementwise 表示 | linalg 表示 |
|---|---|---|
| 迭代空間 | 隱含在 broadcast 規則中 | 顯式的 affine map 列表 |
| reduction | 難以表達（需要額外維度 + 特殊 op） | 一等公民：`iterator_types = ["reduction"]` |
| 形狀相容性 | 執行期檢查 | 編譯期由 map 推導與驗證 |
| 最佳化粒度 | 逐 op | 整個 op 的迭代空間可一起重排 |
| 語意資訊 | 全部丟失 | 保留（named form）或可推導（generic form） |
| 專用 backend | 難 | 容易（matmul → MMA / BLAS） |

Linalg 專案最初由 Google 的 Yuze Luo 等人推動，其 rationale 文件明確主張：**運算的索引結構應當被顯式地表達為資料，而不是隱含在操作的執行順序中**。這與 [8.2](08.2-affine多面體模型.md) 的多面體模型是同一個思想的兩個投影。

## OpDSL：用 Python 定義 linalg op

`linalg` 方言的一個特色是 **OpDSL**——用 Python 定義結構化操作，自動生成 MLIR op 定義（TableGen）、C++ 類別與 dialect 註冊。

一個 OpDSL 定義大致長這樣：

```python
from mlir.ir import *
from mlir.dialects import linalg
from mlir.dialects.linalg import *
from mlir.dialects.arith import *
from mlir.dialects.math import *

GenericOp = linalg.GenericOp

def matmul_impl(a, b, c):
  """a: MxK, b: KxN, c: MxN -> 累加到 c"""
  return ArithAddfOp(c, ArithMulFOp(a, b))

def matmul(args, outs, attributes):
  a, b, c = args
  return matmul_impl(a, b, c)

MatMulOp = linalg.structured_op("MatMul",
    arguments=[("a", S32), ("b", S32), ("c", S32)],
    results=[("c", S32)],
    indexing_maps=[affine_map<(d0, d1, d2) -> (d0, d2)>,
                   affine_map<(d0, d1, d2) -> (d2, d1)>,
                   affine_map<(d0, d1, d2) -> (d0, d1)>],
    iterator_types=["parallel", "parallel", "reduction"],
    doc="矩陣乘法 c += a * b")
```

這裡的 `S32` 是一個 placeholder type，會被替換成具體的 element type。生成後的 dialect 會包含 `linalg.matmul` 這個 op，其 C++ accessor 與 verifier 都是自動產生的。

OpDSL 的價值在於**消除重複**。一個典型的深度學習框架裡有數百個結構化運算；手寫每個的 TableGen 定義、indexing map、iterator types、builder、verifier 是不現實的。OpDSL 把它們壓縮成一份可讀的宣告。

現代 MLIR 中，OpDSL 的部分功能已與 `mlir/python/mlir/dialects/linalg` 與 `mlir/test/python` 整合；CIRCT 專案也提供了更廣泛的 ODS 支援。

## named op 與 generic form 的取捨

實務上的取捨原則：

* **有專用 backend 或常見最佳化機會**的運算，值得有 named form：`matmul`、`conv`、`pool`、`fill`、`dot`。
* **長尾運算**（各種 activation、normalization 的變體），用 `linalg.generic` 就好，不要為每個都新增 named op，否則方言會爆炸。
* **需要精確控制 iteration order 的運算**（例如 softmax 的 max 與 sum 兩階段、或帶有跨維 reduction 的 layernorm），用 `linalg.generic` + 明確的 indexing map 比較誠實。
* **從上游方言降階而來**的運算，如果已經有對應的 named op，降階時應該產生 named op——這樣後續的專用最佳化才有機會。

一個重要的實務陷阱：named op 與 generic form 之間的轉換並非無成本。`linalg.matmul` → `linalg.generic` 是資訊**增加**（通用化），反方向則需要**語意識別**，通常由 pattern 完成，代價不小。實務上若一個 named op 在當前 pipeline 中沒有專用 lowering，直接用 `linalg.generic` 寫會更簡單。

## 完整的 linalg 範例

```mlir
#map = affine_map<(d0, d1, d2) -> (d0, d2)>
#map_b = affine_map<(d0, d1, d2) -> (d2, d1)>
#map_c = affine_map<(d0, d1, d2) -> (d0, d1)>

func.func @matmul_example(%a: tensor<64x32xf32>, %b: tensor<32x128xf32>,
                          %c: tensor<64x128xf32>) -> tensor<64x128xf32> {
  %r = linalg.matmul ins(%a : tensor<64x32xf32>)
                     ins(%b : tensor<32x128xf32>)
                     outs(%c : tensor<64x128xf32>) -> tensor<64x128xf32>
  return %r : tensor<64x128xf32>
}
```

以及一個純 generic 的版本，兩者在語意上等價：

```mlir
func.func @matmul_generic(%a: tensor<64x32xf32>, %b: tensor<32x128xf32>,
                           %c: tensor<64x128xf32>) -> tensor<64x128xf32> {
  %r = linalg.generic {
    indexing_maps = [#map, #map_b, #map_c],
    iterator_types = ["parallel", "parallel", "reduction"]
  } ins(%a : tensor<64x32xf32>)
    ins(%b : tensor<32x128xf32>)
    outs(%c : tensor<64x128xf32>) {
  ^bb0(%a_e: f32, %b_e: f32, %c_e: f32):
    %m = arith.mulf %a_e, %b_e : f32
    %s = arith.addf %c_e, %m : f32
    linalg.yield %s : f32
  } -> tensor<64x128xf32>
  return %r : tensor<64x128xf32>
}
```

## 小結與延伸閱讀

* Structured Op 把運算拆成三部分：**元素語意**（payload region）、**索引映射**（affine map）、**迭代維度類型**（parallel / reduction / window）。三者分離是 `linalg` 的核心設計。
* 索引映射把「語意」重新轉成「可最佳化的結構」：迴圈順序、維度可交換性、可融合性、形狀相容性都能從 affine map 推導。
* 通用 elementwise + broadcast 表示法會丟失全部語意資訊；named form 保留語意並能對接專用 backend，generic form 則提供統一入口。二者互補。
* `linalg.yield` 給出的是「累加後的元素值」，這使 reduction 得以用與 parallel 相同的機制表達，是 tiling 與 vectorization 能統一處理兩者的前提。
* `DestinationStyleOpInterface` 提供方言無關的存取（迭代維度數、map 列表、buffer/tensor 語意），讓通用 pass 不必認識具體 named op。
* OpDSL 以 Python 宣告 indexing map 與 iterator types，自動產生 TableGen 與 C++ accessor，解決長尾運算的定義成本。
