# 8.3 memref 方言：記憶體抽象與佈局

[7.1](07.1-tensor與結構化運算.md) 我們說過 `tensor` 是「不可變的數學值」，`memref` 是「可變的記憶體區域」，兩者之間需要一次 bufferization。本節要把 `memref` 這個方言徹底拆開：它的型別怎麼組成、佈局怎麼表達、操作有哪些、以及最關鍵的——**為什麼 bufferization 是 MLIR 中最難的問題之一**。

## 從 tensor 到 memref：一次語意的斷裂

先把兩者並排：

```mlir
// tensor 側
%t = tensor.empty() : tensor<128x256xf32>
%v = tensor.extract %t[%i, %j] : tensor<128x256xf32>

// memref 側
%m = memref.alloc() : memref<128x256xf32>
%v = memref.load %m[%i, %j] : memref<128x256xf32>
```

看起來只是換個關鍵字，但中間發生的事情完全不同：

| 面向 | tensor | memref |
|---|---|---|
| 值的本質 | 數學對象 | 記憶體區域 + 檢視資訊 |
| 內容何時決定 | 由建構 op 決定 | 由寫入決定 |
| 佔用記憶體 | 否（直到 bufferize） | 是 |
| 別名 | 無 | 有 |
| SSA 可行 | 是 | 否（同一 buffer 可被多次 store） |

SSA 在 memref 上「不可行」的精確意思是：SSA 保證「每個值只被賦值一次」，但 memref 的**內容**可以被多次修改。要讓 SSA 繼續成立，就必須把「buffer」與「buffer 的某個版本」區分開——這就是 `memref.subview` 與版本化的概念，也是 alias 分析存在的原因。

## MemRefType 的組成

一個 `MemRefType` 由四部分組成：

$$
\text{MemRefType} = (\text{element type},\ \text{shape},\ \text{layout},\ \text{memory space})
$$

在 MLIR 中，對應到 C++ API：

```cpp
MemRefType type = cast<MemRefType>(value.getType());
Type elemTy = type.getElementType();
ArrayRef<int64_t> shape = type.getShape();
MemRefLayoutAttrInterface layout = type.getLayout();
Attribute memorySpace = type.getMemorySpace();
```

### element type

元素型別是 `Type`（可能是 `f32`、`i8`、`index` 或 `!quant.any<i8:f32, 1.0>` 等）。它與 `tensor` 的 element type 共用同一套型別系統，這是 [7.1](07.1-tensor與結構化運算.md) 提過的設計結果。

### shape

形狀是 `ArrayRef<int64_t>`，其中 `ShapedType::kDynamic`（值為 $-1$ ）表示動態維度。

```cpp
for (int64_t d : type.getShape()) {
  if (d == ShapedType::kDynamic) { /* 動態維度 */ }
}
```

注意 memref 的 shape 與「實際記憶體大小」**不是同一件事**。形狀描述的是邏輯維度，而實際佔用的位元組數取決於 layout 與 element size。

### layout（佈局）

這是 memref 與 tensor 最關鍵的差異。layout 描述「邏輯索引如何映射到物理位元組」。

最常見的是 **strided layout**：

```mlir
memref<128x256xf32, strided<[256, 1], offset: 0>>
```

其語意是：形狀為 $(d_0, d_1)$ 的張量，第 $(i, j)$ 個元素的位元組偏移是：

$$
\text{offset}(i, j) = \text{base} + i \cdot s_0 + j \cdot s_1
$$

其中 $s_0 = 256$ 、 $s_1 = 1$ 、 $\text{base} = 0$ 。這是 row-major（又稱 C order）佈局。

也可以寫成**緊湊（compact / identity）** layout：

```mlir
memref<128x256xf32>
```

這等價於 `strided<[256, 1], offset: 0>`，其中 stride 由 shape 推導。

還有**動態 stride**：

```mlir
memref<128x256xf32, strided<[?, ?], offset: ?>>
```

stride 與 base 在執行期才確定，適用於外部系統提供的 buffer（如 BLAS 接受任意 stride 的矩陣）。

### memory space（記憶體空間）

這是 memref 獨有的維度，用來區分不同的位址空間：

```mlir
memref<1024xi8, 1>     // memory space 1
memref<1024xi8, 2>     // memory space 2
```

memory space 的編號是方言自定的。在 `gpu` 方言中，space 0 是 global、1 是 shared、2 是 constant、3 是 local。在 `spirv` 中有對應的 StorageClass。對一般的 CPU 編譯，memory space 0 就是普通記憶體。

在 `llvm` 方言中，memory space 最終映射到 LLVM 的 address space。

### Unranked memref

與 `UnrankedTensorType` 對稱，存在 `UnrankedMemRefType`（`memref<*xf32>`），用於 rank 在執行期才確定的情況。

## memref 的核心操作

### 配置（allocation）

```mlir
%m = memref.alloc() : memref<128x256xf32>
%d = memref.alloc(%size) : memref<?xf32>
```

`memref.alloc` 在堆積上配置記憶體，回傳一塊**擁有權**的 buffer。動態尺寸需要一個 `index` operand 指定元素數量。

`memref.alloca` 在**堆疊**上配置：

```mlir
%m = memref.alloca() : memref<128x256xf32>
```

`memref.alloca` 的生命週期受限於當前函式（或更精確地說，由 dialect 定義的語意決定）。在實務上，MLIR 裡 `alloca` 最終通常被 LLVM backend 提升成 stack allocation，但在有 `memref` 逃逸時會被提升成 heap。

### 存取

```mlir
%v = memref.load %m[%i, %j] : memref<128x256xf32>
memref.store %v, %m[%i, %j] : memref<128x256xf32>
```

索引的數量必須等於 memref 的 rank。

### 複製

```mlir
memref.copy %src, %dst : memref<128x256xf32> to memref<128x256xf32>
```

這個 op 值得注意：它的存在本身就暴露了 memref 語意的複雜性。在 LLVM IR 裡，複製一段記憶體需要一個迴圈（或 `llvm.memcpy`）。`memref.copy` 把這個需求提升到 IR 層。

### memref.global 與初始值

全域緩衝區用 `memref.global` 宣告：

```mlir
memref.global "private" constant @weights : memref<3x3xf32> = dense<1.000000e+00>
```

語法結構：

* `"private"` / `"public"` / `"external"`：可見性。
* `constant` / `mutable`：是否唯讀。
* `@weights`：符號名。
* 型別。
* `= dense<...>`：初始值。

`constant` 意味著這個 global 不可被修改，LLVM backend 會把它放在唯讀的 section 裡。

取得 global 的句柄：

```mlir
%g = memref.get_global @weights : memref<3x3xf32>
```

`memref.get_global` 只取得「view」，不複製內容。

### subview 與 reinterpret_cast

`memref.subview` 取出 buffer 的一個子區域：

```mlir
%sv = memref.subview %m[0, 0] [4, 4] [1, 1] : memref<128x256xf32> to memref<4x4xf32, strided<[256, 1], offset: ?>>
```

四個參數：offsets、sizes、strides。結果的 layout 必須與原 memref 相容——注意結果的 stride 通常**不會被壓縮**（上例中的 stride 仍是 `[256, 1]`，即使 shape 變成 $4 \times 4$ ），因為 subview 是在**同一塊記憶體**上的一個視窗。

`memref.reinterpret_cast` 則是在**位元組層級**重新解讀：

```mlir
%rc = memref.reinterpret_cast %m : memref<128x256xf32> to memref<32768xi8>
```

這用於把 `f32` 陣列視為 `i8` 陣列（常見於 SIMD 或序列化）。

### memref.cast

`memref.cast` 在**相容**的 memref 型別之間轉換：

```mlir
%c = memref.cast %m : memref<?x?xf32> to memref<128x256xf32>
```

語意上相容包含幾個條件：element type 相同、shape 與 stride 相容（動態與靜態可以互相轉換）、memory space 相同。具體規則是：**目標型別的每個維度若為靜態，必須與來源在執行期相容**；若目標是動態，則恆成立。

`memref.cast` 是需要執行期檢查的操作（若來源形狀實際不符）。verifier 只檢查靜態可判定的部分。

### expand_strided_metadata

`memref.expand_strided_metadata` 把一個「緊湊但被視為 strided」的 memref 展開成明確帶 stride 的形式：

```mlir
%expanded, %offset, %sizes, %strides = memref.expand_strided_metadata %m
    : memref<128x256xf32> to memref<128x256xf32, strided<[?, ?], offset: ?>>
```

它的用途是**讓 layout 資訊顯式化**，以便於後續的位址計算與向量化的 stride 檢查。

### memref.tensor_load 與 tensor_store

這兩個 op 位於 `bufferization` 方言（不是 `memref`），提供 tensor 與 memref 之間的個別元素轉移：

```mlir
%v = bufferization.tensor_load %t[%i, %j] : tensor<128x256xf32>
bufferization.tensor_store %v, %t[%i, %j] : tensor<128x256xf32>
```

它們是 bufferization 過程中的過渡形式，最終會被完全消除。

## 佈局推導與 stride 計算

當 memref 被建立時，它的 layout 需要被決定。這是「bufferization 的佈局決策」部分。

以 `memref.alloc() : memref<128x256xf32>` 為例，預設 layout 是 identity（緊湊 row-major），stride 為 $[256, 1]$ 。

但如果一個 `tensor` 經過 `tensor.transpose` 或 `tensor.extract_slice` 之後被 bufferize，layout 可能變成非緊湊的：

```mlir
原始:  A: tensor<4x8xf32>
轉置:  A^T: tensor<8x4xf32>
```

若 A 的 layout 是 row-major $[8, 1]$ ，則 A^T 對應的 memref layout 是 **column-major** $[1, 8]$ ，stride 為 $[1, 8]$ 而不是緊湊的 $[4, 1]$ 。

這是一個關鍵的權衡：

* **緊湊 layout**：向量化的 load/store 更快（連續），但若後續運算需要另一種 layout，就要做昂貴的 layout conversion（實際上是一個 transpose）。
* **保留原 layout**：省下轉換，但可能讓後續的向量化變慢。

MLIR 的 bufferization 對此有不同策略：
* **完整 bufferization**（OneShotBufferize）預設嘗試**保持原 layout**，讓 layout conversion 留給後面的 `memref` 相關 pass 處理。
* 也可以選擇「把所有 tensor 統一成某個固定 layout」，代價是可能插入昂貴的轉換。

### stride 計算的程式碼層面

在 C++ 中，memref 的位址計算是透過 `getStridesAndOffset` 這類 API 完成的：

```cpp
SmallVector<int64_t> strides;
int64_t offset;
if (failed(getStridesAndOffset(type, shape, strides, offset)))
  return failure();
```

`getStridesAndOffset` 這個函式的存在就說明了一切：**對一個 memref 的隨機存取，必須知道 stride 與 offset 才能算出位址**。若 stride 是動態的，就必須在執行期從 memref 描述符讀出。

對應到 LLVM dialect，每個 memref 的描述符是一個 struct：

```mlir
// 一個 memref<128x256xf32> 在 LLVM dialect 中是
// { ptr, offset, size1, stride1, size2, stride2 }
```

而位址計算是 `llvm.getelementptr`。

## memref 到 LLVM dialect 的降階

`memref.load` 降階成 `llvm.getelementptr` + `llvm.load`：

```mlir
// memref.load %m[%i, %j] : memref<128x256xf32>
%ptr = llvm.getelementptr %m[%i, %j] : memref<128x256xf32> -> !llvm.ptr
%v = llvm.load %ptr : !llvm.ptr -> f32
```

`llvm.getelementptr` 是關鍵：它接收一個 memref 的描述符、一組索引，產生指向元素的指標。在 LLVM dialect 中，memref 的描述符被分解成：

* 一個 `!llvm.ptr`（基底指標）
* 一個 `index`（offset）
* 每個維度一對 `(size, stride)`

`llvm.getelementptr` 的簽名反映了這個結構：

```mlir
%ptr = llvm.getelementptr %base[%i, %j] : memref<?x?xf32> -> !llvm.ptr
```

注意 memref 的索引在降階時通常先被轉成 `index` 型別，而 LLVM 的 GEP 索引是 `i64`。

降階後，一個二維 memref 的存取會變成：

```mlir
addr = base + offset + i*stride0 + j*stride1
```

在 LLVM IR 中，若 stride 是常數，會被折疊成常數乘法；若 stride 是動態的，則是實際的乘法指令。

## 為什麼 bufferization 是 MLIR 最難的問題之一

現在我們可以正面回答這個問題。讓我們把它拆成幾個子問題。

### 子問題一：從值到 buffer 的映射

一個 `tensor` 是一個值。要把它變成 buffer，需要決定：

1. 這個 tensor 的 buffer 從哪來？（`memref.alloc`？重用某個輸入的 buffer？）
2. 這個 buffer 的 layout 是什麼？
3. 這個 buffer 的生命週期是多久？誰負責釋放？

第 3 點尤其麻煩。一個複雜的 tensor 計算圖中，同一個 buffer 可能在多處被使用。若每個 tensor 都配一塊新 buffer，會有大量配置；若重用，則需要確認重用是安全的。

### 子問題二：alias 分析

這是核心。讓我們用一個例子說明為什麼它非做不可。

```mlir
func.func @f(%a: tensor<4xf32>, %b: tensor<4xf32>) -> tensor<4xf32> {
  %0 = tensor.extract_slice %a[0] [2] [1] : tensor<4xf32> to tensor<2xf32>
  %1 = tensor.extract_slice %b[0] [2] [1] : tensor<4xf32> to tensor<2xf32>
  %2 = tensor.add %0, %1 : tensor<2xf32>
  %3 = tensor.insert_slice %2 into %b[2] [2] [1] : tensor<2xf32> into tensor<4xf32>
  return %3 : tensor<4xf32>
}
```

在 bufferization 時，若 `%a` 的 buffer 被重用為 `%2` 的輸出 buffer，然後 `%3` 又要寫進 `%b` 的 buffer——而 `%b` 的 buffer 與 `%a` 的 buffer 恰好重疊（因為 `%a` 是 `%b` 的 subview），就會產生錯誤。

在 **value 語意**下，這段程式碼完全安全：所有 tensor 都是不可變的值，`%0` 與 `%1` 是兩個獨立的值。問題只在下到 buffer 層時才出現。

因此 bufferization **必須**回答：「哪些 `tensor.extract_slice` / `tensor.insert_slice` 的來源與目標在執行期可能重疊？」

這就是 alias 分析。而 alias 分析的經典結果是「可能重疊」的保守回答——在沒有更強資訊時，一律假設可能重疊。這會讓 bufferization 變得保守、插入大量不必要的 copy。

### 子問題三：ownership 與 in-place

與 alias 相關的另一個問題是**誰擁有 buffer**。

若一個 op 的輸出直接寫進它的輸入 buffer（in-place），就省下一次配置與一次拷貝。但要這麼做，必須確認：

* 輸入 buffer 沒有其他活的使用者（last use）。
* 輸入與輸出的 shape 相容。
* 輸入不是唯讀的（例如 function argument 可能被 caller 使用）。

MLIR 的 `bufferization` 有 `bufferization.writable` 屬性來表達「這個 memref 的內容可以被修改」。`bufferization` 方言的 `isWritable` 查詢就是基於此。

### 子問題四：副作用的可見性

`memref.store` 有副作用。在 value 世界裡沒有副作用，因此 bufferization 必須**保證**所有可能的副作用都被正確表達。這意味著 bufferization 不是單純的「局部替換」，而是一個全域的資料流分析。

### MLIR 的解法：OneShotBufferize

MLIR 的現行解法是 `bufferization` 方言的 **One-Shot Bufferize** pass。與傳統的逐步轉換不同，它是「一次性的」：整個 bufferization 在一個 pass 內完成。

原因是逐步轉換需要中間表示（例如 `tensor.alloc_tensor`、`memref.tensor_store` 之類的 placeholder op），會讓 IR 膨脹且難以最佳化。One-Shot 的做法是：

1. **先做完整的分析**：alias 分析（`bufferization::AliasAnalysis`）、ownership 分析、等價類劃分。
2. **然後一次性改寫**：把每個 tensor 值替換成一個 memref，插入必要的 `bufferization.clone` / `bufferization.copy` op。

`bufferization.clone` 是一個 placeholder op，代表「這裡需要一個 memref 副本，但實際的 copy 還沒決定」：

```mlir
%m = bufferization.clone %t : tensor<4xf32> to memref<4xf32>
```

後續的 `bufferization-dealloc` 等 pass 會把它們替換成真正的 `memref.copy` 或直接移除（若分析判定不需要）。

在 C++ 中的相關介面：

```cpp
// 執行 bufferization
bufferization::OneShotAnalysisState state(op->getBlock());
bufferization::populateBufferizationAnalysisPatterns(op, state);
// ...
bufferization::runOneShotBufferize(op, state);
```

`OneShotAnalysisState` 內含 `bufferization::AliasAnalysis` 與 `bufferization::InPlaceAnalysis` 兩個分析結果。

### bufferization 的分析選項

One-Shot Bufferize 有幾個關鍵選項：

* `bufferize-function-boundaries`：把 `func.func` 的 `tensor` 參數轉成 `memref` 參數。這是最常用的選項。
* `unknown-type-conversion`：遇到無法轉換的 op 時，是丟棄還是報錯。
* `allow-return-allocs`：允許函式回傳 `memref.alloc` 的結果（搭配 `ownership` 系統）。
* `function-boundary-type-conversion`：把函式邊界的參數與回傳值一併轉換。

## aliasing 與 bufferization 的關係：更一般的視角

前面把 alias 分析當成 bufferization 的子問題。但更一般地看：**alias 是 buffer 世界的一級公民**。

LLVM IR 裡的 alias 有三個層次：

1. `noalias` 屬性：兩個指標不指向重疊的記憶體。
2. `readonly` / `writeonly`：只讀或只寫。
3. 型別系統本身：不同的 pointer type 在語意上不 alias。

在 MLIR 的 memref 世界裡，alias 的表達方式有：

* `memref.subview` 建立的視圖**必然**與來源 alias。
* `memref.reinterpret_cast` 建立的視圖必然 alias。
* `memref.alloc` 建立的 buffer 與其他所有 buffer **不 alias**（除非透過 subview 鏈）。
* `memref.get_global` 取得的是一個唯一的全域 buffer。

`bufferization` 的 alias 分析就是建立這些關係的圖。

## 另一個角度：為什麼 memref 不能取代 tensor

如果 memref 已經能表達一切，為什麼還需要 tensor？

三個理由：

**理由一：SSA 與可組合性。** 在 memref 世界裡，「讀一個元素、寫回」需要一個可變的緩衝區加索引。這使得很多純計算必須被表達成「配置 + 寫入」的樣子，IR 變得冗長，且可組合性差。

**理由二：最佳化空間。** 我們在 [7.1](07.1-tensor與結構化運算.md) 已經說過：在 buffer 之前做最佳化（重排、融合、layout 決定）空間大得多。

**理由三：來源語意的直接性。** 機器學習框架的 IR 本來就是 value-based 的；把它們轉成 buffer-based 需要一整套轉換，而 bufferization 正是 MLIR 中最複雜的部分之一。

**代價**：MLIR 因此有兩套表達同一件事的機制，且必須維護 bufferization 的正確性。這是「漸進式降階」這種架構的固有成本。

## memref.global 與初始值的細節

`memref.global` 的初始值是 `ElementsAttr`，即 dense attr：

```mlir
memref.global "private" constant @w : memref<2x2xf32> = dense<[[1.0, 2.0], [3.0, 4.0]]>
memref.global "private" constant @z : memref<4xi8> = dense<[1, 2, 3, 4]>
memref.global "private" constant @e : memref<f32> = dense<0.0>
```

`dense<>` 的語法是 dense attr 的字面形式。若初始值全零，可以寫 `dense<0.0>`。

`memref.global` 的另一種形式是「只有宣告，初始化在別處」：

```mlir
memref.global "external" mutable @input_buf : memref<1024xf32>
```

這用於連接外部系統提供的緩衝區。

## 一個完整的 memref 範例

```mlir
memref.global "private" constant @kernel : memref<3x3xf32> = dense<1.0>

func.func @memref_example(%in: memref<?x?xf32>, %out: memref<?x?xf32>) {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %m = memref.dim %in, %c0 : memref<?x?xf32>
  %n = memref.dim %in, %c1 : memref<?x?xf32>

  %buf = memref.alloc(%m) : memref<?xf32>
  memref.copy %in, %buf : memref<?x?xf32> to memref<?xf32>

  scf.for %i = %c0 to %m step %c1 {
    %k = memref.load @kernel[%i] : memref<3x3xf32>
    %v = memref.load %buf[%i] : memref<?xf32>
    %s = arith.mulf %v, %k : f32
    memref.store %s, %out[%i] : memref<?xf32>
  }
  memref.dealloc %buf : memref<?xf32>
  return
}
```

## 實務注意事項

* **`memref.alloc` 的記憶體生命週期。** 沒有 `memref.dealloc` 的 alloc 會造成洩漏。MLIR 有 `bufferization-dealloc` 與 `-ownership-based-dealloc` 之類的 pass 協助。
* **不要手寫 `memref.cast` 來「修正」形狀。** 若你發現需要 `memref.cast`，多半是上游的 shape 推導有問題。
* **`memref.subview` 的結果 layout 不會被壓縮。** 若需要緊湊的 subview，得先 copy。
* **dynamic stride 的成本。** 動態 stride 會讓位址計算無法折疊成常數乘法，在 hot loop 中代價明顯。
* **優先讓 bufferization 決定佈局。** 手動插入 `memref.cast` 與 `memref.transpose` 會破壞 bufferization 的分析。

## 小結與延伸閱讀

* `MemRefType` 由 element type、shape、layout、memory space 四部分組成；layout（尤其 strided layout）承載了 tensor 刻意捨棄的資訊。
* `memref` 的核心操作涵蓋配置（`alloc`/`alloca`）、存取（`load`/`store`）、複製（`copy`）、視窗（`subview`/`reinterpret_cast`）、型別轉換（`cast`）、metadata 展開（`expand_strided_metadata`）與全域（`global`/`get_global`）。
* 佈局選擇是 bufferization 的核心決策之一：緊湊 layout 利於向量化，保留原 layout 可省下 layout conversion，兩者需權衡。
* memref 降到 LLVM dialect 靠 `llvm.getelementptr` + `llvm.load`/`llvm.store`，memref 描述符被分解成 base 指標、offset 與每維的 (size, stride)。
* Bufferization 難在四個子問題：值到 buffer 的映射、alias 分析、ownership 與 in-place 判斷、以及副作用可見性。MLIR 的 One-Shot Bufferize 以「先全域分析、再一次性改寫」的方式處理。
* 根本原因是 tensor 與 memref 的語意落差：value 語意天然無 alias，buffer 語意天然有 alias，因此兩者之間的轉換必然需要 alias 分析。
