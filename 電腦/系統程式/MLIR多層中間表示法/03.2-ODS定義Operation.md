# 3.2 使用 ODS 定義 Operation、Trait 與型別

## 上一節留下的問題

[3.1](03.1-為什麼需要TableGen.md) 我們建立了「ODS 是 single source of truth」的觀念：TableGen 把 operation 的**結構**抽成模板，工具鏈負責產生 C++。但 ODS 本身到底長什麼樣？一個 `def` 的每一個欄位意味著什麼？`traits` 這個清單裡可以放哪些東西？`assemblyFormat` 的字串語法怎麼對應到實際的組語外觀？這些問題不解決，讀者就算讀懂 TableGen 也寫不出一個 op。

本節的目標是：讀完後，能夠從零寫出一個可執行、可解析、可驗證的 operation，並且清楚知道「哪些部分 ODS 能管、哪些部分必須自己寫」。

在 MLIR 的主線上，本節位於「抽象 → 機制」的轉折點：Operation 是一切皆 Operation 的產物，而 ODS 是讓 Operation 這個抽象**可被大量生產**的工廠。

## 一個 op 的解剖：欄位逐一說明

先看完整的 ODS 定義，本節後面會逐欄位拆解：

```tablegen
// include/mlir/Dialect/My/MyOps.td
include "mlir/IR/OpBase.td"
include "mlir/IR/SymbolInterfaces.td"

def My_Dialect : Dialect {
  let name = "my";
  let cppNamespace = "::mlir::my";
  let summary = "A toy dialect used for demonstration";
}

class My_Op<string mnemonic, list<Trait> traits = []>
    : Op<My_Dialect, mnemonic, traits>;

def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let summary = "Adds two operands";
  let description = [{
    The `my.add` operation adds its two operands and produces a single result
    of the same type.

    Example:

    ```mlir
    %0 = my.add %a, %b : i32
    ```
  }];

  let arguments = (ins AnySignlessIntegerOrFloatLike:$lhs,
                        AnySignlessIntegerOrFloatLike:$rhs);
  let results = (outs AnySignlessIntegerOrFloatLike:$result);

  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
```

### `def My_Dialect : Dialect`

`Dialect` 是一個 ODS class，代表「一個方言」。`let name` 是**組語層**的方言前綴（`my.`），`let cppNamespace` 是 **C++ 層**的命名空間（`::mlir::my`）。兩者刻意分離，是因為組語名稱是穩定的使用者介面，而 C++ 命名空間可以隨專案重構而變動。

`let summary` 與 `let description` 會出現在產生的文件中。

### `class My_Op<string mnemonic, list<Trait> traits = []> : Op<My_Dialect, mnemonic, traits>;`

這行是整個方言的關鍵。它做三件事：

1. 定義一個**模板 class**，參數是 op 的組語助記符與 trait 清單。
2. 把 `Op` 的第一個參數綁定為 `My_Dialect`，因此這個 class 裡的每個 `def` 自動屬於 `my` 方言——不需要每次寫 `My_Dialect`。
3. 把 `traits` 傳遞下去。

`Op` 的完整簽名是：

```tablegen
class Op<Dialect dialect, string mnemonic, list<Trait> traits = [], list<OpInterface> interfaces = []> {
  string summary = ?;
  string description = ?;
  string mnemonic = ?;
  list<Trait> traits = [];
  list<OpInterface> interfaces = [];
  list<OpArgument> arguments = [];
  list<OpResult> results = [];
  list<OpVariadicResult> variadicResults = [];
  string assemblyFormat = ?;
  list<OpBuilder> builders = [];
  string extraClassDeclaration = ?;
  string hasVerifier = 0;
  string hasFolder = 0;
  string hasCanonicalizer = 0;
  string hasCanonicalizeMethod = 0;
  string skipDefaultBuilders = 0;
  bit isTerminator = 0;
  bool isTerminator = false;
  ...
}
```

`?` 是 TableGen 的「未設定」預設值——它表示「這個欄位必須由使用者指定，否則產生器會報錯」。這是 TableGen 的一種型別檢查機制：`string summary = ?` 表示必須給字串，`bit isTerminator = 0` 表示不給就當 0。

### `def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]>`

`def` 產生的名稱 `AddOp` 同時是 **TableGen 記錄名**與 **C++ 類別名**。ODS 產生器會用它來命名 `class AddOp`、`AddOp::parse`、`AddOp::build`。這是刻意的：ODS 記錄與 C++ 類別的一對一對應，讓除錯時看到 `AddOp::build` 就知道是哪個 `def`。

`mnemonic` 是 `"add"`，組語名稱會是 `my.add`（dialect 名 + `.` + mnemonic）。

`traits` 是一個 trait 清單。trait 是**語意限制的標記**，分成兩大類：

* **原生 trait**（`mlir::OpTrait::`）：由 MLIR 核心定義，控制 IR 結構合法性的規則。
* **介面 trait**（`mlir::OpInterface::`）：由 ODS 產生，表示此 op 支援某組能力。

### `let arguments = (ins ...)` / `let results = (outs ...)`

這是 ODR（Operation Definition Rules）的核心語法。`(ins ...)` 與 `(outs ...)` 括號內的內容在 TableGen 內部其實是一個 `dag` 記錄，由 ODR 定義其文法。

每一個元素的形式是：

```
<型別約束>:<名稱>
```

型別約束（type constraint）決定了「這個 operand/result 的型別必須滿足什麼條件」。MLIR 內建了幾百種型別約束，在 `mlir/IR/CommonTypeConstraints.td` 與 `mlir/IR/OpBase.td` 中定義。最常用的幾個：

| 型別約束 | 意義 |
| --- | --- |
| `AnyType` | 任意型別 |
| `AnyIntegerType` | 任意整數型別（含有號/無號/任意精度） |
| `AnySignlessIntegerType` | 任意無符號整數型別（i32、i64…） |
| `AnySignlessIntegerOrFloatLike` | 整數或浮點，且「like」表示寬度可被推導 |
| `AnyFloatType` | 任意浮點型別 |
| `AnyTensorType` | 任意 `RankedTensorType` 或 `UnrankedTensorType` |
| `AnyRankedTensorType` | 任意有 rank 的張量型別 |
| `AnyMemRefType` | 任意 memref 型別 |
| `AnyFunctionType` | 函式型別 |
| `StrAttr` | 字串屬性 |
| `I32Attr` | i32 整數屬性 |
| `DenseI32ArrayAttr` | `DenseI32ArrayAttr` 型別的屬性 |

ODS 也允許自訂型別約束，把 C++ 的 `TypeConstraint` 類別鏡射進來：

```tablegen
def MyTensorType : Type<CPred<"$_self.isa<::mlir::RankedTensorType>()">,
                             "a ranked tensor type">;

def MyOp : My_Op<"foo"> {
  let arguments = (ins MyTensorType:$input);
  let results = (outs AnyType:$output);
}
```

### `let assemblyFormat`

宣告式組裝格式（declarative assembly format）。這是 ODS 最容易被低估但最重要的功能之一：在 2019 年之前，每個 MLIR op 的 `parse`/`print` 都是手寫的 C++，數千行程式碼重複著同樣的樣板。`assemblyFormat` 把常見形狀變成一行字串。

### `let builders`

ODS 可以為 op 產生額外的 `build` 方法。build 方法是「**從具名參數建構 op**」的便利層，避免呼叫端寫 `OperationState` 的細節：

```tablegen
def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let arguments = (ins AnySignlessIntegerOrFloatLike:$lhs,
                        AnySignlessIntegerOrFloatLike:$rhs);
  let results = (outs AnySignlessIntegerOrFloatLike:$result);

  let builders = [
    OpBuilder<(ins "Value":$lhs, "Value":$rhs, "Type":$resultType), [{
      build($_builder, $_state, ValueRange{lhs, rhs}, resultType);
    }]>,
    OpBuilder<(ins "Value":$lhs, "Value":$rhs), [{
      build($_builder, $_state, lhs, rhs, lhs.getType());
    }]>,
  ];
}
```

`OpBuilder` 的第一個參數是「建構函式的參數清單」（用 C++ 簽名字串表示），第二個是函式體（TableGen 裡的字串，可以是 `[{ ... }]` 的區塊形式）。`$_builder`、`$_state` 是隱式的建構環境變數。

注意第二個 builder 示範了 ODS 的**推導能力**：`SameOperandsAndResultType` trait 讓產生器知道 result 型別可以從 operand 推導，因此可以自動產生「不指定 result 型別」的 builder。

### `let extraClassDeclaration`

逃生門：在產生的 op 類別裡貼上任意 C++ 宣告。這是 ODS 與手寫 C++ 之間的受控介面：

```tablegen
def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let extraClassDeclaration = [{
    /// 判斷是否為恆等加法（其中一個 operand 為零）
    bool isIdentityAdd(mlir::Operation *op) const {
      return mlir::matchPattern(op->getOperand(1), m_Zero());
    }
  }];
}
```

## 三大類 argument constraint

ODS 對 operand/result 的約束不只「型別條件」，還有**數量**與**結構**條件。

### Variadic

Variadic 表示「這個參數可以出現 0 到多次」。ODS 語法是把型別約束換成一個包裝類別：

```tablegen
def CallOp : My_Op<"call", [CallOpInterface]> {
  let arguments = (ins FlatSymbolRefAttr:$callee, Variadic<AnyType>:$args);
  let results = (outs Variadic<AnyType>:$results);
}
```

`Variadic<T>` 展開後的 C++ 型別是 `::mlir::Operation::operand_range`（取值時）或 `::mlir::MutableOperandRange`（建構時），accessor 名為 `getArgs()` / `getArgsMutable()`。

Variadic 帶來一個**次序問題**：如果一個 op 同時有固定數量的 operand 與 variadic operand，IR 裡必須記住「variadic 段有多長」。ODS 透過 operand segment 機制解決：

```tablegen
def MyOp : My_Op<"mixed"> {
  let arguments = (ins AnyType:$fixed, Variadic<AnyType>:$variadic);
  let traits = [AttrSizedOperandSegments];
}
```

`AttrSizedOperandSegments` 是一個 trait，它讓 op 多帶一個 `operandSegmentSizes` 屬性（例如 `[1, 3]`），告訴 parser 前面 1 個 operand 屬於 `$fixed`，後面 3 個屬於 `$variadic`。ODS 據此產生 `getODSOperandIndexAndLength(index)` 這類映射函式。

### Optional

Optional 表示「這個參數可以不出現」。ODS 語法是 `Optional<T>`：

```tablegen
def LoadOp : My_Op<"load"> {
  let arguments = (ins AnyMemRef:$memref, Optional<AnyIndex>:$indices);
  let results = (outs AnyType:$value);
}
```

`Optional<T>` 展開後的 C++ 型別是 `::mlir::Value`（可能為 null），accessor 是 `getIndices()` 回傳 `::mlir::Value`（單值），或 `getIndicesMutable()`。

### 數量約束與 `SameOperandsAndResultType`

除了 variadic/optional，還有「恰好 N 個」的約束。ODS 用 `AttrSizedOperandSegments` 之外的 trait 表達：

```tablegen
def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let arguments = (ins AnySignlessIntegerOrFloatLike:$lhs,
                        AnySignlessIntegerOrFloatLike:$rhs);
  let results = (outs AnySignlessIntegerOrFloatLike:$result);
}
```

`SameOperandsAndResultType` 表示「所有 operand 與所有 result 必須同型」。ODS 據此自動產生：

* `verify()`：檢查型別一致。
* `build(builder, state, Value lhs, Value rhs)`：result 型別由 operand 推導。
* `getOperation()->getResultTypes()` 的推導。

而「恰好兩個 operand」這個約束，是由 ODS 從 `arguments` 清單的長度推導出來的：宣告了兩個 operand 就是恰好兩個，不需要另外寫 trait。（對照 `mlir::OpTrait::NOperands<2>::Impl`，那是在**手寫 C++** 風格裡的等價寫法，ODS 會自動選擇。）

## Trait 全景

Trait 是附在 op 上的「行為與限制標記」。MLIR 核心的原生 trait 分成三大類。

### 一、影響 IR 合法性的 trait

| Trait | 意義 |
| --- | --- |
| `Pure` | 不修改全域狀態，輸出只依賴輸入；可被 DCE 刪除 |
| `ConstantLike` | 是常數；`getConstantValue` 有意義 |
| `HasParent<"N">` | 必須直接位於 `N` 這個 op 之下 |
| `HasParent` | 必須有父 op |
| `IsTerminator` | 是 block 的 terminator |
| `ZeroRegions` / `OneRegion` / `VariadicRegions` | region 數量約束 |
| `SameOperandsAndResultType` | 所有 operand/result 同型 |
| `SameTypeOperands` | 所有 operand 同型（但可與 result 不同型） |
| `TypesMatchWith<...>` | operand 與 result 型別之間的轉換規則 |
| `AttrSizedOperandSegments` | 需要 operand segment 大小屬性 |
| `ZeroResults` / `OneResult` | result 數量約束 |
| `NoTerminator` | block 不需要 terminator |
| `SingleBlockImplicitTerminator<"Op">` | 單一 block，且有隱式 terminator |
| `MultiBlockImplicitTerminator<"Op">` | 多 block，有隱式 terminator |
| `RegionKindInterface` 相關 | region 結構是 SSACFG 或 Graph |

### 二、影響**最佳化與分析**行為的 trait

這一類最具策略性——它們不改變 IR 的合法性，但改變**其他 pass 如何對待這個 op**。

`Pure` 是最典型的一個。它讓 MLIR 的 DCE（dead code elimination）可以刪除沒有使用者的 pure op，也讓「把 op 提升/下沉到迴圈」的各種 pass 有依據。

`ConstantLike` 讓 `OperationFolder`（operation folder）能把 `arith.constant` 之類的 op 折疊成常數屬性。

`IsTerminator` 是 CFG 建構的基礎：`SuccessorOperands` trait 決定「從這個 op 可以走到哪些 block」。

`SingleBlockImplicitTerminator<"Op">` 是一個非常實用的語意工具。它表示：「這個 op 的 body region 必定只有一個 block，且該 block 的 terminator 必定是 `Op`；如果使用者沒寫 terminator，parser 會自動補上。」`scf.execute_region`、`func.func` 之類都用得上。

### 三、介面 trait（ODS 產生）

ODS 產生的介面 trait，例如 `DeclareOpInterfaceMethods<SymbolOpInterface>`，讓 op 宣告「我實作了某介面」，並讓 ODS 產生介面方法的預設 stub。

### 一個使用多個 trait 的實例

```tablegen
def LoadOp : My_Op<"load", [
    Pure,
    MemRefsNormalizable,
    AttrSizedOperandSegments,
    DeclareOpInterfaceMethods<MemoryEffectOpInterface>,
]> {
  let arguments = (ins Arg<AnyMemRef, "the memory to read from", [MemRead]>:$memref,
                        Variadic<AnyIndex>:$indices);
  let results = (outs AnyType:$value);
}
```

這裡的 `Arg<...>` 是 ODS 的進階 argument 描述形式，允許同時指定型別約束、說明文字、以及**記憶體效果**（`[MemRead]`）。記憶體效果讓 MLIR 能做 alias analysis 與 effect-based transformation（bufferization 就重度依賴它）。

## `assemblyFormat` 的宣告式語法

這是 ODS 中最需要仔細學的部分，因為它是 MLIR 組語外觀的直接決定者。

### 基本元素

| 元素 | 意義 |
| --- | --- |
| `$x` | 綁定到名為 `x` 的 operand 或 result（依 context 決定） |
| `type($x)` | 列印/解析 operand `x` 的型別 |
| `attr-dict` | 省略的屬性字典（`{...}`），自動解析與列印 |
| `` `literal` `` | 固定字面文字 |
| `oilist` / `custom<...>` | 自訂子格式 |

### 一個完整例子

```tablegen
let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
```

對應的組語：

```mlir
%0 = my.add %a, %b {tag = 1} : i32
```

ODS 據此產生對稱的 `parse` 與 `print`：

```cpp
::mlir::ParseResult AddOp::parse(::mlir::OpAsmParser &parser,
                                 ::mlir::OperationState &result) {
  ::mlir::OpAsmParser::UnresolvedOperand lhs, rhs;
  ::mlir::Type lhsType, rhsType;
  if (parser.parseOperand(lhs) ||
      parser.resolveOperand(lhs, lhsType, result.operands))
    return ::mlir::failure();
  if (parser.parseComma() ||
      parser.parseOperand(rhs) ||
      parser.resolveOperand(rhs, rhsType, result.operands))
    return ::mlir::failure();
  if (parser.parseOptionalAttrDict(result.attributes))
    return ::mlir::failure();
  ::mlir::Type resultType;
  if (parser.parseColonType(resultType))
    return ::mlir::failure();
  return ::mlir::success();
}

void AddOp::print(::mlir::OpAsmPrinter &p) {
  p << " ";
  p.printOperand(getLhs());
  p << ", ";
  p.printOperand(getRhs());
  p.printOptionalAttrDict((*this)->getAttrs());
  p << " : ";
  p.printType(getResult().getType());
}
```

### 關鍵語法：operands 與 results 的方向性

ODS 有一個容易踩雷的地方：在 `assemblyFormat` 裡，`$name` 指的是**operand**（`arguments` 清單）或 **result**（`results` 清單），取決於**哪一邊需要這個名字**。當 operand 與 result 名字相同（常見：兩邊都叫 `$value`），ODS 會要求你明確指定方向：

```tablegen
// 明確區分
let assemblyFormat = "$input attr-dict `:` `(` type($input) `->` type($output) `)`";
```

ODS 對此的規則是：如果名稱在 operands 與 results 中重複，且出現在 operand 位置，ODS 會發出警告要求改用 `qualified` 語法。現代 ODS 提供：

```tablegen
let assemblyFormat = "$input `:` type($input) `->` type($output)";
```

這裡 `type($input)` 明確表示「印 input 的型別」，而 `$input` 出現在 operand 位置。ODS 會產生一個警告編譯選項 `ODS` 的 `hasInvalidTypeBuilder` 檢查。

### `custom<...>` 關鍵字

當宣告式語言不足以描述時，退回手寫：

```tablegen
def SwitchOp : My_Op<"switch"> {
  let arguments = (ins AnyType:$value, Variadic<AnyType>:$cases);
  let results = (outs Variadic<AnyType>:$results);
  let assemblyFormat = "custom<SwitchOp>($value, $cases, $results)";
}
```

`custom<SwitchOp>(...)` 表示「遇到這段時，呼叫 `SwitchOp::parseSwitchOp` / `SwitchOp::printSwitchOp` 這些靜態函式」。ODS 會自動產生指向這些函式的膠水碼。

`custom` 也支援帶 directive 的形式：

```tablegen
let assemblyFormat = "custom<MyAttr>($value) `:` type($result)";
```

`custom<MyAttr>` 會去尋找 `MyAttr::parse` 與 `MyAttr::print` 這對靜態函式，讓**自訂型別**（如 `ShapedType` 的子類）能以同樣的宣告式語法被嵌入 op 的格式。

### `attr-dict` 與省略的屬性

`attr-dict` 關鍵字讓 ODS 自動處理「不在格式中被顯式綁定的屬性」的解析與列印。列印時，只有**不在 elided 集合中**的屬性才會被印出。這就是為什麼 ODS 有 `elidedAttrs` 這類設定。

### `oilist`

`oilist` 讓格式支援「零個或多個可選片段」：

```tablegen
let assemblyFormat = "$value oilist(`attrs` $attr) attr-dict";
```

對應組語：

```mlir
%0 = my.op %v attrs {a = 1 : i32}
%1 = my.op %v
```

## ODS 產生的 C++ 類別結構

`-gen-op-decls` 產生的類別骨架如下（以 `AddOp` 為例，簡化但結構正確）：

```cpp
class AddOp : public ::mlir::Op<AddOp,
                                 ::mlir::OpTrait::NOperands<2>::Impl,
                                 ::mlir::OpTrait::OneResult,
                                 ::mlir::OpTrait::ZeroRegions,
                                 ::mlir::OpTrait::IsTerminator> {
public:
  using ::mlir::Op::Op;
  static ::llvm::StringRef getOperationName() { return "my.add"; }
  static ::llvm::ArrayRef<::mlir::Type> getTypeIds() {
    static ::llvm::ArrayRef<::mlir::Type> types = {
        ::mlir::Type::get<::mlir::NoneType>()};
    return types;
  }

  // --- operand/result accessors (由 ODS 產生) ---
  ::mlir::Value getLhs() { return this->getOperand(0); }
  ::mlir::Value getRhs() { return this->getOperand(1); }
  ::mlir::Value getResult() { return this->getResult(0); }

  ::mlir::Operation::operand_range getOperands() {
    return this->getOpOperands();
  }

  // --- builder (由 ODS 產生或由 builders 清單指定) ---
  static void build(::mlir::OpBuilder &builder, ::mlir::OperationState &state,
                    ::mlir::Value lhs, ::mlir::Value rhs, ::mlir::Type result);

  // --- parse/print (由 assemblyFormat 產生) ---
  static ::llvm::ParseResult parse(::mlir::OpAsmParser &parser,
                                  ::mlir::OperationState &result);
  static void print(::mlir::OpAsmPrinter &p);

  // --- verifier (由 trait 或 hasVerifier 決定) ---
  ::mlir::LogicalResult verify();
};
```

`-gen-op-defs` 產生的 `.cpp.inc` 則包含 `parse`、`print` 的本體，加上 `verify()` 的實作、trait 相關的靜態函式，以及 `getAttributeNames()` 之類的 helper。

### accessor 的命名規則

ODS 從 `$name` 產生命名規則：

| ODS 名稱 | accessor | 型別 |
| --- | --- | --- |
| `$lhs`（operand） | `getLhs()` | `Value` |
| `$lhs`（variadic operand） | `getLhs()` | `Operation::operand_range` |
| `$lhs`（optional operand） | `getLhs()` | `Value`（可為 null） |
| `$result`（result） | `getResult()` | `Value` |
| `$flag`（attribute） | `getFlag()` | 對應的 attr 型別 |
| `$flag`（optional attribute） | `getFlag()` | `std::optional<Attr>` |
| 全部 operand | `getOperands()` | `operand_range` |

ODS 產生 `getLhsAttr()`（回傳 `Attribute`）與 `getLhs()`（回傳轉換後的型別）兩種版本，前者用於屬性。

## `hasVerifier` 與自訂 verifier 掛接

ODS 能驗證**結構**：operand 數量、型別約束、result 數量。但「第二個 operand 必須是第一個的兩倍」這種**語意**規則，ODS 無法表達（見 [3.1](03.1-為什麼需要TableGen.md) 對 TableGen 限制的討論）。

ODS 的解法是 `hasVerifier` 欄位：

```tablegen
def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let arguments = (ins AnySignlessIntegerOrFloatLike:$lhs,
                        AnySignlessIntegerOrFloatLike:$rhs);
  let results = (outs AnySignlessIntegerOrFloatLike:$result);

  let hasVerifier = 1;
}
```

`hasVerifier = 1` 會讓 `-gen-op-decls` 在類別中產生 `::mlir::LogicalResult verify();` 的宣告，而**不**產生預設實作。你必須手寫：

```cpp
// lib/Dialect/My/MyOps.cpp
#define GET_OP_CLASSES
#include "MyOps.cpp.inc"

::mlir::LogicalResult AddOp::verify() {
  // 結構檢查（數量、型別）由 trait 自動完成，
  // 這裡只寫語意檢查。
  if (getLhs().getType() != getRhs().getType())
    return emitOpError("requires matching operand types");

  if (getLhs().getType().getIntOrFloatBitWidth() > 32)
    return emitOpError("does not support 64-bit operands yet");

  return ::mlir::success();
}
```

`emitOpError()` 來自 `mlir::OpState`，它會自動把 op 在來源檔中的**位置**（file:line）附在錯誤訊息前面，這是 MLIR 診斷品質的關鍵設計：

```
error: 'my.add' op requires matching operand types
note: see current operation: %0 = my.add %a, %b : i32
```

ODS 還提供更細緻的掛接點：`hasFolder`、`hasCanonicalizer`、`hasCanonicalizeMethod`，分別對應 fold 與 canonicalization 方法的產生方式。

### fold 的掛接

```tablegen
def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let hasFolder = 1;
}
```

```cpp
::mlir::OpFoldResult AddOp::fold(::mlir::FoldAdaptor adaptor) {
  // 恆等：x + 0 = x
  if (matchPattern(getRhs(), m_Zero()))
    return getLhs();
  return ::mlir::OpFoldResult();
}
```

`OpFoldResult` 可以是 `Attribute`（常數折疊結果）、`Value`（引用既有值）、或空（表示無法折疊）。`FoldAdaptor` 提供了 operand 與 attribute 的統一存取，容忍「operand 已被常數折疊成 attribute」的情況。

把整條管線走一遍。

### 步驟 1：寫 ODS 與方言骨架

  let cppNamespace = "::mlir::my";

### 步驟 5：三方對照

同一個事實，三種表現：

| 面向 | ODS（宣告） | MLIR 組語（用法） | C++（使用） |
| --- | --- | --- | --- |
| 名稱 | `def AddOp : My_Op<"add", ...>` | `my.add` | `mlir::my::AddOp` |
| operand | `$lhs`, `$rhs` | `%a, %b` | `op.getLhs()`, `op.getRhs()` |
| result | `$result` | `: i32` | `op.getResult()` |
| 結構驗證 | `SameOperandsAndResultType` | 解析時自動檢查 | `op.verify()` |
| 建構 | `let builders` / 預設推導 | — | `builder.create<AddOp>(loc, lhs, rhs)` |

這張表是本節的核心：**同一件事在三個世界裡的樣貌**，而 ODS 是把它們綁在一起的錨點。

## 為何 ODS 也需要自訂型別（TypeDef）

operation 的 operand/result 是「型別的容器」，但很多方言還需要**自訂型別**（如 `my.tensor<[4, 8]>`、`my.pipeline<...>`）。ODS 提供了 `TypeDef` 與 `AttrDef` 支援這件事：

```tablegen
def My_TensorType : TypeDef<My_Dialect, "Tensor"> {
  let mnemonic = "tensor";
  let parameters = (ins "int64_t":$size);
  let assemblyFormat = "`<` $size `>`";
  let genVerifyDecl = 1;
}

def My_IntAttr : AttrDef<My_Dialect, "Int"> {
  let mnemonic = "int";
  let parameters = (ins "int64_t":$value);
  let assemblyFormat = "`<` $value `>`";
}
```

`TypeDef` 會產生：

* `mlir::my::TensorType` C++ 類別，含 `getSize()` / `getValue()` accessor。
* `parse` / `print` 實作。
* 對應的 `Type` ID 與 `isa<TensorType>` 支援。

`genVerifyDecl = 1` 讓你手寫 `LogicalResult verify(verify::TensorTypeAdaptor adaptor)`。

`TypeDef` 與 `Op` 共享同一套 ODR 資料模型，這是 ODS 的一個漂亮之處：`parameters` 裡的 `$size` 同樣產生 accessor，同樣支援 `assemblyFormat`。也就是說，**描述 op 的語言和描述型別的語言是同一套**。

## 成本與權衡

ODS 不是免費的。讓我們誠實地算一下成本：

**建置時間成本。** `mlir-tblgen` 需要解析整個 ODS 與它 include 的所有基礎檔案（`OpBase.td`、`CommonTypeConstraints.td` 等數千行）。大型方言（例如 `mlir/Dialect/Linalg/LinalgOps.td` 有數千行）的 tblgen 執行時間以秒計。MLIR 專案用 `add_public_tablegen_target` 加上 CMake 的平行建置來緩解，並且靠「ODS 只依賴少數基礎 .td」來避免每次都重算。

**編譯體積成本。** 產生的 `.inc` 檔案很大。`linalg` 單一方言的 op 宣告就有數萬行，編譯時間以分鐘計。這是 MLIR 建置時間的主因之一。

**學習曲線成本。** ODS 的錯誤訊息不好讀，特別是「型別約束不存在」這類錯誤，需要在上游 `.td` 檔裡搜尋正確名字。

換來的是：**消除了一整類必然會出現的 bug**（結構與實作不一致），並且把「新增 operation」的單位成本從「數百行 C++」降到「數行 ODS」。

## 小結與延伸閱讀

* `def X : Dialect_Op<"mnemonic", [traits]>` 中，`traits` 決定結構合法性、優化行為與能力介面；`arguments`/`results` 用 ODR 的 `dag` 語法描述 operand 與 result 的數量、型別約束與名稱。
* 進階 constraint：`Variadic<T>`（可變長）、`Optional<T>`（可缺省）、`AttrSizedOperandSegments`（混合 operand 的分段資訊）；`SameOperandsAndResultType` 同時帶來推導出的 builder。
* `let assemblyFormat` 用 `$name`、`type($name)`、`attr-dict`、反引號字面量與 `custom<...>` 描述組語外觀，ODS 據此產生對稱的 `parse` 與 `print`；語意無法表達時退到 `custom`。
* ODS 能驗證結構，不能驗證語意：`hasVerifier = 1` 掛接手寫的 `verify()`，`hasFolder = 1` 掛接 `fold()`，兩者都用 `emitOpError()` 取得來源位置診斷。
* `TypeDef` 與 `AttrDef` 讓自訂型別與 attribute 共享同一套 ODS 資料模型，operation 與型別可以用同一種語言描述。
* 延伸閱讀：`mlir/docs/OpDefinitions.md`（ODS 官方說明與語法參考）、`mlir/include/mlir/IR/OpBase.td`（`Op` class 的權威定義）、`mlir/include/mlir/IR/CommonTypeConstraints.td`（內建型別約束清單）、`mlir/include/mlir/IR/OpDefinition.h`（trait 與 `Op` 的 C++ 定義）、`mlir/docs/GenericTypes.md`（`TypeDef` 與 `AttrDef`）、`mlir/test/lib/Dialect/Test/TestOps.td`（可執行的小型方言範例）。
