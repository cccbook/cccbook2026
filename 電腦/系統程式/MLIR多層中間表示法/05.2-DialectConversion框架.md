# 5.2 Dialect Conversion：ConversionTarget、TypeConverter 與合法性

[5.1](05.1-GreedyPatternRewriteDriver.md) 解決的是「在同一個抽象層內做局部改寫」的問題：pattern 這邊改一改，那邊折一折，最後逼近一個不動點。但真實的編譯器需要另一種能力——**把某個抽象層整體消滅掉**。

把 `tensor` 方言的 `tensor.empty` 降成 `memref.alloc`、把 `linalg.generic` 降成一串 `arith` 與 `scf` 指令、把 `func` 降成 `llvm.func`——這些都不是「局部改寫」，而是「整類 op 必須消失」的任務。本節介紹的 Dialect Conversion 框架，就是 MLIR 為這類任務提供的機制。

## 為什麼降階需要不同於普通 pattern rewrite 的機制

表面上，conversion 好像只是「一堆 pattern + 一個驅動器」。但它的約束本質上完全不同，可以用三個條件概括：

**條件一：完整性。** 降階的成功定義不是「改寫了一些東西」，而是「目標 op 的數量變成零」。這是一個全域的、全稱量化的命題：

$$
\forall o \in \mathrm{ops}(\text{region}),\quad \mathrm{legal}(o) = \mathrm{true}
$$

對比之下，greedy rewrite 的成功定義是「不再有可套用的 pattern」，是存在量化的。

**條件二：過程中的合法性。** 在 greedy rewrite 中，IR 在改寫的中途可以處於任意狀態；Driver 只在最後才檢查。但在 conversion 中，**每一步改寫之後的 IR 都必須是合法的**。原因是 conversion 常被用來做「先降階一半，再插入一些低階 op」的組合操作；若中途允許非法狀態存在，就會出現「高階 op 還沒降完，卻已經混進低階 op」的混亂 IR。

**條件三：型別的一致性。** 降階經常伴隨型別變化（例如 `tensor<f32>` 降成 `memref<f32>`）。在 greedy rewrite 中，只要替換前後的 value 型別一致就沒問題；但在 conversion 中，降階過程可能短暫地需要用到「尚未轉換的型別」或「已經轉換的型別」。

這三個條件，正是 MLIR 把 conversion 從 greedy rewrite 中獨立出來的原因。MLIR 的 conversion driver 是一個**獨立的重寫引擎**，它有自己的一套合法性追蹤、型別轉換與 rollback 機制，而不是在 greedy driver 上加開關。

## `ConversionTarget`：合法性的權威來源

`ConversionTarget` 是一個「這次轉換想要達到什麼樣子」的描述物件。它以 op 名稱（`OperationName`）與方言名稱為 key，記錄每類 op 的合法性。

```cpp
namespace mlir {
class ConversionTarget {
public:
  enum class LegalizationAction {
    /// The operation is legal and can exist in the output.
    Legal,
    /// The operation is illegal and must be converted.
    Illegal,
    /// The operation is partially legal: the operation itself is legal, but
    /// nested regions may contain illegal operations.
    PartiallyLegal,
  };

  /// Mark the given operation as legal.
  template <typename OpT> void addLegalOp();
  void addLegalOp(OperationName opName);

  /// Mark the given operation as illegal.
  template <typename OpT> void addIllegalOp();
  void addIllegalOp(OperationName opName);

  /// Mark all operations of the given dialects as legal.
  template <typename DialectT> void addLegalDialect();
  void addLegalDialect(StringRef dialectName);

  /// Mark all operations of the given dialects as illegal.
  template <typename DialectT> void addIllegalDialect();
  void addIllegalDialect(StringRef dialectName);

  /// Mark the given operation as dynamically legal based on the given callback.
  template <typename OpT>
  void addDynamicallyLegalOp(std::function<bool(Operation *)> callback);
  void addDynamicallyLegalOp(OperationName opName,
                             std::function<bool(Operation *)> callback);

  /// Mark all operations of the given dialects as dynamically legal.
  template <typename DialectT>
  void addDynamicallyLegalDialect(std::function<bool(Operation *)> callback);

  /// Mark all unknown operations (those not explicitly mentioned) as legal or
  /// illegal based on the callback.
  void markUnknownOpDynamicallyLegal(
      std::function<bool(Operation *)> callback);
  void markUnknownOpDynamicallyLegal(
      std::function<std::optional<bool>(Operation *)> callback,
      bool recursivelyLegal = false);

  /// Mark the given operation as recursively legal: the operation and all
  /// operations nested within it are legal.
  template <typename OpT> void markOpRecursivelyLegal();
  void markOpRecursivelyLegal(OperationName opName);

  /// Return true if the given operation is legal. 'opAction' is populated with
  /// the legalization action of the operation.
  bool isLegal(Operation *op, LegalizationAction &opAction) const;
  bool isLegal(Operation *op) const;
};
} // namespace mlir
```

### 四種宣告方式對應四種設計需求

| 需求 | 宣告方式 | 語意 |
| --- | --- | --- |
| 這類 op 完全不需要動 | `addLegalOp<arith::AddFOp>()` | 該 op 及其內部 region 都視為合法 |
| 這類 op 必須消失 | `addIllegalOp<my::HighLevelOp>()` | 必須有 pattern 能把它轉成合法的東西 |
| 這整個方言是目標 | `addLegalDialect<arith::ArithDialect>()` | 該方言所有 op 合法 |
| 合法性取決於上下文 | `addDynamicallyLegalOp<my::Op>(cb)` | 由 callback 決定 |

`markUnknownOpDynamicallyLegal` 特別重要：它決定了「target 完全不認識的 op」怎麼辦。回傳 `true` 表示「隨便留著」，回傳 `false` 表示「這些也要轉」。而在 full conversion 中，未被宣告為 legal 的 op 基本上會被視為需要轉換的對象，因此實務上通常會明確宣告所有允許存在的方言。

### `PartiallyLegal` 的意義

`LegalizationAction` 三值的設計，是為了處理「op 本身合法，但內部 region 可能不合法」的情況。

典型例子：一個 `func.func` op。`func.func` 這個 op 本身是合法的（它是目標方言的一部分），但它的 body region 裡可能還有 `my.high_level` op，需要被降階。於是我們要宣告：

```cpp
target.addDynamicallyLegalOp<func::FuncOp>([](func::FuncOp op) {
  return std::nullopt;   // PartiallyLegal：op 本身合法，region 交給遞迴檢查。
});
```

回傳型別是 `std::optional<bool>`，三種取值對應三種 action：

| callback 回傳 | action | 意義 |
| --- | --- | --- |
| `std::optional<bool>(true)` | `Legal` | 完全合法，region 內部也不再檢查 |
| `std::optional<bool>(false)` | `Illegal` | 不合法，必須被轉換 |
| `std::nullopt` | `PartiallyLegal` | op 本身合法，合法性取決於內部 region |

「合法操作子集」這個詞，指的就是這種可以依 op 的屬性或型別判定的動態合法性。例如：

```cpp
// 只有在使用者為已知合法的 op 時，my.transfer 才合法。
target.addDynamicallyLegalOp<my::TransferOp>([](my::TransferOp op) {
  return op.getSource().getDefiningOp() != nullptr &&
         llvm::isa<arith::AddFOp>(op.getSource().getDefiningOp());
});
```

## `ConversionPattern`：帶著型別轉換與 adaptor 的 pattern

`ConversionPattern` 是 `RewritePattern` 的子類，但簽章不同：

```cpp
namespace mlir {
class ConversionPattern : public RewritePattern {
public:
  ConversionPattern(MLIRContext *ctx, TypeConverter *typeConverter = nullptr,
                    PatternBenefit benefit = 1);

  /// Return the type converter for this pattern.
  TypeConverter *getTypeConverter() const;

  /// Rewrite the given 'op' with the given 'adaptor'...
  virtual LogicalResult matchAndRewrite(Operation *op, OpAdaptor adaptor,
                                         ConversionPatternRewriter &rewriter) const = 0;

  /// An adaptor for the operands of the matched operation...
  class OpAdaptor {
  public:
    ValueRange getOperands();
    // 以及 getOperands() 的各個索引存取器
  };
};
} // namespace mlir
```

與 `OpRewritePattern<T>` 的差異有三個：

**第一，root 仍是同一個 op，但操作數是「已轉換」的。** `OpAdaptor` 內含的是經過 `TypeConverter` 轉換後的 operand 值。當 driver 匹配到 op `X` 時，它先把 `X` 的 operand 做型別轉換，得到 adaptor；pattern 拿到的 `adaptor.getOperands()` 已經是目標型別的值。這是 conversion 能「順帶做型別轉換」的關鍵。

**第二，rewriter 是 `ConversionPatternRewriter`。** 它額外提供 `getTypeConverter()` 與 `remapValue(Value)`，並且嚴格檢查改寫後的 IR 合法性。

**第三，型別轉換的負責者不同。** 在 greedy rewrite 中，「新 op 的 operand 型別」完全由 pattern 作者負責；在 conversion 中，`TypeConverter` 定義了「型別如何映射」，driver 會檢查新 op 的 operand 型別是否符合轉換後的目標型別，若不符合則要求 pattern 透過 materialization 機制處理。

最常用的寫法是 `OpConversionPattern<T>`：

```cpp
template <typename SourceOp>
class OpConversionPattern : public ConversionPattern {
public:
  using OpAdaptor = typename SourceOp::Adaptor;
  OpConversionPattern(MLIRContext *ctx, TypeConverter *typeConverter = nullptr,
                      PatternBenefit benefit = 1);

  LogicalResult matchAndRewrite(SourceOp op, OpAdaptor adaptor,
                                 ConversionPatternRewriter &rewriter) const override;
};
```

## `TypeConverter`：型別映射與 materialization

`TypeConverter` 是 conversion 中的型別映射表。它有三個部分：

```cpp
namespace mlir {
class TypeConverter {
public:
  using ConversionCallbackFn = std::function<std::optional<Type>(Type)>;
  using MaterializationCallbackFn =
      std::function<Value(Type resultType, Type inputType, Location loc,
                          PatternRewriter &rewriter)>;

  /// Register a conversion function. The callback should return the converted
  /// type, or std::nullopt if the type is not convertible.
  void addConversion(ConversionCallbackFn callback, TypeConverterAnchor anchor);

  /// Register a callback to materialize a value of 'resultType' from a value
  /// of 'inputType' in the source dialect.
  void addSourceMaterialization(MaterializationCallbackFn callback,
                                TypeConverterAnchor anchor);

  /// Register a callback to materialize a value of 'resultType' from a value
  /// of 'inputType' in the target dialect.
  void addTargetMaterialization(MaterializationCallbackFn callback,
                                TypeConverterAnchor anchor);

  /// Convert the given type. Returns std::nullopt if no conversion is
  /// registered for the type.
  std::optional<Type> convertType(Type type) const;

  /// Convert the given types.
  LogicalResult convertTypes(TypeRange types,
                             SmallVectorImpl<Type> &results) const;

  /// Return true if the given type is legal (i.e., unchanged by conversion).
  bool isLegal(Type type) const;

  /// Materialize a conversion from the given input value to the given result
  /// type.
  Value materializeTargetConversion(
      Type resultType, TypeConverter::MaterializationCallbackFn callback,
      Type inputType, Value inputValue) const;
};
} // namespace mlir
```

### 型別轉換 callback

```cpp
TypeConverter typeConverter;
typeConverter.addConversion([](Type type) -> std::optional<Type> {
  if (auto shaped = dyn_cast<ShapedType>(type))
    return shaped.clone ranks...
  return std::nullopt;
});
```

回傳 `std::nullopt` 表示「這個型別我不管」，此時該型別被視為**不合法**（需要被轉換），或者被視為原樣保留？實務上的約定是：回傳 `nullopt` 代表「無法轉換」，conversion 會失敗並要求 pattern 使用 materialization 來過渡。

### Materialization：conversion 中最容易被忽略、卻最關鍵的機制

考慮這樣一個情況：把 `tensor<f32>` 降成 `memref<f32>`。假設某個 op 的 operand 在降階過程中一會兒是 `tensor<f32>`、一會兒是 `memref<f32>`。如果新產生的 op 要求 `memref<f32>`，但手上只有 `tensor<f32>` 的值，怎麼辦？

答案就是 **materialization**：conversion 提供一個「把某個型別的值轉成另一個型別的值」的合法代表物。MLIR 定義了兩個方向：

- **Source materialization**：從**來源**方言的值產生一個**目標**型別的值（方向是「源 → 目標」的插入）。
- **Target materialization**：從**目標**方言的值產生一個**來源**型別的值。

以 `tensor → memref` 為例：

- 目標 materialization：手上有一個 `memref<f32>`，但某個尚未降階的高階 op 需要 `tensor<f32>`。此時插入一個 `bufferization.to_tensor`（或其等價物），把 `memref` 轉回 `tensor`。
- 來源 materialization：手上有一個 `tensor<f32>`，但需要餵給 `memref` op。此時插入 `bufferization.to_memref`（或 `memref.cast` 之類）。

materialization 的存在，讓 conversion driver 可以**在合法的 IR 內部**完成「型別逐步過渡」，而不需要 pattern 作者手動處理每一次型別不匹配。這也解釋了為什麼 conversion 要求「過程中 IR 必須合法」：materialization 產生的 op 是合法 op（例如 `bufferization.to_tensor` 宣告為 legal），所以即使轉換未完成，IR 依然通過 verifier。

### `TypeConverter` 與 `TargetMaterialization` 的整合點

當 pattern 想「保留某個高階 op，但把它的 operand 換成低階型別」時，標準做法是：

```cpp
// 取得轉換後的目標型別。
Type targetType = converter->convertType(op.getType()).value();
// 產生一個合法的「橋接」值。
Value bridged = converter->materializeTargetConversion(
    targetType, materializeToTensor, op.getType(), op.getResult());
```

把這些零件組裝起來，可以做一個完整可讀的範例。

## 完整範例：把 `my.add` 降成 `arith.addf`

假設有個高階方言 `my`，其中 `my.add` 接受兩個 `f32` operand，產生一個 `f32` result，並且它的 operand 在語意上是「值」，我們要把它降成 `arith.addf`。

### 步驟一：定義目標方言與來源方言

```tablegen
// my_ops.td
def My_AddOp : My_Op<"add", [Pure]> {
  let arguments = (ins F32:$lhs, F32:$rhs);
  let results = (outs F32:$result);
  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
```

### 步驟二：建立 `TypeConverter`

我們希望 `f32` 保持不變，但順便示範「源/目標 materialization」的註冊：

```cpp
#include "mlir/Dialect/Arith/IR/Arith.h"
#include "mlir/Dialect/Func/IR/FuncOps.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/Transforms/DialectConversion.h"

using namespace mlir;

/// 建立本範例使用的 TypeConverter。
static TypeConverter makeTypeConverter() {
  TypeConverter converter;

  // f32 保持原樣；其他型別我們不做轉換，視為不合法並在 conversion 中報錯。
  converter.addConversion([](Type type) -> std::optional<Type> {
    if (type.isF32())
      return type;
    return std::nullopt;
  });

  // 目標 materialization：目標型別的值 -> 來源型別的代表值。
  // 本例沒有需要跨型別的 op，註冊一個明確失敗的 callback 以便診斷清楚。
  converter.addTargetMaterialization(
      [](Type resultType, Type inputType, Location loc,
         PatternRewriter &rewriter) -> Value {
        return nullptr;
      });

  // 來源 materialization：來源型別的值 -> 目標型別的代表值。
  converter.addSourceMaterialization(
      [](Type resultType, Type inputType, Location loc,
         PatternRewriter &rewriter) -> Value {
        return nullptr;
      });

  return converter;
}
```

### 步驟三：寫 conversion pattern

```cpp
namespace {

/// 把 my.add 降成 arith.addf。
struct MyAddToArithAdd : public OpConversionPattern<my::AddOp> {
  using OpConversionPattern::OpConversionPattern;

  LogicalResult matchAndRewrite(my::AddOp op, OpAdaptor adaptor,
                                 ConversionPatternRewriter &rewriter) const override {
    // adaptor.getOperands() 已經過 TypeConverter 轉換。
    // 萬一型別轉換失敗，會得到不合法的 operand，因此這裡再確認一次。
    if (!adaptor.getLhs().getType().isF32() ||
        !adaptor.getRhs().getType().isF32())
      return rewriter.notifyMatchFailure(op, "expected f32 operands after conversion");

    rewriter.replaceOpWithNewOp<arith::AddFOp>(op, adaptor.getLhs(),
                                                adaptor.getRhs());
    return success();
  }
};

} // namespace
```

### 步驟四：建立 `ConversionTarget` 並執行轉換

```cpp
/// 把模組中的 my.add 降成 arith.addf。
struct MyAddLoweringPass : public PassWrapper<MyAddLoweringPass, OperationPass<ModuleOp>> {
  MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID(MyAddLoweringPass)

  StringRef getArgument() const override { return "my-add-lowering"; }

  void getDependentDialects(DialectRegistry &registry) const override {
    registry.insert<arith::ArithDialect>();
  }

  void runOnOperation() override {
    MLIRContext *ctx = &getContext();
    TypeConverter converter = makeTypeConverter();

    ConversionTarget target(*ctx);
    // my 方言的所有 op 都非法，必須被轉換掉。
    target.addIllegalDialect<my::MyDialect>();
    // arith 與 func 是我們想要的目標。
    target.addLegalDialect<arith::ArithDialect>();
    target.addLegalDialect<func::FuncDialect>();
    // 模組 op 本身合法，但其 region 需要被遞迴檢查。
    target.markOpRecursivelyLegal<ModuleOp>();
    // func.func 本身合法，body 交給遞迴檢查。
    target.addDynamicallyLegalOp<func::FuncOp>(
        [](func::FuncOp) { return std::nullopt; });

    RewritePatternSet patterns(ctx);
    patterns.add<MyAddToArithAdd>(ctx, &converter);

    if (failed(applyFullConversion(getOperation(), target, std::move(patterns))))
      signalPassFailure();
  }
};
```

對應的 MLIR 輸入：

```mlir
module {
  func.func @add(%a: f32, %b: f32) -> f32 {
    %0 = my.add %a, %b : f32
    return %0 : f32
  }
}
```

轉換後：

```mlir
module {
  func.func @add(%a: f32, %b: f32) -> f32 {
    %0 = arith.addf %a, %b : f32
    return %0 : f32
  }
}
```

在 `mlir-opt` 中執行（假設 pass 已註冊）：

```bash
mlir-opt input.mlir -my-add-lowering -o output.mlir
```

## `applyPartialConversion` 與 `applyFullConversion`

這兩個函式的簽章相同：

```cpp
namespace mlir {
/// Partially convert the given operation to the given target. Only the
/// operations that are illegal (or dynamically illegal) are converted.
LogicalResult applyPartialConversion(Operation *op, ConversionTarget &target,
                                     FrozenRewritePatternSet &patterns,
                                     ConversionConfig config = {});

/// Fully convert the given operation to the given target. All operations in
/// the region must be legal after the conversion.
LogicalResult applyFullConversion(Operation *op, ConversionTarget &target,
                                  FrozenRewritePatternSet &patterns,
                                  ConversionConfig config = {});
}
```

差異在語意上的對比：

| 面向 | `applyPartialConversion` | `applyFullConversion` |
| --- | --- | --- |
| 成功條件 | 所有被標記為 illegal 的 op 都已消失 | 區域內**所有** op 都合法 |
| 允許殘留的 IR | 允許（例如尚未打算降階的高階 op） | 不允許 |
| 未被 target 認識的 op | 實務上仍建議宣告 legal，但殘留是被容忍的 | 必須被轉換掉，否則失敗 |
| 典型用途 | 只降階某個子方言、保留其他高階抽象 | 整個模組降成單一目標抽象層 |
| 對 pipeline 的約束 | 鬆 | 嚴格（見 [5.3](05.3-Partial與FullLowering.md)） |

`ConversionConfig` 目前提供的是轉換過程的額外控制，例如 `enableProgressiveLowering` 讓轉換在每個 pattern 套用後嘗試「漸進式降階」，以及 `enableDebugInfo` 這類診斷開關。

### 失敗時的 rollback 語意

這是 conversion 與 greedy rewrite 最大的行為差異之一。

greedy rewrite 失敗時，IR 通常**已經被部分改寫**，pass 作者要自己去想「怎麼讓 IR 回到可接受的狀態」。而 conversion 的 driver 具備 rollback 機制：當轉換過程無法把所有非法 op 合法化時，driver 會把改寫過程中的所有變更**回復**到轉換開始前的狀態，然後回傳 `failure()`。實務上可以把它想成是一種交易（transaction）語意：

$$
\text{convert}(\mathrm{IR}_0) =
\begin{cases}
\mathrm{IR}_1 & \text{若成功，}\mathrm{IR}_1 \text{ 完全合法}\\
\mathrm{IR}_0 & \text{若失敗，IR 被回復到原狀}
\end{cases}
$$

這個語意帶來兩個好處：

1. **pass 可以安全地在失敗時 `signalPassFailure()`**，不必擔心留下半降階的 IR 給後續 pass。
2. **錯誤診斷可以指涉原本的 IR**。driver 會收集轉換過程中的失敗原因（每個非法 op 為何無法被合法化），組成一份聚合診斷。

典型的失敗訊息大致如下：

```text
error: failed to legalize operation 'my.add' that was explicitly marked illegal
note: see current operation:
%0 = my.add %a, %b : f32
note: (call stack for failure reporting is printed at the end of the output)
```

轉換失敗時的診斷會把「哪個 op 無法被合法化」以及「當時 IR 的樣子」一起印出，這對除錯相當有價值。相關選項 `mlir::enableDebugInfo`（在 `ConversionConfig` 中）可讓診斷更詳細。

## `LegalizationAction` 與 dialect legality

在 target 中宣告合法性時，除了「op 級別」之外，還有「方言級別」的宣告：

```cpp
target.addIllegalDialect<my::MyDialect>();     // 整個方言非法
target.addLegalDialect<arith::ArithDialect>();  // 整個方言合法
target.addDynamicallyLegalDialect<some::Dialect>(
    [](Operation *op) { return isLegalByAttr(op); });
```

當 driver 遇到一個非法 op 時，它的合法化流程是：

```text
legalize(op):
    1. 尋找可匹配的 conversion pattern（依 benefit 排序）
    2. 若找到，套用；driver 重新檢查新產生的 op
    3. 若找不到：
       a. 若 op 的 action 是 PartiallyLegal，檢查其內部 region
       b. 否則，產生 "failed to legalize" 錯誤
```

注意第 2 步之後的「重新檢查」：conversion pattern 產生的新 op 可能又是非法的，此時同樣要繼續合法化。這就是為什麼 `ConversionPattern` 可以「鏈式」降階——`my.a` → `my.b` → `arith.c` 這種兩段式降階是合法的。

## `replaceOp` / `replaceOpWithNewOp` / `eraseOp`

在 conversion 中，pattern 對 op 的處置語意與 greedy rewrite 基本相同，但有一個額外限制：**被替換掉的值必須是合法的**，否則 driver 會要求 pattern 使用 materialization。

| 呼叫 | 用途 | 合法性要求 |
| --- | --- | --- |
| `rewriter.replaceOp(op, newValues)` | 用既有 value 取代 op 的結果 | `newValues` 的型別必須是轉換後的目標型別 |
| `rewriter.replaceOpWithNewOp<NewOp>(op, operands...)` | 建立新 op 取代舊 op | 新 op 的 operand 型別必須與轉換後的型別一致 |
| `rewriter.eraseOp(op)` | 刪除 op（無結果的 op，如 `my.barrier`） | op 不得有被使用的結果 |

一個常見的錯誤是：pattern 忘了做型別轉換，直接把 `op.getLhs()`（原始型別）塞給新 op。在 greedy rewrite 中這不會報錯（因為前後型別一致）；在 conversion 中，若目標型別不同，driver 會報錯：

```text
error: failed to legalize operation 'my.add' ...
note: type mismatch: expected 'f32', but got 'tensor<f32>'
```

要修正，不是硬塞原始值，而是使用 adaptor 的值（已轉換），或顯式呼叫 materialization。

## 降階過程的型別管理：以 `tensor → memref` 為例

再看一個更能顯示 materialization 價值的例子。假設 `my.compute` 的 operand 是 `tensor<f32>`，我們要把它降成一串接受 `memref<f32>` 的 op。

在轉換過程中，`my.compute` 的 result 型別是 `tensor<f32>`，但它即將被刪除；此時若 pattern 需要把它交給某個低階 op，就必須先生成一個 `memref<f32>`。這個 `memref` 從哪來？兩個可能：

1. 來源 materialization：把 `tensor` 轉成 `memref`（例如 `bufferization.to_memref`）。
2. 目標 materialization：反過來，把 `memref` 轉回 `tensor` 餵給尚未降階的高階 op。

```cpp
// 在 pattern 中，兩種方向的 materialization 都可能用到。
TypeConverter *converter = rewriter.getTypeConverter();

// 想要一個目標型別（memref）的值，但手上只有來源型別（tensor）的值。
Type desired = converter->convertType(op.getType()).value();
Value asMemref = converter->materializeTargetConversion(
    desired, /*callback=*/materializeToMemref, op.getType(), op.getResult());

// 反過來：手上是 memref，但需要一個 tensor 餵給尚未降階的 op。
Value asTensor = converter->materializeTargetConversion(
    op.getType(), /*callback=*/materializeToTensor, memrefType, memrefValue);
```

要注意方向的對應：`materializeTargetConversion` 的簽章是 `(resultType, callback, inputType, inputValue)`，回傳一個 `resultType` 型別的值，代表 `inputValue`（`inputType` 型別）在目標抽象層中的合法代表。

## 設計比較：conversion vs. greedy rewrite

| 面向 | Greedy rewrite | Dialect conversion |
| --- | --- | --- |
| 目標 | 逼近某個規範形 | 讓非法 op 全部消失 |
| 合法性追蹤 | 無 | 逐 op 追蹤 `LegalizationAction` |
| 型別轉換 | 由 pattern 作者手動負責 | 由 `TypeConverter` 統一描述 |
| 過程中 IR 合法性 | 不保證 | 保證（每一步都合法） |
| 失敗後的 IR 狀態 | 可能半改寫 | rollback 到原狀 |
| 收斂控制 | `maxIterations` | 由合法性條件自然收斂 |
| 適用 | canonicalization、局部清理 | 降階、跨抽象層轉換 |

可以把兩者理解為同一個「重寫引擎」的兩種配置：conversion 換上了一套更嚴格的「規則系統」，並因此獲得更強的保證，但也更受限。

## 小結與延伸閱讀

- Conversion 與普通 rewrite 的差異不在「pattern 怎麼寫」，而在「成功條件」：conversion 要求所有目標 op 完全消失，且過程中 IR 必須保持合法。
- `ConversionTarget` 是合法性的唯一權威來源；`addLegalOp` / `addIllegalOp` / `addLegalDialect` / `addIllegalDialect` 描述靜態合法性，`addDynamicallyLegalOp` 與 `markUnknownOpDynamicallyLegal` 描述依上下文決定的合法性，`PartiallyLegal` 則處理「op 合法但 region 不合法」的情形。
- `TypeConverter` 不只負責型別映射，`addSourceMaterialization` 與 `addTargetMaterialization` 才是讓「混合抽象層 IR」在轉換期間維持合法的關鍵。
- `applyPartialConversion` 只要求被標記為 illegal 的 op 消失；`applyFullConversion` 要求區域內所有 op 都合法。兩者失敗時都會 rollback，IR 回復到轉換前狀態。
- 在 conversion pattern 中，必須使用 `OpAdaptor` 提供的（已轉換）operand，而不是原始 operand；直接使用原始 operand 是最常見的「type mismatch」來源。
