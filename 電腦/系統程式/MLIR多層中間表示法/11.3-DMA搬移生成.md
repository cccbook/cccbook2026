# 11.3 DMA 搬移生成：從資料依賴到搬運指令

[11.2](11.2-張量分塊與片上緩衝排程.md) 決定了磚的形狀與片上緩衝區的容量，但那些 tile 還只是 `tensor`。要讓 NPU 真的執行，必須把資料從 DRAM 搬到 SRAM，再把結果搬回去。這個「搬」不是單純的 memcpy，而是整個編譯過程中**能量與延遲成本最高**的一環。

本節要回答：

> 編譯器如何從一份「抽象的資料流程式的 IR」，推導出「具體的搬運指令序列」？這中間需要哪些分析？演算法長什麼樣？

## 為什麼搬移在 NPU 上特別關鍵

### 能耗視角

在典型的加速器上，**資料搬移佔總能耗的 50% 到 90%**（大致而言，取決於模型與架構）。這個比例是所有架構決策的根源：

* **Google 第一代 TPU 晶片（2015）** 明確以降低能耗為首要目標，設計上移除了 cache 層級，改以 46MB 片上 SRAM + 700MB/s 記憶體頻寬。移除 cache 是個大膽的決定——它意味著**所有資料重複利用都必須由編譯器在編譯期安排好**，因為硬體已經不提供這個服務了。
* **TPU v2（2017）** 引入分散式記憶體與網路連線，進一步把「片上資料中心（pod）」變成排程單位。
* 一般 NPU 設計中，SRAM 的讀取能耗大約是 DRAM 讀取的數倍到數十倍（取決於製程與實作），因此**把資料從 DRAM 搬上來一次、在 SRAM 裡重複使用 100 次**，是明確的贏。

這就導致了一個編譯器的工作目標：

> 最小化「從 DRAM 搬運的總位元組數」，而不是最小化運算指令數。

這個目標與 GPU 編譯器（在 GPU 上，通常是最大化 coalescing 與減少 cache miss）有共通之處，但因為 NPU 沒有硬體 cache，緩衝區管理完全由編譯器負責，責任更重。

### 延遲視角

另一個角度：DMA 引擎與運算單元是**平行**工作的。如果編譯器排得好，搬移時間被完全隱藏在運算時間裡（這就是 [11.2](11.2-張量分塊與片上緩衝排程.md) 的 double buffering 與 pipelining 的目的）。如果排不好，DMA 會變成序列上的瓶頸，效能直接砍半。

所以搬移生成的演算法有**兩個互相衝突的目標**：

1. 正確且完整（不能漏搬、不能多搬）。
2. 排程得當（能重疊的排程重疊、能提早的提早）。

## DMA 引擎的抽象

### 硬體模型

一個典型的 DMA 引擎（descoped model）包含：

* **一個或多個 channel**：每個 channel 是一條獨立的搬移流水線，channel 之間可以平行。
* **Descriptor 佇列（queue）**：一個有序的 descriptor 序列。硬體依序處理同一佇列中的 descriptor。
* **Descriptor**：描述一次搬移的固定大小記錄。

Descriptor 的典型內容：

| 欄位 | 意義 |
| --- | --- |
| `src` | 來源位址（在來源位址空間） |
| `dst` | 目的位址（在目的位址空間） |
| `len` | 搬運位元組數 |
| `stride` | 元素間距（支援 2D 搬移） |
| `format` | 位元組寬度：8/16/32/64 bit |
| `flags` | 中斷、優先序等 |

Descriptor 通常固定大小（例如 32 或 64 bytes），因此一次搬移有最小粒度（例如 64 bytes）。這解釋了 11.2 提到的對齊要求：**未對齊的搬移在硬體上根本無法描述**。

### 在 IR 中如何表達 descriptor

有兩種基本做法。

**做法一：descriptor 作為屬性陣列。**

```mlir
mychip.dma.submit channel 0 {
  descriptors = [
    { src = 0 : i64, dst = 0 : i64, len = 65536 : i64, format = "f32" },
    { src = 65536 : i64, dst = 65536 : i64, len = 65536 : i64, format = "f32" }
  ]
}
```

優點：**單一 op 提交一批搬運**，最接近硬體（整批 descriptor 一次寫入 DMA 的 descriptor RAM）。缺點：位址必須是編譯期常數（因為描述在屬性裡），這對動態位址是個問題。

**做法二：descriptor 作為 op（帶 operand）。**

```mlir
%d0 = mychip.dma.copy %src, %dst : memref<4096xf32> to !mychip.sram<65536>
%d1 = mychip.dma.copy %src2, %dst2 : memref<4096xf32> to !mychip.sram<65536>
mychip.dma.group %d0, %d1 : !mychip.dma.desc, !mychip.dma.desc
```

優點：operand 可以是 SSA 值，位址可以是動態的；資料流關係顯式。缺點：需要一個額外的「把 op 序列化成 descriptor 陣列」的步驟，且這一步在硬體層才做。

**實務建議：** 大多數系統會兩者並用——在中層用 op 形式表達（利於分析与重寫），在硬體層降階成 descriptor 陣列。`async` 方言（下面詳述）正是這樣的中層表示。

## IR 必須回答的四個問題

這是本節的核心洞察。IR 要能產生正確的 DMA 序列，就必須能回答：

1. **誰產生資料？** 哪個 op 寫入這塊 buffer。
2. **誰消費資料？** 哪個 op 讀取這塊 buffer。
3. **資料多大？** buffer 的大小與型別。
4. **何時可搬？** 產生者完成之後、消費者開始之前；且搬移必須在資源上可行（SRAM 有空間、channel 有空閒）。

這四個問題，正好對應 MLIR 的四個既有機制：

| 問題 | MLIR 機制 |
| --- | --- |
| 誰產生 / 誰消費 | **bufferization**（`bufferization.to_memref` / `to_tensor`），把 `tensor` 轉成 `memref` 時決定 ownership |
| 資料多大 | `memref` 的 shape 與 element type |
| 何時可搬 | **alias 分析** + **依賴圖**（`AliasAnalysis`、副作用分析 `MemoryEffectsOpInterface`） |
| 資源可行性 | SRAM 容量檢查、channel 數限制（排程 pass） |

因此，DMA 生成的演算法骨架是：

```
輸入：已經 bufferize 的函式（memref 型別）
輸出：一串 DMA op，插在正確的位置

1. 對每個 memref 做別名分析，求出「所有別名集合」
2. 對每個別名集合，求出「唯一的寫入者」（若不唯一，需要插入拷貝或改用 copy-on-write）
3. 沿著 SSA 支配關係，對每個「定義點 → 使用點」邊，若定義點不在 SRAM，產生 DMA 搬移
4. 依賴關係排程：把 DMA 放到可行的最早位置（軟體 pipelining）
5. 檢查資源：SRAM 容量、channel 數；不足時回報或嘗試調整
```

讓我們把每一步做細。

## 從 memref 依賴推導 DMA：演算法

### 步驟 0：前置條件——必須先 bufferize

這是一個重要的實務順序問題：**DMA 生成必須在 bufferization 之後**。原因很直接：`tensor` 型別是值語意，編譯器無法從中判斷「這份資料住在哪裡」、「是否需要實際搬移」。只有經過 `bufferization` 轉成 `memref` 之後，資料的物理位置與 alias 關係才明確。

```mlir
// bufferize 之前：抽象
%0 = linalg.matmul ins(%a, %b) outs(%c) : tensor<128x128xf32>

// bufferize 之後：具體
%0 = linalg.matmul ins(%a_buf, %b_buf) outs(%c_buf)
    : memref<128x128xf32, 3>
```

注意 memory space `3` 標示了這是在 SRAM 上。這個標示是後續 DMA 生成能運作的關鍵：如果 buffer 在 DRAM 上，就不需要搬。

### 步驟 1：別名分析

`mlir::AliasAnalysis` 提供的介面是 `mlir::AliasAnalysis::getAliasSets(Block *block)`，回傳一組 `AliasResult`，每個元素對應一個記憶體位置，回傳值可以是 `NoAlias`、`MustAlias`、`MayAlias`、`Unknown`。

自訂 pass 中典型的用法：

```cpp
mlir::AliasAnalysis aliasAnalysis = getAnalysis<mlir::AliasAnalysis>();
auto aliasSets = aliasAnalysis.getAliasSets(&entryBlock);
```

alias set 之間可能有 `MayAlias` 的關係，代表兩者「可能」指向同一塊記憶體。在這種情況下，DMA 生成必須保守處理——例如假設它們可能重疊，因而需要額外的同步或使用拷貝。

### 步驟 2：決定 ownership 與寫入者

對每個 alias set，找出寫入它的 op 集合：

* **恰好一個寫入者**：ownership 明確，可以直接產生搬移。
* **多個寫入者**：資料被多次修改（例如原地累加）。此時搬移只需要在**第一次寫入前**做一次，後續的寫入就地進行。判斷方式是找出支配關係鏈上的「第一個」寫入。
* **零個寫入者**：這個 buffer 從外部傳入（例如是函式參數），可能已經在 SRAM 上，也可能需要搬。

這個「寫入者」的識別，在 MLIR 中常與 `bufferization` 的結果相關：如果 `bufferization` 把 `outs` 設定為 `in-place`（就地更新），那麼累加的寫入者就是那個 op。

### 步驟 3：產生搬移

核心規則可以形式化為：

> 對每條資料流邊 $u \to v$ （ $u$ 寫入 alias set $S$ ， $v$ 讀取 $S$ ），若 $u$ 產生的 buffer 位於 DRAM 而 $v$ 需要它在 SRAM，則在 $u$ 與 $v$ 之間插入 DMA 搬移，把資料從 DRAM 的 $S$ 搬到 SRAM 的一個 buffer。

「之間」的位置由**支配關係**決定：DMA 必須插在 $u$ 之後、 $v$ 之前，且要放在兩者之間最靠前的合法位置（越早越好，這樣搬移可以更早開始，與其他工作重疊）。

實作上，MLIR 提供了 `mlir::DominanceInfo` 來做這件事：

```cpp
mlir::DominanceInfo domInfo(func);
```

### 步驟 4：軟體 pipelining

把搬移「提早」到能與前一個 tile 的運算重疊，是 double buffering 的 IR 表達。演算法大致是：

對一條長的搬移鏈 $D_0 \to D_1 \to D_2 \to \ldots$ （每個 $D_i$ 對應一個 tile），把 $D_{i+1}$ 提到 $D_i$ 的消費點之前，讓兩個搬移同時在不同的 buffer 上進行。

更精確地說，若有序列：

```
S0: compute(t0) uses B0
S1: compute(t1) uses B1
S2: compute(t2) uses B2
```

原始的搬移會插在各自 compute 之前，得到 `dma(B0); compute(t0); dma(B1); compute(t1); ...`。Pipelining 後變成 `dma(B0); dma(B1); compute(t0); dma(B2); compute(t1); ...`，使得 dma(B_{i+1}) 與 compute(t_i) 重疊。

要能重疊，就需要**兩份以上的 buffer**（這正是 11.2 的容量公式裡那個係數 $m$ 的來源），且搬移 op 必須是**非同步**的（發起後不阻塞）。

### 步驟 5：資源檢查

最後檢查：

* SRAM 總容量：所有同時 live 的 buffer 之和 $\le S$ 。
* Channel 數：同時發起的 DMA 不超過 channel 數。
* 搬移的最小粒度：長度必須是硬體粒度的倍數。

若超出，需要回報並要求上游調整 tile size，或在 pass 內部做簡單的縮小（但那會改變語意形狀，通常不該在這一層做）。

## `async` 方言：MLIR 對非同步搬移的標準答案

MLIR 上游的 `async` 方言（`mlir::async::AsyncDialect`）正是為這個問題設計的。它的核心 op：

| op | 語意 |
| --- | --- |
| `async.execute` | 啟動一段非同步工作，回傳一組 token 與結果 |
| `async.copy` | 一次非同步拷貝（外部記憶體 $\to$ 外部記憶體） |
| `async.fill` | 一次非同步填值 |
| `async.group` | 把多個 token 打包成一個群組句柄 |
| `async.await` | 等待群組完成 |
| `async.yield` | 在 `async.execute` 的 region 內結束 |

一個完整的使用範例：

```mlir
// 在 async.execute 內做搬移
%0 = async.execute {
  %c = async.copy %src to %dst : memref<1024xf32> to memref<1024xf32>
  async.yield
} : () -> ()
```

`async.execute` 回傳一個 token 型別 `!async.token`。`async.group` 可以把多個 token 合併：

```mlir
%g = async.group [%t0, %t1] : !async.token, !async.token -> !async.group
async.await %g : !async.group
```

`async.await` 會把群組內的 token 串行化：它會在 IR 中建立對 token 的依賴，並在轉換為非 async 的方言時插入同步。

### 為什麼 `async` 方言適合當 DMA 生成的中層表示

1. **它把「非同步」這個概念標準化了。** 你不需要自創 `mychip.async_dma`，因為 `async.copy` 的語意已經涵蓋。
2. **它把 token 依賴表達為資料流依賴**，這讓 pass 可以用既有的演算法（DCE、依賴分析）來處理。
3. **降階目標是明確的**：把 `async.copy` 變成硬體的 descriptor 提交，是一個相對局部的工作。

但 `async` 方言也有侷限：

* 它的 `copy` 只支援「外部記憶體到外部記憶體」的語意，沒有「搬到特殊 memory space（SRAM）」的概念。NPU 後端要自己擴充。
* `async.execute` 的 region 語意有點彆扭——它其實是「啟動一個 work queue 的工作」，區域內的 op 被視為工作項目。

因此，一個常見的折衷是：**自訂方言定義 DMA op，但採用 `async` 的 token / group 語意**，或者直接繼承 `async` 的介面（例如實作 `AsyncInterface`）。

## `gpu.memcpy` 與 `nvgpu`：可以借鑑的先例

MLIR 上游的 GPU 相關方言提供了很好的參考：

* `gpu.memcpy` / `gpu.memcpy_async`：非同步拷貝 op。`gpu.memcpy_async` 帶有 `srcMemspace` / `dstMemspace` 屬性，以及 `SyncGroup` 屬性用來分組同步——這個設計正是 NPU descriptor group 的先例。
* `nvgpu` 方言中的 `nvgpu.ldmatrix`、`nvgpu.mma.sync` 等：把矩陣乘法的 micro-kernel 細節建模成 op。

值得注意的相似性：

| 概念 | GPU 方言 | NPU 借鑑 |
| --- | --- | --- |
| 非同步搬移 | `gpu.memcpy_async` | `async.copy` / 自訂 `npu.dma.copy` |
| 搬移分組同步 | `SyncGroup` 屬性 | `async.group` / descriptor 佇列 |
| 硬體記憶體層次 | `gpu.shared_memory` | `memref<..., #mychip.sram<...>>` |
| 硬體運算原語 | `nvgpu.mma.sync` | `npu.pe.mma` |
| 硬體資源數量 | `gpu.block_dim` 等屬性 | `rows` / `cols` 屬性 |

`gpu.memcpy_async` 的 `SyncGroup` 屬性特別值得注意：它是一個整數，讓多個 memcpy 屬於同一個同步群組，編譯器據此產生正確的 barrier 組。這比 `async.group` 的 token 風格更貼近硬體（硬體上是「同一個 channel 內的 descriptor 依序執行」）。NPU 方言可以直接沿用這個模式：

```mlir
mychip.dma.copy %src, %dst { sync_group = 0 : i32 } : memref<...> to !mychip.sram<...>
```

## DMA 生成 pass 的偽碼

把上面的分析組織成一個 pass。為了對齊 MLIR 的實作慣例，我們把它寫成一個 `OperationPass<func::FuncOp>`。

```cpp
namespace {

/// 收集一個函式中所有「跨記憶體空間」的 memref 邊界。
struct Boundary {
  Value value;      // 被搬移的 memref
  unsigned srcSpace; // 來源 memory space
  unsigned dstSpace; // 目的 memory space
  OpOperand *use;    // 消費該值的使用點
};

class DmaGeneratePass
    : public mlir::PassWrapper<DmaGeneratePass, mlir::OperationPass<mlir::func::FuncOp>> {
public:
  MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID(DmaGeneratePass)

  void runOnOperation() override;
  StringRef getArgument() const final { return "npu-dma-generate"; }

private:
  void collectBoundaries(mlir::func::FuncOp func);
  void insertCopies(mlir::func::FuncOp func);
};

} // namespace
```

核心流程：

```cpp
void DmaGeneratePass::runOnOperation() {
  mlir::func::FuncOp func = getOperation();
  mlir::MLIRContext *ctx = func.getContext();

  // 1) 建立分析
  mlir::AliasAnalysis aliasAnalysis = getAnalysis<mlir::AliasAnalysis>();
  mlir::DominanceInfo domInfo(func);

  // 2) 找出所有需要搬移的邊界
  llvm::SmallVector<Boundary> boundaries;
  func.walk([&](mlir::Operation *op) {
    for (mlir::OpOperand &use : op->getOpOperands()) {
      mlir::Value v = use.get();
      auto memref = v.getDefiningOp<mlir::MemRefType>();
      if (!memref)
        continue;
      // 判斷這個 memref 的 memory space 是否需要搬到目標 space
      unsigned src = memref.getMemorySpace();
      unsigned dst = targetSramSpace; // 從 Target 描述取得
      if (src == dst)
        continue;
      // 只有在被「寫入後才讀取」的情況才需要搬；這裡簡化為
      // 判斷來源 op 是否在同一個 space
      boundaries.push_back({v, src, dst, &use});
    }
  });

  // 3) 產生搬移 op
  mlir::OpBuilder builder(ctx);
  for (const Boundary &b : boundaries) {
    mlir::Operation *producer = b.value.getDefiningOp();
    if (!producer)
      continue;

    // 在生產者之後、使用者之前的合法最早位置插入
    builder.setInsertionPointAfter(producer);
    mlir::Value sramBuf = builder.create<Mychip_SramAllocOp>(
        producer->getLoc(), sramType, sramCapacityAttr);
    builder.create<Mychip_DmaCopyOp>(producer->getLoc(),
                                     mychipDmaCopyType,
                                     b.value, sramBuf);
    // 把使用點改寫成使用 SRAM buffer
    b.use->set(sramBuf);
  }
}
```

這個偽碼是**簡化**的：真實的實作還需要處理 alias、寫入者判定、非支配的使用者、以及 pipelining。但它展示了骨架。值得注意的是 `b.use->set(sramBuf)` 這一步——把 operand 換成新的值，是 bufferization 風格的「重導向」動作，MLIR 的 `OpBuilder` 提供了 `Value::replaceUsesWithIf` 這類輔助。

### 真正的實作應該長什麼樣

一個更接近真實的版本，應該把「邊界判定」從「memref 的 space 不同」改為「**資料的物理位置在 producer 與 consumer 之間改變了**」。判斷依據是：

* `producer` 的結果 buffer 位於 $S_1$ 。
* `consumer` 需要該 buffer 位於 $S_2$ 。
* $S_1 \ne S_2$ → 需要搬移。

而 buffer 位於哪個 space，則是 **bufferization 的產物**——在 bufferize 時指定 `bufferization.buffer_layout` 屬性，或由一個專門的「place buffers in SRAM」pass 決定。這個 pass 才是負責執行 11.2 的容量計算的地方：

```
Pass 1: bufferization        — 把 tensor 轉成 memref，決定 ownership
Pass 2: npu-place-buffers   — 依容量模型，把該放 SRAM 的 memref 標成 SRAM space
Pass 3: npu-dma-generate    — 依 space 差異產生搬移
Pass 4: npu-pipeline        — 重排 DMA 以重疊搬移與運算
Pass 5: npu-schedule        — 排程 SRAM banks、檢查資源
```

把「放置」與「搬移」分成兩個 pass 是重要的分層：放置是**最佳化**（受容量模型約束），搬移是**機械性**的。

## 循環 pipelining 與多 buffer

### 循環中的 DMA pipeline

考慮一個帶 $K$ 維迴圈的 matmul。搬移序列應該是：

```
dma(A_0), dma(B_0)
compute(A_0, B_0)      ; 同時 dma(A_1), dma(B_1)
compute(A_1, B_1)      ; 同時 dma(A_2), dma(B_2)
...
```

在 IR 中，用 `async` 方言表達：

```mlir
// 簡化的 pipeline 結構
%t0 = async.execute { %c = async.copy %a[0] to %buf_a0 ; async.yield } : () -> ()
%t1 = async.execute { %c = async.copy %b[0] to %buf_b0 ; async.yield } : () -> ()
%g0 = async.group [%t0, %t1] : !async.token, !async.token -> !async.group
async.await %g0 : !async.group
%r0 = mychip.pe.mma %buf_a0, %buf_b0 { rows = 128 : i64, cols = 128 : i64 }

// 下一輪的搬移提前發起
%t2 = async.execute { %c = async.copy %a[1] to %buf_a1 ; async.yield } : () -> ()
...
```

這裡 `%buf_a0` 與 `%buf_a1` 是兩份不同的 SRAM 區域，實務上通常用 `memref.alloc` 在兩個不同 memory space 實例上，或用一個帶索引的 buffer pool。

### 多 buffer 的容量代價

多 buffer 的 SRAM 需求是線性成長的。若用 $m$ 份 buffer 做 pipeline：

$$
\text{bytes} = e \cdot m \cdot (t_M t_K + t_K t_N) + e \cdot t_M t_N
$$

其中最後一項是輸出（通常不需要 double buffer，因為輸出是一次寫入）。

若 $m = 2$ （double buffering），容量需求是 11.2 公式裡係數 2 的來源。若要 triple buffering 以容忍更長的 stall，係數變成 3。

**權衡分析。** 假設運算一個 tile 需要 $T_{compute}$ 拍，搬一個 tile 需要 $T_{dma}$ 拍。

* 單緩衝：總時間 $\approx (T_{compute} + T_{dma}) \times n$ 。
* 雙緩衝：若 $T_{dma} \le T_{compute}$ ，總時間 $\approx T_{compute} \times n + T_{dma}$ ；否則 $\approx T_{dma} \times n + T_{compute}$ 。
* 一般化 $m$ 緩衝：吞吐受限於 $\max(T_{compute}, T_{dma})$ 。

所以增加 buffer 份數的收益是**單調遞減但趨於飽和**的：從 1 到 2 通常是接近 2 倍的收益，從 2 到 3 只有在 $T_{dma}$ 與 $T_{compute}$ 非常接近時才有明顯效果。SRAM 是寶貴資源，因此實務上通常從 2 開始，只有在 profile 顯示搬移是瓶頸時才增加。

## 一個完整的 IR 範例

把高階到硬體層的整條鏈路寫出來。

**高階：**

```mlir
func.func @forward(%a: tensor<256x512xf32>, %b: tensor<512x128xf32>)
    -> tensor<256x128xf32> {
  %cst = arith.constant 0.0 : f32
  %init = tensor.empty() : tensor<256x128xf32>
  %z = linalg.fill ins(%cst : f32) outs(%init : tensor<256x128xf32>) -> tensor<256x128xf32>
  %r = linalg.matmul ins(%a, %b : tensor<256x512xf32>, tensor<512x128xf32>)
                outs(%z : tensor<256x128xf32>) -> tensor<256x128xf32>
  return %r : tensor<256x128xf32>
}
```

**bufferize 之後（`npu-place-buffers` 決定哪些 buffer 在 SRAM）：**

```mlir
func.func @forward(%a: memref<256x512xf32>, %b: memref<512x128xf32>)
    -> memref<256x128xf32> {
  %cst = arith.constant 0.0 : f32
  %init = memref.alloc() : memref<256x128xf32, 3>
  linalg.fill ins(%cst : f32) outs(%init : memref<256x128xf32, 3>)
  %r = memref.alloc() : memref<256x128xf32, 3>
  linalg.matmul ins(%a, %b : memref<256x512xf32>, memref<512x128xf32>)
                outs(%r : memref<256x128xf32, 3>) -> memref<256x128xf32, 3>
  return %r : memref<256x128xf32, 3>
}
```

**DMA 生成之後（簡化，忽略 K 維迴圈展開）：**

```mlir
func.func @forward(%a: memref<256x512xf32>, %b: memref<512x128xf32>)
    -> memref<256x128xf32> {
  %cst = arith.constant 0.0 : f32

  %a_sram = mychip.sram.alloc() { size = 65536 : i64 } : !mychip.sram<65536>
  %b_sram = mychip.sram.alloc() { size = 65536 : i64 } : !mychip.sram<65536>
  %out_sram = mychip.sram.alloc() { size = 65536 : i64 } : !mychip.sram<65536>

  %ta = mychip.dma.copy %a, %a_sram { sync_group = 0 : i32 } : memref<256x512xf32> to !mychip.sram<65536>
  %tb = mychip.dma.copy %b, %b_sram { sync_group = 0 : i32 } : memref<512x128xf32> to !mychip.sram<65536>
  mychip.dma.wait %ta, %tb : !mychip.dma.token, !mychip.dma.token

  %init = memref.alloc() : memref<256x128xf32, 3>
  linalg.fill ins(%cst : f32) outs(%init : memref<256x128xf32, 3>)
  linalg.matmul ins(%a_sram, %b_sram : !mychip.sram<65536>, !mychip.sram<65536>)
                outs(%init : memref<256x128xf32, 3>) -> memref<256x128xf32, 3>
  return %init : memref<256x128xf32, 3>
}
```

**硬體層（descriptor 形式）：**

```mlir
mychip.dma.submit channel 0 {
  descriptors = [
    { src = 0 : i64, dst = 0 : i64, len = 65536 : i64, format = "f32" },
    { src = 131072 : i64, dst = 65536 : i64, len = 65536 : i64, format = "f32" }
  ]
}
```

從這個範例可以看到 DMA 生成的三個副產品：**SRAM 配置**、**搬移時機**、以及 **memory space 的重導向**。

## 驗證策略

DMA 生成是那種「靜態看起來對、動態才會炸」的 pass。建議的驗證手段：

1. **差分測試**：同一個 kernel，用與不用 DMA pass 兩條路徑執行，比對輸出。這個方法能抓到絕大多數索引與時序錯誤。
2. **descriptor 檢查器**：寫一個小的驗證 pass，檢查每個 descriptor 的 `len` 是硬體粒度的倍數、`dst + len` 不超過 SRAM 容量、`src + len` 不超過來源 buffer 大小。這類「硬體常數檢查」最好寫成 verifier，放在 dialect 層。
3. **race detector**：模擬硬體的非同步行為，檢查是否有「讀未初始化資料」或「buffer 在仍被使用時被覆寫」。這需要一個模擬 DMA 執行的 runtime。
4. **資源報告**：印出一張表，說明每個 SRAM 區域的使用者與生命週期，便於人工檢查排程品質。

## 小結與延伸閱讀

* 搬移是 NPU 上最大的成本項（能耗佔比與延遲），因此編譯器的目標是**最小化從 DRAM 搬運的位元組數**，而不是最小化指令數。
* 產生 DMA 所需的四個資訊——誰產生、誰消費、資料多大、何時可搬——正好對應 MLIR 的 bufferization、memref shape、alias 分析與依賴圖。
* 演算法骨架是：alias 分析 → 決定唯一寫入者 → 沿資料流邊插 DMA → 軟體 pipelining → 資源檢查。
* `async` 方言的 `async.copy` / `async.group` / `async.await` 是非同步搬移的標準中層表示；`gpu.memcpy_async` 的 `SyncGroup` 屬性則是「描述符分組」的直接先例。
* 實務分層是：**bufferize → 放置 buffer 到 SRAM（最佳化）→ 生成 DMA（機械性）→ pipeline（重疊）→ 資源排程**。
