# 2.1 型別系統：Type、Storage 與 Typeless 的設計

第一部我們把注意力放在 IR 的**結構**上：`Operation`、`Block`、`Region`。從這一部開始，我們轉向 IR 的**語意載體**——型別與屬性。

先問一個根本問題：MLIR 為什麼不像早期 LLVM 那樣選擇「typeless IR + 選項旗標」的路線？

LLVM 在 2003 年前後就已經放棄了早期那種「每個值都帶一個抽象型別 ID（bty）」的設計，改用 typed pointers 與多樣化的值種類。原因很實際：抽象型別 ID 需要維護全域的型別表、要處理型別的合併（union）、要在每次操作時做間接查詢，而且把「這個操作合法嗎」的判斷延後到驗證階段才做，錯誤訊息也會變得遙遠。

MLIR 面對的是一個更廣的抽象層譜系（從 tensor 到 LLVM 指令），因此選擇了相反但更細緻的路線：**每一層都保留足夠的型別資訊，但型別系統本身是「多型別但可辨識」的**——同一個 context 內有許多具體型別（`i32`、`f32`、`tensor<128x256xf32>`、`memref<?x?xf32, strided<[?, ?], offset: ?>>`），每個值都精確指向其中一個。

## Type 的核心介面

`mlir::Type` 是所有型別的共同基類。它的設計刻意做得很薄：

```cpp
class Type {
public:
  bool isa<ConcreteType>() const;
  bool isa_and_nonnull<ConcreteType>() const;
  Type getDialect() const;   // 這個型別所屬的方言
};
```

`Type` 幾乎沒有方法，因為它只是一個指向**堆積上被 uniqued 的 storage 物件**的指標。所有型別的實際資料都在 storage 裡。

C++ 端的向下轉型範式：

```cpp
void dumpType(mlir::Type type) {
  if (auto intType = dyn_cast<mlir::IntegerType>(type)) {
    llvm::outs() << "integer of width " << intType.getWidth() << "\n";
  } else if (auto f32 = dyn_cast<mlir::FloatType>(type)) {
    llvm::outs() << "float of width " << f32.getWidth() << "\n";
  } else if (auto tensor = dyn_cast<mlir::RankedTensorType>(type)) {
    llvm::outs() << "ranked tensor of shape " << tensor.getShape() << "\n";
  }
}
```

`isa` 與 `dyn_cast` 之所以便宜，是因為每個型別類別都有一個唯一的 **TypeID**（`MLIRContext::getTypeID<ConcreteType>()`），而 storage 物件的第一個欄位就存著它。`isa` 是「讀 ID 並比對」，`dyn_cast` 是「讀 ID 並調整指標」。

## Uniquing：context 內的型別池

MLIR 的 `MLIRContext` 內含一個**型別池**。每個 context 為每一類 storage 維護一個以「key」為索引的 map：

```cpp
// 概念上的結構
template <typename StorageT>
class TypeUniquer {
  llvm::DenseMap<StorageKey, StorageT> storage;
  // key 由 storage 的 key 函式計算
};
```

`mlir::detail::TypeUniquer::get` 的流程是：

1. 由 `ConcreteType` 的 `KeyTy`（一組描述 storage 內容的 key）建立查詢鍵；
2. 在 pool 裡查詢；
3. 命中則回傳既有的 `Type` 指標（uniqued）；
4. 未命中則配置新的 storage、呼叫建構函式、註冊到 pool。

以 `IntegerType` 為例，key 是 `(width, signedness)`：

$$
\text{key}(\text{IntegerType}) = (\text{width},\ \text{signedness}) \in \mathbb{N} \times \{s, u, si\}$$

因此 `i32` 在同一個 context 內永遠是同一個指標。

這個設計帶來的直接好處是**型別比較退化為指標比較**。`a.getType() == b.getType()` 不需要深層比較，兩行程式碼就解決了。在大型 IR 上，型別比較是熱路徑，這一點非常重要。

**代價**是型別不能跨 context 使用。`Type` 是 context-local 的，不同 context 的 `i32` 是不同指標。這在 MLIR 的實務中幾乎不是問題（一般只有一個 context），但在 FFI 或多 context 場景要注意。

Python 端也遵守這個規則：`Context` 物件是所有 type 與 operation 的歸屬地。

## 內建型別巡禮

MLIR 的內建型別（`mlir` dialect 的 builtin types）涵蓋了大部分硬體與陣列計算需要的基本概念。

### Index 型別

`Index` 是 MLIR 的一個特殊設計：一種「大小未定的整數」，用來表示索引、偏移量、迴圈計數器。

```mlir
%i = arith.constant 0 : index
%j = arith.index_cast %i : index to i64
```

它存在的理由是：**索引在硬體上的寬度是實作相關的**。同一份高階 IR 降階到 32 位元與 64 位元的目標時，索引寬度可能不同。用 `index` 讓高階層不必綁死，下層再決定要 cast 成 `i32` 還是 `i64`。

`index` 不能直接做大多數算術運算（例如 `arith.addi` 要求 `signless` 整數），必須先 cast。這是刻意的：`index` 的算術語意在 overflow 時沒有明確答案。

### Integer 型別：位元寬與符號性

MLIR 的整數型別有三個屬性：**寬度**（1 到 64 以上的 bits）與**符號性**（signless / signed / unsigned）。

```mlir
%a = arith.constant 5 : i32          // signless
%b = arith.constant -5 : si32        // signed
%c = arith.constant 5 : ui32         // unsigned
```

符號性的三種形態：

| 形態 | MLIR 語法 | 語意 |
|---|---|---|
| signless | `i32` | 位元模式，運算結果解讀由使用者決定 |
| signed | `si32` | 有二補碼解讀，`si32` 範圍為 $[-2^{31}, 2^{31}-1]$ |
| unsigned | `ui32` | 有非負解讀，`ui32` 範圍為 $[0, 2^{32}-1]$ |

**signless 是預設**，這是 MLIR 相較 C/LLVM 的一個重要取捨。LLVM 的整數沒有符號性（`i32` 是位元模式），需要靠 `nsw`/`nuw` 旗標表達 overflow 語意。MLIR 選擇讓「有符號性」成為**型別的一部分**，好處是：

* 運算（例如 `arith.divsi` vs `arith.divui`）的合法性可以由型別決定；
* 轉換與最佳化規則可以依型別精細匹配；
* signedness 不再是散落在指令旗標裡的隱性資訊。

代價是**同一個值在不同 signedness 下需要轉換**（`arith.sitofp`、`arith.uitofp`），而且設計方言時必須明確決定整數的符號性。MLIR 的 `arith` 方言對整數運算要求 signless，因為那些運算（如 `addi`、`muli`、`andi`）在位元層面與符號性無關；有符號性相關的運算（`divsi`、`shli` vs `ashr`）則直接以型別區分操作名稱。

宽度與符號性的組合實例：

```cpp
mlir::IntegerType i32 = builder.getI32Type();        // signless
mlir::IntegerType si32 = builder.getSignlessIntegerType(32);
mlir::IntegerType s32 = builder.getSignedIntegerType(32);
mlir::IntegerType u32 = builder.getUnsignedIntegerType(32);
```

### Float 型別

`FloatType` 涵蓋 IEEE 754 的各種寬度，以及新興的壓縮格式：

```mlir
%a = arith.constant 1.0 : f16
%b = arith.constant 1.0 : f32
%c = arith.constant 1.0 : f64
%d = arith.constant 1.0 : bf16
%e = arith.constant 1.0 : f8E4M3FN
```

MLIR 為浮點提供了 `getFloatSemantics()` 回傳語意列舉：

* `FloatSemantics::IEEE`（`f16` / `f32` / `f64` / `f128`）
* `FloatSemantics::BF16`
* `FloatSemantics::Float8E4M3FN`、`Float8E4M3FNUZ`、`Float8E5M2`、`Float8E5M2FNUZ` 等

浮點的 NaN payload、 Signaling NaN 等細節由 `FloatType` 的語意旗標表達。這些旗標在 `arith` 比較運算中特別重要：NaN 上的比較結果取決於是否有 payload 與是否為 signaling。

### Vector 型別

`VectorType` 表示固定寬度的 SIMD 向量：

```mlir
%v = vector.load %ptr : vector<8xf32>, memref<?xf32>
%w = vector.fma %v, %v, %v : vector<8xf32>
```

Vector 的構成要素：

* `elementType`：元素型別（必須是 `FloatType`、`IntegerType` 或 `IndexType`）。
* `numElements`：元素數量。
* `shape`：形狀（多維向量用）。
* `scalable`：**可縮放向量**旗標。`vector<16x[4]xf32>` 這種寫法表示「16 個，每個是 4 個 scalable 單位」，用於 SVE / RVV 這類硬體向量長度由暫存器決定的架構。

```mlir
// 固定長度
vector<8xf32>
// scalable
vector<16x[4]xf32>
```

`VectorType::get` 與 `VectorType::getChecked` 傳入 `ArrayRef<int64_t>` 形狀，負數代表 scalable 維度：

```cpp
auto v8 = VectorType::get({8}, f32);
// scalable：-1 表示長度由硬體決定
auto vScale = VectorType::get({-1}, f32);
```

### Complex 型別

`ComplexType` 把實部與虛部打包成一個值：

```mlir
%c = complex.constant 1.0 : complex<f32>
```

`complex` 方言的運算（如 `complex.add`）會展開成 `arith.addf` 與 `arith.subf` 的組合。

### Tuple 與 None

`TupleType` 表示異質的元組，用於多返回值：

```mlir
func.func @pair() -> (i32, f32)
```

`NoneType` 是「沒有型別」，用於不需要結果的操作。

### Function 型別

`FunctionType` 描述函式的簽章：

```cpp
auto fnType = builder.getFunctionType(
    /*inputs=*/{builder.getI32Type(), builder.getF32Type()},
    /*results=*/{builder.getI32Type()});
```

## Tensor 型別

`TensorType` 是機器學習編譯的核心抽象，分為 ranked 與 unranked 兩種。

### RankedTensorType

形狀已知、維度數已知的張量：

```mlir
tensor<128x256xf32>
tensor<?x?xf32>          // 維度未知，但維度數已知
tensor<*xf32>            // unranked，維度數也未知
tensor<128x256x!vector<8xf32>>
```

`RankedTensorType` 的核心 API：

```cpp
mlir::RankedTensorType t = dyn_cast<mlir::RankedTensorType>(type);
auto shape = t.getShape();        // ArrayRef<int64_t>
auto elem  = t.getElementType();  // Type
int64_t rank = t.getRank();
bool dynamic = t.isDynamicDim(0);
```

動態維度用 `ShapedType::kDynamic`（值為 `-1`）表示。

### UnrankedTensorType

```mlir
tensor<*xf32>
```

維度數未知。這個型別主要用在**尚未完成形狀推導**的中間階段，是允許 shape inference 尚未收斂時的過渡狀態。

### DenseElementsAttr 與張量的關係

張量的**值**不是一個 `Value`（SSA value），而是一個 `Attribute`——具體地說是 `DenseElementsAttr`：

```mlir
%c = arith.constant dense<[1.0, 2.0, 3.0]> : tensor<3xf32>
```

`DenseElementsAttr` 保存的是**型別化的元素位元組**，而不是文字表示。它提供：

* `getValues<APInt>()` / `getValues<APFloat>()`：以原生型別取出元素；
* `isSplat()`：是否是單一值重複填充（broadcast 的常見情形，壓縮儲存）；
* `getValuesPerElement()`：每個元素的位元組數。

這也解釋了 MLIR 的一個重要設計：**常數不佔用 SSA value 與 operand 空間**，而是作為屬性附著在產生它的 op 上。

## MemRef 型別

`MemRefType`（`UnrankedMemRefType` 為無秩版本）描述「一段記憶體的視圖」：

```mlir
memref<?x?xf32, strided<[?, ?], offset: ?>>
memref<128xf32>
memref<*xf32>
```

`MemRefType` 的構成：

| 欄位 | 說明 |
|---|---|
| shape | 各維度大小，動態維度為 `kDynamic` |
| elementType | 元素型別 |
| layout | 記憶體佈局（identity 或 strided） |
| memorySpace | 記憶體空間（預設為 nullptr，代表通用位址空間） |

`StridedLayoutAttr` 描述帶有 stride 的非緊密佈局：

```mlir
memref<128xf32, strided<[1], offset: 0>>
memref<4x4xf32, strided<[8, 1], offset: 0>>   // 一個 4x4 子矩陣
```

`memref` 的出現解決了高階 tensor 與低階機器碼之間的落差：`tensor` 是**值語意**（不可變、有形狀、無位址），`memref` 是**引用語意**（有位址、有佈局、可變）。`bufferization` 方言的工作正是把前者轉成後者。

```mlir
// memref 的運算
%v = memref.load %buf[%i, %j] : memref<128x256xf32>
memref.store %v, %buf[%i, %j] : memref<128x256xf32>
```

## Type 的 Dialect 歸屬

每個 `Type` 都屬於一個方言。這不是裝飾性的資訊，而是驅動多項核心機制的關鍵。

`Type::getDialect()` 回傳擁有該型別的方言：

```cpp
if (auto t = dyn_cast<mlir::TensorType>(type)) {
  // builtin 方言
}
```

**為什麼需要歸屬？**

1. **型別的可辨識性與轉換責任**。轉換框架在把一個型別轉成另一個型別時，會查詢「哪個方言的轉換路徑處理這個型別」。`TypeConverter` 的 `addConversion` 就是註冊「從型別 A 到型別 B 的轉換」。
2. **Dialect 卸載（unloading）**。MLIR 允許卸載未使用的方言，卸載時連帶其自有型別一起釋放。歸屬資訊讓這件事可以安全進行。
3. **命名空間隔離**。不同方言可以有同名但不同語意的型別。

**方言自有型別**的建立需要走 dialect 的 uniquer：

```cpp
// 在方言類別中
class MyDialect : public mlir::Dialect {
public:
  explicit MyDialect(mlir::MLIRContext *ctx) : mlir::Dialect(getDialectNamespace(), ctx, TypeID::get<MyDialect>()) {
    addTypes<MyTensorType, MyLayoutType>();
  }
};

// 型別定義
class MyTensorType : public mlir::Type::TypeBase<MyTensorType, mlir::Type,
                                                detail::MyTensorTypeStorage> {
public:
  using Base::Base;
  mlir::Type getElementType() const;
  static MyTensorType get(mlir::MLIRContext *ctx, mlir::Type elementType);
};
```

注意 `TypeBase` 這個模板：它把「storage 的生命週期管理」、「uniquing」、「TypeID 關聯」、「downcast 支援」全部自動處理。方言作者通常只需要定義 storage 的 key 與存取器。

```cpp
struct MyTensorTypeStorage : public mlir::TypeStorage {
  using KeyTy = mlir::Type;
  bool operator==(const KeyTy &key) const { return elementType == key; }

  MyTensorTypeStorage(mlir::Type elementType) : elementType(elementType) {}

  mlir::Type elementType;
};
```

`KeyTy` 決定了 uniquing 的鍵；`operator==` 決定命中判斷。對於不可變的 key（整數寬度、符號性）這很直接；對於 key 本身是一個 `Type` 的情況（如 `MyTensorType` 以 elementType 為 key），比對就是指標比較，因為 elementType 也已被 uniqued。

## ODS 中的 Type Constraint 宣告

TableGen 讓型別約束成為操作定義的一部分：

```tablegen
def AddIOp : Arith_Op<"addi", [Pure, SameOperandsAndResultType]> {
  let arguments = (ins SignlessIntegerLike:$lhs, SignlessIntegerLike:$rhs);
  let results = (outs SignlessIntegerLike:$result);
  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
```

常用的內建 constraint：

| Constraint | 意義 |
|---|---|
| `AnyType` | 任意型別 |
| `AnyInteger` | 任意整數（含 signless/signed/unsigned） |
| `SignlessIntegerLike` | signless 整數，寬度不限 |
| `IntegerLike` | signless 整數，寬度為 1 的倍數 |
| `I32` / `I64` | 固定寬度 |
| `AnyFloat` | 任意浮點 |
| `F32` / `F64` | 固定寬度浮點 |
| `AnySignlessInteger` | signless 整數 |
| `AnyIntegerOrFloat` | 整數或浮點 |
| `AnyTensor` / `AnyRankedTensor` | 張量 |
| `AnyMemRef` | memref |
| `AnyVector` | 向量 |
| `AnyTypeOf<[Types]>` | 從 type constraint 清單選取 |

自訂 constraint：

```tablegen
def AnyFloatOrInt : AnyTypeOf<[AnyFloat, AnyInteger]>;
def ScalarOrTensor : AnyTypeOf<[AnyType, AnyTensor]>;
```

constraint 也可以帶有**額外驗證**（需要 C++ 輔助函式）：

```tablegen
def NonZeroI64 : Type<
  And<[CPred<"$_self.cast<IntegerType>().getWidth() == 64">,
       CPred<"!$_self.cast<IntegerType>().getWidth() == 0">]>,
  "64-bit integer">;
```

constraint 不只是文件，它被轉譯成 `Op::verify()` 中的實際檢查程式碼。

## 為何選擇「多型別但可辨識」

現在可以回答本章的核心問題。MLIR 的型別系統在兩個極端之間取了一個位置：

* **不是 typeless**：每個值都有精確的型別，錯誤在建立時就被抓出來。
* **不是單一抽象型別 ID**（早期 LLVM 的 `bty`）：型別是結構化的、可被 pattern 匹配的、可被轉換的。

「可辨識」（identifiable）這個詞很關鍵：一個型別不只是「某個 ID」，它帶有**結構資訊**。`tensor<128x256xf32>` 讓最佳化器知道這是二維、元素是 32 位元浮點；`memref<?x?xf32, strided<[?, ?], offset: ?>>` 讓它知道這是動態形狀、非連續佈局。轉換框架可以依型別的**形狀**而非僅僅名稱來做決策：

```cpp
// 依型別結構而非名稱判斷
auto ranked = dyn_cast<mlir::RankedTensorType>(oldType);
if (ranked && ranked.getElementType().isF32()) {
  // 走 f32 專屬路徑
}
```

**Typed IR 對錯誤偵錯的價值**，可以用一個對比說明。假設一個整數與浮點混用的 bug：

* 在 typeless IR 中，錯誤會一路流到後端，最後以「非法指令」或靜默的錯誤結果出現，診斷資訊早已遺失。
* 在 typed IR 中，`arith.addi` 的 operand 是 `f32` 會在 **verify 階段**被立刻抓出，錯誤訊息包含操作名、位置、以及期望與實際的型別。

這個差異在高階方言中尤其重要，因為高階 IR 經歷的轉換次數多、來回修改頻繁，型別錯誤若不在早期攔截，會在數十次轉換後才以一個完全無關的症狀浮現。

另一個價值是**最佳化的精確性**。以 elementwise 為例，如果型別是 signless 的 `i32`，融合規則必須小心處理 overflow；若型別是 `f32`，就可以自由地做向量化與重排。

## 用 C++ 與 MLIR 展示型別操作

```cpp
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/Dialect/Arith/IR/Arith.h"

using namespace mlir;

void exploreTypes(OpBuilder &builder) {
  MLIRContext *ctx = builder.getContext();

  // 內建型別
  Type i32 = builder.getI32Type();
  Type f32 = builder.getF32Type();
  Type index = builder.getIndexType();

  // 判斷與轉型
  if (auto intType = dyn_cast<IntegerType>(i32)) {
    unsigned width = intType.getWidth();
    bool isSigned = intType.isSigned();
    bool isSignless = intType.isSignless();
    (void)width; (void)isSigned; (void)isSignless;
  }

  // 張量型別
  auto tensorType = RankedTensorType::get({128, 256}, f32);
  ArrayRef<int64_t> shape = tensorType.getShape();
  (void)shape;

  // memref 型別
  auto memRefType = MemRefType::get({-1, -1}, f32);
  (void)memRefType;

  // uniquing 檢查：同一 context 內兩次取得必為同一指標
  assert(i32 == builder.getI32Type());

  // 建立一個帶型別的操作
  Value lhs = builder.create<arith::ConstantOp>(
      builder.getUnknownLoc(), builder.getI32IntegerAttr(7));
  Value rhs = builder.create<arith::ConstantOp>(
      builder.getUnknownLoc(), builder.getI32IntegerAttr(9));
  Value sum = builder.create<arith::AddIOp>(
      builder.getUnknownLoc(), lhs, rhs).getResult();
  // sum.getType() == i32
  (void)sum;
}
```

MLIR 端：

```mlir
// 內建型別
%i = arith.constant 42 : i32
%f = arith.constant 3.14 : f32
%idx = arith.constant 0 : index

// 型別轉換
%as_f32 = arith.sitofp %i : i32 to f32
%as_i64 = arith.index_cast %idx : index to i64

// 張量與 memref
%t = arith.constant dense<1.0> : tensor<4xf32>
%m = memref.alloca() : memref<4xf32>
memref.store %f, %m[%idx] : memref<4xf32>

// 向量
%v = vector.broadcast %f : f32 to vector<8xf32>
```

## 常見陷阱

1. **`i` 與 `si` / `ui` 混用**。`arith.addi` 要求 signless；`arith.addsi` 在 MLIR 中並不存在——有符號性相關的運算透過型別區分（`arith.divsi` 接受 `si32`，`arith.divui` 接受 `ui32`）。
2. **index 不能直接運算**。`arith.addi %idx, %idx : index` 是非法的，因為 `index` 不是整數型別（它是 `IndexType`）。必須先 `arith.index_cast`。
3. **DenseElementsAttr 的元素型別要與張量一致**。`dense<[1.0, 2.0]> : tensor<2xi32>` 會驗證失敗。
4. **跨 context 的型別不能比較**。`ctx1.getI32Type() == ctx2.getI32Type()` 恆為 false，即使語意相同。
5. **動態維度與靜態維度的 shape 推導**。`tensor<?xf32>` 的 shape 推導結果是 `tensor<4xf32>` 或失敗，不能是 `tensor<?xf32>`（除非推導失敗）。

## 小結與延伸閱讀

* `mlir::Type` 是所有型別的共同基類，實際資料存在於 context 內被 uniqued 的 storage 中；uniquing 使型別比較退化為指標比較，代價是型別不可跨 context 使用。
* 內建型別涵蓋 `Index`（大小未定的索引）、三種符號性的 `IntegerType`、各種寬度與語意的 `FloatType`、支援 scalable 的 `VectorType`、`ComplexType`、`TupleType` 與 `FunctionType`。
* `TensorType` 分 ranked 與 unranked；`MemRefType` 額外攜帶 layout 與 memory space，兩者構成「值語意」與「引用語意」的對立，也是 `bufferization` 轉換的核心。
* 每個型別歸屬於一個方言，這是 `TypeConverter` 路由、`Dialect` 卸載與命名空間隔離的基礎；ODS 的 type constraint 會被轉譯成 `verify()` 中的實際檢查。
