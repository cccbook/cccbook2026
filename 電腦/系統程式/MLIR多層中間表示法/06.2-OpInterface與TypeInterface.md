# 6.2 Interface：在不修改 Op 定義下擴充多態行為

在 [6.1](06.1-Verifier與結構不變式.md) 我們談到 op 宣告自己的不變式。但有一類問題，op 定義本身無法回答：「這個 op 會不會寫記憶體？」「這個 op 是不是一個函式符號？」「這個 op 的迭代空間是什麼？」

這些問題的共同點是：**答案取決於 op 的「角色」，而不是 op 的「形狀」**。同一個角色可能由數十種不同方言的 op 共同扮演。這一章介紹的 Interface 機制，就是 MLIR 用來表達「角色」的正式手段。

## 為什麼需要 Interface

先看一個具體的痛點。假設你要寫一個「刪除所有沒有副作用的 op」的 pass。最自然的想法是：

```cpp
// 這個寫法很直覺，但幾乎沒有人這樣寫。
if (isa<arith::AddFOp, arith::MulFOp, tensor::ExtractOp, linalg::MatmulOp,
        my::MyPureOp, ...>(op))
  continue;
```

這個清單永遠寫不完，而且每當上游新增一個純 op，你都得回來維護。

另一種想法是「加一個 trait」：

```tablegen
def My_Op : My_Op<"my_op", [Pure]> { ... }
```

`Pure` 這個 trait 確實存在，而且被大量使用。但 trait 的限制是：**它只能宣告「是或不是」**。`Pure` 能說「這個 op 沒有副作用」，卻說不了「這個 op 有哪些副作用、作用在哪個資源上」。

而後者正是現代編譯器需要知道的。舉例來說，一個 pass 要做「把獨立的記憶體存取重排以提高 ILP」，它需要知道：

- 這個 op 會讀記憶體嗎？讀哪一個？
- 這個 op 會寫記憶體嗎？寫哪一個？
- 兩個 op 會不會 alias？

「哪一個記憶體」這個資訊，需要一個**有參數**的方法來表達。trait 無法承載。

### Trait 與 Interface 的分工

| | Trait | Interface |
| --- | --- | --- |
| 承載的資訊 | 布林標記或少量靜態資料 | 有方法、可以有狀態 |
| 宣告方式 | `OpTrait` / `Trait` | `OpInterface` / `TypeInterface` / `AttributeInterface` |
| 能否有多個實作 | 單一（可多個 trait 組合） | 單一 op 可實作多個 interface |
| 能否外部擴充 | 否（需修改 op 定義） | **是**（external model） |
| 典型用途 | `Pure`、`OneResult`、`SameOperandsAndResultType` | 副作用分析、符號查詢、迭代空間描述 |

一句話總結：**trait 描述「結構特徵」，interface 描述「行為能力」**。

## `OpInterface` / `TypeInterface` / `AttributeInterface`

MLIR 提供三種 interface：

```cpp
namespace mlir {

/// Operation 介面。
template <typename ConcreteType, typename Traits, typename BaseType,
          typename ValueT = Value, typename SummaryT = ...>
class OpInterface;

/// Type 介面。
template <typename ConcreteType, typename Traits, typename BaseType,
          typename ValueT = Type, typename SummaryT = ...>
class TypeInterface;

/// Attribute 介面。
template <typename ConcreteType, typename Traits, typename BaseType,
          typename ValueT = Attribute, typename SummaryT = ...>
class AttributeInterface;

} // namespace mlir
```

它們共同的基底是 `mlir::detail::Interface`（定義於 `mlir/Support/InterfaceSupport.h`），提供了：

- **方法宣告**：介面定義一組純虛函式，所有實作者必須提供。
- **外部模型（external model）**：可以在不修改 op 定義的情況下，讓某個 op 實作介面。
- **`TypeID` 查表**：每個介面在編譯期生成一張「實作表」，執行期以 `TypeID` 查找。
- **`isa` / `cast` / `dyn_cast` 的支援**。

### ODS 中的介面宣告

介面通常在方言的 `.td` 檔案中宣告。以一個描述「有迭代空間的結構化 op」的自訂介面為例：

```tablegen
// my_interfaces.td
def My_StructuredOpInterface : OpInterface<"StructuredOpInterface", OpInterfaceTrait::HasOneResult> {
  let description = [{
    描述一個具有迭代空間 (iteration space) 的結構化 op。
    實作者必須提供迭代維度數、每個維度的靜態長度，以及
    op 的結果與哪個維度綁定 (tied) 的資訊。
  }];

  let methods = [
    InterfaceMethod<
      /*desc=*/"回傳迭代空間的維度數",
      /*retTy=*/"unsigned",
      /*methodName=*/"getNumLoops"
    >,
    InterfaceMethod<
      /*desc=*/"回傳每個迭代維度的長度；動態維度回傳 ShapedType::kDynamic",
      /*retTy=*/"SmallVector<int64_t>",
      /*methodName=*/"getStaticLoopRanges"
    >,
    InterfaceMethod<
      /*desc=*/"回傳結果綁定的迭代維度索引",
      /*retTy=*/"int64_t",
      /*methodName=*/"getTiedIndex"
    >,
  ];

  let extraClassDeclaration = [{
    /// 便利方法：迭代空間是否為全靜態。
    bool hasStaticIterationSpace() {
      return llvm::all_of(getStaticLoopRanges(),
                          [](int64_t dim) { return dim != ShapedType::kDynamic; });
    }
  }];
}
```

`OpInterface<"StructuredOpInterface", Traits>` 的第一個參數是介面的**類別名稱字串**（不含命名空間前綴），第二個參數是介面要求的 trait。第二個參數的意義是「實作者必須同時滿足這些 trait」——例如要求 `HasOneResult` 意味著實作者的 op 必須有一個 result，這樣介面方法裡才能安全地使用 `getResult()`。

### 帶有 trait 的介面

介面可以宣告自己的輔助 trait，讓實作者以 trait 的形式獲得額外能力：

```tablegen
def My_StaticShapeOpInterface : OpInterface<"StaticShapeOpInterface", Traits> {
  let traits = [DeclareOpInterfaceMethods<My_StructuredOpInterface>];
}
```

介面之間也可以有繼承關係（透過 `Interface` 關鍵字在 ODS 中表達），這在實務上用得比想像中多——例如「有迭代空間的介面」與「有映射的介面」往往有共同部分。

## 外部模型：不解修改 op 定義就能實作介面

這是 interface 相對於 trait 最關鍵的能力。

假設我們想讓 `arith` 方言裡的某個既有 op（`arith.addf`）也能被視為具有「迭代空間」——但我們不能修改 `arith` 的原始定義（那在別的專案裡）。解法是**外部模型（external model）**：

```cpp
namespace mlir {
namespace arith {

/// 讓 arith.addf 以外部模型的方式實作 My_StructuredOpInterface。
class AddFOpStructuredInterface
    : public My_StructuredOpInterface::ExternalModel<
          AddFOpStructuredInterface, arith::AddFOp> {
public:
  unsigned getNumLoops() const { return 0; }

  SmallVector<int64_t> getStaticLoopRanges() const { return {}; }

  int64_t getTiedIndex() const { return 0; }
};

} // namespace arith
} // namespace mlir
```

然後註冊：

```cpp
void registerMyInterfaces(DialectRegistry &registry) {
  registry.addExternalModel<arith::AddFOpStructuredInterface,
                            arith::AddFOp>();
}
```

註冊之後，`isa<My_StructuredOpInterface>(op)` 對 `arith.addf` 就會回傳 `true`。

### 外部模型的代價

外部模型不是免費的：

- 它**不能**為 op 增加新的 operand、result 或屬性，只能提供行為。
- 它是**附加**的：op 本身的定義完全不變，所以 op 的語意不會改變，只是「被看見的方式」改變了。
- 註冊必須在 op 被建立之前完成，否則已存在的 op 實例不會被回溯更新。因此註冊通常放在 dialect 的 `initialize()` 或 `MLIRContext` 建立時的 dialect registry 中。

## `isa` / `cast` / `dyn_cast` 與 `TypeID`

MLIR 的 `isa` / `cast` / `dyn_cast` 定義於 `mlir/Support/LLVM.h`（轉接自 LLVM 的 `llvm::isa`）。對一般類別，它們走的是 C++ 的繼承關係；對介面，它們走的是**執行期的 `TypeID` 查表**。

```cpp
// 一般類別：繼承鏈比對。
if (isa<arith::AddFOp>(op)) { ... }

// 介面：TypeID 查表。
if (isa<My_StructuredOpInterface>(op)) {
  auto structured = cast<My_StructuredOpInterface>(op);
  unsigned loops = structured.getNumLoops();
}
```

這個查表的機制由 `mlir/Support/Casting.h` 中的 `InterfaceCastInfo` 專化提供。核心流程是：

```text
isa<InterfaceT>(value):
    1. 取得 value 的具體 TypeID（對 op 而言是 OperationName 的識別碼）
    2. 在 InterfaceT 的實作表中查找該 TypeID
    3. 找到則回傳 true，否則回傳 false
```

### `TypeID` 的唯一性

`TypeID`（定義於 `mlir/Support/TypeID.h`）是 MLIR 的執行期型別識別碼，具有兩個性質：

1. **唯一性**：同一個 C++ 型別永遠對應到同一個 `TypeID`；不同型別對應到不同 `TypeID`。
2. **穩定性**：在同一個行程的生命週期內，`TypeID` 的值固定。

取得方式：

```cpp
mlir::TypeID id = mlir::TypeID::get<My_StructuredOpInterface>();
```

要讓一個類別能作為介面的具體實作者，它必須有唯一的 `TypeID`。在實務上，MLIR 透過兩種方式達成：ODS 產生的 op 類別會自動獲得；自行撰寫的類別則需要提供 `static mlir::TypeID getTypeID()`（或繼承 `mlir::TypeID::TypeIDBase` 這類提供該機制的基底類別）。具體要求以 `mlir/Support/TypeID.h` 的說明為準。

值得留意的是：`TypeID` 與 C++ 的 `typeid` 不同，它不依賴 RTTI，也不保證跨行程穩定——它的用途是同一個 `MLIRContext` 內的快速查找。

## 常見的既有介面

MLIR 上游提供了一批廣泛使用的介面。知道它們的存在，能省下大量重寫。

| 介面 | 標頭檔 | 用途 |
| --- | --- | --- |
| `FunctionOpInterface` | `mlir/Interfaces/FunctionInterfaces.h` | 描述可作為函式的 op：`getFunctionType()`、`getArgAttrs()`、`getResultAttrs()`、`getAllArgAttrs()` |
| `MemoryEffectOpInterface` | `mlir/Interfaces/SideEffectInterfaces.h` | 描述記憶體副作用 |
| `SymbolOpInterface` | `mlir/IR/SymbolTable.h` | 描述符號（可被 `SymbolTable` 查詢與重命名） |
| `SymbolTableCollection` | `mlir/IR/SymbolTable.h` | 批次查找符號的輔助類別 |
| `RegionBranchTerminatorOpInterface` | `mlir/Interfaces/ControlFlowInterfaces.h` | 描述可终结於 region 的 op：`hasSuccessorRegions()`、`getSuccessorRegions()` |
| `InferTypeOpInterface` | `mlir/Interfaces/InferTypeOpInterface.h` | 描述可以推導結果型別的 op |
| `CallOpInterface` | `mlir/Interfaces/CallInterfaces.h` | 描述函式呼叫的 op |
| `DestinationStyleOpInterface` | `mlir/Dialect/Linalg/IR/LinalgInterfaces.td` | 描述 linalg 風格的目的地導向 op：迭代空間與 indexing map |
| `LinalgStructuredInterface` | 同上 | 描述結構化 linalg op 的綁定與索引資訊 |

### `SymbolOpInterface`

`SymbolOpInterface` 是最簡單但最常見的介面。它讓「這個 op 是一個符號」這件事變成可查詢的：

```cpp
// 取得一個函式的名字。
if (auto sym = dyn_cast<SymbolOpInterface>(op)) {
  StringAttr name = sym.getNameAttr();
}
// 或者直接用輔助類別批次查找。
SymbolTableCollection symbolTable(op->getParentOfType<ModuleOp>());
auto func = symbolTable.lookupNearestSymbolFrom<func::FuncOp>("main");
```

它的價值在於：**不需要知道具體是哪一種符號 op**。`func.func`、`gpu.module`、`llvm.mlir.global`、`mlir.program.global` 都可以是符號。

### `RegionBranchTerminatorOpInterface`

控制流分析（例如 `scf` 的 region 簡化、`cf` 的 reachability 分析）需要知道「哪些 op 可以是 region 的終結者」。這個介面提供了：

```cpp
struct TerminatorInfo {
  bool hasSuccessorRegions();
  void getSuccessorRegions(RegionBranchPoint &point);
};
```

有了它，pass 就不必對 `scf.yield`、`cf.br`、`cf.cond_br` 做硬編碼的 `isa` 鏈。

### `InferTypeOpInterface` 與型別推導

`InferTypeOpInterface` 描述「這個 op 可以根據 operand 與屬性推導出 result 型別」：

```cpp
// 介面方法。
LogicalResult inferReturnTypes(MLIRContext *ctx, std::optional<Location> loc,
                                ValueRange operands, DictionaryAttr attributes,
                                OpaqueProperties properties, RegionRange regions,
                                SmallVectorImpl<Type> &results);
```

MLIR 也在 `mlir/IR/ShapeInference.h` 提供 `mlir::inferReturnTypes` 這組自由函式，以及 `mlir::ShapeInference` 輔助類別，讓 op 在自己需要時推導型別。對 op 定義而言，ODS 的 `InferTypeOpInterface` trait 與 `let hasCanonicalizer`/`let hasFolder` 之類的搭配，讓「推導型別 → 建立 op → 驗證」的流程標準化。

## `MemoryEffectOpInterface` 與 `getEffects`

這是 interface 最有價值的用例之一，值得單獨深入。

### 問題：副作用資訊的三個層次

編譯器對副作用的詢問通常是三層的：

1. **最弱**：「這個 op 會不會影響別的 op 的結果？」——答案是「會」。
2. **中等**：「這個 op 會不會讀寫記憶體？」——答案是「會讀 `memref`，會寫 `memref`」。
3. **最強**：「這個 op 對**哪一個**資源有什麼效果？」——答案是「對 `%memref0` 有 `Read`，對 `%memref1` 有 `Write`」。

trait 只能表達第一層（`Pure` / `NoMemoryEffect`）。`MemoryEffectOpInterface` 讓表達第二、三層成為可能。

### 介面定義

```cpp
namespace mlir {
namespace MemoryEffects {

/// 記憶體效果的列舉。
enum class Effect {
  Read,        ///< 讀取記憶體
  Write,       ///< 寫入記憶體
  Allocate,    ///< 配置記憶體
  Free,        ///< 釋放記憶體
  Unknown,     ///< 未知效果
};

/// 一個效果實例：效果 + 受影響的資源。
class EffectInstance {
public:
  Effect getEffect() const;
  Value getResource() const;   // 可能為空，代表「未知資源」。
};

} // namespace MemoryEffects

class MemoryEffectOpInterface : public OpInterface<MemoryEffectOpInterface, Traits> {
public:
  /// 回傳此 op 的所有記憶體效果。
  virtual void getEffects(SmallVectorImpl<MemoryEffects::EffectInstance> &effects) = 0;

  /// 便利方法：此 op 沒有任何效果。
  bool hasNoEffect() {
    SmallVector<MemoryEffects::EffectInstance> effects;
    getEffects(effects);
    return effects.empty();
  }
};
} // namespace mlir
```

### 實作範例

```cpp
/// 一個有副作用的自訂 op：讀取 input、寫入 output。
class MyLoadStoreOpInterface
    : public MemoryEffectOpInterface::ExternalModel<MyLoadStoreOpInterface, my::LoadStoreOp> {
public:
  void getEffects(SmallVectorImpl<MemoryEffects::EffectInstance> &effects) const {
    effects.emplace_back(MemoryEffects::Effect::Read, getInput());
    effects.emplace_back(MemoryEffects::Effect::Write, getOutput());
  }
};
```

對沒有副作用的 op，可以使用內建的 `Pure` trait 捷徑，或實作空的 `getEffects`：

```cpp
class MyPureOpInterface
    : public MemoryEffectOpInterface::ExternalModel<MyPureOpInterface, my::PureOp> {
public:
  void getEffects(SmallVectorImpl<MemoryEffects::EffectInstance> &) const {
    // 沒有任何效果。
  }
};
```

### 副作用資訊的用途

| 使用者 | 怎麼用 |
| --- | --- |
| DCE（死碼消除） | 無副作用且結果未被使用的 op 可被刪除 |
| 排程與指令選取 | 已知效果的 op 可以自由重排 |
| Speculation（推測執行） | 只有讀效果的 op 可以被安全地跨越分支移動 |
| 記憶體重用分析 | 依據讀寫資源判斷兩個 op 是否可能 alias |
| 向量化合法性檢查 | 確認轉換後的 op 集合仍然維持原本的語意 |

最後一項特別值得說明：把 `memref` 上的迴圈轉成 `vector` 指令時，必須保證「被消除的 load/store 沒有被引入新的 aliasing」。這類分析正是建立在 `getEffects` 回報的資源之上。

## ODS 流程：在 op 上宣告實作介面

完整的流程有三步。

**第一步：宣告介面。** 在 `.td` 檔案中定義介面（本節開頭已示範）。

**第二步：在 op 上宣告要實作哪些介面方法。** 這一步使用 ODS 的 `DeclareOpInterfaceMethods` 巨集：

```tablegen
def My_ElementwiseOp : My_Op<"elementwise", [Pure, DeclareOpInterfaceMethods<My_StructuredOpInterface>]> {
  let arguments = (ins F32:$input);
  let results = (outs F32:$result);
  let assemblyFormat = "$input attr-dict `:` type($result)";
}
```

`DeclareOpInterfaceMethods<My_StructuredOpInterface>` 的作用是：

1. 讓 ODS 產生的 op 類別**繼承**該介面（因此 `isa<My_StructuredOpInterface>(op)` 恆為真）。
2. 要求你在 op 的 C++ 類別中**實作**介面宣告的每一個方法（編譯期檢查）。

**第三步：在 C++ 中實作方法。**

```cpp
namespace my {

unsigned ElementwiseOp::getNumLoops() const {
  return 0;
}

SmallVector<int64_t> ElementwiseOp::getStaticLoopRanges() const {
  return {};
}

int64_t ElementwiseOp::getTiedIndex() const {
  return 0;
}

} // namespace my
```

也可以不寫 `DeclareOpInterfaceMethods`，改用 `let extraClassDeclaration` 直接混入方法宣告：

```tablegen
def My_ElementwiseOp : My_Op<"elementwise", [Pure]> {
  let arguments = (ins F32:$input);
  let results = (outs F32:$result);

  let extraClassDeclaration = [{
    unsigned getNumLoops() const { return 0; }
    SmallVector<int64_t> getStaticLoopRanges() const { return {}; }
    int64_t getTiedIndex() const { return 0; }
  }];
}
```

兩種寫法的差別：`DeclareOpInterfaceMethods` 會強制你實作所有介面方法（漏一個就編譯失敗），而且自動處理繼承；`extraClassDeclaration` 完全由你控制，容易漏掉方法宣告導致介面沒被真正實作。

### 讓 op 實作多個介面

一個 op 可以同時實作多個介面，只要在 trait 列表中列出即可：

```tablegen
def My_Conv2DOp : My_Op<"conv2d", [
    DeclareOpInterfaceMethods<My_StructuredOpInterface>,
    DeclareOpInterfaceMethods<MemoryEffectOpInterface>,
    DeclareOpInterfaceMethods<SymbolOpInterface>
  ]> {
  let arguments = (ins F32:$input, F32:$filter);
  let results = (outs F32:$result);
}
```

## 在 C++ 中使用介面

```cpp
/// 一個使用 MemoryEffectOpInterface 的 pass：刪除所有沒有副作用且結果未使用的 op。
struct DeadPureOpElimination
    : public PassWrapper<DeadPureOpElimination, OperationPass<func::FuncOp>> {
  void runOnOperation() override {
    func::FuncOp func = getOperation();
    bool changed = false;

    SmallVector<Operation *> candidates;
    func.walk([&](Operation *op) {
      auto effectInterface = dyn_cast<MemoryEffectOpInterface>(op);
      if (!effectInterface)
        return;
      if (!effectInterface.hasNoEffect())
        return;
      if (op->use_empty())
        candidates.push_back(op);
    });

    for (Operation *op : candidates) {
      op->erase();
      changed = true;
    }

    if (changed)
      signalPassFailure();   // 實際上應該是標記需要重跑，而非失敗。
  }
};
```

注意這個 pass 對**任何**方言都有效——無論是 `arith`、`linalg`、`tosa` 還是第三方方言，只要它們的 op 實作了 `MemoryEffectOpInterface` 並誠實回報效果，就能被正確處理。這正是 interface 相對於硬編碼 `isa` 清單的價值。

## Interface 與 Trait 的取捨

| 情境 | 建議 |
| --- | --- |
| 需要一個布林性質，且所有實作者行為一致 | 用 trait（如 `Pure`） |
| 需要方法、需要參數、需要執行期判斷 | 用 interface |
| 需要在不改動 op 定義的前提下擴充 | 用 interface 的 external model |
| 需要多個實作共存於同一 op | 用多個 interface |
| 性質緊密相關於 op 的結構特徵 | 用 trait（編譯期成本較低） |
| 性質需要被外部查詢與推廣 | 用 interface |

在實務上，trait 的成本較低（編譯期已知，無執行期查表），interface 則較靈活但有執行期查表開銷。MLIR 的策略是：把最常用、最簡單的性質做成 trait（`Pure`、`OneResult`、`Commutative`），把需要 richer 介面的做成 interface。

## 設計比較：Interface 與多重繼承

| 面向 | MLIR Interface | C++ 抽象基類 | 混入（mixin） |
| --- | --- | --- | --- |
| 執行期查找 | `TypeID` 查表 | 需知道靜態型別 | 需知道靜態型別 |
| 外部擴充 | 支援 | 需繼承 | 需繼承 |
| 菱形繼承問題 | 無（無繼承鏈） | 可能發生 | 可能發生 |
| 跨方言通用 | 是 | 需共同基底類 | 需共同基底類 |
| 編譯期成本 | 查表 | 靜態分派 | 靜態分派 |

MLIR 選擇 interface 而非抽象基類，主要理由是**跨方言的互操作性**。如果 `FunctionOpInterface` 是 C++ 抽象基類，`func.func` 與 `gpu.func` 就得同時繼承它，而 MLIR 的 op 是由 ODS 產生、彼此之間沒有共同繼承鏈的（op 之間是「has-a」關係，不是「is-a」）。Interface 把「能力」與「繼承」解耦，這是 MLIR 能容納數十個彼此獨立的方言的關鍵基礎設施之一。

## 小結與延伸閱讀

- Trait 承載靜態的布林特徵，Interface 承載帶方法的多態行為；前者成本低但表達力有限，後者透過 `TypeID` 查表支援跨方言的動態多態。
- Interface 的最大價值是**外部模型**：可以在不修改 op 定義的前提下讓既有 op 獲得新角色，代價是不能增加 operand/result/屬性，且必須在 op 建立前註冊。
- `isa` / `cast` / `dyn_cast` 對介面走的是執行期 `TypeID` 查表而非繼承鏈；實作者必須具備唯一且穩定的 `TypeID`。
- `MemoryEffectOpInterface` 讓「這個 op 對哪個資源有什麼效果」可被查詢，是 DCE、排程、speculation、alias 分析與向量化合法性檢查的共同基礎。
- ODS 的 `DeclareOpInterfaceMethods<Interface>` 同時完成「繼承介面」與「強制實作方法」兩件事，比手寫 `extraClassDeclaration` 更不易出錯。
