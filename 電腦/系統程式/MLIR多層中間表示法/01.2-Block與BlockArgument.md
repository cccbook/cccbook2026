# 1.2 Block、Block Argument 與控制流圖

在 [1.1](01.1-一切皆Operation.md) 我們確立了 `Operation` 是 MLIR 唯一的抽象基元，並看見 `Operation` 內含 `Region` 欄位。這一節要往下鑽一層：`Region` 裡裝的是什麼？答案是 `Block`，而 `Block` 裡裝的又回到 `Operation`。

這個三層結構（Operation → Region → Block → Operation）本身就是 MLIR 與 LLVM 最鮮明的差異所在。在 LLVM 裡，`BasicBlock` 是 `Function` 內的線性容器，`phi` 節點是 BasicBlock 的頭部實例。而在 MLIR 裡，`Block` 是一個**區域**（`Region`）內的基本單元，`Block Argument` 取代了 `phi` 節點。這個改動不是造型上的偏好，而是直接改變了 SSA 語意的表達能力。

## Block 作為基本區塊

`mlir::Block` 代表一段具有單一進入點的指令序列。它的關鍵屬性包括：

| 成員 | 說明 |
|---|---|
| `arguments` | 區塊參數（`BlockArgument`）列表 |
| `operations` | 區塊內的操作列表（雙向鏈結） |
| `parent` | 擁有它的 `Region` |

Block 內的操作以雙向鏈結串接，因此支援從任意位置向前向後遍歷：

```cpp
Block &block = region.front();
for (Operation &op : block) {
  // 遍歷區塊內所有 op
}
for (auto it = block.begin(); it != block.end(); ++it) {
  // 可以用 iterator 做插入位置
  builder.setInsertionPoint(it);
}
```

一個 Block **不一定**要有 terminator，取決於它所屬的 Region 的語意（下一節主題）。但在 SSACFG 語意的區域中，除了 entry block 之外的每個 block 都必須以 terminator 結束。

## Block Argument 如何取代 Phi 節點

這是本節最重要的觀念，讓我們從 LLVM 的做法開始。

在 LLVM IR 中，兩個 block 之間的值傳遞必須透過 `phi` 節點：

```llvm
define i32 @f(i1 %c, i32 %a, i32 %b) {
entry:
  br i1 %c, label %then, label %else
then:
  %x = add i32 %a, 1
  br label %merge
else:
  %y = add i32 %b, 2
  br label %merge
merge:
  %z = phi i32 [ %x, %then ], [ %y, %else ]
  ret i32 %z
}
```

注意 `phi` 節點的三個特性：它是 block 的頭部、它列舉「從哪個前驅來、對應什麼值」、它與前驅的數量必須一一對應。

MLIR 的 `cf` 方言把這整套機制翻轉過來：**值由目標 block 宣告，前驅 block 傳入。**

```mlir
func.func @f(%c: i1, %a: i32, %b: i32) -> i32 {
  cf.cond_br %c, ^then, ^else
^then:
  %x = arith.addi %a, %c1 : i32
  cf.br ^merge(%x : i32)
^else:
  %y = arith.addi %b, %c2 : i32
  cf.br ^merge(%y : i32)
^merge(%z: i32):
  return %z : i32
}
```

現在 `%z` 是 `^merge` 的 **Block Argument**，它的定義點就是 `^merge` 的開頭。`cf.br ^merge(%x : i32)` 是它的**使用點**——傳入的 `%x` 綁定到 `%z`。

這個設計的好處是顯而易見的：

1. **單一賦值自動成立**。`%z` 只被宣告一次，不可能被重新賦值。LLVM 的 `phi` 節點本質上也是單一賦值，但它的宣告位置與使用位置分離，需要額外的一致性檢查。
2. **不需要前驅匹配檢查**。LLVM 中 `phi` 的 incoming 數量必須等於前驅數量，且順序對應，這個約束在 MLIR 中變成「每個 `cf.br` 的 operand 數量必須等於目標 block 的參數數量」——由 region 驗證器在每個 terminator 上就地檢查，而不是需要全域比對。
3. **block 可以有多個前驅但只有一種型別**。`^merge(%z: i32)` 的型別只宣告一次。

讓我們把這個對應關係寫成數學形式。在 LLVM 中，一個 `phi` 節點可以表示為：

$$
\varphi(x) = \begin{cases} v_1 & \text{if predecessor} = p_1 \\ v_2 & \text{if predecessor} = p_2 \\ \vdots & \end{cases}
$$

在 MLIR 中，這個 piecewise 函數被「分裂」成兩個部分：

* **使用端**（每個前驅一處）： $p_i \mapsto v_i$ ，記錄在 `cf.br` 的 operands 裡；
* **定義端**（目標 block 一處）： $\varphi$ 這個名字對應到 block argument ` $z$ ，型別為 $\text{type}(v_1) = \text{type}(v_2) = \text{type}(z)$ ，三者必須相同。

$$\text{type}(v_1) = \text{type}(v_2) = \cdots = \text{type}(z)$$

這個等式由 block 參數的型別與 terminator 的 operand 型別共同約束。

## 「區域入口的隱式值」這個設計

Block Argument 更深一層的意義是：**它是區域入口處隱式存在的值**。

把它想成函式的隱式參數。`^merge(%z: i32)` 語意上等價於：

$$
\text{merge}(z: \text{i32}) \rightarrow \text{void}
$$

只是這個「函式」的呼叫點不在別處，而是散落在各個前驅的 terminator 上。於是：

* region 變成一個**多點進入（multi-entry）**的建構；
* 每個進入點帶著一組值。

這個觀點非常重要，因為它讓 MLIR 能自然表達「循環帶參數」（`scf.for` 的 induction variable 與迭代參數）與「依賴前驅的值」的區別——前者是 region 入口就固定好的參數（`scf.for` 只有一個進入點），後者是 `cf` 風格的前驅傳值。

```mlir
scf.for %i = %lb to %ub step %step iter_args(%acc = %init) -> i32 {
  %new = arith.addi %acc, %i : i32
  scf.yield %new : i32
}
```

這裡 `%acc` 是 block argument，但它的「呼叫點」只有一個（region 的隱式入口），而且初值 `%init` 由 `iter_args` 指定。這與 `cf.br` 的多前驅傳值有本質差異。

## Operation 的前驅後繼如何維護

MLIR **沒有**像 LLVM 那樣為 block 維護明確的 predecessor / successor 列表。這是一個刻意的設計選擇。

LLVM 的 `BasicBlock` 有 `predecessors` 與 `successors` 列表，由 `BranchInst` 的 `addSuccessor` 維護。這帶來一個維護成本問題：任何改變控制流的指令（建立、刪除、替換、分裂、合併）都必須小心地更新這些列表，漏掉一次就是一個不穩定的 IR。

MLIR 的做法是：**前驅後繼完全由 terminator 推導**。

```cpp
// 取得某個 block 的前驅：掃描同一 region 中各 block 的 terminator
SmallVector<Block *> preds;
for (Block &other : *block->getParent()) {
  Operation *term = other.getTerminator();
  if (!term)
    continue;
  for (Block *succ : successorsOfTerminator(term)) {
    if (succ == &block)
      preds.push_back(&other);
  }
}
```

`Block::getPredecessors(Region *parent)` 的實作是掃描 parent region 中的**所有** block，找出它們的 terminator，看有哪些分支指向了 `block`。

```cpp
// 取得某個 block 的後繼
for (Block *succ : block.getSuccessors()) {
  // succ 是 branch op 的目標 block
}
```

`Block::getSuccessors()` 的實作則是找到本 block 的 terminator，讀取其 `SuccessorOperands`（一個 `mlir::SuccessorOperands` 介面），從中取出目標 block。

`SuccessorOperands` 是一個關鍵的 dialect 介面：

```cpp
// 概念上的介面
class SuccessorOperands {
  mlir::OperandRange getSuccessorOperands(RegionBranchPoint point);
  mlir::SuccessorOperands getSuccessorOperands();
};
```

`cf.br` 與 `cf.cond_br` 實作它，而 `scf.for` 也實作它（用 `scf.yield` 的 operands 對應 region 的 block arguments）。因此，只要一個 op 實作了 `SuccessorOperands`，它就能被通用的 CFG 演算法（如 `mlir::DominanceInfo`、`mlir::PostDominanceInfo`、`mlir::SparseBackwardDataFlowAnalysis`）正確處理。

**這是把控制流資訊「隱藏」在 op 語意裡的關鍵。** 一個方言若要支援 CFG 分析，只要實作 `SuccessorOperands` 與 `RegionBranchTerminatorOpInterface`（若 region 有 entry block 與 terminator 區別）即可。

代價是查詢前驅是 $O(n)$ 的（要掃描 region 中所有 block）。在大型 IR 上這可能偏慢，但實務上通常可接受；若成為瓶頸，可以快取。

## Terminator 的約定

**Terminator 是一種特化的 operation**：它是 block 的最後一個 op，定義了控制流離開該 block 的方式。

MLIR 對 terminator 有兩種層級的定義：

1. **語意層**：`NoTerminator` trait 宣告「這個 op 的 region 不需要 terminator」，或 `SingleBlockImplicitTerminator` 之類。
2. **介面層**：`OpTrait::IsTerminator` 讓 op 被標記為 terminator。

在 SSACFG region 中，驗證器會要求：

* 每個 block 的最後一個 op 必須是 terminator；
* entry block 以外的 block，其 terminator 必須「branch 到別處」。

```mlir
// 這是不合法的：block 沒有以 terminator 結束
^bb0:
  %0 = arith.constant 0 : i32
```

會得到類似以下的診斷：

```
error: block with no terminator was found
```

在 C++ 裡，terminator 的取得方式：

```cpp
// 取得 block 的 terminator
if (Operation *term = block.getTerminator()) {
  // ...
}
```

`Block::getTerminator()` 會回傳最後一個 op，如果它帶有 `IsTerminator` trait，否則回傳 `nullptr`。

判斷某個 op 是否為 terminator：

```cpp
if (op->mightHaveTrait<OpTrait::IsTerminator>()) {
  // ...
}
```

`mightHaveTrait` 比 `hasTrait` 便宜：前者只查操作碼的 trait 集合，不需完整的 trait 物件比對。

## Region 的 entry block 規則

在 SSACFG 語意的 region 中：

* region 可以有零個、一個或多個 block；
* 零個 block 是合法的（例如 `scf.if` 沒有 then region 的內容時）；
* **entry block 是 region 內第一個 block**（`region.front()`）；
* entry block 可以有 block arguments，這些 argument 由 region 外部（通常是持有該 region 的 op 的 operands）傳入；
* entry block 的 terminator 若是 `br`，通常用來離開 region。

「entry block」這個概念在 MLIR 中是**約定**而非強制類別繼承。`Region` 有一個 `RegionKind` 屬性：

```cpp
// SSACFG region
mlir::RegionKind::SSACFG
// Graph region
mlir::RegionKind::Graph
```

`Region::getKind()` 決定該 region 是否要求 entry block 與 terminator。SSACFG region 的驗證規則：

```cpp
// 概念上的驗證流程
if (region.empty())
  return success();  // 空的 SSACFG region 合法

// 第一個 block 是 entry block
Block &entry = region.front();
// entry block 的 terminator 若存在且是 br，必須指向 region 內的 block
```

## 與 LLVM CFG 的差異比較

| 面向 | LLVM IR | MLIR IR |
|---|---|---|
| 值的跨 block 傳遞 | `phi` 節點，位於 block 頭部 | `Block Argument`，位於目標 block 開頭 |
| 值的宣告位置 | 與使用位置分離 | 定義即使用點的對應（terminator operand） |
| 前驅列表 | `BasicBlock` 顯式維護 `predecessors` | 不維護，由 terminator 推導 |
| 後繼列表 | `BasicBlock` 顯式維護 `successors` | 不維護，由 `SuccessorOperands` 推導 |
| 前驅匹配檢查 | `phi` incoming 數量須等於前驅數量 | terminator operand 數量須等於目標 block 參數數量 |
| 分支 | `br` / `switch` / `indirectbr` 指令 | `cf.br` / `cf.cond_br` / `cf.switch`，或方言自訂 |
| 多返回 | `ret` 指令 | `cf.return` 或方言自訂 terminator |
| 區塊參數 | 無（參數只屬於函式） | 每個 block 皆可有參數 |
| 支配分析 | `DominatorTree` | `mlir::DominanceInfo`（region-aware） |
| 區塊可放入更多操作 | 需 `BasicBlock::splitBasicBlock` | `Block::splitBlock` 為一級 API |

## 具體程式碼範例

讓我們用完整的 MLIR 與 C++ 展示 `cf.br` / `cf.cond_br` 與 block argument 的對應。

```mlir
// 一個以 MLIR 描述的 if-else 函式
func.func @select(%cond: i1, %a: i32, %b: i32) -> i32 {
  cf.cond_br %cond, ^true, ^false
^true:
  %t = arith.addi %a, %a : i32
  cf.br ^exit(%t : i32)
^false:
  %f = arith.mulf %b, %b : i32
  cf.br ^exit(%f : i32)
^exit(%result: i32):
  func.return %result : i32
}
```

等價的 C++ 建構：

```cpp
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinOps.h"
#include "mlir/Dialect/CF/IR/CF.h"
#include "mlir/Dialect/Arith/IR/Arith.h"
#include "mlir/Dialect/Func/IR/FuncOps.h"

using namespace mlir;

static void buildSelect(ModuleOp module, Location loc) {
  OpBuilder builder(module.getBodyRegion());
  Type i32 = builder.getI32Type();
  Type i1 = builder.getI1Type();

  // 建立 func.func，主體先留空
  auto funcType = builder.getFunctionType({i1, i32, i32}, {i32});
  auto func = builder.create<func::FuncOp>(loc, "select", funcType);
  Block *entry = func.addEntryBlock();
  builder.setInsertionPointToStart(entry);

  Value cond = entry->getArgument(0);
  Value a = entry->getArgument(1);
  Value b = entry->getArgument(2);

  // 建立兩個分支目標 block
  Block *trueBlock = func.getBody().addBlock();
  Block *falseBlock = func.getBody().addBlock();
  Block *exitBlock = func.getBody().addBlock();
  // exit block 有一個參數，對應 LLVM 的 phi
  exitBlock->addArgument(i32, loc);

  // 條件分支
  builder.create<cf::CondBranchOp>(loc, cond, trueBlock, falseBlock);

  // true 分支
  builder.setInsertionPointToStart(trueBlock);
  Value t = builder.create<arith::AddIOp>(loc, a, a).getResult();
  builder.create<cf::BranchOp>(loc, exitBlock, ValueRange{t});

  // false 分支
  builder.setInsertionPointToStart(falseBlock);
  Value f = builder.create<arith::MulIOp>(loc, b, b).getResult();
  builder.create<cf::BranchOp>(loc, exitBlock, ValueRange{f});

  // 匯流點
  builder.setInsertionPointToStart(exitBlock);
  Value result = exitBlock->getArgument(0);
  builder.create<func::ReturnOp>(loc, ValueRange{result});
}
```

用 `OpBuilder::create` 建立 `cf.br` 時，overload 會自動處理 operand 數量與目標 block 參數數量的一致性。

在 Python 側，`cf` 方言的操作同樣可用：

```python
from circt.ir import InsertionPoint
from circt.dialects import arith, cf, func

with InsertionPoint(entry) as b:
    cf.cond_br(cond, true_block, false_block)
    true_block.add_argument(i32)   # 匯流點參數
    cf.br(exit_block, [t])
```

`Block.add_argument` 在 Python 中可用，是因為 `Block` 有直接的 Python 綁定（不同於多數只有 `OpView` 的操作）。

## 用 C++ 查詢 CFG

前驅後繼既然是推導出來的，就要有便利的查詢方式：

```cpp
// 取得某個 block 的 terminator
Operation *term = block.getTerminator();

// 依 terminator 的型別取出後繼 block
if (auto br = dyn_cast<cf::BranchOp>(term)) {
  Block *dest = br.getDest();
  (void)dest;
} else if (auto condBr = dyn_cast<cf::CondBranchOp>(term)) {
  Block *trueDest = condBr.getTrueDest();
  Block *falseDest = condBr.getFalseDest();
  (void)trueDest; (void)falseDest;
}
```

`Block` 本身也提供了便利方法：

```cpp
// 取得 block 的所有後繼
SmallVector<Block *> succs;
block.getSuccessors(succs);
```

前驅的取得則需要掃描整個 region，MLIR 以靜態方法提供：

```cpp
// 取得 block 在指定 region 中的所有前驅
SmallVector<Block *> preds;
Block::getPredecessors(&block, region, preds);
```

`cf::CondBranchOp` 另有一個重要變體：**帶 block arguments 的 `cf.cond_br`**：

```mlir
cf.cond_br %cond, ^then(%x : i32), ^else(%y : i32)
```

這個寫法比「先 `cf.br` 到 then、再 `cf.br` 回 exit」更精簡，也讓前驅關係更直接。C++ 介面：

```cpp
builder.create<cf::CondBranchOp>(loc, cond, trueBlock, ValueRange{t},
                                 falseBlock, ValueRange{f});
```

## 小結與延伸閱讀

* `Block` 是 region 內的基本單元；`Block Argument` 取代了 LLVM 的 `phi` 節點，把「值從哪個前驅來」的資訊從定義端移到使用端。
* Block argument 可以理解為「區域入口的隱式值」，即把 region 視為多點進入的隱式函式；`cf` 的多前驅傳值與 `scf.for` 的單入口參數是同一個機制的兩種用法。
* MLIR 不顯式維護前驅/後繼清單，而是由 terminator 與 `SuccessorOperands` 介面推導，代價是查詢為 $O(n)$ 掃描，收益是控制流改寫時不必手動維護雙邊一致性。
* Terminator 是 block 的最後一個 op，在 SSACFG region 中每個 block 都必須以 terminator 結束；region 的 `RegionKind` 決定是否強制 entry block 與 terminator。
