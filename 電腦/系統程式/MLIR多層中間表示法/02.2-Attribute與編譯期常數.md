# 2.2 Attribute：編譯期常數與詮釋資料

[2.1](02.1-MLIR型別系統.md) 處理了「值的型別」，但一個完整型別的 IR 還需要承載「值是什麼」。在 SSA 世界裡，這個問題的答案有兩條路：把值建成 SSA value，或者把它變成編譯期已知、可以內嵌的**屬性**。

MLIR 兩者都提供，而且刻意把兩者的邊界劃得很清楚：型別恆定、數量固定的資料用 **Attribute**（編譯期常數）；型別恆定但數量可能變動的資料（例如一整個張量）也用 Attribute；而執行期才知道的值才用 **SSA value**。

這一節的主題是 Attribute。但更根本的問題是：**為什麼常數不做成 SSA value？**

## 為什麼常數不用 SSA value

考慮一個最簡單的情形——把整數 42 加到某個變數上。LLVM 的做法是：

```llvm
%c = add i32 %x, 42
```

LLVM 把常數直接編碼進指令的 opcode 與 operand 裡（`add` 有 `add nsw` 等變體，常數 42 直接放在 operand 欄位）。而 MLIR 的做法是：

```mlir
%c = arith.addi %x, %k42 : i32
%k42 = arith.constant 42 : i32
```

MLIR 把常數提升成一個獨立的 `arith.constant` operation。

這個差異乍看之下是「多了一個 op」，但它換來四個實質的能力。

**第一，可折疊（folding）。** 因為常數是 op，`arith.constant` 實作了 `OpTrait::ConstantLike` 與 fold 介面，轉換框架可以直接把它折疊進使用它的 op：

```mlir
%c = arith.addi %x, %k42 : i32
```

在 canonicalization 之後變成：

```mlir
%c = arith.addi %x, %k42 : i32   // 若 arith.addi 有 constant folding 規則
```

更明顯的例子是 `arith.constant` 自己的屬性可以直接被 `arith.addi` 吸收，形成 `arith.constant` op 的消除。

**第二，可雜湊（hashability）。** 這是關鍵的一點。MLIR 的轉換框架（`ConversionPattern`）與許多分析需要**以常數值為鍵**來查表，例如：

```cpp
// 依常數值分派的 pattern
struct MatchConstant : OpRewritePattern<arith::ConstantOp> {
  MatchConstant(mlir::MLIRContext *ctx) : OpRewritePattern(ctx) {}
  LogicalResult matchAndRewrite(arith::ConstantOp op,
                                PatternRewriter &rewriter) const override {
    auto intAttr = dyn_cast<IntegerAttr>(op.getValue());
    if (!intAttr || intAttr.getInt() != 42)
      return failure();
    // ...
  }
};
```

若常數是 SSA value，就必須先追蹤它的 def op 才能拿到值；用屬性則可以直接 `dyn_cast<IntegerAttr>` 取得。屬性還可以被 **interned 與雜湊**，因此「這兩個 op 的常數是否相同」是一次 O(1) 的指標比較。

**第三，可序列化。** 屬性有明確的文字表示（`dense<[1.0, 2.0]> : tensor<2xf32>`），可以直接被印出、被序列化存檔、被雜湊進 cache key。

**第四，型別化的儲存。** `DenseElementsAttr` 保存的是型別化的位元組，不是文字。`getValues<APFloat>()` 取出的就是真正的 IEEE 754 位元組，不需要再解析。

**代價**是常數佔用了一個 op 的空間，且 SSA 使用者列表要維護。MLIR 認為這個代價值得，因為高階方言中常數的比例通常不高，而帶來的表達力（可被 pattern 匹配、可被 dialect 自訂語法渲染）非常可觀。

## Attribute 的三大類

`mlir::Attribute` 是所有屬性的共同基類，同樣是薄介面 + uniqued storage。

MLIR 把屬性分為三個大類，這個分類不是隨意的，它決定了屬性在語意上的角色。

### 第一類：編譯期常數

這些屬性攜帶「值」。

| 屬性類別 | 承載的資料 | 範例 |
|---|---|---|
| `IntegerAttr` | 任意精度整數（+ 型別） | `42 : i32` |
| `FloatAttr` | 浮點（+ 型別） | `3.14 : f32` |
| `StringAttr` | 字串 | `"hello"` |
| `DenseElementsAttr` | 型別化的密集元素陣列 | `dense<[1.0,2.0]> : tensor<2xf32>` |
| `DenseIntElementsAttr` | 整數陣列（`DenseElementsAttr` 的特化） | `dense<[1,2]> : tensor<2xi32>` |
| `DenseFPElementsAttr` | 浮點陣列 | `dense<[1.0]> : tensor<1xf32>` |
| `DenseResourceElementsAttr` | 從資源檔載入的密集資料 | 二進位 blob |
| `SplatElementsAttr` | 單值填充的陣列 | `dense<0.0> : tensor<128xf32>` |
| `ArrayAttr` | 屬性陣列 | 見下節 |
| `ComplexAttr` | 複數（實部 + 虛部） | `complex.constant` 的值 |
| `OpaqueAttr` | 不透明的位元組 blob | 外部格式保留 |

`IntegerAttr` 特別值得注意：它的整數是**任意精度**的。`IntegerAttr` 內部存的是 `APInt`，不只是一個 32 位元整數：

```cpp
auto intAttr = builder.getI32IntegerAttr(42);
APInt wide = intAttr.getValue();   // APInt，可以是任意寬度
int64_t v = intAttr.getInt();      // 轉成 int64_t（會檢查是否溢位）
```

`FloatAttr` 同理，內部是 `APFloat`，可以表示 IEEE 的所有特殊值：

```cpp
auto f = builder.getF32FloatAttr(3.14f);
bool isNaN = f.getValue().isNaN();
```

### 第二類：型別資訊

這些屬性不是「值」，而是**關於型別或結構的描述**。

| 屬性類別 | 承載的資料 | 範例 |
|---|---|---|
| `TypeAttr` | 一個 `Type` | `tensor<2xf32>` 屬性 |
| `FunctionTypeAttr` | 一個 `FunctionType` | 函式簽章 |
| `ArrayAttr` of `TypeAttr` | 一組型別 | 變數宣告的型別串列 |
| `IntegerSetAttr` | 親和性遮罩 | 向量化資訊 |
| `DataLayoutSpecAttr` | 資料佈局規格 | 字串型別的佈局 |

`TypeAttr` 是最常用的例子。`func.func` 的簽章就是一個 `FunctionTypeAttr`：

```mlir
func.func @foo(%a: i32) -> i32 attributes {llvm.emit_c_interface}
```

其內部屬性為：

```mlir
function_type = (i32) -> i32
```

### 第三類：單位值與標記

`UnitAttr` 表示「這個屬性存在，這件事本身就是意義」。

```mlir
func.func @pure_fn() attributes {noinline}
```

這裡 `noinline` 是一個 `UnitAttr`：沒有值，只有「有／沒有」兩種狀態。`UnitAttr` 是所有 `UnitAttr` 實例共用的**單例**——它不需要 uniquing 的鍵，因為內容恆定。

`UnitAttr` 的用途非常廣：旗標、trait 樣的屬性（例如 `sym_visibility = "public"` 是 StringAttr，但 `llvm.emit_c_interface` 就是 UnitAttr）。

## DictionaryAttr 與 ArrayAttr：組合性

這兩種屬性構成了 MLIR 屬性系統的「複合」部分。

### DictionaryAttr

`DictionaryAttr` 是一個**有序**的 `(name, attribute)` 對序列。它是 operation 屬性容器的預設型別：

```cpp
// 取得 operation 的所有屬性
DictionaryAttr attrs = op->getAttrDictionary();

// 取得單一屬性
Attribute v = op->getAttr("mode");

// 設定屬性
op->setAttr("mode", builder.getStringAttr("fast"));
```

`DictionaryAttr` 是**有序**的（MLIR 保證其迭代順序穩定），這在序列化成可重現的輸出時很重要。

### ArrayAttr

`ArrayAttr` 是一個有序的屬性序列：

```cpp
auto arr = builder.getArrayAttr({builder.getI32IntegerAttr(1),
                                  builder.getI32IntegerAttr(2)});
```

`ArrayAttr` 在 MLIR 中無處不在：函式的參數型別串列、`scf.if` 的結果型別、`func.call` 的 callee operand 型別、`AffineMap` 的結果串列。

### NamedAttribute 與 DictionaryAttr 的關係

`NamedAttribute` 是一個 `(StringAttr name, Attribute value)` 的配對：

```cpp
class NamedAttribute {
  StringAttr getName() const;
  Attribute getValue() const;
};
```

`DictionaryAttr` 內部就是 `ArrayRef<NamedAttribute>`。因此：

* `DictionaryAttr` = 一個 `NamedAttribute` 陣列；
* `ArrayAttr` = 一個 `Attribute` 陣列。

```cpp
// DictionaryAttr 的內部
ArrayRef<NamedAttribute> attrs = dictAttr.getValue();

// ArrayAttr 的內部
ArrayRef<Attribute> values = arrayAttr.getValue();
```

這個統一性讓 MLIR 能用同一套 API 處理「具名的屬性集合」與「匿名的屬性序列」。

### C++ 操作

```cpp
// 建立 DictionaryAttr
NamedAttributeList list;
list.append("mode", builder.getStringAttr("fast"));
list.append("level", builder.getI32IntegerAttr(3));
DictionaryAttr dict = list.getDictionary(ctx);

// 走訪
for (NamedAttribute na : dict) {
  StringRef name = na.getName().getValue();
  Attribute value = na.getValue();
  (void)name; (void)value;
}
```

`NamedAttributeList` 是建構 dictionary 時的便利類別，它在加入項目時會自動處理**排序**（`DictionaryAttr` 要求按名稱排序以確保 uniquing 的一致性）。這個排序要求是重要的：它使得「相同內容的 dictionary」一定是同一個指標。

## 為什麼常數不用 SSA value（再深化：屬性 vs 值 的形式對比）

讓我們把兩種表達放在表格中對照，並給出形式語言的視角。

一個 op 的完整語意可以寫成：

$$
\text{op} : (\tau_1 \times \tau_2 \times \cdots \times \tau_n) \rightarrow (\sigma_1 \times \cdots \times \sigma_m)
$$

其中 $\tau_i$ 是 operand 的型別， $\sigma_j$ 是 result 的型別。而**屬性**為 op 附加了一個額外的參數：

$$
\text{op} : (\tau_1, \ldots, \tau_n) \xrightarrow{A} (\sigma_1, \ldots, \sigma_m), \quad A \in \mathcal{A}
$$

$\mathcal{A}$ 是所有屬性的集合。

關鍵在於 $\mathcal{A}$ 的元素是**有限且可結構化匹配**的。若常數做成 SSA value，則「這個 op 的第二個 operand 是否等於 42」這個問題就變成一個資料流問題（需要追蹤 def），而用屬性表達，它退化為「取出一個 `IntegerAttr`，讀 `.getInt()`」。

這就是為什麼 MLIR 的 `arith.constant` 是 `ConstantLike`：

```tablegen
def ConstantOp : Arith_Op<"constant", [
    ConstantLike, AllTypesMatch<["value"]>,
    Pure, DeclareOpInterfaceMethods<FoldableOpInterface>
  ]> {
  let arguments = (ins TypedAttrInterface:$value);
  let results = (outs SignlessIntegerOrFloatLike:$result);
}
```

`AllTypesMatch<["value"]>` 表示 value 屬性的型別必須與 result 型別一致——這是一個由 ODS 自動產生的驗證。

## 方言自訂屬性與 exists 語法

MLIR 允許方言定義自己的屬性類別，並提供**存在式語法**（existential syntax），讓屬性可以簡短地出現在 op 的文字形式中。

```mlir
llvm.func @f() attributes {llvm.linkage = #llvm.linkage<external>} { ... }
```

這裡 `#llvm.linkage<external>` 是 `LLVMLinkageAttr`（一個 `EnumAttr` 的特化）的一個**實例**。它的語法是：

```
#dialect-name<attr-body>
```

這種寫法稱為 **dialect attribute literal**，它與 `#` 開頭的「方言屬性套件」（dialect attribute bundle）不同：

```mlir
#llvm.isa<base>                 // 屬性套件
#llvm.linkage<external>         // 具體屬性實例
```

在 C++ 端，這些由 `attrdef` 定義的屬性可以用 `AttrDef` 模板建立：

```tablegen
def LLVM_LinkageAttr : EnumAttr<CPred<"$_self.isa<::mlir::LLVM::LinkageAttr>()">,
                                "linkage", [LLVM_AttrBase]> {
  let cases = [
    [External, "external"],
    [Weak,     "weak"],
    [LinkOnce, "linkonce"],
    [AppendingLinkage, "appending"],
    [Internal, "internal"],
    [Private,  "private"],
    [Common,   "common"],
    [ExternalWeak, "extern_weak"],
    [Available_externally, "available_externally"],
  ];
}
```

`EnumAttr` 讓 `LinkageAttr` 自動獲得：從字串建立、轉成字串、以及列舉值的驗證。

### 屬性字典中的複合型別

屬性字典的值也可以是複合型別，這讓「一個屬性承載多個子屬性」成為可能：

```mlir
func.func @f() attributes {
  llvm.linkage = #llvm.linkage<external>,
  some = {a = 1 : i32, b = "x"}
} { ... }
```

`some` 的值是一個 `DictionaryAttr`，包含 `a`（`IntegerAttr`）與 `b`（`StringAttr`）。

## Properties 與 Discardable Attribute 的差異

MLIR 的 operation 有**兩種**屬性容器，這個區分是 2023 年之後引入的重要改進。

| | Inherent Attributes（固有屬性） | Discardable Attributes（可丟棄屬性） |
|---|---|---|
| 宣告方式 | ODS 的 `let arguments` / `let results` 加上 `let attributes` | `let discardableAttributes` |
| 儲存位置 | **存在 operation 物件內**，作為固定欄位 | 存在 operation 外的**側表（side table）** |
| 存取成本 | 直接存取欄位 | 需要一次 hash lookup |
| 序列化 | 一律序列化 | 可選擇丟棄 |
| 典型用途 | op 的語意核心（例：`arith.constant` 的 value） | 除錯資訊、註解、方言特定的非語意資料 |

ODS 裡的宣告：

```tablegen
def MyOp : MyDialect_Op<"myop"> {
  let arguments = (ins I32:$input);
  let results = (outs I32:$output);
  // 固有屬性：直接存在 op 內
  let attributes = (ins StringAttr:$label);
  // 可丟棄屬性：存在側表，可被丟棄
  let discardableAttributes = (ins UnitAttr:$debug_only);
}
```

**為什麼需要這個區分？**

1. **記憶體效率**。operation 是編譯器中最數量龐大的物件。若每個 op 都帶一個 `DictionaryAttr`，即使字典是空的也要一個指標與一個 uniquing 查詢。把大部分「非語意」屬性移到側表，讓 op 本體保持緊湊。
2. **可丟棄性**。有些屬性只在開發期有用（例如 `DebugInfoOpInterface` 產生的除錯資訊、`sparse_tensor` 的中間 metadata）。把它們標為 discardable，意味著在某些模式下可以被序列化器丟棄，減少輸出體積。
3. **語意與非語意的清晰劃分**。固有屬性是 op 語意的**組成部分**（例如 `arith.constant` 的 `value`），改變它就改變了 op 的意義，因此它的存取是熱路徑；discardable 屬性是附加資訊。

在 C++ 端，兩者的 API 幾乎相同：

```cpp
// 固有屬性
StringRef label = op->getLabelAttr().getValue();

// 可丟棄屬性
if (auto unit = op->getAttrOfType<UnitAttr>("debug_only")) {
  // ...
}
```

ODS 為 discardable 屬性生成的 accessor 與固有屬性相同（`getDebugOnlyAttr()`），因為對使用者來說差異不應可見——這是「隱藏的實作細節，公開的統一介面」的典型做法。

## Attribute 的 Uniquing 與記憶體

`Attribute` 與 `Type` 一樣，在 context 內被 uniqued。`Attribute` 的 storage 池結構與 `Type` 類似，但**多了一層**：

```
MLIRContext
 ├── TypeUniquer per storage class
 └── AttributeUniquer per storage class
```

對於**方言自有**的屬性，uniquing 由方言的 `AttributeUniquer` 處理：

```cpp
class MyDialect : public mlir::Dialect {
public:
  explicit MyDialect(mlir::MLIRContext *ctx)
      : mlir::Dialect(getDialectNamespace(), ctx, TypeID::get<MyDialect>()) {
    addAttributes<MyAttr>();
  }
};
```

屬性定義：

```cpp
struct MyAttrStorage : public mlir::AttributeStorage {
  using KeyTy = int64_t;
  bool operator==(const KeyTy &key) const { return value == key; }
  static llvm::hash_code hashKey(const KeyTy &key) { return llvm::hash_code(key); }
  static MyAttrStorage *construct(mlir::AttributeStorageAllocator &allocator,
                                  const KeyTy &key) {
    return new (allocator.allocate<MyAttrStorage>()) MyAttrStorage(key);
  }
  int64_t value;
};

class MyAttr : public mlir::Attribute::AttrBase<MyAttr, mlir::Attribute,
                                               detail::MyAttrStorage> {
public:
  using Base::Base;
  static MyAttr get(mlir::MLIRContext *ctx, int64_t value) {
    return Base::get(ctx, value);
  }
  int64_t getValue() const { return getImpl()->value; }
};
```

這裡的 `construct` 與 `hashKey` 是 **Placement new** 的典型用法：在配置的空間裡直接建構 storage，避免額外的 heap 配置。

### 記憶體的代價

uniquing 意味著**屬性永不銷毀**（在 context 活著期間）。對於編譯器來說這通常是可接受的，因為 context 在一次編譯結束時整體釋放。但如果一個編譯流程會產生大量「短命」的屬性（例如在 pattern 重寫過程中不斷產生新的 `DictionaryAttr`），記憶體可能會累積。

MLIR 的緩解手段是 **operation 的屬性一旦被刪除就沒有回收機制**，但因為 dictionary 本身被 uniqued，相同的 dictionary 內容只存一份。實務上建議：**避免在 hot loop 中產生 unique 的字串屬性**。

## 程式碼與 MLIR 語法範例

### C++

```cpp
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinAttributes.h"
#include "mlir/IR/BuiltinTypes.h"

using namespace mlir;

void buildAttributes(OpBuilder &builder, Location loc) {
  MLIRContext *ctx = builder.getContext();

  // 編譯期常數
  auto intAttr = builder.getI32IntegerAttr(42);
  auto fAttr = builder.getF32FloatAttr(3.14f);
  auto strAttr = builder.getStringAttr("hello");
  auto boolAttr = builder.getBoolAttr(true);
  auto unitAttr = builder.getUnitAttr();

  // 密集元素
  auto dense = DenseElementsAttr::get(
      RankedTensorType::get({2}, builder.getF32Type()),
      {APFloat(3.0f), APFloat(4.0f)});

  // 型別資訊
  auto typeAttr = TypeAttr::get(RankedTensorType::get({2}, builder.getF32Type()));
  auto fnTypeAttr = TypeAttr::get(
      builder.getFunctionType({builder.getI32Type()}, {builder.getI32Type()}));

  // 陣列
  auto arrayAttr = builder.getArrayAttr({intAttr, strAttr});

  // 字典
  NamedAttributeList named;
  named.append("int", intAttr);
  named.append("str", strAttr);
  named.append("nested", arrayAttr);
  DictionaryAttr dict = named.getDictionary(ctx);

  // 讀取
  if (auto d = dict.getAs<IntegerAttr>("int")) {
    int64_t v = d.getInt();
    (void)v;
  }

  // 綁定到 operation
  Operation *op = builder.create<arith::ConstantOp>(loc, builder.getI32Type(), intAttr);
  op->setAttr("label", strAttr);
  op->setAttr("unit", unitAttr);
  op->setAttr("dict", dict);

  // 移除屬性
  op->removeAttr("label");
}
```

### MLIR

```mlir
// 整數、浮點、字串、布爾
%i = arith.constant 42 : i32
%f = arith.constant 3.140000e+00 : f32
%s = "test.str"() {value = "hello"} : () -> ()

// 密集與稀疏
%d = arith.constant dense<[1.0, 2.0, 3.0]> : tensor<3xf32>
%splat = arith.constant dense<0.0> : tensor<1024xf32>

// 字典屬性
func.func @f() attributes {
  int = 42 : i32,
  str = "hello",
  nested = [1 : i32, "two"],
  dict = {x = 1 : i32, y = 2 : i32},
  unit_only
} {
  func.return
}

// 方言自訂屬性
llvm.func @g() attributes {llvm.linkage = #llvm.linkage<external>} {
  llvm.return
}

// 陣列型別屬性
func.func @h(%a: i32, %b: f32) attributes {function_type = (i32, f32) -> ()} {
  func.return
}
```

## 常見陷阱

1. **`DictionaryAttr` 要求按名稱排序**。手動建構 dictionary 時若未排序，uniquing 會產生前所未見的結果（同一內容兩個指標）。用 `NamedAttributeList` 會自動處理。
2. **`DenseElementsAttr` 的元素型別必須與張量一致**。`dense<[1,2]> : tensor<2xf32>` 驗證失敗。
3. **屬性不可跨 context**。與 type 相同的限制。
4. **`UnitAttr` 不能帶值**。`unit_only = 1 : i32` 與 `unit_only` 是不同的東西；前者是 `IntegerAttr`。
5. **discardable 屬性在某些 pass 後可能消失**。若一條轉換路徑假設某個 discardable 屬性存在，會在最佳化之後失效——除非該屬性對語意有影響，否則應把它宣告為固有屬性。

## 小結與延伸閱讀

* `Attribute` 分為編譯期常數（`IntegerAttr`、`FloatAttr`、`DenseElementsAttr` 等）、型別資訊（`TypeAttr`）與單位值（`UnitAttr`）三類，並由 `DictionaryAttr` / `ArrayAttr` 提供組合性。
* 常數以屬性而非 SSA value 表達，使「某個 operand 是否等於 42」從資料流問題退化為 O(1) 的屬性匹配，並讓 op 保有可折疊、可雜湊、可序列化的性質。
* `NamedAttribute` 是 `(名稱, 值)` 配對，`DictionaryAttr` 是它的有序陣列、`ArrayAttr` 是 `Attribute` 的有序陣列，兩者共享同一組迭代與建構 API。
* 方言可用 `attrdef` 定義自有屬性，並以 `#dialect.name<body>` 的存在式語法出現在屬性字典中。
* 固有屬性直接存於 operation 物件內，discardable 屬性存於側表且可被序列化器丟棄；ODS 用 `let attributes` 與 `let discardableAttributes` 區分兩者。
