# 3.3 宣告式重寫規則（DRR）與 Pattern 的對應

## 手寫 RewritePattern 的成本

[3.2](03.2-ODS定義Operation.md) 我們讓 operation 的**結構**可以被自動產生。但 MLIR 真正的威力不只在於定義 op，而在於**改寫** op：把一個 op 樹換成另一個 op 樹，是 dialect 實作裡占比最大的工作。

要改寫，第一步是「匹配」：在給定的 op 樹裡找到符合某個形狀的子樹；第二步是「替換」：把它換成新的形狀。C++ 的 `RewritePattern` 要求你把這兩步都手寫。

假設我們想把 `my.add` 的一個特例——`0 + x`——正規化成 `x`。手寫的 pattern 大致是：

```cpp
namespace {
struct AddZeroCanonicalization : public mlir::OpRewritePattern<mlir::my::AddOp> {
  using OpRewritePattern::OpRewritePattern;

  mlir::LogicalResult matchAndRewrite(mlir::my::AddOp op,
                                        mlir::PatternRewriter &rewriter) const override {
    mlir::Value rhs = op.getRhs();
    mlir::Attribute zero = rewriter.getI32IntegerAttr(0);
    mlir::Value zeroValue = rewriter.create<mlir::arith::ConstantOp>(
        op.getLoc(), rewriter.getI32Type(), zero);
    if (!rhs || !rhs.hasOneUse())
      return mlir::failure();

    if (!matchPattern(rhs, m_Zero()))
      return mlir::failure();

    rewriter.replaceOp(op, rhs);
    return mlir::success();
  }
};
} // namespace
```

這段程式碼裡有幾件事是機械性的、重複的，而且容易寫錯：

* 「拿到 rhs」「判斷 rhs 是零」——**匹配邏輯**寫成 C++ 程式碼，而不是宣告式描述。
* 每次新增一個類型的操作（例如 `my.mul`），就要複製整段 match 邏輯，只換 op 類別。
* 匹配失敗時的 early return 樣板。
* 若要匹配「恆等元件」（恆等常數、零、常量），`m_Zero()` 這種 matcher 物件用起來比 `matchPattern` 更簡潔，但兩者混用時風格不統一。

隨著方言擴展，pattern 檔案會膨脹成數千行高度相似的 C++。維護成本來自幾個方向：

1. **重複**：同一個匹配形狀（例如「恆等加法」）在多個方言、多個轉換中重複實作。
2. **脆弱**：pattern 的匹配條件分散在多個方法裡，條件之間的邏輯關係（短路順序、副作用）不直觀。
3. **難以閱讀**：C++ 語法噪音淹沒了「我要匹配什麼」這個意圖。
4. **難以測試**：要驗證一個 pattern，通常得寫一個完整的 IR 檔案再用 `mlir-opt` 跑。

DRR（Declarative Rewrite Rules，宣告式重寫規則）就是為了消除這些成本而生的。

## DRR 的語法

DRR 是 TableGen 之上的一個小語言，專門描述 pattern。它活在 `.td` 檔案裡，透過 `include` 引用 ODS 檔案。

### 一個完整的 DRR 範例

```tablegen
// include/mlir/Dialect/My/MyCanonicalization.td
include "mlir/Dialect/My/MyOps.td"

def AddZeroCanonicalization : Pat<"add-zero", (AddOp:$x, Zero)> {
  let summary = "0 + x -> x";
  let replacement = "$x";
}
```

這段定義的語意是：匹配一個 `AddOp`，其第一個 operand 是 `$x`（任意），第二個 operand 匹配 `Zero`（MLIR 內建的一個「零值」matcher）。替換結果是把整個 op 換成 `$x` 這個 operand。

在 C++ 中，`Zero` 對應 `mlir::matchPattern` 家族中的 `m_Zero()` matcher——它的定義在 `mlir/IR/Matchers.h`：

```cpp
/// Matches a zero constant, including the case where the constant is
/// materialized by a `arith.constant` operation.
struct Zero {
  bool match(mlir::Operation *op) const;
};
```

### DRR 關鍵字一覽

| 關鍵字 | 意義 |
| --- | --- |
| `Pat<"name", (args)>` | 定義一個 pattern，含名稱與匹配結構 |
| `bind<...>` | 在 pattern 中綁定一個值 |
| `replace<...>` | 明確指定替換結果 |
| `attr-dict` | 匹配並保留屬性字典 |
| `constraint<...>` | 附加 side condition |
| `(OpName:$arg)` | 匹配一個 op，把它的第 k 個 operand 綁定到 `$arg` |
| `(OpName attr-dict)` | 匹配一個 op 的屬性字典 |
| `^` | 綁定到某個 op 的「包含關係」父節點 |
| `$` | 綁定到值（operand 或 result） |
| `<` `>` | 綁定到 op 的區域（region） |

### `Pat` 的語法骨架

```tablegen
def PatternName : Pat<"pattern-name", (matcher1, matcher2, ...)> {
  let summary = "...";
  let replacement = "...";   // 或使用 replace<
}
```

`Pat` 的第二個參數是一個 tuple，列出這個 pattern 的**頂層 matcher**，每個 matcher 對應一個要匹配的子元素。

### 綁定符號 `$`、`<`、`>` 的分工

這三個符號在 DRR 中各有明確分工：

* `$x` 綁定一個 **value**（operand 或 result）。
* `<x>` 綁定一個 **region**。
* `^x` 綁定一個 **operation**（用於表達「這個 op 是某個 op 的子 op」這種巢狀關係）。

看一個更複雜的例子：

```tablegen
def TransferWriteToStore : Pat<"transfer-write-to-store", (TransferOp:$op)> {
  let summary = "transfer write becomes a store";
  let replacement = [{
    $op[`buffer`($_op[`addr`($op)]), `size`($_op[`size`($op)])]
  }];
}
```

這個例子展示了三件事：

1. `$op` 綁定了 `TransferOp` 這個 operation。
2. `$_op[...]` 這種寫法存取**被綁定 op 的屬性**。
3. 替換體可以是一段「組語風格」的模板，DRR 會把它翻譯成具體的 op 建構呼叫。

### 替換體的寫法

替換體（`replacement`）可以寫成三種形式：

**一、綁定變數直接回傳。**

```tablegen
def AddZeroCanonicalization : Pat<"add-zero", (AddOp:$x, Zero)> {
  let replacement = "$x";
}
```

**二、`replace<...>` 形式，表達「用這些東西取代」。**

```tablegen
def AddMulCanonicalization : Pat<"add-mul", (AddOp:$x, (MulOp:$y, $z))) {
  let replacement = (AddOp $x $y, MulOp $y $z);
}
```

**三、組語風格字串模板。**

```tablegen
def CastFoldCanonicalization : Pat<"cast-fold", (CastOp:$op)> {
  let replacement = "$op";
}
```

第三種形式在實務上非常常見，DRR 會把字串解析成一個 op 樹模板，其中：

* `$name` 展開成綁定的值。
* `opname[attr1, attr2]` 展開成一個 op，`attr` 若是綁定則用其值，否則視為字面量屬性。
* `$_op[...]` 是「引用被綁定 op 的屬性」。

### `attr-dict` 與 `constraint`

```tablegen
def TransferOpCanonicalization : Pat<"transfer-canonicalize",
    (TransferOp:$op, (Op:$inner) { attr-dict })> {
  let summary = "保留屬性並加上約束";
  let replacement = "...";
}
```

`constraint<...>` 附加一個**side condition**，用 C++ 布林運算式表達：

```tablegen
def NonZeroCanonicalization : Pat<"non-zero", (AddOp:$x, $y)> {
  let constraint = "!(::mlir::matchPattern($y, m_Zero()))";
  let replacement = "$x";
}
```

`constraint` 的內容是任意 C++ 運算式，裡面可以用 `$name` 指涉綁定值。這是 DRR 與純宣告式匹配的橋樑——但它也是 DRR 的弱點所在（後述）。

## DRR 與 C++ Pattern 的對應關係

DRR 不是另一套執行引擎，它是 **C++ pattern 的產生器**。`-gen-drr` 動作會把 `.td` 裡的 `Pat` 展開成一個 `mlir::RewritePattern` 子類。

以 `AddZeroCanonicalization` 為例，DRR 產生的 C++ 大致如下：

```cpp
namespace {
struct AddZeroCanonicalization : public ::mlir::OpRewritePattern<::mlir::my::AddOp> {
  using ::mlir::OpRewritePattern::OpRewritePattern;

  ::mlir::LogicalResult matchAndRewrite(::mlir::my::AddOp op,
                                        ::mlir::PatternRewriter &rewriter) const override {
    ::mlir::Value x, y;
    if (!::mlir::matchPattern(op, ::mlir::m_Op<AddOp>(::mlir::m_AnyValue(), ::mlir::m_Zero())))
      return ::mlir::failure();
    ...
    rewriter.replaceOp(op, x);
    return ::mlir::success();
  }
};
} // namespace
```

對照關係如下：

| DRR 語法 | 生成的 C++ | 對應的 C++ 手寫寫法 |
| --- | --- | --- |
| `(AddOp:$x, $y)` | `m_Op<AddOp>(m_AnyValue(), m_AnyValue())` | `matchPattern(op, m_Op<AddOp>(...))` |
| `Zero` | `m_Zero()` | `matchPattern(rhs, m_Zero())` |
| `let replacement = "$x"` | `rewriter.replaceOp(op, x)` | 同左 |
| `let constraint = "..."` | `if (!(...)) return failure();` | 手寫 if |
| `let summary` | `getDescription()` | 手寫字串 |

所以 DRR 的定位是：**用宣告式語法產生 `RewritePattern` 子類**，而不是取代 pattern 機制本身。`PatternRewriter`、`PatternApplicator`、benefit 排序、`GreedyPatternRewriteDriver` 這些核心機制完全共用。

### `m_Op` matcher 家族

DRR 產生的程式碼依賴 `mlir/IR/Matchers.h` 提供的 matcher 物件：

```cpp
template <typename OpT> struct OpMatcher {
  ::llvm::function_ref<::llvm::LogicalResult(typename OpT::Adaptor,
                                             ::mlir::ArrayRef<::mlir::Value>)>
      bindFn;
  ::llvm::function_ref<::llvm::LogicalResult(typename OpT::Adaptor,
                                             ::mlir::DictionaryAttr)>
      verifyFn;
};
```

`m_Op<AddOp>(...)` 會建立一個 matcher，它依序：

1. 檢查 op 的型別是不是 `AddOp`。
2. 依序呼叫每個子 matcher，檢查 operand / 屬性。
3. 把綁定的值寫進 `OpT::Adaptor` 的對應欄位。

`OpT::Adaptor` 是 ODS 產生的**扁平化 operand 視圖**，把 variadic operand 展開成單一序列。

## 一個完整的 DRR 使用流程

### 步驟 1：在 ODS 檔案中定義 op

```tablegen
// include/mlir/Dialect/My/MyOps.td
include "mlir/IR/OpBase.td"

def My_Dialect : Dialect {
  let name = "my";
  let cppNamespace = "::mlir::my";
}

class My_Op<string mnemonic, list<Trait> traits = []>
    : Op<My_Dialect, mnemonic, traits>;

def AddOp : My_Op<"add", [Pure, SameOperandsAndResultType]> {
  let summary = "Adds two operands";
  let arguments = (ins AnySignlessIntegerOrFloatLike:$lhs,
                        AnySignlessIntegerOrFloatLike:$rhs);
  let results = (outs AnySignlessIntegerOrFloatLike:$result);
  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
```

### 步驟 2：定義 DRR

```tablegen
// include/mlir/Dialect/My/MyCanonicalization.td
include "mlir/Dialect/My/MyOps.td"

def AddZeroCanonicalization : Pat<"add-zero", (AddOp:$x, Zero)> {
  let summary = "0 + x -> x";
  let replacement = "$x";
}

def SelfMultiplyCanonicalization : Pat<"self-mul", (MulOp:$x, $x)> {
  let summary = "x * x -> x";
  let replacement = "$x";
}
```

注意第二個 pattern 的特別之處：`(MulOp:$x, $x)` 出現了**同一個綁定名兩次**。DRR 的語意是「第二個 operand 必須等於第一個 operand」，這是一個**結構性的等值約束**，不需要 C++ side condition。這是 DRR 相對於手寫 pattern 的一個實質優勢。

### 步驟 3：產生 C++

```cmake
set(LLVM_TARGET_DEFINITIONS include/mlir/Dialect/My/MyCanonicalization.td)
mlir_tablegen(MyCanonicalization.h.inc -gen-drr)
mlir_tablegen(MyCanonicalization.cpp.inc -gen-drr)
add_public_tablegen_target(MyCanonicalizationIncGen)
```

`-gen-drr` 會產生兩個檔案：宣告與實作。產生的 pattern 類別位於 `mlir::my::` 命名空間（由 ODS 的 `cppNamespace` 決定）。

### 步驟 4：在 pass 中引入

```cpp
// lib/Dialect/My/MyPasses.cpp
#include "mlir/Dialect/My/MyOps.h"
#include "mlir/Transforms/GreedyPatternRewriteDriver.h"

#include "MyCanonicalization.h.inc"

namespace mlir {
namespace my {

void populateMyCanonicalizationPatterns(RewritePatternSet &patterns) {
  patterns.add<AddZeroCanonicalization, SelfMultiplyCanonicalization>();
}

void registerMyPasses() {
  PassRegistration<MyCanonicalizePass>();
}

} // namespace my
} // namespace mlir
```

`RewritePatternSet::add<T>()` 是模板參數形式，會依 `T` 的基底類別推導「這是 operation pattern 還是 conversion pattern」，並且自動處理 `PatternBenefit`。

### 步驟 5：執行

```mlir
module {
  func @f(%a: i32) -> i32 {
    %c0 = arith.constant 0 : i32
    %0 = my.add %c0, %a : i32
    return %0 : i32
  }
}
```

執行 `mlir-opt --canonicalize` 後（假設 `my.add` 已註冊 canonicalization patterns）：

```mlir
module {
  func @f(%a: i32) -> i32 {
    return %a : i32
  }
}
```

## 從 IR 到 Pattern：執行期的匹配機制

DRR 只描述「要匹配什麼」，實際匹配是由 MLIR 的 `PatternApplicator` / `OperationEquivalence` 完成的。理解這個流程有助於判斷 pattern 的效能。

`PatternApplicator` 對每個 operation 呼叫所有可能的 pattern 的 `matchAndRewrite`。匹配分成三層：

1. **根 op 的型別檢查**：`PatternApplicator` 先檢查 pattern 的根 matcher 型別是否與當前 op 相容（這是 `m_Op<AddOp>` 做的事），不相容就跳過，這是最廉價的過濾。
2. **子 matcher 遞迴**：對 operand、屬性、region 遞迴套用 matcher。
3. **side condition 與 constraint**：最後才評估 `constraint` 這類昂貴的布林條件。

這個順序意味著**把便宜的約束放在前面的 pattern 會更快**。MLIR 為此提供 `PatternBenefit`：

```cpp
struct AddZeroCanonicalization : public mlir::OpRewritePattern<mlir::my::AddOp> {
  using OpRewritePattern::OpRewritePattern;
};
```

在 ODS 中則可以透過 `let benefit = N;` 指定。Benefit 高的 pattern 在 greedy 驅動器中優先嘗試。

### Greedy rewrite driver 的迴圈

```cpp
void GreedyPatternRewriteDriver::simplify(MutableArrayRef<Region> regions) {
  bool changed = true;
  while (changed) {
    changed = false;
    // 對每個 op 嘗試所有 pattern
    ...
  }
}
```

greedy 驅動器的關鍵性質：

* **不斷重複直到不變**（fixpoint）。因此 pattern 必須是「收斂」的——如果 `A -> B` 且 `B -> A`，greedy driver 會無限迴圈。MLIR 透過 `PatternApplicator` 的「一個 op 只能被改寫一次」（在單次遍歷中）來減少這個風險，但跨遍歷仍可能-loop。
* **由上而下**（top-down）嘗試，先處理外層 op。
* 每個 op 成功改寫後，其後代會被重新排入工作佇列。

這些性質決定了 DRR pattern 的設計原則：**一個 pattern 應該朝著「更簡單」的方向移動**，否則可能不收斂。

## DRR 的限制

DRR 的設計目標是涵蓋「**大部分**重寫規則」，但它確實有明確的邊界。

**限制一：不支援複雜的 side condition。**
`constraint` 可以放 C++ 運算式，但一旦條件需要跨越多個綁定值做複雜推論（例如「檢查 operand 的 defining op 是不是某個特定 op 並且它的屬性滿足某個不等式」），C++ 運算式會變得又長又難讀，等於退化成手寫 pattern，只是多包了一层殼。

**限制二：無法表達「需要 fallback」的匹配。**
有時 pattern 應該先嘗試 A 形狀，若失敗再試 B 形狀。手寫 C++ 可以用多個 `matchPattern` 呼叫優雅表達；DRR 只能寫多個 `Pat`，由 greedy driver 依序嘗試——但兩者的語意不完全等價（DRR 的多個 Pat 是「任一命中即改寫」，而不是「依序 fallback 並攜帶上下文」）。

**限制三：無法表達跨 op 的全域條件。**
例如「這個 function 裡沒有其他 op 使用這個 value」。這需要 dominance 資訊或符號表資訊，DRR 完全無能为力，只能退化到 `constraint` 裡寫 C++，或直接寫 C++ pattern。

**限制四：需要 fallback 的 op 產生。**
DRR 產生的 pattern 依賴 ODS 產生的 accessor，而 ODS accessor 在某些情況下需要使用者提供額外資訊（例如 `attr-dict` 的處理需要 op 支援 `getAttributeNames()`）。若 op 的 ODS 定義不足，DRR 產生的程式碼會編譯失敗——這時必須回到手寫 pattern。

**限制五：學習成本與上游支援有限。**
相較於 `assemblyFormat`（幾乎所有 op 都用），DRR 在上游方言中使用得相對少（主要在 `tosa`、`sparse_tensor` 等）。這不代表 DRR 有問題，但意味著可參考的範例較少，學習要靠文件與少量實例。

## 何時該用 DRR，何時必須寫 C++ pattern

給一個可操作的判準：

| 情境 | 建議 |
| --- | --- |
| 匹配形狀是「某個 op 的某組 operand」，條件可局部表達 | 用 DRR |
| 需要比較兩個 operand 是否相同 | 用 DRR（重複綁定名） |
| 需要匹配「某個屬性等於某個值」 | 用 DRR（`attr-dict` + constraint） |
| 需要跨越多個 op 的資訊（dominance、符號表、全域計數） | 寫 C++ pattern |
| 需要根據 op 的 defining op 做多層判斷 | 寫 C++ pattern |
| 條件複雜到 `constraint` 超過三行 | 寫 C++ pattern |
| 需要非 local 的 fallback 語意 | 寫 C++ pattern |
| 產生新的 op 需要非標準的建構流程 | 寫 C++ pattern |
| 需要精細控制 benefit 與改寫順序 | 兩者皆可（DRR 亦支援 `let benefit`） |

一個實務上的折衷策略：**先用 DRR 表達能表達的部分，把差異放進 `constraint`；當 `constraint` 超過合理長度時，把該 pattern 改寫成 C++。**

## 三方對照：DRR、C++ 與 IR

再回到 [3.2](03.2-ODS定義Operation.md) 末尾建立的三方對照，現在加入 DRR 這一維：

| 面向 | DRR（宣告） | C++ Pattern（實作） | MLIR 組語（被改寫的對象） |
| --- | --- | --- | --- |
| 匹配根 op | `(AddOp:$x, Zero)` | `matchPattern(op, m_Op<AddOp>(m_AnyValue(), m_Zero()))` | `%0 = my.add %c0, %a : i32` |
| 綁定 | `$x` | `Value x` | `%a` |
| 替換 | `let replacement = "$x"` | `rewriter.replaceOp(op, x)` | `%a`（result 直接被取代） |
| 等值約束 | 重複綁定名 `$x, $x` | `lhs == rhs` | `%0 = my.mul %a, %a` |
| 額外條件 | `let constraint = "..."` | 手寫 `if` | — |
| 描述文字 | `let summary` | `getDescription()` | — |

## 成本分析：DRR 真的省了多少

假設一個方言有 40 條 canonicalization 規則，其中 25 條可以用 DRR 表達，15 條必須手寫。

手寫全部 40 條，平均每條 18 行 C++： $40 \times 18 = 720$ 行。

改用 DRR：25 條 DRR，平均 5 行 TableGen： $25 \times 5 = 125$ 行；15 條手寫： $15 \times 18 = 270$ 行。總計 395 行，其中 TableGen 125 行、C++ 270 行。

節省 $720 - 395 = 325$ 行，約 45%。但真正的價值不在行數，而在於：

* **新增 op 時，canonicalization 規則的模板可以複用**。若 `AddOp` 與 `MulOp` 都需要「零運算」規則，DRR 版本只需改兩行 op 名稱。
* **規則意圖更清楚**。`Pat<"add-zero", (AddOp:$x, Zero)>` 一眼就能看出規則是什麼；對應的 C++ 需要讀完整個函式。
* **可以在產生階段做驗證**。`-gen-drr` 會檢查綁定的名稱是否存在、operand 索引是否合法，這類錯誤在 C++ 裡要到編譯期才發現。

## 從 DRR 到更高階：PDL 與 declarative pipeline

DRR 是「宣告式改寫」的早期嘗試，它的後繼者與延伸方向值得一提。

**PDL（Pattern Description Language）** 是一個更激進的想法：把「匹配條件」與「改寫行為」都交給使用者寫**可執行的 interleaved pattern**。MLIR 提供 `pdl` 方言，以及 `PDLPattern` / `PDLRewrite`，讓使用者寫：

```mlir
pdl.pattern @constant_fold : match(root) {
  %zero = pdl.attribute.constant 0
  pdl.match %root : AddOp
  pdl.rewrite %root with "replaceOp"(%zero) : (i32) -> i32
}
```

PDL 的優勢是**可以在 MLIR 層級（而非 C++ 層級）描述並執行改寫**，這對自動產生的轉換（例如 XLA 的 pattern 產生器）特別有用。

**Declarative pipeline** 與 `pdl` 方言一起，讓 pass 的序列本身也能宣告式描述，甚至可以在執行期依 IR 內容決定要跑哪些 pattern。

DRR、PDL 與 C++ pattern 三者的定位可以這樣記：

* **DRR**：C++ pattern 的**產生器**，寫在 `.td` 裡，產生 C++。
* **PDL**：IR 層級的**執行期 pattern 語言**，寫在 `.mlir` 裡，直接在 MLIR 執行。
* **C++ pattern**：需要任意邏輯時的**終極逃生門**。

## 小結與延伸閱讀

* DRR 是 TableGen 之上描述重寫規則的語言，由 `mlir-tblgen -gen-drr` 產生 `mlir::RewritePattern` 子類，與 C++ pattern 共用同一套匹配與重寫引擎。
* `Pat<"name", (matchers)>` 定義 pattern；`$` 綁定值、`<>` 綁定 region、`^` 綁定 op；重複綁定名即為結構性等值約束。
* `let replacement` 指定替換體，`let constraint` 附加 side condition，`let summary` 提供描述，`let benefit` 影響 greedy driver 的嘗試順序。
* DRR 的邊界在於：跨 op 的全域條件、多層 fallback、複雜推論——遇到這些就必須寫 C++ pattern。
* 判準：能在「op + operand 形狀 + 屬性」層次完整表達的用 DRR；需要 dominance、符號表、或非局部資訊的用 C++。
* 延伸閱讀：`mlir/docs/DeclarativeRewrites.md`（DRR 語法參考）、`mlir/include/mlir/IR/Matchers.h`（`m_Op`、`m_Zero` 等 matcher 定義）、`mlir/include/mlir/Transforms/GreedyPatternRewriteDriver.h`（greedy driver）、`mlir/docs/PDL.md`（PDL 語言）、`mlir/test/lib/Dialect/Test/TestPatterns.cpp`（可執行範例）。
