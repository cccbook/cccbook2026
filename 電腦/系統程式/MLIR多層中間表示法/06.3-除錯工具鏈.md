# 6.3 實戰除錯：mlir-opt、IR 傾印與錯誤定位

前兩節談的是「怎麼寫出正確的 MLIR 程式碼」，本節談的是「寫錯了怎麼找出來」。這是一個實務上面臨的真實比例問題：MLIR 的除錯成本不低，而掌握工具鏈能把這個成本壓下來。

本節的內容以 `mlir-opt` 為核心——它是 MLIR 社群最重要的除錯與測試工具，也是所有方言開發者每天都會打交道的對象。

## `mlir-opt` 基礎

`mlir-opt` 是 MLIR 的通用 pass 驅動器。它做三件事：

1. 讀取 `.mlir` 檔案（也可以從標準輸入）。
2. 依命令列指定的 pipeline 執行 pass。
3. 印出結果 IR（或其他輸出）。

最基本的使用：

```bash
# 執行一個 pass。
mlir-opt input.mlir -canonicalize -o output.mlir

# 從標準輸入讀取，輸出到標準輸出。
cat input.mlir | mlir-opt -canonicalize

# 產生 LLVM IR 形式的輸出（需要先降到 llvm dialect）。
mlir-opt input.mlir -convert-scf-to-cf -convert-arith-to-llvm \
         -convert-func-to-llvm -reconcile-unrealized-casts \
         -o output.ll

# 檢查檔案是否合法（不做任何轉換，只做 parse + verify）。
mlir-opt input.mlir -o /dev/null
```

最後一條是個不起眼但極其有用的命令：**當你不確定 IR 是否有問題時，先跑它**。如果這裡就失敗，問題在輸入；如果通過，問題在你的 pass。

### `--help` 與 pass 列表

```bash
# 列出所有已註冊的 pass。
mlir-opt --help

# 只列出某個字串開頭的 pass。
mlir-opt --help | grep -i buffer

# 顯示某個 pass 的說明文件。
mlir-opt --help-hidden | grep -A 20 "convert-linalg-to-loops"
```

`mlir-opt --help` 是探索方言的入口。當你不確定某個方言提供了哪些 pass、pass 的引數是什麼時，這是最可靠的第一手資訊——比搜尋網路可靠，因為它反映的是你手上這個版本。

## 常用選項速查

### Pipeline 組合

```bash
# 用通用 pipeline 語法組合多個 pass。
mlir-opt input.mlir -pass-pipeline='builtin.module(func.func(canonicalize,loop-fusion))'

# 巢狀 pipeline 反映 IR 的層級結構：module -> func -> loop。
mlir-opt input.mlir -pass-pipeline='builtin.module(func.func(scf.for(loop-invariant-code-motion)))'

# 在 pipeline 中插入除錯用的 pass。
mlir-opt input.mlir -pass-pipeline='builtin.module(print-ir-before=canonicalize,canonicalize)'
```

`-pass-pipeline=` 與單一 pass 選項（`-canonicalize`）可以共存，但**順序由命令列上的位置決定**，容易混淆。實務上建議：簡單情形用單一 pass 選項，複雜情形統一用 `-pass-pipeline=`。

### IR 傾印

這組選項是除錯的日常主力：

```bash
# 在每個 pass 之前印出 IR。
mlir-opt input.mlir --mlir-print-ir-before-all

# 在每個 pass 之後印出 IR。
mlir-opt input.mlir --mlir-print-ir-after-all

# 只在某個 pass 之後印出。
mlir-opt input.mlir --mlir-print-ir-after=canonicalize

# 只在某個 pass 之前印出。
mlir-opt input.mlir --mlir-print-ir-before=canonicalize

# 只在失敗時印出 IR（最有用的除錯選項之一）。
mlir-opt input.mlir --mlir-print-ir-after-failure

# 只印出最後的 IR（預設行為）。
mlir-opt input.mlir -canonicalize
```

「只印特定 pass」的語法支援前綴比對：

```bash
# 印出所有以 convert- 開頭的 pass 之後的 IR。
mlir-opt input.mlir --mlir-print-ir-after=convert-
```

`--mlir-print-ir-after-all` 的輸出格式值得熟悉。每個 pass 都會產生一段：

```text
// -----// IR Dump: canonicalize //----- //
func.func @f(%arg0: i32) -> i32 {
  %0 = arith.constant 1 : i32
  %1 = arith.addi %arg0, %0 : i32
  return %1 : i32
}

// -----// IR Dump: cse //----- //
...
```

這讓你能直接看出「哪一個 pass 把 IR 改壞了」：看最後一個 IR dump 與失敗訊息之間的差距。

### 通用格式輸出

```bash
# 用通用格式印出 IR。
mlir-opt input.mlir --mlir-print-op-generic
```

通用格式是 MLIR 的**抽象語法形式**，每個 op 都以 `Dialect.op` 的形式出現，所有屬性都完整列出：

```mlir
"func.func"() ({
  ^bb0(%arg0: i32):
    %0 = "arith.constant"() {value = 1 : i32} : () -> i32
    %1 = "arith.addi"(%arg0, %0) : (i32, i32) -> i32
    "func.return"(%1) : (i32) -> ()
}) {function_type = (i32) -> i32} : () -> ()
```

它的用途有兩個：

**第一，看清楚 op 的真實屬性。** 自訂的 assembly format 會隱藏某些屬性（例如 `operand_segment_sizes`、隱含的 `library_call`）。通用格式把它們全部顯示出來。

**第二，做機械式比對。** 當你需要確認「兩個版本的下游產物是否相同」或「某個屬性有沒有被改動」時，通用格式因為沒有簡化，比較結果更可靠。

### 除錯資訊

```bash
# 印出 source location。
mlir-opt input.mlir --mlir-print-debuginfo

# 印出 stack trace（配合 --mlir-print-ir-after-failure 使用效果最好）。
mlir-opt input.mlir --mlir-print-stacktrace

# 限制印出的 scope，避免 nested region 造成的大量輸出。
mlir-opt input.mlir --mlir-print-local-scope
```

`--mlir-print-debuginfo` 會讓每個 op 帶上它對應的原始碼位置：

```mlir
%0 = arith.addi %arg0, %c1 : i32 loc("test.mlir":3:5)
```

這是追蹤「這個 op 是從哪裡來的」的最直接手段。

`--mlir-print-local-scope` 限制印出範圍到當前 operation 的區域（不遞迴進入巢狀的符號定義），在處理大型模組（例如含大量 `llvm.mlir.global`）時能大幅減少雜訊。

### 效能與雜項

```bash
# 關閉多執行緒（除錯時有用，可讓輸出順序固定）。
mlir-opt input.mlir -mlir-disable-threading

# 印出各個 pass 的耗時統計。
mlir-opt input.mlir --mlir-timing

# 當元素屬性很大時，把它的內容省略成摘要。
mlir-opt input.mlir --mlir-elide-elementsattrs-if-larger=64

# 輸出到檔案。
mlir-opt input.mlir -canonicalize -o out.mlir

# 輸出到標準輸出（預設）。
mlir-opt input.mlir -canonicalize
```

`--mlir-timing` 的輸出類似：

```text
=== Timing Analysis ===
  0.0000s (  0.0%)      MLIRParser
  0.1421s ( 95.2%)      Canonicalizer
  0.0072s (  4.8%)      CSE
```

它是找出「pipeline 中哪一段是瓶頸」的第一手資料。在 MLIR 開發中，canonicalization 與 conversion 通常是耗時大戶。

`--mlir-elide-elementsattrs-if-larger` 針對 `dense` 屬性：`dense<...>` 陣列在元素數量多時會佔據大量輸出。設定門檻（例如 64）之後，超過門檻的元素屬性會被摘要成類似 `dense<"[9]">` 的形式。

## `--split-input-file` 與 `// -----` 分隔符

MLIR 的 lit 測試框架（`llvm-lit`）用一種特殊格式，讓單一檔案可以包含多個獨立的測試案例。

```mlir
// RUN: mlir-opt %s --split-input-file --verify-diagnostics | FileCheck %s

// -----

func.func @test1() {
  // CHECK: arith.constant
  %0 = arith.constant 1 : i32
  return
}

// -----

func.func @test2() {
  // expected-error @+1 {{expected SSA operand}}
  %0 = arith.addi %1 : i32
  return
}
```

`// -----` 這一行分隔出的每一段，會被**分別**餵給 `mlir-opt`（因為 `--split-input-file` 的作用），因此每段可以獨立宣告自己的 `// CHECK:` 或 `// expected-error`。

這個格式是 MLIR 測試的標準寫法。掌握它的原因是：**它讓「最小化重現」變得非常容易**。當你遇到一個 bug 時，只要把問題的 IR 複製到一個新檔案、用 `// -----` 包起來，就是一個可以貼進 issue 的最小重現案例。

### `--verify-diagnostics`

`--verify-diagnostics` 會讀取 IR 中的診斷註解，並驗證**實際產生的診斷**是否與註解一致：

```mlir
// expected-error @+1 {{operand #0 must be 32-bit float}}
%0 = arith.addf %arg0, %c1_i32 : f32
```

如果程式碼有錯、診斷訊息的文字也改了，測試就會失敗——這提供了一道防護，避免診斷訊息在重構中悄悄改變。

註解的變體：

| 註解 | 意義 |
| --- | --- |
| `// expected-error @+1 {{...}}` | 下一行應該產生符合此樣式的錯誤 |
| `// expected-warning @+1 {{...}}` | 下一行應該產生警告 |
| `// expected-note @+1 {{...}}` | 下一行應該產生 note |
| `// expected-remark @+1 {{...}}` | 下一行應該產生 remark |
| `@+1` | 相對於註解行的行號偏移 |
| `@+2` | 偏移兩行 |

這個機制與 [6.1](06.1-Verifier與結構不變式.md) 的診斷串接直接相關：診斷訊息的**文字**也成了可測試的契約。

## `--verify-each`

`--verify-each`（預設開啟）控制「是否在每個 pass 之後驗證 IR」。可以用 `--verify-each=false` 關閉。

```bash
# 關閉每個 pass 後的驗證，觀察 pass 是否會把 IR 弄壞（壞掉時會在最後才報錯）。
mlir-opt input.mlir --verify-each=false -my-pass
```

這個選項在診斷「pass 是否破壞 IR」時非常有用：若開啟時報錯、關閉時通過最後的驗證，代表問題出在某個 pass 中途產生但被後續 pass 修好了（或掩蓋了）。

在 C++ 端對應的是 `PassManager::enableVerifier()` / `disableVerifier()`。

## 診斷訊息解讀

MLIR 的錯誤訊息通常包含三個部分：**錯誤描述、note（補充說明）、以及 IR 片段**。逐類解讀。

### 「expected N results」

```text
error: 'my.op' op expected 1 results, but got 0
```

這是 ODS 產生的結構檢查。成因通常是：

- `replaceOp` 的替換值數量與原 op 的 result 數量不符。
- `OpConversionPattern` 產生的新 op 的 result 數量與被替換的 op 不同。
- 手寫 assembly format 中，解析出來的 operand 數量與 ODS 宣告不一致。

定位方式：在 `replaceOp` 的呼叫處檢查 `values.size()` 與 `op->getNumResults()`。

### 「operand #0 does not dominate this use」

```text
error: 'my.op' op operand #0 ('%0') does not dominate this use
```

這是 dominance 檢查。成因通常是：

- Pattern 從 block A 取得一個值，卻把新 op 插入到 block B，而 B 不由 A 支配。
- Region 重排或 block 合併時，block argument 的作用域改變了。
- 迴圈的 iter_args 處理不當：新 op 放在迴圈體內，卻引用了迴圈之後才定義的值。

定位方式：用 `--mlir-print-ir-before=<pass>` 看改寫前的結構，確認 value 的定義點與使用點。

### 「type mismatch」類

```text
error: 'arith.addf' op operand #0 must be 32-bit float, but got 'tensor<f32>'
```

ODS 的型別檢查。成因：

- Pattern 忘記做型別轉換。
- 在 conversion 中用了 `op.getLhs()`（原始型別）而非 `adaptor.getLhs()`（已轉換型別），見 [5.2](05.2-DialectConversion框架.md)。
- 降階順序錯誤：某個方言的 op 在型別已經被轉換之後才被降階。

### 「failed to legalize operation」

```text
error: failed to legalize operation 'my.high' that was explicitly marked illegal
note: see current operation:
%0 = my.high %a : f32
```

這是 conversion 的失敗。成因是沒有任何 pattern 能把該 op 變成合法的形式。定位方式：

- 確認 pattern 的 root op 名稱正確——`RewritePattern` 的 root 名稱寫錯時不會報錯，只是永遠不匹配。
- 確認 pattern 有被加進 `RewritePatternSet`。
- 用 `--mlir-print-ir-after=<前一個 pass>` 確認轉換時機正確。

### 「region is not isolated」

```text
error: operand #0 ('%v') is used by an operation in a successor block, but is not
       a successor operand
```

graph region 的隔離性檢查。成因是在 graph region 中跨 block 使用 value，卻沒有透過 `SuccessorOperands` 宣告。

### 「does not dominate this use」之外的 SSA 錯誤

```text
error: operand #0 ('%v') does not dominate this use
```

與前類似，但更明確指出是 SSA 支配關係問題。

## `mlir-reduce`：把重現案例縮到最小

`mlir-reduce` 是 MLIR 的**差異化測試（delta debugging）**工具。它的輸入是一個「會失敗的測試」，輸出是一個「仍會失敗、但更小」的測試。

```bash
# 基本用法。
mlir-reduce test.mlir -o reduced.mlir

# 指定測試指令與其引數。
mlir-reduce test.mlir -o reduced.mlir \
  --test-arg=mlir-opt \
  --test-arg=--split-input-file

# 使用既有的測試腳本。
mlir-reduce test.mlir -o reduced.mlir --test-script=/path/to/test.sh
```

`mlir-reduce` 的運作原理是反覆嘗試各種「刪減」：

1. 刪掉一個 op。
2. 刪掉一個 block。
3. 刪掉一個屬性。
4. 縮減常數的值。
5. 刪掉一段 `// -----` 分隔的測試案例。

每一個刪減之後都重跑測試，若測試**仍然失敗**（即 bug 仍然重現），就保留這個刪減。這個過程是 $O(n)$ 次測試執行， $n$ 為原始案例的大小。

在 MLIR 的開發流程中，標準做法是：

```text
使用者回報 bug（附帶一個重現檔案）
        ↓
維護者用 mlir-reduce 縮減
        ↓
得到最小案例，提交為 regression test
```

要注意 `mlir-reduce` 需要「測試必須失敗才算 bug 存在」這個前提。如果你的測試是「應該成功」，可以用 `--test-arg` 搭配一個反轉結果的腳本。

## `mlir-tblgen` 與方言工具鏈

`mlir-tblgen` 是 ODS 的程式碼產生器。方言作者用它從 `.td` 檔案產生 C++ 標頭檔與實作：

```bash
# 產生 op 的 C++ 類別宣告。
mlir-tblgen -gen-op-decls -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td \
  -o MyDialectOps.h.inc

# 產生 op 的 C++ 實作骨架。
mlir-tblgen -gen-op-defs -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td \
  -o MyDialectOps.cpp.inc

# 產生 dialect 的宣告。
mlir-tblgen -gen-dialect-decls -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td \
  -o MyDialect.h.inc

# 產生 dialect 的實作。
mlir-tblgen -gen-dialect-defs -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td \
  -o MyDialect.cpp.inc

# 產生介面宣告。
mlir-tblgen -gen-interface-decls -I include mlir/Dialect/MyDialect/IR/MyDialectInterfaces.td \
  -o MyDialectInterfaces.h.inc
```

除錯技巧：

```bash
# 列出 mlir-tblgen 支援的所有產生器（-gen-*）與選項。
mlir-tblgen --help

# 把產生的 C++ 直接印到標準輸出，不落地成檔案，方便快速檢視。
mlir-tblgen -gen-op-decls -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td -o -

# 產生後立刻用 grep 找出某個方法是否真的被產生出來。
mlir-tblgen -gen-op-decls -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td -o - \
  | grep -n "getNumLoops"
```

在 dialect 開發中，最常見的除錯需求是「**我的 ODS 巨集為什麼沒有產生我想要的東西**」。此時把 `.td` 檔案用 `mlir-tblgen` 展開，看巨集展開後的 `def` 定義，是最快的路徑。

### 方言專屬的 opt 工具

慣例上，每個方言會提供一個自己的工具，例如 `mlir-opt` 加上該方言的 pass：

```bash
# 社群工具的例子。
mlir-opt input.mlir -my-lowering
```

更進階的做法是建立方言專屬的 driver：

```cpp
#include "mlir/Tools/mlir-opt/MlirOptMain.h"

int main(int argc, char **argv) {
  mlir::DialectRegistry registry;
  registry.insert<my::MyDialect>();
  my::registerMyPasses();

  return mlir::asMainReturnCode(
      mlir::MlirOptMain(argc, argv, "My dialect optimizer\n", registry));
}
```

`MlirOptMain` 會自動處理命令列解析、pass 管理、驗證與輸出。

## 一個完整的除錯流程

把上面的工具組合成一個可重複使用的流程。

### 步驟一：確認問題可以重現

```bash
mlir-opt repro.mlir -my-pass --mlir-print-ir-after-all 2>&1 | tail -50
```

記錄：最後一個成功的 IR dump 是什麼？失敗訊息的第一行是什麼？

### 步驟二：判斷是解析問題還是轉換問題

```bash
# 只 parse + verify，不做任何轉換。
mlir-opt repro.mlir -o /dev/null
```

若這裡就失敗，問題在輸入 IR（型別、terminator、屬性）。若通過，問題在 pass。

### 步驟三：縮小範圍

```bash
# 只跑單一 pass。
mlir-opt repro.mlir -my-pass --mlir-print-ir-before=my-pass

# 用 pipeline 語法在中間插入檢查。
mlir-opt repro.mlir -pass-pipeline='builtin.module(print-ir-before-all,func.func(my-pass,print-ir-after-all))'
```

### 步驟四：找出改壞的那一步

```bash
# 關閉每步驗證，看問題是否在 pass 中途產生。
mlir-opt repro.mlir -my-pass --verify-each=false

# 開啟 stack trace 取得更多脈絡。
mlir-opt repro.mlir -my-pass --mlir-print-stacktrace
```

### 步驟五：把問題縮到最小

```bash
mlir-reduce repro.mlir -o minimal.mlir --test-arg=mlir-opt --test-arg=-my-pass
```

### 步驟六：轉成 regression test

```mlir
// RUN: mlir-opt %s --split-input-file --verify-diagnostics | FileCheck %s

// -----

func.func @minimal_case(%a: f32) -> f32 {
  // CHECK-LABEL: func.func @minimal_case
  // CHECK: arith.addf
  %0 = my.buggy_op %a : f32
  return %0 : f32
}
```

## 除錯流程 checklist

把整節內容壓縮成一張清單：

| 階段 | 動作 | 工具 |
| --- | --- | --- |
| 重現 | 固定命令列，記錄確切錯誤訊息 | `mlir-opt` |
| 判斷階段 | 只 parse + verify | `mlir-opt -o /dev/null` |
| 定位 pass | 印出每個 pass 前後的 IR | `--mlir-print-ir-after-all` |
| 定位 op | 印出通用格式，看清真實屬性 | `--mlir-print-op-generic` |
| 追蹤來源 | 印出 source location | `--mlir-print-debuginfo` |
| 判斷何時破壞 | 關閉逐步驗證 | `--verify-each=false` |
| 取得脈絡 | 印出 stack trace | `--mlir-print-stacktrace` |
| 縮減 | 差異化測試 | `mlir-reduce` |
| 追蹤效能 | 各 pass 耗時 | `--mlir-timing` |
| 固定順序 | 關閉多執行緒 | `-mlir-disable-threading` |
| 產生回歸測試 | 分割輸入 + 診斷註解 | `--split-input-file --verify-diagnostics` |
| 開發 ODS | 展開巨集 | `mlir-tblgen` |

## 從通用格式反推 assembly format

除錯時常遇到的情況是：通用格式顯示的 op 結構與你預期不符。此時需要回到 ODS 定義確認：

```bash
# 看看這個方言的 ODS 定義。
mlir-tblgen -gen-op-defs -I include mlir/Dialect/MyDialect/IR/MyDialectOps.td \
  -o /dev/stdout | head -80
```

MLIR 的 ODS 還有一個貼心設計：`mlir-tblgen` 也能產生 assembly format 的 parser 與 printer 骨架，把「格式定義」與「實作」分開：

```tablegen
let hasCustomAssemblyFormat = 1;
```

或使用 ODS 內建的格式描述：

```tablegen
let assemblyFormat = "$input `,` $filter attr-dict `:` type($result)";
```

當格式行為不符合預期時，先確認 ODS 的 `assemblyFormat` 是什麼，再看產生的 parser/printer 程式碼，比直接讀 C++ 實作快得多。

## 小結與延伸閱讀

- `mlir-opt` 是 MLIR 除錯的瑞士刀；`--mlir-print-ir-after-all`、`--mlir-print-op-generic`、`--mlir-print-debuginfo` 與 `--mlir-print-ir-after-failure` 覆蓋了絕大多數情境。
- `--split-input-file` 與 `// -----` 分隔符讓單一檔案能承載多個獨立測試案例，是撰寫 regression test 的標準格式；`--verify-diagnostics` 讓診斷訊息的文字也成為可測試契約。
- `mlir-reduce` 以差異化測試把重現案例縮到最小，是 MLIR 開發流程中把使用者回報轉為 regression test 的標準工具。
- `mlir-tblgen` 是理解 ODS 行為的第一手工具；把 `.td` 展開成 C++ 是診斷「為什麼巨集沒產生我想要的東西」的最快路徑。
- 一個可重複的除錯流程是：重現 → 只 parse 判斷階段 → 印出每步 IR 定位 pass → 通用格式定位 op → `mlir-reduce` 縮減 → 轉成 regression test。
