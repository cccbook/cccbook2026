# 4.2 多執行緒平行化與 IR 隔離性

## 平行化的誘惑與陷阱

[4.1](04.1-Pass生命週期與巢狀執行.md) 我們建立了 pass manager 的樹狀模型，並注意到 `OperationPass<func::FuncOp>` 在一個有 100 個函式的模組上會被執行 100 次——每次作用在一個不同的函式上。這看起來像是免費的平行機會。

但「看起來可以平行」與「實際上可以平行」之間，隔著一個極難的問題：**MLIR 的 IR 是可變的共享狀態**。

一個 operation 的 operand 有多個 use、result 有多個 use。當 pass A 執行時若刪掉或替換了一個 op，pass B 若在另一個執行緒上讀取同一個 op 的 use-list，就會讀到不一致的狀態。更糟的是，若 pass A 刪掉了一個 op，而 pass B 正在遍歷該 op 的某個區域，就會是 use-after-free。

本節要回答：MLIR 用什麼機制讓平行化**安全**，這個機制的代價是什麼，以及什麼情況下你**不能**依賴平行性。

## 為什麼 pass 之間不能自由平行

先建立一個決定性的區分。

**同一層（同一 manager）的 pass 之間有先後依賴，必須串行。**

pipeline 語意 `builtin.module(canonicalize, cse, canonicalize)` 表示明確的先後順序。第二個 `canonicalize` 之所以有意義，正是因為第一個改變了 IR 讓第二個有事可做。若兩者平行，整個 pipeline 的意義就消失了。

更根本地說，同層 pass 之間的順序是**由加入順序隱含定義的偏序**（[4.1](04.1-Pass生命週期與巢狀執行.md) 的模型），MLIR 必須尊重這個偏序。

**不同實例的同一個 pass 可以平行。**

`OperationPass<func::FuncOp>` 的 100 個實例，每個作用在一個不同的 `func.func` 上。兩個不同的函式在 IR 樹裡是**不相交的子樹**——沒有任何 operand/result 跨越函式邊界（除非透過全域符號或外部引用，那屬於另一種依賴，稍後討論）。

因此，MLIR 的平行化模型可以形式化為：

> **Pass manager 的同一層，在「作用於不相交 op 集合的不同實例」之間平行；不同層之間串行；同層的 pass 序列之間串行。**

這是一個非常保守但非常安全的模型。它的直接推論是：

* Module pass 沒有平行機會（只有一個實例）。
* Function-level pass 有 $n_\text{func}$ 個可平行實例。
* Loop-level pass 有 $n_\text{loop}$ 個可平行實例。

## MLIR 的多執行緒實作

### `PassManager` 的平行化控制

```cpp
class PassManager : public Operation::OpState {
public:
  /// 執行 pass 管線。
  void run(Operation *op);

  /// 設定是否啟用多執行緒。
  void enableMultithreading(bool enabled = true);

  /// 取得多執行緒是否啟用。
  bool isMultithreadingEnabled() const;

  /// 設定 IR 驗證器是否啟用。
  void enableVerifier(bool verifierEnabled = true);

  /// 取得 IR 驗證器狀態。
  bool isVerifierEnabled() const;
};
```

`enableMultithreading` 對應命令列旗標：

```bash
# 預設啟用
mlir-opt input.mlir --canonicalize

# 明確停用
mlir-opt input.mlir --canonicalize --mlir-disable-threading
```

`--mlir-disable-threading` 是除錯時的救命選項：當一個 pass 在平行下出現難以重現的 bug 或 crash 時，先用它把問題縮到單執行緒。

### `ThreadingUtilities`

MLIR 的平行執行建立在 LLVM 的 thread pool 之上：

```cpp
namespace mlir {
namespace ThreadingUtilities {

/// 在指定的 thread pool 上執行一個函式。
void executeOnThreadPool(llvm::ThreadPoolInterface &pool,
                         llvm::function_ref<void()> function);

/// 取得全域 thread pool。
llvm::ThreadPoolInterface &getGlobalThreadPool();

} // namespace ThreadingUtilities
} // namespace mlir
```

`getGlobalThreadPool()` 回傳 LLVM 的全域 thread pool，它由 `llvm::ThreadPool` 支撐：

```cpp
llvm::ThreadPool threadPool(numThreads);
```

MLIR 也提供 `mlir::ExecutionEngine` 與 `mlir::JitRunner` 在平行編譯多個函式時使用 thread pool，但那條路徑屬於編譯後端，不在本節範圍。

### `OpPassManager` 的平行執行點

平行化的機制在 `OpPassManager` 內部。概念上，它的執行流程是：

```cpp
void OpPassManager::run(Operation *op) {
  // 1. 決定要作用於哪些子 op（依 op 型別過濾）
  // 2. 若此 manager 下的 pass 都可以在 op 上執行，且已啟用多執行緒：
  //      把每個子 op 交給 thread pool 的一個 task
  // 3. 否則：循序處理每個子 op
}
```

一個 pass manager 下的 pass 集合之所以能對不同 op 平行，是因為 pass 是**可複製**的（`clonePass`），每個子 op 拿到一份獨立的 pass 實例與獨立的 analysis 快取。

這裡有一個重要的實作細節：**pass 的 `Option` 值在複製時會被 copy**，但 pass 內部的**可變狀態**（例如統計計數器）在實務上通常不被依賴。如果你的 pass 依賴跨實例的共享狀態（例如累加一個全域計數器），那在平行下會有資料競爭。

### 一個實際的平行 pass 程式碼

```cpp
// lib/Transforms/MyFunctionPass.cpp
#include "mlir/Dialect/Func/IR/FuncOps.h"
#include "mlir/IR/PatternMatch.h"
#include "mlir/Pass/Pass.h"

namespace {

struct MyFuncOptimizePass
    : public PassWrapper<MyFuncOptimizePass, OperationPass<func::FuncOp>> {
  MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID(MyFuncOptimizePass)

  MyFuncOptimizePass() = default;
  MyFuncOptimizePass(const MyFuncOptimizePass &other)
      : PassWrapper(other) {}

  StringRef getArgument() const final { return "my-func-optimize"; }
  StringRef getDescription() const final {
    return "Optimize each function independently";
  }

  void getDependentDialects(DialectRegistry &registry) const override {
    registry.insert<arith::ArithDialect>();
  }

  void runOnOperation() override {
    func::FuncOp func = getOperation();

    RewritePatternSet patterns(&getContext());
    patterns.add<MyPattern>(&getContext());

    if (failed(applyPatternsAndFoldGreedily(func, std::move(patterns))))
      signalPassFailure();
  }
};

} // namespace
```

這個 pass 之所以能平行，正是因為它：

1. 是 `OperationPass<func::FuncOp>`（作用於函式）。
2. 只在函式內部工作，不讀取模組層級的共享可變狀態。
3. 其區域性 pattern 不依賴函式外的資訊。

### 對照：不安全的平行 pass

```cpp
struct UnsafeGlobalPass
    : public PassWrapper<UnsafeGlobalPass, OperationPass<func::FuncOp>> {
  void runOnOperation() override {
    func::FuncOp func = getOperation();

    // 問題 1：直接操作全域模組結構，跨函式共享可變狀態。
    ModuleOp mod = func->getParentOfType<ModuleOp>();
    for (func::FuncOp other : mod.getOps<func::FuncOp>()) {
      if (other != func) {
        // 讀取並可能改寫另一個函式 —— 另一個執行緒可能正在改寫它。
        other.walk([&](Operation *op) { ... });
      }
    }

    // 問題 2：靜態計數器在平行下是資料競爭。
    static std::atomic<int> counter;
    counter++;
  }
};
```

這個 pass 在單執行緒下「看起來沒問題」，在平行下會產生：

* **use-after-free**：另一個執行緒可能剛好刪除了 `other` 裡的某個 op。
* **資料競爭**：`counter++` 不是原子的（即使改成 atomic，也會讓統計數字失去意義——不同執行緒的增量順序不確定）。

MLIR 沒有在 runtime 偵測這些問題，它**信任** pass 作者遵守以下規則：

> **一個 pass 只能操作分配給它的那棵 op 子樹。**

這就是「IR 隔離性」的實質：**隔離不是被強制，而是被假設，並由 pass 的執行模型（每個實例拿到一棵獨立子樹）所支撐**。

## IR 在平行下的可變性規則

把規則寫得更精確一點。

### 規則一：不同實例的 op 子樹不相交

`OperationPass<func::FuncOp>` 的兩個實例，一個作用在 `func::FuncOp` A，另一個作用在 B。這兩棵子樹在 IR 結構上不相交。

但「不相交」有個重要的例外：**全域符號與外部引用**。若 `func A` 呼叫 `func B`，A 的 op 裡會有一個 `SymbolRefAttr` 指向 B，但那是**屬性值**，不是 operand 指標，因此不構成共享可變狀態。A 若只是「讀取」B 的屬性，是安全的；A 若要「改寫」B，就不安全。

符號的正確做法是：把跨符號的改寫提升成 module-level pass，或用 `SymbolTable` / `SymbolTableCollection` 這類提供所有權語意的機制來協調（見本節後段的「全域符號」）。

### 規則二：同一個 Operation 的資料結構不可同時被兩個執行緒改寫

`Operation` 的內部結構包含：

* operand use-list（雙向連結）
* result use-list（雙向連結）
* block list（`iplist`）
* region list（`ilist`）
* attribute dictionary
* operand/result 的 `Value` 物件

其中 `Value` 的型別是 `OpResult` 或 `BlockArgument`，它們持有指向 owning `Operation` 的指標，並被 use-list 維護。任何新增或移除 use 都會改變 `Operation::use_begin()` 的迭代結果。

MLIR 的 use-list 是 **intrusive** 的（`Value` 物件內嵌指向 use-list 節點的指標），因此「刪除一個 op」的成本是 $O(1 + k)$ ，其中 $k$ 是該 op 的 use 數量，而不是 $O(n)$ 。這對平行效能很重要。

### 規則三：pass 之間的依賴屏障

MLIR 用**依賴屏障**來保證平行安全。這個機制的核心在 `OpPassManager::run`：

```
對 manager 下的每個子 op:
  收集所有「可以在此 op 上執行」的 pass
  若已啟用多執行緒且 pass 是 parallel-safe:
      把 (子 op, pass 序列) 交給 thread pool
  否則:
      在當前執行緒循序執行
```

「依賴屏障」在這裡的含義是：**同一個 manager 內、作用在同一棵子樹上的 pass 序列，永遠在同一個 task 中串行執行**。跨 task 之間只有「不同的 op 子樹」這一個共享點。

### 規則四：IR 驗證器是平行安全的

pass 執行後的 IR 驗證（`verify()`）在平行下是安全的，因為每個 task 驗證的是自己那棵子樹。但要注意：驗證器若要檢查跨邊界的性質（例如「某個 op 的 parent 是特定類型」），仍然只讀取自己的子樹，沒有問題。

### 規則五：analysis 快取在平行下是 per-instance 的

analysis 的快取是**依照 operation 的粒度**建立的：對 `func::FuncOp` 的分析結果存在以該 `func::FuncOp` 為 key 的快取中。兩個平行實例各自維護自己那棵子樹的分析結果，不會共享可變狀態。

但有一個陷阱：**如果一個 analysis 的計算需要存取模組層級的資訊**（例如符號表），那麼在平行下呼叫它時，讀取模組層的符號表是安全的（符號表在建構後是唯讀的），但**修改**符號表就不安全。

## Thread pool 的設定

### 由 LLVM 管理

MLIR 的 `PassManager` 在啟用多執行緒時使用 LLVM 的全域 thread pool。thread pool 的執行緒數由 LLVM 的選項控制：

```bash
# 指定執行緒數
mlir-opt input.mlir --canonicalize --llvm-num-threads=4

# 單執行緒（等同 --mlir-disable-threading）
mlir-opt input.mlir --canonicalize --llvm-num-threads=1
```

`--llvm-num-threads=0` 表示「使用所有硬體執行緒」。

### 明確建立自己的 thread pool

在自訂工具中，可以直接控制：

```cpp
#include "llvm/Support/ThreadPool.h"
#include "mlir/IR/MLIRContext.h"
#include "mlir/Pass/PassManager.h"

int main(int argc, char **argv) {
  unsigned numThreads = std::thread::hardware_concurrency();
  if (numThreads == 0)
    numThreads = 1;

  llvm::ThreadPool pool(numThreads);

  mlir::MLIRContext context;

  mlir::OpPassManager pm("builtin.module");
  pm.addPass(mlir::createCanonicalizerPass());

  // 手動把工作分派到 pool 上。
  ThreadingUtilities::executeOnThreadPool(pool, [&]() {
    auto module = mlir::parseSourceFile<mlir::ModuleOp>("input.mlir", &context);
    if (!module)
      return;
    (void)pm.run(module.get());
  });

  return 0;
}
```

注意這個例子其實沒有平行收益（只有一個 module）。真正的用法是**把多個 module 平行編譯**：

```cpp
llvm::ThreadPool pool(numThreads);

// 收集多個 module
std::vector<std::unique_ptr<mlir::ModuleOp>> modules;
for (const std::string &path : inputPaths) {
  auto mod = mlir::parseSourceFile<mlir::ModuleOp>(path, &context);
  if (!mod) {
    errs() << "failed to parse " << path << "\n";
    return 1;
  }
  modules.push_back(std::move(mod));
}

// 平行編譯
std::vector<bool> failed(modules.size(), false);
ThreadingUtilities::executeOnThreadPool(pool, [&]() {
  for (size_t i = 0; i < modules.size(); ++i) {
    mlir::OpPassManager pm("builtin.module");
    pm.addPass(mlir::createCanonicalizerPass());
    if (mlir::failed(pm.run(modules[i].get())))
      failed[i] = true;
  }
});
```

這裡的平行性是**跨 module** 的，每個 module 有自己的 `OpPassManager` 與 analysis 快取，彼此完全獨立。這是批次編譯場景（如編譯器 farm、大規模模型編譯）的標準做法。

**但要注意：`mlir::MLIRContext` 是共享的。** `MLIRContext` 本身是 thread-safe 的（它有內部的 mutex 保護 dialect/type 的註冊表），但**在 context 上建立的 `Operation` 不可跨執行緒同時改寫**。上例中每個 module 屬於不同的 module op，因此是安全的。

## 全域符號的挑戰

前面提到，函式之間可能透過符號引用互相影響。這是平行化中**最需要小心**的部分。

考慮這個 pipeline：

```cpp
OpPassManager &funcPM = pm.nest<func::FuncOp>("func.func");
funcPM.addPass(createInlinerPass());   // 會修改呼叫者與被呼叫者
```

`InlinerPass` 同時修改「呼叫者函式」與「被呼叫者函式」。若以 function-level pass 平行執行，就會出現：執行緒 1 正在把 `f` 內聯到 `g`，同時執行緒 2 正在把 `h` 內聯到 `g`——兩者都在改寫 `g`。

MLIR 的處理方式有幾種：

**做法一：提升到模組層級。**

```cpp
pm.addPass(createInlinerPass());   // ModulePass，單執行緒
```

這是最簡單也最安全的做法，代價是失去平行性。

**做法二：使用符號表的所有權語意。**

MLIR 提供 `SymbolTable::replaceAllSymbolUses` 這類 API，它會**批次**地把所有對某符號的引用一次改掉，避免迭代過程中的失效。`SymbolTableCollection` 則提供跨多個符號表的批次操作：

```cpp
mlir::SymbolTableCollection symbolTables;
symbolTables.add(module);
```

**做法三：使用 `SymbolDCE`、`SymbolUserMap` 這類專門處理的 pass。**

MLIR 上游的 `SymbolDCEPass` 就是在符號層級工作的模組級 pass。

**做法四：設計 pass 使其不需要跨函式改寫。**

例如把「把某個函式加上某個屬性」這種操作做成 symbol table 的批次更新，而不是遍歷所有使用點。

## 一個完整可執行的平行 pipeline 範例

```cpp
#include "mlir/Dialect/Arith/IR/Arith.h"
#include "mlir/Dialect/Func/IR/FuncOps.h"
#include "mlir/IR/BuiltinOps.h"
#include "mlir/IR/MLIRContext.h"
#include "mlir/Pass/PassManager.h"
#include "mlir/Transforms/Passes.h"
#include "llvm/Support/ThreadPool.h"

int main(int argc, char **argv) {
  mlir::MLIRContext context;
  context.getOrLoadDialect<mlir::arith::ArithDialect>();
  context.getOrLoadDialect<mlir::func::FuncDialect>();

  auto module = mlir::parseSourceFile<mlir::ModuleOp>("input.mlir", &context);
  if (!module)
    return 1;

  // 模組層：串行。
  mlir::OpPassManager pm("builtin.module");
  pm.addPass(mlir::createCanonicalizerPass());
  pm.addPass(mlir::createCSEPass());

  // 函式層：每個 func.func 一個實例，彼此平行。
  mlir::OpPassManager &funcPM = pm.nest<mlir::func::FuncOp>("func.func");
  funcPM.addPass(mlir::createLoopInvariantCodeMotionPass());
  funcPM.addPass(mlir::createMem2RegPass());

  // 啟用多執行緒（預設即為啟用）。
  pm.enableMultithreading();

  if (mlir::failed(pm.run(module.get())))
    return 1;

  module->print(mlir::llvm::outs());
  return 0;
}
```

## 平行性的效能模型

粗略估算加速比。設：

* $N$ ：模組中的函式數量。
* $w$ ：單一函式的平均工作量。
* $c$ ：可用的核心數。
* $p$ ：per-task 開銷（pass 實例複製、analysis 初始化、IR 驗證）。

理想的負載平衡下（ $N \gg c$ ），加速比：

$$
S = \frac{N\,w}{c\left(\frac{N\,w}{c} + p\right)} \approx \frac{N\,w}{\frac{N\,w}{c} + c\,p}
$$

當 $N\,w \gg c^2 p$ 時， $S \to c$ ，即接近核心數上限。當 $N$ 很小（例如只有 2 個函式）時， $S$ 幾乎為 1，甚至因為 $p$ 而低於 1。

這解釋了實務上的觀察：

* 小模組上，開啟多執行緒可能**變慢**（per-task 開銷佔比高）。
* 大模組上，加速比接近核心數。
* ` $p$ 越大（例如開啟 IR 驗證、或 pass 有複雜的 initial 分析），並行門檻越高。

因此 MLIR 專案在 CI 中對小測試通常關閉 threading：

```bash
mlir-opt input.mlir --mlir-disable-threading
```

而對大規模 benchmark（如模型編譯）則開啟。

## 除錯平行 bug 的實務建議

平行 bug 難以重現，MLIR 提供以下工具鏈：

1. **`--mlir-disable-threading`**：先把問題縮到單執行緒。若消失，就是平行問題。
2. **`--mlir-print-ir-after-all`**：印出每個 pass 後的 IR，檢查是否有 pass 寫壞了 IR。
3. **ThreadSanitizer**：用 `-fsanitize=thread` 編譯 MLIR 與你的 pass，TSan 會精確指出資料競爭的位置。
4. **AddressSanitizer**：抓 use-after-free。
5. **保守的平行 pass 設計原則**：
   * 只操作自己那棵子樹。
   * 不使用 static 可變狀態。
   * 不依賴 pass 實例之間的共享資料。
   * 需要全域資訊時，改成 module-level pass。

## 與 LLVM 的平行模型對比

LLVM 的平行模型與 MLIR 有本質差異，值得對照。

LLVM IR 的平行化主要體現在：

* **Loop-level parallelization**：`LoopVectorize` 產生向量迴圈、`LoopUnroll` 決定展開、`LoopIdiomRecognize` 識別 memcpy 之類的 idiom。
* **Function-level parallelization**：用 ThinLTO 把 IR 分割成 module，在各 module 內部做平行最佳化，最後在連結期做跨 module 的最佳化。

MLIR 的對應機制是：

| 面向 | LLVM | MLIR |
| --- | --- | --- |
| 平行粒度 | 迴圈（vectorizer） | operation 子樹（function/loop-level pass） |
| 平行對象 | pass 內部的資料平行 | 不同 pass 實例作用於不同 op |
| 隔離機制 | 迴圈迭代空間分割 | op 子樹不相交 |
| 跨邊界操作 | 模組摘要（summary） | `SymbolTable` / `SymbolTableCollection` |

MLIR 的模型更簡潔但表達力較弱：LLVM 的 loop vectorizer 能在一個函式**內部**做真正的資料平行，MLIR 的 pass 模型則是「整棵子樹交給一個執行緒」。MLIR 透過 **dialect 與 pass 的組合**來補足：例如 `gpu` 方言把 loop 轉成 `gpu.launch_func`，把平行性表達成 IR 層級的 op，而不是編譯器的內部機制。

這個差異是哲學性的：**MLIR 把平行性本身也表達成 IR**，讓硬體後端（GPU/NPU）與編譯器共享同一個表達平行性的語彙。

## 小結與延伸閱讀

* MLIR 的平行模型是「同一層的 pass 序列作用於不相交 op 子樹的不同實例」；同層 pass 之間、同層與子層之間都必須串行。
* 安全性由 pass manager 的執行模型保證：每個實例拿到獨立的 op 子樹、獨立的 pass 副本、獨立的 analysis 快取；MLIR 信任 pass 作者遵守「只操作自己的子樹」。
* `--mlir-disable-threading` 是除錯平行問題的第一步；ThreadSanitizer 與 AddressSanitizer 是精確定位的手段。
* 跨函式的符號改寫是平行安全的最大破口，應提升為 module-level pass，或使用 `SymbolTable` / `SymbolTableCollection` 的批次 API。
* 平行加速比受 per-task 開銷 $p$ 限制，模型 $S \approx \frac{N\,w}{\frac{N\,w}{c} + c\,p}$ 說明小模組上多執行緒可能變慢。
* 延伸閱讀：`mlir/include/mlir/Pass/PassManager.h`（`enableMultithreading` 與平行執行入口）、`mlir/include/mlir/Support/ThreadingUtilities.h`（thread pool 介面）、`mlir/lib/Pass/Pass.cpp`（平行執行的實作）、`mlir/docs/Workers.md`（MLIR 的 threading 設計說明）、`llvm/docs/ThreadPool.rst`（LLVM thread pool）。
