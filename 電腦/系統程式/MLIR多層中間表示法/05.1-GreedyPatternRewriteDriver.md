# 5.1 Greedy Pattern Rewrite Driver 的運作與收斂

前一節我們逐一介紹了 `RewritePattern`、`PatternRewriter` 與 pattern 的宣告方式，並留下了一個問題：把一堆 pattern 交給編譯器之後，誰來決定「先套用哪一個」、「套用之後要不要再回去看被改動的地方」、「這個過程會不會永遠停不下來」？

本章第二部的主軸，就是把 pattern 從「一堆可以單獨呼叫的函式」變成「一個可執行、可收斂、可觀測的改寫引擎」。這是 MLIR 從「可變 IR 的編輯工具」走向「可重複執行的編譯流水線」的關鍵一步。

## 為什麼需要一個 Driver

如果把 pattern 當成普通的函式呼叫，會立刻遇到三個問題。

第一，**順序問題**。假設 IR 裡同時有 `a + b` 與 `b + c` 兩種運算式，其中一個 pattern 針對加法交換律、另一個針對特定常數折疊，先套用哪一個會改變後續的匹配結果。MLIR 的答案是：**不保證順序，但保證「只要還有能改善的 pattern，就不會停」**——也就是把改寫過程視為一個不斷逼近某個不動點（fixed point）的迭代過程。

第二，**回饋問題**。一個 pattern 改寫了 op `X` 之後，`X` 的使用者（users）可能因此產生新的匹配機會；同時 `X` 的操作數來源 op 也可能變成可被簡化的對象。Driver 必須把這些「受影響的點」重新放回待處理佇列。

第三，**收斂問題**。兩個 pattern 可能互相抵消：`x + 0 -> x` 與 `x -> x + 0` 會讓 IR 在兩種形式之間無限往返。如果 Driver 沒有收斂控制，編譯器會掛住。

因此 MLIR 提供三個主要的改寫入口：

| 函式 | 行為 | 典型用途 |
| --- | --- | --- |
| `applyPatternsAndFoldGreedily` | 套用 pattern，並在過程中執行 folding 與 region 簡化 | canonicalization、一般的局部清理 |
| `applyPatternsGreedily` | 套用 pattern，但不 folding、不簡化 region | 需要嚴格控制 IR 形狀的 pass |
| `applyFullConversion` / `applyPartialConversion` | 在合法性前提下套用 pattern（conversion 專用 Driver） | 降階到低階方言 |

後兩者會在 [5.2](05.2-DialectConversion框架.md) 與 [5.3](05.3-Partial與FullLowering.md) 詳細說明；本節聚焦第一條路徑。

## Driver 的資料結構

Greedy Driver 內部維持三個核心狀態：

1. **Worklist**：一串待處理的 `Operation *`，附帶「這些 op 可能匹配到的 pattern benefit 列表」。Driver 不保證 worklist 的全域排序，但保證優先處理 worklist 中較早被推入的 op。
2. **Folding worklist**：需要嘗試 folding 的 op。folding 與 pattern 套用分成兩條線，是收斂控制的關鍵之一。
3. **已處理集合**：避免同一個 op 在同一輪中被重複無意義地推進。

在 modern MLIR 中，`applyPatternsAndFoldGreedily` 內部以 `GreedyPatternRewriteDriver` 類別實作：

```cpp
namespace mlir {
// 對 region 內的所有 op 貪婪套用 patterns，並在過程中 folding 與簡化 region。
LogicalResult applyPatternsAndFoldGreedily(
    Region &region, GreedyRewriteConfig config,
    RewritePatternSet &patterns,
    const GreedyPatternRewriteDriver::Listener *listener = nullptr);
} // namespace mlir
```

而 `GreedyRewriteConfig` 是所有可調行為的集中地：

```cpp
struct GreedyRewriteConfig {
  /// 要使用的 pattern 的最大迭代次數。預設為 10。
  unsigned maxIterations = 10;

  /// 是否由上而下（pre-order）走訪 op。預設 true。
  bool useTopDownTraversal = true;

  /// 是否啟用 region 簡化（例如移除空 block、合併 block）。預設 true。
  bool enableRegionSimplification = true;

  /// region 簡化的激進程度。
  SimplificationLevel regionSimplification = SimplificationLevel::Normal;

  /// 嚴格模式：每次改寫之後重新驗證 IR 是否合法。預設 false。
  bool strictMode = false;

  /// 可選的觀察者，用來接收改寫事件。
  std::unique_ptr<GreedyPatternRewriteDriver::Listener> listener;
};
```

這幾個選項不是裝飾品，它們決定了改寫引擎在面對「病態」pattern 集合時的行為，本節後段的「收斂控制」與「選項細節」會回到這些細節。

## `applyPatternsAndFoldGreedily` 的工作流程

把整個流程寫成偽碼，大致如下：

```text
applyPatternsAndFoldGreedily(region, config, patterns):
    driver = GreedyPatternRewriteDriver(region, config, patterns)
    return driver.simplify()

simplify():
    iteration = 0
    while iteration < config.maxIterations:
        iteration += 1
        while worklist not empty:
            op = worklist.pop()
            if op was erased: continue
            # 1. 收集候選 pattern，依 benefit 排序
            candidates = patterns.match(op)        # 依 getBenefit() 降冪
            # 2. 嘗試套用第一個成功且「有實際改變」的 pattern
            if applyFirstValidPattern(op, candidates):
                # 3. 成功後把受影響的 op 重新推回 worklist
                notifyReplaced(op)                  # 使用者、操作數來源
            else:
                # 4. 這個 op 沒有 pattern 能改，嘗試 folding
                tryFold(op)
        # 5. region 簡化：刪空 block、合併 block 等
        if config.enableRegionSimplification:
            simplifyRegions(region, config.regionSimplification)
    return success
```

幾個關鍵設計值得逐一拆開。

### 候選 pattern 的挑選與 benefit

Driver 會把「所有可能匹配此 op 的 pattern」依 `getBenefit()` 由高到低排序，逐一嘗試。MLIR 內建的多數 canonicalization pattern 使用預設 benefit `1`；特定的高價值轉換（例如把 `vector.extract` 與 `vector.insert` 合併、或把鏈式 `tensor.extract_slice` 併入 `tensor.insert_slice`）會顯式提高 benefit。

這個排序不是「正確性機制」，而是「效率啟發式」：較高 benefit 的 pattern 通常能移除更多 op、或開啟更多後續機會，先套用可以減少總迭代次數。benefit 相同時，Driver 大致以註冊順序作為平手breaker，這也意味著**依賴註冊順序的行為是不穩定的**，撰寫 pass 時不應假設特定平手順序。

### 「有實際改變」的判定

一個常被忽略的細節：pattern 回傳 `success` 並不代表 IR 改變了。例如 pattern 只呼叫 `rewriter.modifyOpInPlace` 修改屬性，或呼叫 `notifyMatchFailure` 之後又回傳 `success`。Driver 必須判斷「這次改寫是否產生了新的匹配機會」，否則會把 op 反覆推回 worklist 而永遠收斂不了。

MLIR 的做法是比較改寫前後的變更事件：只有當 rewriter 真的執行了 `replaceOp`、`eraseOp`、`updateRootInPlace` 等「會產生新 op 或改變結構」的操作時，才會把 op 與其相關 op 重新推回 worklist。

### 回饋到 worklist 的三類 op

改寫 op `X` 之後，以下三類 op 進入 worklist：

| 來源 | 理由 |
| --- | --- |
| `X` 的使用者（users） | 結果型別或值的來源改變，可能讓上游 pattern 重新匹配 |
| `X` 的操作數之定義 op | 新的 op 被產生，可能有更高等級的優化機會 |
| `X` 自身的新定義 | 新 op 需要被 folding、被新 pattern 匹配 |

這個回饋機制就是為什麼「一次套用」與「貪婪套用」結果會不同：前者只走一趟，後者會不斷回頭看受影響的鄰居。

## 收斂控制：為什麼 `x + 0` 會打轉

現在來看本章的核心案例。假設 IR 中有這樣的運算式：

```mlir
%c0 = arith.constant 0.0 : f32
%r  = arith.addf %x, %c0 : f32
```

`arith` 的常數折疊規則會把 `x + 0.0` 折成 `x`；這沒有問題，因為折疊是**收斂的**：folding 只把 op 換成等價的、更簡單的形式，而「更簡單」有明確的度量（op 數、指令數）。問題出在 pattern 之間。

考慮兩條合法的 canonicalization pattern：

```text
Pattern A（benefit = 2）：arith.addf %x, %c0  ->  %x        // 消除加零
Pattern B（benefit = 1）：%x（來源為 my.id）->  my.addz %x  // 包裝
```

如果 `B` 的右側產生了 `arith.addf %x, %c0`，而 `A` 又把它折回 `%x`，那麼兩者會形成迴圈：

```text
my.id(%x)  --B-->  arith.addf(%x, %c0)  --A-->  %x
```

而 `%x` 的來源是 `my.id`？若 `my.id` 的定義被 `B` 重新產生，就回到起點，形成一個長度為 2 的環。

在實務上，這類問題的典型來源有兩種：

1. **不同作者寫的 pattern 各自「看起來合理」**，但合起來不收斂。例如某個方言的 pattern 把 `x` 包成 `my.wrap(x)`，而另一個通用 pattern 又把 `my.wrap(x)` 拆回 `x`。
2. **高階 pattern 創造了低階的「正規形」**，而低階 pattern 認為正規形應該被消掉。`x + 0 -> x` 與 `x -> x + 0` 之所以會出事，正是因為第二條 pattern 的 motive 是「統一表示法」，而第一條 pattern 的 motive 是「最小化」。

要讓這些 pattern 共存，必須有至少一個明確的約束機制。MLIR 提供三層。

### 第一層：folding 與 pattern 分離

`applyPatternsAndFoldGreedily` 中，folding 走的是**每個 op 自己的 `fold` 鉤子**，而不是 pattern。`fold` 必須滿足嚴格的收斂條件：回傳值（若非 `failure()`）代表一個**等價且不更複雜**的替代物。`arith.addf` 的 folder 知道 `x + 0.0 = x`，但它**不會**知道 `x = x + 0.0` 是一個好主意——因為那會增加 op 數量，違反 folder 的契約。

換句話說：**fold 是「等價簡化」，canonicalization pattern 是「風格改寫」**。把風格改寫交給 pattern、把等價簡化交給 folder，是收斂性的第一道防線。

### 第二層：`maxIterations`

`GreedyRewriteConfig::maxIterations`（預設 10）給整個迭代過程一個硬上界。Driver 跑完 10 輪就停止並回傳 `success`。它不保證「已達最簡」，但保證「一定會停」。

實務建議：

| 情境 | 建議 `maxIterations` |
| --- | --- |
| 一般 canonicalization | 保持預設 10 |
| 已知需要多輪傳播（如常數傳播跨數個 block） | 放寬到 20~30 |
| 診斷不收斂 | 先設成 2~3，用 `--mlir-print-ir-after` 觀察每輪的變化 |
| 不需要 folding 的場景 | 改用 `applyPatternsGreedily`，直接切斷 folding 這條回饋線 |

### 第三層：`benefit` 的排序紀律

benefit 的作用不是解決迴圈，而是**讓「更好的形式」先勝出**。若 `A`（消除加零）benefit 高於 `B`（包裝），Driver 每輪都會先套用 `A`，把 op 變成 `%x`；接著 `B` 又把它包回去。下一步 Driver 重新收集候選，此時 `A` 仍然不匹配（因為 `arith.addf` 已經被消掉），於是 worklist 清空，過程終止。

換言之，**benefit 高的 pattern 若能「吃掉」低 benefit pattern 的產物，迴圈就會被打破**。這也解釋了為什麼把 `x -> x + 0` 這類「加上常數」的 pattern benefit 設得比「消除常數」低，是一個普遍的有效實務。

## 一個真正不收斂的 pattern 對

下面給出一個最小可重現的例子。假設有個玩具方言 `my`，定義兩個 op：

```tablegen
// 玩具方言：僅用來示範不收斂。
def My_IdentityOp : My_Op<"identity", [Pure]> {
  let arguments = (ins F32:$input);
  let results = (outs F32:$result);
  let assemblyFormat = "$input attr-dict `:` type($result)";
}

def My_AddZeroOp : My_Op<"addzero", [Pure]> {
  let arguments = (ins F32:$input);
  let results = (outs F32:$result);
  let assemblyFormat = "$input attr-dict `:` type($result)";
}
```

注意 `My_AddZeroOp` **沒有** `hasFolder`、也沒有對應的 folder，因此 folding 路線不會把它折回 `my.identity`，迴圈得以成立。

```cpp
#include "mlir/IR/PatternMatch.h"
#include "mlir/Dialect/Arith/IR/Arith.h"

namespace {

/// 把 my.identity 改寫成 my.addzero：模擬「為了統一表示法而加上常數」的 pattern。
struct WrapIdentity : public mlir::OpRewritePattern<my::IdentityOp> {
  using OpRewritePattern::OpRewritePattern;

  mlir::LogicalResult matchAndRewrite(my::IdentityOp op,
                                      mlir::PatternRewriter &rewriter) const override {
    rewriter.replaceOpWithNewOp<my::AddZeroOp>(op, op.getInput());
    return mlir::success();
  }
};

/// 把 my.addzero 改寫回 my.identity：模擬「消除多餘加法」的 pattern。
struct UnwrapAddZero : public mlir::OpRewritePattern<my::AddZeroOp> {
  using OpRewritePattern::OpRewritePattern;

  mlir::LogicalResult matchAndRewrite(my::AddZeroOp op,
                                      mlir::PatternRewriter &rewriter) const override {
    rewriter.replaceOpWithNewOp<my::IdentityOp>(op, op.getInput());
    return mlir::success();
  }
};

} // namespace

void registerMyPatterns(mlir::RewritePatternSet &patterns) {
  patterns.add<WrapIdentity>(patterns.getContext());
  patterns.add<UnwrapAddZero>(patterns.getContext());
}
```

對應的 MLIR：

```mlir
func.func @demo(%x: f32) -> f32 {
  %0 = my.identity %x : f32
  return %0 : f32
}
```

這段 IR 在兩個 pattern 下會在 `my.identity` 與 `my.addzero` 之間無限往返，直到 `maxIterations` 用盡。注意 `UnwrapAddZero` 每次改寫都產生**新的 op**，因此 rewriter 一定回報「有變更」，Driver 無法用「沒變就停止」來脫身——這正是收斂問題比想像中更頑固的原因。

在 `mlir-opt` 中可以直接觀察到這個行為（假設 `-my-canonicalize` pass 註冊了上述 pattern）：

```bash
mlir-opt demo.mlir -my-canonicalize --mlir-print-ir-after-all
```

輸出會顯示 `my.identity` 與 `my.addzero` 交替出現，直到迭代次數用盡。要讓流程終止，可以：

1. 移除其中一條 pattern（正確做法：既然兩者語義等價，保留一條即可）。
2. 給其中一條 pattern 加上前提，例如只有當輸入來自特定 op 時才允許改寫。
3. 把 `maxIterations` 設小，並在 pass 內用 `-verify-diagnostics` 觀察。

### 如何診斷「疑似不收斂」

實務上可用以下手法：

- 用 `--mlir-print-ir-after-all` 印出每一輪改寫後的 IR，觀察是否有 op 形式在反覆出現。若某個 op 形態出現兩次以上且內容相同，幾乎可以確定是迴圈。
- 用 `--mlir-timing` 觀察 pass 耗時異常。
- 暫時把 pattern 數量減半（二分法），找出互相衝突的最小集合。
- 使用 `PatternRewriter::notifyMatchFailure` 加上 `DEBUG_TYPE` 開關，讓每個 pattern 的匹配失敗原因可視化。

## `applyPatternsGreedily`：不折疊的嚴格版本

有時候 folding 反而是麻煩製造者。例如在做**形狀對齊**（shape alignment）時，你希望把 `tensor<64x64>` 與 `tensor<?x64>` 統一成同一種表示；folding 卻可能在你之前就把 `tensor<64x64>` 的常量形狀折掉，使得對齊 pattern 永遠匹配不到。或者你在做 IL 的形狀實驗，需要精確控制每一步 IR 的形狀。

`applyPatternsGreedily` 提供這種嚴格模式：

```cpp
/// 套用 patterns 但不 folding、不簡化 region。
LogicalResult applyPatternsGreedily(
    Region &region, const GreedyRewriteConfig &config,
    RewritePatternSet &patterns,
    const GreedyPatternRewriteDriver::Listener *listener = nullptr);
```

它與 `applyPatternsAndFoldGreedily` 的差異可以總結為：

| 面向 | `applyPatternsAndFoldGreedily` | `applyPatternsGreedily` |
| --- | --- | --- |
| 套用 pattern | 是 | 是 |
| 呼叫 op 的 `fold` 鉤子 | 是 | 否 |
| 簡化 region（刪空 block 等） | 是（可關閉） | 否 |
| 收斂風險來源 | pattern 之間、pattern 與 folder 之間 | 僅 pattern 之間 |
| 典型用途 | canonicalization | 形狀敏感的重寫、實驗性 pass |

由於 folding 路線被切斷，`applyPatternsGreedily` 的收斂性幾乎完全取決於 pattern 集合本身的品質。實務上，若某個 pass 用 `applyPatternsGreedily`，那麼它應該**自己**承擔收斂責任：例如限制 pattern 只能作用於特定 op、或者搭配明確的 `maxIterations`。

## 選項細節：`useTopDownTraversal` 與 `regionSimplification`

### `useTopDownTraversal`

預設為 `true`，表示 Driver 以 pre-order 走訪：先處理外層 op，再處理內層 op。這符合大多數 canonicalization 直覺——先做高階簡化，再深入 block 內部。

但並非永遠正確。考慮：

```mlir
func.func @f(%x: f32) -> f32 {
  %0 = arith.addf %x, %c0 : f32
  return %0 : f32
}
```

若有一個 pattern 需要看到 `return` 的 operand 才知道要做什麼（例如「把 `return` 直接回傳的 addf 拆開」），top-down 會先處理 `arith.addf`（無匹配），再處理 `return`（此時 `addf` 仍在，匹配成功並改寫），接著回到 `addf`。這其實沒問題。

真正需要關閉 top-down 的情境是：**某個 pattern 只在外層 op 被改寫之後，內層 op 才會出現可匹配形式**，而內層的改寫結果又會影響外層。也就是「依賴關係是自下而上」的情況。關掉 top-down 會改變第一次套用的順序，但不改變最終可達的不動點集合——前提是 pattern 集合本身收斂。

實務上，`useTopDownTraversal = false` 比較少見，多數方言的 canonicalization 依賴預設值。

### `regionSimplification`

`enableRegionSimplification` 預設 `true`，`regionSimplification` 的預設等級是 `SimplificationLevel::Normal`。這個選項控制 Driver 對 region 結構的整理強度：

- 移除沒有任何 op 的 block（但不能是 entry block，除非它是唯一 block）。
- 合併只有單一前驅的 block（前提是沒有 branch operand 依賴其位置）。
- 在 `Normal` 等級下，才進一步合併 branch 指令鏈與 phi-like block argument。

`regionSimplification` 的副作用是：**它會改變 block 的拓樸結構**。若你的 pass 假設某個 block 存在，或某個 value 由特定 block argument 定義，簡化可能破壞這個假設。在做形狀敏感的實驗時，設 `enableRegionSimplification = false` 是安全做法。

另外一點容易被忽略：Driver 會在**每輪迭代之後**才做 region 簡化，因此簡化的效果要等到下一輪才會反映到 pattern 匹配上。這也解釋了為什麼某些需要「刪掉空 block 後才能匹配」的 pattern 需要至少兩輪。

## folding 與 canonicalization pattern 的差異

這兩者經常被混為一談，但在 MLIR 中是**結構上不同**的機制。

| 面向 | folding（`fold` 鉤子） | canonicalization pattern |
| --- | --- | --- |
| 定義位置 | op 定義中的 `let hasFolder = 1;` 與 `Op::fold` | 獨立於 op 定義的 `OpRewritePattern` |
| 視野 | 只看自己這個 op 的操作數與屬性 | 可看整個 region（通常以 context op 為 root） |
| 等價性要求 | 必須與原 op 語義等價 | 必須與原 op 語義等價，但可在 op 間移動計算 |
| 結果型別 | 通常維持原 op 的型別 | 可以改變型別（但需透過合法的 materialization） |
| 收斂性 | 內建：只允許「更簡單」的形式 | 需靠 benefit 紀律與 `maxIterations` |
| 觸發時機 | Driver 自動在 worklist 中呼叫 | Driver 依 benefit 排序匹配 |

在 ODS 中，一個 op 宣告 folder 的方式如下：

```tablegen
def Arith_AddFOp : Arith_Op<"addf", [Pure, ...]> {
  let arguments = (ins F32OrF64:$lhs, F32OrF64:$rhs);
  let results = (outs F32OrF64:$result);

  let hasFolder = 1;
}
```

對應的 C++ 實作（放在 op 的 `.cpp` 檔案中）：

```cpp
OpFoldResult arith::AddFOp::fold(FoldAdaptor adaptor) {
  // 加零恆等：x + 0.0 = x。
  if (matchPattern(adaptor.getRhs(), m_ZeroFloat()))
    return getLhs();
  if (matchPattern(adaptor.getLhs(), m_ZeroFloat()))
    return getRhs();

  // 其餘情形（例如兩個操作數都是已知常數）交給 arith 的常數運算路徑處理，
  // 這裡無法簡化，回傳空值表示「沒有可用的折疊」。
  return {};
}
```

這裡有個關鍵差異：`fold` 回傳的是 `OpFoldResult`——可能是**一個 Value**（直接取代原 op），也可能是一個**常數屬性**（原 op 被替換為一個新常數 op）。這個「回傳 Value 取代自己」的機制，比 pattern 的 `replaceOp` 更受限，但也因此更安全。

相對地，canonicalization pattern 想做同樣的事，就必須寫：

```cpp
struct RemoveAddZero : public mlir::OpRewritePattern<arith::AddFOp> {
  using OpRewritePattern::OpRewritePattern;

  mlir::LogicalResult matchAndRewrite(arith::AddFOp op,
                                      mlir::PatternRewriter &rewriter) const override {
    if (!mlir::matchPattern(op.getRhs(), mlir::m_ZeroFloat()))
      return rewriter.notifyMatchFailure(op, "rhs is not zero");
    rewriter.replaceOp(op, op.getLhs());
    return mlir::success();
  }
};
```

這兩種寫法在結果上等價，但**語意不同**：folder 是 op 定義的一部分，其正確性由 dialect 作者保證，且必然收斂；pattern 是全域的，可能與其他 pattern 衝突。**能用 folder 就不要用 pattern**，這是 MLIR 社群反覆強調的設計準則。

## `RewritePattern` 的 root 綁定與 benefit

`RewritePattern` 的 `root` 是「這個 pattern 掛載在哪一種 op 上」。`OpRewritePattern<T>` 把 root 型別綁定為 `T`，Driver 在比對時只會把 `T` 的 op 交給這個 pattern 檢查。

`OpRewritePattern<T>` 的好處是型別安全：`matchAndRewrite` 直接收到 `T`，不需要做 `dyn_cast`。但它也限制了通用性——若一個 pattern 想同時處理 `arith.addf` 與 `arith.addi`，就必須改用底層的 `RewritePattern` 並自行 cast：

```cpp
struct NormalizeAdd : public mlir::RewritePattern {
  NormalizeAdd(mlir::MLIRContext *ctx) : RewritePattern("normalize-add", ctx) {}

  mlir::LogicalResult matchAndRewrite(mlir::Operation *op,
                                      mlir::PatternRewriter &rewriter) const override {
    if (!isa<arith::AddFOp, arith::AddIOp>(op))
      return mlir::failure();
    // 兩種 op 共用的正規化處理（例如把常數操作數換到固定的一側）。
    return mlir::success();
  }
};
```

這裡 `RewritePattern(const Twine &rootName, MLIRContext *ctx, PatternBenefit benefit = 1)` 的第一個參數是 **root 的 op 名稱字串**，不是型別。名字寫錯不會在編譯期被抓到，只會讓 pattern 永遠不被匹配——這是實務上最常見的「pattern 沒有生效」原因。

benefit 的宣告方式：

```cpp
struct ExpensiveButValuable : public mlir::OpRewritePattern<my::Op> {
  ExpensiveButValuable(mlir::MLIRContext *ctx)
      : OpRewritePattern<my::Op>(ctx, /*benefit=*/10) {}
  // matchAndRewrite 的實作省略，重點在於 benefit 的傳入方式。
};
```

benefit 的語意是「相對優先度」，不是「成本」。Driver 在排序候選時使用降冪排列，同 benefit 依註冊順序。

## 改寫後的 IR 合法性

改寫可能破壞 IR 的不變式。最典型的三種情況：

1. **結果數量不匹配**。`replaceOp(op, values)` 會斷言 `values.size() == op->getNumResults()`，在 release build 這種斷言可能被關閉，導致 IR 損壞。
2. **型別不一致**。新 op 的 operand 型別與原 op 不同，卻沒有經過合法的型別轉換。
3. **Region 結構被破壞**。例如刪掉了一個含有其他 op 的 block，或留下沒有 terminator 的 block。

MLIR 的防線有兩道：

**第一道：rewriter 內建斷言。** `PatternRewriter::replaceOp` 在替換前會檢查新值的數量與型別是否符合原 op 的結果型別：

```cpp
void PatternRewriter::replaceOp(Operation *op, ValueRange newValues) {
  assert((!op->getResults().empty() || newValues.empty()) &&
         "cannot replace an op with no results but with new values");
  assert(op->getNumResults() == newValues.size() &&
         "incorrect # of replacement values");
  // ...
}
```

**第二道：verifier。** 這是第 6.1 節的主題。Greedy Driver 在 `strictMode = true` 時會在每次改寫之後驗證 IR；預設則是由 pass manager 在 pass 結束後、或由 `mlir-opt` 的預設 verifier 檢查。

`strictMode` 的取捨：

| | `strictMode = false`（預設） | `strictMode = true` |
| --- | --- | --- |
| 每次改寫後驗證 | 否 | 是 |
| 效能 | 快 | 明顯變慢（每次改寫 O(IR 大小)） |
| 失效時機 | pass 結束後才發現 | 立刻發現，錯誤訊息指出是哪個 pattern |
| 建議 | 一般正式 pipeline | 開發新 pattern 時開啟 |

實務上，若一個 pattern 會產生違反 verifier 的 IR，`strictMode = true` 會給出類似這樣的診斷：

```text
error: 'my.addzero' op operand #0 must be 32-bit float, but got ...
```

這比在 pass 結束時才看到一個不相干的錯誤要好定位得多。

## 實作範例：一個完整的 canonicalization pass

把前面討論的東西整合成一個可用的 pass：

```cpp
#include "mlir/Dialect/Arith/IR/Arith.h"
#include "mlir/Dialect/Func/IR/FuncOps.h"
#include "mlir/IR/Builders.h"
#include "mlir/IR/BuiltinTypes.h"
#include "mlir/Pass/Pass.h"
#include "mlir/Transforms/GreedyPatternRewriteDriver.h"

namespace mlir {
namespace {

/// 示範用 pattern：把 arith.addf(x, 0.0) 折成 x。
struct RemoveAddFloatZero : public OpRewritePattern<arith::AddFOp> {
  using OpRewritePattern::OpRewritePattern;

  LogicalResult matchAndRewrite(arith::AddFOp op,
                                PatternRewriter &rewriter) const override {
    if (!matchPattern(op.getRhs(), m_ZeroFloat()))
      return rewriter.notifyMatchFailure(op, "rhs is not a zero float");
    rewriter.replaceOp(op, op.getLhs());
    return success();
  }
};

/// 把上面的 pattern 應用到整個 module 上。
struct MyCanonicalizePass : public PassWrapper<MyCanonicalizePass, OperationPass<ModuleOp>> {
  MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID(MyCanonicalizePass)

  StringRef getArgument() const override { return "my-canonicalize"; }

  void getDependentDialects(DialectRegistry &registry) const override {
    registry.insert<arith::ArithDialect>();
  }

  void runOnOperation() override {
    RewritePatternSet patterns(&getContext());
    patterns.add<RemoveAddFloatZero>(&getContext());

    GreedyRewriteConfig config;
    config.maxIterations = 20;
    config.strictMode = true;   // 開發期開啟，及早發現破壞不變式的 pattern。

    if (failed(applyPatternsAndFoldGreedily(getOperation(), config, patterns)))
      signalPassFailure();
  }
};

} // namespace

std::unique_ptr<Pass> createMyCanonicalizePass() {
  return std::make_unique<MyCanonicalizePass>();
}
} // namespace mlir
```

對應的 `mlir-opt` 操作：

```bash
# 對整個模組套用 canonicalization。
mlir-opt input.mlir -my-canonicalize -o output.mlir

# 印出每次改寫後的 IR，觀察收斂過程。
mlir-opt input.mlir -my-canonicalize --mlir-print-ir-after-all

# 只在改寫失敗時印出 IR。
mlir-opt input.mlir -my-canonicalize --mlir-print-ir-after-failure

# 產生通用格式輸出，便於比對 op 屬性。
mlir-opt input.mlir -my-canonicalize --mlir-print-op-generic
```

## 收斂性與迴圈的正式化

為了理解 `maxIterations` 的必要性，可以把 Greedy Driver 視為一個非確定性的不動點求解器：

$$
\mathcal{F}(P) = \{\, p(\mathrm{IR}) \mid p \in P \,\}
$$

Greedy Driver 反覆從 $\mathcal{F}$ 中選取一個適用且「有改善」的轉換，直到沒有任何適用的改善為止。若 $\mathcal{F}$ 中存在循環 $\mathrm{IR}_0 \to \mathrm{IR}_1 \to \cdots \to \mathrm{IR}_k = \mathrm{IR}_0$ ，Driver 將永不停止。

`maxIterations = m` 提供了「最多走 $m$ 步」的保證，代價是：若合法的不動點需要 $m'$ 步到達且 $m' > m$ ，Driver 會提前停止，留下**未完全最佳化**但**合法**的 IR。

這解釋了 MLIR 的一個重要實務原則：**pass 的輸出永遠是「合法的 IR」，但不一定是最簡的 IR**。第二輪的 canonicalization（`-canonicalize -canonicalize`）有時會比第一輪多改掉一些東西，這不是 bug，而是 `maxIterations` 截斷的直接後果。

## 設計比較：greedy 與其他優化策略

| 策略 | 優點 | 缺點 | 適用 |
| --- | --- | --- | --- |
| Greedy（MLIR 預設） | 實作簡單、易於增量擴充 pattern | 不保證最優、易陷入局部終點 | canonicalization、局部清理 |
| E-graph / e-rewrite | 全域搜尋、自動化學、重寫飽和 | 複雜度高、pattern 必須等價 | 少量結構化規則的飽和搜尋 |
| Pass 固定順序 | 完全可預測、易於 debug | 順序敏感、容易遺漏 | 有明確階段的降階 pipeline |
| Cost-based（LLVM 式） | 有 cost model 指引 | 需要維護 cost model | 選指令、指令排程 |

MLIR 的 greedy 模式是刻意的選擇：它讓方言作者能夠**各自貢獻局部規則**，而 compiler 團隊只需維護一套通用的收斂引擎。第 5.2 節要介紹的 conversion 框架，則是在 greedy 之上再疊一層「合法性約束」，用來處理「必須降階到某個層級」的問題。

## 小結與延伸閱讀

- Greedy Driver 的核心是「worklist + 回饋 + 不動點」：改寫一個 op 後，其使用者與操作數來源都會被重新排入待處理佇列，直到沒有可改善之處。
- 收斂性主要靠三層機制維持：folding 與 canonicalization pattern 的職責分離、`maxIterations` 的硬上界、以及以 benefit 表達的「更簡形式優先」紀律。
- `x + 0 -> x` 與 `x -> x + 0` 之所以會打轉，是因為兩條 pattern 的動機不同（最小化 vs. 正規化）；只要讓「消除」類 pattern 的 benefit 高於「添加」類 pattern，迴圈即可被打破。
- `applyPatternsGreedily` 切斷 folding 這條回饋線，適合形狀敏感或實驗性的重寫；代價是收斂責任回到 pattern 作者身上。
- `strictMode` 讓 verifier 在每次改寫後立刻執行，是開發新 pattern 時定位「改寫破壞不變式」最有效的開關。
