# 2.1　POSIX 與行程模型的歷史成因

> 本節導論：POSIX 不是天上掉下來的規格，它是一連串歷史偶然的凝固。要判斷它「還適不適用」，得先知道它「為什麼長成這樣」。

## 2.1.1 從 Multics 到 UNIX：兩個世界觀

要理解行程模型，得從 1960 年代的兩個作業系統專案說起。

**Multics（1964–）** 是 MIT、貝爾實驗室、奇異公司合作的大型分時作業系統。它的野心極大：單一層級的檔案系統、動態連結、記憶體分段、多層權限環（protection rings）。它引入了後來影響深遠的概念，例如 **環（ring）** 的權限分級（Ring 0 到 Ring 3）。

但 Multics 太複雜了，進度緩慢、資源耗費巨大，貝爾實驗室於 1969 年退出。**UNIX** 正是作為對 Multics 的反動而誕生：Ken Thompson 與 Dennis Ritchie 想要一個「小而美」的系統，拋棄 Multics 的複雜性，保留少數核心概念。

這個「反動」形塑了 UNIX 的基因：

* 拋棄多層權限環，改用簡單的 **使用者態 / 核心態** 二分。
* 拋棄複雜的分段，改用簡單的 **行程（process）** 與 **位址空間**。
* 拋棄單一層級檔案系統的複雜度，改用簡單的 **目錄樹**。

換句話說，**UNIX 的簡單，是對 Multics 複雜性的反應**。而 POSIX 後來又把 UNIX 的這套選擇標準化、固化。於是我們今天繼承的，是「一個 1970 年代對 1960 年代的反動」的結果。

## 2.1.2 為什麼是「行程」？

「行程（process）」這個抽象，是 UNIX 的核心。它的定義是：**一個執行中的程式，擁有獨立的位址空間、檔案描述子表、訊號處理、以及一個執行執行緒（後來才有多執行緒）**。

為什麼選這個抽象？因為它同時解決了三個 1970 年代的問題：

**（1）隔離（isolation）**：多個使用者同時使用一台分時機器，需要彼此隔離，避免一個程式讀到另一個程式的資料。行程的獨立位址空間提供了這個隔離。

**（2）資源管理（resource accounting）**：分時系統需要對每個使用者的資源使用計費或限制。行程是資源的歸屬單位：每個行程有自己的 CPU 時間、記憶體、開啟的檔案。

**（3）程式生命週期（lifecycle）**：程式需要被啟動、執行、結束、回收。`fork()` / `exec()` / `wait()` 這組 API 提供了完整的生命週期管理。

這三個需求，在 1970 年代的分時系統裡都是真實且迫切的。行程是對它們的優雅回答。

## 2.1.3 fork() 的歷史偶然

`fork()` 是 UNIX 最獨特的設計之一：它複製當前行程，產生一個幾乎完全相同的子行程。這個設計在今天看來很奇怪（為什麼不直接「建立一個新行程並載入程式」？），但它有深刻的歷史原因。

在早期的 UNIX（PDP-7、PDP-11）上，**記憶體很小**，而「複製一個行程」比「從頭建立一個行程」容易實作：核心只要複製頁表、複製檔案描述子表即可。`exec()` 則是「把新的程式映像覆蓋到當前位址空間」。`fork()` + `exec()` 的組合，讓「建立新程式」變成「先複製、再覆蓋」，實作簡單。

後來為了效能，`fork()` 演化出 **寫時複製（Copy-on-Write, COW）**：`fork()` 時不真的複製記憶體，只複製頁表並把頁面設為唯讀；任一方寫入時才觸發頁面複製。這個最佳化讓 `fork()` 變快，但也讓「`fork()` 的成本」變得複雜——它與「行程的記憶體使用量」及「寫入量」有關。

`fork()` 的歷史偶然性在於：**它是「小記憶體時代」的實作便利，卻成了半世紀的介面標準**。今天我們有 `posix_spawn()`（效率較好的替代），但 `fork()` 仍是 POSIX 的核心，因為無數程式依賴它。

## 2.1.4 POSIX 的標準化：把偶然變成永恆

1988 年，IEEE 發布 POSIX（IEEE 1003.1），把 UNIX 的系統呼叫介面標準化。這件事的意義深遠：

* **可移植性**：程式只要用 POSIX API，就能在任意 POSIX 系統上編譯執行。這在 1980–1990 年代的「UNIX 戰爭」（各種不相容的 UNIX 變體）中，是巨大的進步。
* **生態固化**：一旦標準化，所有程式、函式庫、工具都圍繞它建立。這個生態一旦形成，就極難改變。

POSIX 的成功，也正是它成為包袱的原因：**它把一個 1970 年代的設計，變成了一個幾乎不可動搖的產業標準**。任何「新作業系統」如果不相容 POSIX，就要面對「沒有應用程式可用」的冷啟動問題。這正是第 11 章「冷啟動魔咒」要討論的。

## 2.1.5 檔案系統樹：給人看的組織方式

POSIX 的另一個核心抽象是 **階層式檔案系統（hierarchical file system）**：一個以 `/` 為根的目錄樹，每個節點是檔案或目錄。

這個設計的原點是 **「給人用的」**：人類透過有意義的目錄名稱（`/usr/bin`、`/etc`、`/home/alice`）來組織與尋找資料。它是一種 **認知輔助（cognitive aid）**，幫助人類在大量檔案中導航。

但這個設計對機器而言，其實是低效率的：

* **路徑查找是字串比對**：每次 `open("/a/b/c")` 都要逐層解析路徑，比對目錄項。這對人類友善，對機器是開銷。
* **命名空間是全域的**：所有程式共享同一棵目錄樹，這帶來命名衝突、權限管理的複雜度。
* **持久性假設**：檔案系統假設資料要「持久保存」，需要 fsync、需要日誌（journaling）、需要一致性檢查。但一次性軟體的資料是短命的，這些持久性機制全是浪費。

## 2.1.6 環境變數與 Shell：隱性狀態的溫床

POSIX 還有兩個「給人用」的介面：**環境變數（environment variables）** 與 **Shell**。

* **環境變數**：一組 `KEY=VALUE` 的字串，由父行程傳遞給子行程，用來傳遞設定（`PATH`、`HOME`、`LANG`）。它的問題是：**它是一個隱性的、全域的、字串型別的狀態**。程式行為會因為環境變數不同而改變，這讓程式難以預測、難以驗證。
* **Shell**：一個命令列直譯器，讓人類組合程式。它的問題是：**它是一層額外的、以字串為基礎的程式設計語言**，充滿了引號跳脫、glob 展開、變數替換的陷阱。

這兩個介面，在「人類操作機器」的世界裡是必要的。但在「機器生成程式、機器調度算力」的世界裡，它們是純粹的 **隱性狀態噪音（implicit state noise）**：既不必要，又讓系統行為難以推理。

## 2.1.7 小結：一份為 1970 年代最佳化的設計

把本章的歷史線索整理成表：

| POSIX 抽象 | 誕生原因 | 隱含假設 |
| --- | --- | --- |
| 行程（process） | 分時系統的多使用者隔離與資源計費 | 程式長期執行、需要隔離 |
| `fork()` | 小記憶體時代的實作便利 | 複製整個位址空間是可接受的 |
| 檔案系統樹 | 人類用目錄組織持久資料 | 資料要持久、要給人導航 |
| 環境變數 | 傳遞設定給子行程 | 設定是字串、全域、隱性 |
| Shell | 人類組合程式 | 有人會手動操作 |
| 系統呼叫 C ABI | 穩定的二進位介面 | 程式是編譯好的機器碼 |

每一列都對應一個「1970 年代成立、今天鬆動」的假設。這不是說 POSIX 錯了，而是說 **它是為一個已經消失的世界最佳化的**。
