# 1.3 SPEC 基準測試與效能評估方法論

## 學習目標

讀完本節後，你應當能夠：

1. 說明 SPEC CPU2017 的套件結構、評分指標（speed 與 rate）與執行規則。
2. 解釋為什麼 IPC、MHz 與「核心數」各自都不能單獨代表效能，並識別常見的評估陷阱。
3. 正確使用幾何平均與加權方法彙整基準結果，理解其統計意涵與局限。
4. 從真實案例（含廠商行銷數字）辨識效能宣稱的漏洞，設計可信的評估實驗。

## 1.3.1 為什麼需要標準基準測試

效能評估的方法論光譜，從粗糙到精緻大致是：**上市時間標語（peps）→ 核心程式（kernels，如 LINPACK）→ 整支真實程式 → 標準化套件（如 SPEC）**。每一層都在「真實性」與「可控性」之間取捨：玩具程式可重現但易被調校欺騙（針對性最佳化）；真實應用最真實但難以在實驗室複製控制變因。SPEC（Standard Performance Evaluation Corporation）的價值在於提供一組**公開、可複製、防作弊規則**的真實程式套件，讓不同系統的數字有共同比較基礎。

歷史教訓值得記住：1980–90 年代 VAX 與多家廠商曾用自行挑選的程式宣稱效能優勢；MIPS、Alpha 之間的行銷大戰催生了 SPEC 標準化。**基準測試史就是不斷被作弊手段逼著進化的歷史**——理解每一代作弊手法，才能理解每一代規則設計的原因。

## 1.3.2 SPEC CPU2017 的結構

SPEC CPU2017 包含四個套件，依用途交叉分類：

| 套件 | 語言 | 說明 |
|---|---|---|
| SPECspeed 2017 Integer | C, C++ | 單任務整數運算速度（編譯器、壓縮、模擬器、AI 推理子集等） |
| SPECspeed 2017 Floating Point | C, C++, Fortran | 單任務浮點（流體力學、量子化學、影像、深度學習子集等） |
| SPECrate 2017 Integer | C, C++ | 多任務整數吞吐（多個副本同時跑） |
| SPECrate 2017 Floating Point | C, C++, Fortran | 多任務浮點吞吐 |

**Speed 與 Rate 的差別是本節第一個重點**：

- **SPECspeed**：跑一個副本，量「單一任務多快完成」，反映單執行緒效能、記憶體延遲敏感度、分支預測品質。
- **SPECrate**：同時跑多個獨立副本（通常每核心一個或多個），量「總吞吐」，反映核心數、SMT、快取與記憶體頻寬的多工承載能力。

兩者的分數沒有直接換算關係。一台 speed 分數高但 rate 平平的機器（大單核、少核心），適合延遲敏感型負載（交易、互動服務）；反之（多小核）適合吞吐型負載（批次編譯、CI）。**選機器的第一步永遠是先分類你的負載是 speed 型還是 rate 型**——這與上一節的 compute/memory-bound 分類同屬「負載畫像」方法論。

評分規則要點：每個基準程式以參考機器時間為基準換算成分數，**對各基準取幾何平均**得到套件分數；結果必須附上完整組態（編譯器版本、最佳化旗標、記憶體組態、作業系統），SPEC 規則禁止對單一基準做針對性最佳化（如偵測輸入特徵而跳過工作），並要求提供可檢驗的輸出正確性。基準間不可比（不同演算法、不同記憶體足跡），只有同套件的幾何平均分數可比。

## 1.3.3 彙整的統計學：為什麼是幾何平均

SPEC 採幾何平均（geometric mean）而非算術平均，原因有三：

1. **尺度不變**：幾何平均對「用什麼機器當分母」不敏感，算術平均會被參考機選擇扭曲。
2. **對稱處理倍率**：快 2 倍與慢 2 倍的影響互相抵消，符合「比值」的直覺。
3. **壓抑極端值**：單一基準的異常不會像算術平均那樣主導結果。

但幾何平均不是萬靈丹：它**假設你對所有基準等權關注**。若你的實際負載 80% 時間在跑類似 `gcc` 的程式，那麼 SPECint 總分對你的意義有限，你該看的是對應基準的個別分數——甚至自己跑自家負載。教科書必須強調：**基準分數是「畫像」，不是「承諾」**。正確用法是把它當作尋找候選機器的篩選器，最終驗證永遠是你的實際負載。

此外，相同硬體上不同編譯旗標可造成 20–40% 的分數差異，這是「調校 vs. 作弊」的灰色地帶：使用 `-O3 -march=native` 是合法調校，偵測 SPEC 輸入並特判是作弊。閱讀他人發布的 SPEC 數字時，第一件事是比對其組態揭露的完整性。

## 1.3.4 IPC 評估陷阱與 MHz 迷思

教科書的標準恆等式：

$$\text{CPU 時間} = \frac{\text{指令數} \times CPI}{\text{時脈}} \quad\Longleftrightarrow\quad \text{效能} = \frac{\text{IPC} \times \text{時脈}}{\text{指令數}}$$

由於指令數由 ISA 與編譯器決定，跨 ISA 比較時三者都會變動，**任何單一項都不能代表效能**。以下逐一拆解常見迷思。

### 迷思一：MHz 迷思

「頻率高一倍就快一倍」在 2000 年代 GHz 大戰中被行銷徹底濫用，也在 Intel NetBurst（Pentium 4）上被真實打臉：NetBurst 拉到 20 級超深流水線以衝高時脈，結果分支誤預測懲罰與功耗暴增，同頻率下 IPC 遠低於前代，最終路線崩潰。反例是現代 Apple M 系列與 AMD Zen：時脈低於許多競品，靠高 IPC（寬解碼、大 ROB、優秀分支預測）取得單執行緒領先。**指令數、IPC、時脈三者相乘才是答案；任何只宣稱一項的數字都應提高警覺。**

### 迷思二：IPC 直接比較

同一台機器上 IPC 可比（同一 ISA、同一指令數）；跨機器比較 IPC 有兩重陷阱：

1. **指令數不同**：ISA 語意不同，CISC（x86）一條 `add` 可能對應 RISC 兩條，x86 的 IPC 天然「佔便宜」但效能未必。
2. **混合工作負載下 IPC 沒有意義**：一個程式內部不同階段 IPC 可差 5 倍（計算密集段 vs. 等記憶體段），平均 IPC 掩蓋了瓶頸所在。正確做法是用 `perf stat` 分段測量，並搭配 top-down 分析（Intel 的 TMA 方法論：將 pipeline slot 分類為 retiring / bad speculation / frontend bound / backend bound），把「低 IPC」歸因到具體微結構原因。

### 迷思三：以「最快基準」代表機器

廠商海報常引用 SPEC 套件中對自己最有利的單一基準。實際案例：某代處理器在影像類 FP 基準領先，但在編譯類整數基準落後，行銷只提前者。研究生的基本功是**拿到完整揭露的結果檔（SPEC 允許公開 result 摘要），畫出逐基準的相對效能長條圖，再判斷平均值背後的離散度**。若各基準間差異達 2 倍以上，任何單一總分都是誤導。

### 真實案例：SPEC 數字與實際負載的落差

雲端供應商曾以 SPECrate 選購 CPU 後發現資料庫延遲未如預期改善——原因在於資料庫是延遲敏感（speed 型）且對記憶體延遲與 TLB 極度敏感，而 SPECrate 量的是吞吐。之後業界補上了專門的資料庫基準（TPC 系列）與延遲分位數要求（P99）。這個案例的方法論教訓：**基準選擇錯誤比量測誤差更具破壞性，且往往要到部署後才被發現**。另一個著名案例是 Intel 於 2018 年在部分 SPEC 報告中使用了可比較性受限的編譯器版本，被 SPEC 網站下架部分結果——顯示即使是龍頭廠商，也會在組態揭露上出現灰區，獨立驗證永遠必要。

## 1.3.5 建立可信的評估實驗

綜合前三節，一套研究級的效能評估應包含：

1. **控制變因**：固定 CPU governor（performance）、關閉 turbo 或固定頻率、綁核（taskset/numactl）、記錄散熱狀態；多核心實驗需注意 NUMA 拓撲與干擾（co-scheduling noise）。
2. **多次重複與統計**：至少 3–5 次重複，報告平均與變異數；SPECspeed 規則本身要求多次執行取中位數。
3. **完整揭露**：硬體型號、頻率、記憶體組態、編譯器與旗標、OS 與 kernel 版本、量測工具版本。
4. **對照組**：至少一個已知上界的對照（roofline 上限、或前代已公開結果），使數字「有錨」。
5. **畫像而非單點**：同時報告 speed 與 rate、IPC、頻寬利用、AI 分布，讓讀者能自行判斷你的負載像什麼。

## 本章小結

- SPEC CPU2017 以四個套件（speed/rate × integer/FP）覆蓋單任務延遲與多任務吞吐兩種畫像；speed 量單任務完成時間，rate 量併發吞吐，兩者不可互換。
- 幾何平均提供尺度不變、對稱的彙整，但假設等權關注；基準分數是負載畫像的篩選器，最終驗證必須回到實際負載。
- 效能 $=$ 指令數、IPC、時脈三者交互的結果：MHz 迷思（NetBurst 教訓）、跨 ISA IPC 比較陷阱、以及「挑選基準」的行銷手法，都是單一指標謬誤的不同面目。
- 可信評估的支柱：控制變因、重複統計、完整揭露、對照錨點、畫像化呈現。研究生的效能論文若缺其中任一項，審查者都有正當理由質疑。

## 習題

1. **（計算）** 某處理器執行程式花了 40 秒，共執行 $2.0 \times 10^{10}$ 條指令，時脈 2.5 GHz。求 CPI。若新一代處理器時脈 3.2 GHz、CPI 相同但指令數因 ISA 較繁瑣增加 15%，求新機器的執行時間，並判斷整體是快了還是慢了。
2. **（計算，幾何平均）** 三個基準在機器 A 上的加速比分別為 1.5、1.0、6.0，在機器 B 上為 2.0、2.0、2.0。分別計算兩台機器的幾何平均與算術平均，並說明為何 SPEC 選幾何平均、以及此例中算術平均會如何誤導。
3. **（分析）** 你的實驗室新購 CPU 在 SPECrate 2017 int 上比舊機快 2.1 倍，但夜間批次資料庫工作只快了 1.15 倍。提出至少三個定量假設（如 speed/rate 錯配、記憶體延遲敏感、I/O 瓶頸），並為每一個設計一個可用 `perf` 或組態實驗驗證的測試。
4. **（計算）** 某程式在 3 GHz 機器上 IPC 為 1.2，執行 $5 \times 10^{10}$ 條指令。若分支預測改善使有效 IPC 提升到 1.5，但時脈降到 2.4 GHz 以節電，求新舊執行時間並計算整體效能變化百分比。
5. **（批判性閱讀）** 某廠商宣稱「我們的新晶片 IPC 比競品高 30%」。請列出至少三個你會要求的補充資訊（如量測的 ISA、負載、頻率條件），以及每一項為何是必要證據，並設計一個用 SPEC CPU2017 result 檔進行獨立驗證的流程。
