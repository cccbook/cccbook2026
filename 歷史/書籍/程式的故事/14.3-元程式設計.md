# 14.3 元程式設計（Metaprogramming）在動態語言中的極致發揮

## 回顧：元程式設計的三代技術

本書至此已埋了三條元程式設計的線索，動態語言時代把它們推到極致：

| 代 | 技術 | 章 |
|----|------|-----|
| 第一代 | Lisp 宏（代碼即列表） | 7.2 |
| 第二代 | C++ 模板（編譯期展開） | 11.3 |
| 第三代 | **動態語言的執行期元程式**：反射、開放類別、method_missing | 本章 |

## Ruby 的元程式設計武器庫

Ruby（松本行弘/Matz, 1995）的設計宣言：**「語言應取悅人類，而非機器」**。它把 Smalltalk 的物件模型、Perl 的實用、Lisp 的元程式融為一體。Rails 把這些能力用到了工業極限：

**1. `define_method` 與動態方法生成**：

```ruby
class Order < ActiveRecord::Base
end
order = Order.find_by(email: "a@b.c")   # find_by 不存在於源碼中！
order.paid?                              # 對每個欄位自動生成
```

Rails 的 ORM 攔截不存在的呼叫（`method_missing`），按命名慣例動態生成方法——**框架在執行期為你的類別「編寫」代碼**。這是 14.1 慣例優於配置的技術實現基礎：**慣例由元程式編譯為行為**。

**2. 開放類別（monkey patching）**：任何類別執行期可被重新開啟修改——表達力的極端，也是大型專案的維護夢魘（**兩個庫改同一個內建類別 → 衝突**）。

**3. DSL 的黃金時代**：Rails 的路由與遷移、RSpec 的測試語法、Gemfile——**Ruby 程式大量長出「內嵌小語言」**：

```ruby
get "/users/:id" => "users#show", as: :user   # 這是 Ruby 代碼，也像配置語言
```

DSL 思想的譜系：Lisp 的宏 DSL（7.2）→ Unix 的配置文件 → Ruby 的內部 DSL → **2020s 的 Kubernetes YAML 與 Terraform HCL（外部 DSL 的迴歸）**。

## 元程式設計的代價：可推論性的崩塌

2010s，Ruby 社群開始系統性反思（著名的「**魔法過多**」論戰）：

1. **靜態分析失效**：方法在執行期才存在——IDE 跳轉、重命名、自動補全全部殘廢（13.3 的動態危機在 Rails 中最嚴重）
2. **錯誤訊息遠離源頭**：`method_missing` 鏈中的異常，堆疊指向框架深處
3. **新人的斷崖**：元類、singleton class 的機制需要數月才能掌握
4. **社群的修正**：Sorbet（Stripe 2019 的 Ruby 型別檢查器）、Rails 逐步減少魔法——**動態元程的高峰之後，是型別與顯式化的回歸**（13.3 鐘擺的又一圈）

## 元程式設計的跨語言譜系總結

| 語言 | 元程式形態 | 巔峰 | 退潮/轉化 |
|------|-----------|------|----------|
| Lisp | 宏（編譯期，同像性） | 1960s–80s | 思想散入各語言 |
| C++ | 模板（編譯期） | 1990s–2000s | constexpr、Concepts 正式化 |
| Ruby/Rails | 執行期動態生成 | 2005–2012 | Sorbet、顯式化運動 |
| Python | 裝飾器、metaclass | 2000s– | dataclass 正式化（減少手寫元程式） |
| JS | eval、Proxy、原型操作 | 2000s | TypeScript 化 |
| Rust | 過程宏（編譯期、型別安全） | 2015+ | 當代主流：**把 Ruby 式魔法搬回編譯期** |
| Zig | comptime | 2016+ | 元程式與普通代碼同語言——理論終點 |

**清晰的歷史方向**：元程式設計的鐘擺從「執行期魔法」盪向「編譯期顯式」——因為**大型協作需要機器可推論的代碼**（13.3 的主旋律）。

## 轉場：當「元程式設計師」變成模型

2020s 的 LLM 是元程式設計歷史的最後一塊拼圖：

- 過去：人類寫**元程式**（宏/模板/動態生成）來避免重複
- 現在：人類用自然語言描述，**LLM 直接生成專用代碼**——每個請求都是「一次性編譯」的客製代碼，**抽象層被生成層替代**

這意味著深刻的歷史反轉：**為可複用而設計的抽象（模板、泛型、框架慣例），在 AI 時代可能被「為單一情境直接生成」的部分取代**——抽象的成本（學習、除錯、間接性）與生成的成本（即時、可丟棄）重新比價。這是第 16 章的主題。

## 小結

| 概念 | 內容 | 歷史命運 |
|------|------|---------|
| method_missing | 執行期動態生成 | 魔法過多論戰後退潮 |

| LLM 生成 | 統計式元程式 | 第 16 章的主題 |
