# 8.3 雲端巨頭「白嫖」爭議與許可證逆轉：MongoDB、Elastic、Redis 的商業大戰

## 什麼是「白嫖」？

2010 年代後期，被雲端衝擊的開源公司發現一個殘酷的商業現實：

> 你以 AGPL 開源的資料庫，**AWS 拿去當「託管服務」賣，賺了你十倍的錢，且一分錢回饋都不用付**。

開源的精神之一是「**自由使用**」——但**當使用者的規模不對等**（AWS 的營收是這些開源公司的數十倍），**免費的自由就變成了單向的剝削**，俗稱「白嫖」（freeriding）。

## 三場許可證「逃脫戰」

### 1. MongoDB（2018 年 10 月）

- 2018 年，MongoDB **將許可證自 AGPL 變更為「SSPL（Server Side Public License）」**（背景：雲廠商推出以 MongoDB 相容協議或強橫託管服務蠶食其市場）：
  - 新條款要求：**任何「把資料庫作服務」的廠商，必須把服務層的原始碼**（monitoring/provisioning）**全部公開**；
  - **SSPL 最終未被 OSI 收錄為開源許可證**——被認為對「提供服務的廠商」施加了過度的義務；
  - MongoDB 的許可證**仍然「源碼可得（source-available）」**，但已不再被視為開源許可證。

### 2. Elastic / Elasticsearch（2021 年 1 月）

- 2021 年初，Elastic 宣布將 Elasticsearch 的許可證從 Apache 2.0 變更為**雙許可：SSPL ＋ Elastic License 2.0**；
- 原因：AWS 的託管服務定價打法被 Elastic 視為低成本的 clone 取勝；
- 爆炸性後果：AWS **在 2021 年 4 月發起 OpenSearch 專案**，以 Apache 2.0 延續整條技術線——**被廠商拿走的標準，成了競爭者的旗艦**；
- **2024 年 8 月**：Elastic 又戲劇性回轉——**把 AGPL 加入多許可選項**（SSPL、Elastic License、AGPL 三選一），呈現「**法律防商戰 vs 生態要自由**」的循環妥協。

### 3. Redis（2024 年 3 月）

- 2024 年 3 月，Redis 宣布其 **Redis 7.4 起從 BSD 變更為三選一商用許可**（RSALv2 / SSPL v1 / 商業條款）——**不再被視為 OSI 開源**；
- 對 Open Source 社群的反應同樣激烈：**Valkey（Linux 基金會託管的分叉）**隨即誕生，繼續以 BSD 佈道；
- **2025 年 5 月**，Redis 加入 **AGPLv3** 作為可選許可證——試圖以「**可被 OSI 承認**」的選項緩解與社群的裂痕。

## 這三案的共同特徵

1. **對象都是雲商（特別是 AWS）**——雲廠商「**把開源當上架商品托管牟利而不回饋**」被視為典型的白嫖；
2. **許可證變更的結果都是「不再是 OSI 開源」**——**Open Source Definition（OSD）無法直接處理雲端服務的裂縫**；
3. **許可證成為彈性商業工具**：先「source-available」，再於壓力下**折回開源方向**（Elastic、Redis 皆如此）；
4. **社群的「剪枝」**：**每次變更許可證都催生分叉**——OpenSearch（自 Elasticsearch）、Valkey（自 Redis）、MariaDB（2010，自 MySQL，因 Oracle 收購）——**分叉運動是生態的免疫反應**。

## 反對「白嫖」的三種律師論證

這場戰爭中，開源界出現三個主要論述：

| 立場 | 代表 | 論點 |
|---|---|---|
| **「白嫖是自由的一部分」** | OSI、FSF | OSD 要求**不限用途**；禁止「作為服務提供」就違反開源定義 |
| **「許可證是工具不是信仰」** | MongoDB / Elastic / Redis 公司 | 開源是策略而非終極目標；**許可證要用來保護商業** |
| **「基金會/標準才是終解」** | CNCF、Linux 基金會陣營 | 建立**中立技術標準**（K8s、OpenTelemetry），服務層允許自由競爭，** AWS 的服務本身也建在開源之上** |

## 制度反思：開源的「勝利與代價」

這場「許可證大戰」暴露的深層問題：

1. **OSD 是 1998 年為「桌面與伺服器軟體」設計的**——雲端「SaaS」的出現，使「軟體」與「服務」從一體變成兩回事；
2. **「白嫖」的界線難以量化**：一般企業以開源做 CRM 與雲商以開源做託管服務，形式上都是「合法消費」——**規模與商業目的的不對等才是爭議核心**；
3. **回饋之路仍然可行**：**紅帽的「服務費」**、**GitLab 的 Open Core**、**基金會託管模式**——許可證不是唯一答案。

## 小結

2018–2024 年的許可證大戰證明：**開源的「自由」與「永續商業」之間的新型張力，已成為整個開源運動的憲法級議題**。當基礎設施級的軟體能被任何規模的玩家自由取用，回饋機制的設計就變成了生態存亡的關鍵。下一章，我們跨進 AI 時代——開源的戰場將再度升級。
