# 1999 - 極限編程 XP：把好實務做到極限

## 案件摘要
1999 年，Kent Beck 出版《Extreme Programming Explained: Embrace Change》，為 C3 專案的血淚教訓立傳。
XP 的辦案手法是：把公認的好實務——測試、重構、結對、小型發布——各自**推到極限**，讓它們互相放大。
核心線索是 TDD 紅綠燈循環：紅（寫失敗的測試）→ 綠（寫最少的程式讓它過）→ 重構（把債還清）。
回饋週期從「天」壓縮到「分鐘」，軟體開發第一次學會以分鐘為單位思考。
C3 專案本身以失敗收場，但它孵出的十二實務，成為敏捷運動的工程地基。

## 前因 -- 為什麼會有這個案子
- **Chrysler C3 專案的地獄**：1993 年克萊斯勒的 C3 薪資系統（約 8 萬類目、上千萬行目標碼）以 Smalltalk 開發，原計畫瀑布式推進，1996 年 Kent Beck 進場救火時專案已深陷泥沼，最終 1999 年上線失敗——但專案裡長出的實務活了下來。
- **傳統回饋週期太長**：瀑布式從需求→設計→實作→測試→上線，一輪以月計；錯誤發現得越晚，修復成本呈**指數**上升。Beck 的問題是：如果把回饋週期壓到極限，會發生什麼？
- **好的實務早就在，只是沒人全套用**：測試先行、程式碼審查、持續整合、簡單設計，每單項都有人做；Beck 與 Ward Cunningham（CRC 卡、第一個 unit test framework 的雛形）在 1980s–90s 的顧問工作中累積了原型。
- **關鍵推理**：單獨做「測試」是成本，全套做「測試＋結對＋重構＋小型發布」是槓桿——每個實務為下一個實務鋪路：

$$
\text{XP} = \lim_{\text{回饋週期} \to 0}\big(\text{測試} + \text{重構} + \text{結對} + \text{小步發布} + \text{客戶在場}\big)
$$

「極限」二字不是激烈，而是**取極限**：測試→人人天天測；結對→所有程式碼都兩人寫；發布→每兩週一次；設計→永遠只做當下最簡單的設計。

## 線索與推理 -- 數學式、程式、理論

### 1. 案件現場：XP 十二實務

| 實務 | 極限化的對象 | 目的 |
|---|---|---|
| 小型發布（Small Releases） | 發布週期：月 → 週 | 早拿到回饋 |
| 規劃遊戲（Planning Game） | 需求由客戶定優先序 | 業務與技術對話 |
| 現場客戶（On-site Customer） | 客戶距離：樓層 → 同桌 | 需求即時澄清 |
| 隱喻（Metaphor） | 架構的共用語言 | 概念完整性 |
| 簡單設計（Simple Design） | 設計範圍：只做當下需要的 | 對抗過度工程（YAGNI） |
| 測試先行（TDD） | 測試時機：寫碼**前** | 規格即程式 |
| 重構（Refactoring） | 每次修改都順手還債 | 控制技術債 |
| 結對程式設計（Pair Programming） | 寫碼人數：1 → 2 | 即時審查＋知識共享 |
| 集體所有權（Collective Ownership） | 程式碼屬於全隊 | 沒有瓶頸人 |
| 持續整合（Continuous Integration） | 整合頻率：月 → 每日多次 | 整合地獄絕跡 |
| 40 小時週（Sustainable Pace） | 加班：常態 → 禁止 | 過勞的錯誤更貴 |
| 編碼標準（Coding Standards） | 全隊同一風格 | 讓結對與集體所有權可行 |

### 2. TDD 紅綠燈循環

$$
\text{紅} \xrightarrow{\;\text{寫失敗的測試}\;} \text{綠} \xrightarrow{\;\text{寫最少的程式讓它過}\;} \text{重構} \xrightarrow{\;\text{清理設計，測試仍綠}\;} \text{紅}
$$

- **紅（Red）**：先寫一段會失敗的測試——它就是**可執行的規格**。測試失敗證明兩件事：功能還不存在，且測試本身真的在檢查東西。
- **綠（Green）**：寫「剛好足夠」的程式碼讓測試通過，作弊也無妨（寫死回傳值）——先求對，再求好。
- **重構（Refactor）**：在測試全綠的保護傘下清理內部結構，不改外部行為。
- **測試先行 vs 測試後補**：事後補的測試常被實作「帶著走」（寫成跟著錯的實作走）；先行的測試由**需求**帶著走——這是 TDD 的本質區別，不是順序的美學偏好。
- **為什麼叫「極限」**：不是激烈，而是取極限——每個好實務都被推到「理論上還能再多的上限」，讓實務之間互相放大而非互相稀釋。

### 3. 重構：Martin Fowler《Refactoring》(1999)

Fowler 同年出版《Refactoring: Improving the Design of Existing Code》，把重構從手藝變成**目錄化的手法集**（Extract Method、Inline Method、Move Method、Replace Conditional with Polymorphism…）。

- 定義：在不改變可觀察行為的前提下，調整程式內部結構以提升可理解性與修改成本。
- 關鍵推理：重構之所以敢做，是因為有測試護航；TDD 與重構互為因果——**沒有測試的重構是賭博，沒有重構的 TDD 是技術債的複利**。
- 程式碼異味（code smells）：長函式、巨型類別、散彈式修改——每一種味道對應一組處方手法。

### 4. 數學線索：回饋週期與修改成本

- **回饋週期縮短**：瀑布式一輪 $O(\text{days} \to \text{weeks})$，TDD 一輪 $O(\text{minutes})$。錯誤從注入到被發現的間隔 $T$ 越短，定位與修復成本越低——因為剛動過的程式碼還在腦中：

$$
\text{修復成本}(T) \approx C_0 \cdot e^{kT},\qquad \text{回饋週期 } T:\ \text{days} \to \text{minutes}
$$

- **重構降低修改成本**：設計品質以修改成本衡量——重構讓下一次修改的邊際成本 $C_{\text{next}}$ 不隨迭代次數 $n$ 上升：

$$
\text{未重構}:\ C_{\text{next}}(n) = C_0 + b n;\qquad \text{持續重構}:\ C_{\text{next}}(n) \approx C_0
$$

- **YAGNI（You Aren't Gonna Need It）**：為「以後可能需要」而寫的程式碼是負資產——寫了要測、要維護，而「以後」多半不來。

### 5. 數學線索：測試覆蓋率

覆蓋率定義為被測試執行到的語句（或分支）佔比：

$$
\text{coverage} = \frac{\text{被執行的語句數}}{\text{總語句數}}
$$

- 覆蓋率是**必要非充分**條件：100% 語句覆蓋仍可能漏掉邊界組合（兩個分支都跑過、但沒依序跑過）。
- XP 的務實立場：不必追求 100%，但要**所有新碼都有測試**——覆蓋率的意義在「防止測試盲區擴大」，而非數字本身。

### 6. Python 實作：TDD 紅綠燈（字串計算機）

```python
# ── 第一步：紅（寫失敗的測試）──────────────────────────
def test_add():
    assert add("") == 0                    # 空字串 → 0
    assert add("1") == 1                   # 單一數字
    assert add("1,2") == 3                 # 兩個逗號分隔
    assert add("1,2,3,4") == 10            # 多個數字
    assert add("1\n2,3") == 6              # 換行也是分隔符
    assert add("//;\n1;2") == 3            # 自訂分隔符 ;
    try:
        add("1,-2")                        # 負數必須報錯
        assert False, "應該拋出例外"
    except ValueError:
        pass

# ── 第二步：綠（寫最少的程式讓它過，一步步長大）─────────
def add(text):
    if not text:
        return 0
    if text.startswith("//"):
        delim, text = text[2], text.split("\n", 1)[1]
        text = text.replace(delim, ",")
    text = text.replace("\n", ",")
    nums = [int(t) for t in text.split(",") if t]
    negs = [n for n in nums if n < 0]
    if negs:
        raise ValueError(f"negatives not allowed: {negs}")
    return sum(nums)

# ── 第三步：重構後確認全綠 ────────────────────────────
test_add()
print("All tests green. add('//;\\n1;2;3') =", add("//;\n1;2;3"))
# All tests green. add('//;\n1;2;3') = 6
```

## 結案 -- 後果與影響
- **TDD 與單元測試文化**：測試先行從異端變成主流，單元測試成為職業標配，覆蓋率進入 CI 流水線。
- **JUnit（2000）與測試框架**：Kent Beck 與 Erich Gamma 為 Java 寫下 JUnit，SUnit（Smalltalk）的血統開枝散葉——pytest、RSpec、Go test 皆是後裔。
- **結對程式設計**：即時程式碼審查與知識共享被證實能降低缺點率，成為多數 Agile 團隊（含 Pair/Mob programming）的常備實務。
- **成為 Agile（2001）的核心實務**：XP 是 2001 年 Agile Manifesto 十七位簽署者中 Beck 與 Cunningham 的實務根基；Scrum 提供管理框架、XP 提供工程實務，兩者合體成為今日敏捷團隊的標準形。
- **重構工業化**：Fowler《Refactoring》（第 2 版 2018）與 IDE 的自動重構（Extract/Inline/Move）讓重構從手藝變成一鍵操作；技術債成為工程管理圈的通用語彙。
- **C3 專案本身的結局**：1999 年上線失敗、2000 年解散——但從災難現場帶出的實務，成為這個時代最重要的遺產。
- **對瀑布式需求的反證**：現場客戶與規劃遊戲證明「需求可以被談判」——規格不是石碑，而是對話的快照；這是 XP 對 $C_e$（符合性）最直接的攻堅。
